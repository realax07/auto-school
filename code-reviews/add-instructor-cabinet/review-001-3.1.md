### MIN-1 (minor): использование приватного `auth._session_user_id` вместо публичной механики

Файл: backend/dashboard.py:101

Эндпоинт обходит `require_session` и вызывает underscore-функцию другого
модуля ради контрактного тела `{"ok": false}` вместо `{"detail": ...}`.
Обоснование в комментарии корректное (паттерн /api/auth/me), но это скрытая
связность на приватный символ. Рекомендация: в auth.py expose-нуть
переиспользуемый helper (например, публичный `session_user_id()` или
`require_session_contract()`), dashboard.py — использовать его. Не блокирует:
семантика 401 идентична require_session (проверено по auth.py:84–94 — ленивая
чистка истекших, None на неверном токене).

### MIN-2 (minor): блок сайдбара «Демо-кабинет» — контент не из мокапа и не в перечне wiring-отличий

Файл: frontend/instructor-dashboard.html:42

`<div class="side-bottom"><strong>Демо-кабинет</strong><p>Все данные
вымышленны — реальное содержимое разделов появится позже.</p>…` — в мокапе
этого блока нет (в design/mocks/dashboard-instructor.html `.side-bottom`
используется только в CSS). design.md разрешает ровно пять wiring-отличий:
nav-кнопки, ФИО/инициалы, демо-метки, элементы выхода, profile-panel. Прямая
кнопка выхода разрешена (FR-22), но новый текстовый блок — за пределами
перечня. Ключевые блоки FR-19 не затронуты, поэтому minor. Рекомендация:
либо зафиксировать блок в design.md как шестое отличие, либо оставить кнопку
выхода без нового сопроводительного текста.

### MIN-3 (minor): сценарий «Сессия истекла (TTL 12 ч)» не покрыт отдельным тестом

Файл: tests/test_instructor_dashboard.py

TC-FR18D-002 проверяет 401 только на неверном токене; истечение TTL не
тестируется (в _sessions нельзя подкрутить expires извне). Поведение идентично
(ленивая чистка в _session_user_id), риск низкий. Рекомендация: тест, который
кладет запись с истекшим expires в auth._sessions напрямую, либо явная запись
в «не проверено» приемки 4.1.

### MIN-4 (minor): инициалы аватара без guard на короткие поля

Файл: frontend/instructor-dashboard.html (wiring-скрипт)

`((i.surname||' ').trim()[0]+(i.name||' ').trim()[0]).toUpperCase()` — при
пустом surname/name после trim `[0]` даст undefined и в аватар попадет
артефакт (в т.ч. «NAN»). По arch-review §1.3 поля NOT NULL и register требует
patronymic, так что случай вырожденный. Рекомендация: `.filter(Boolean)` по
аналогии со сборкой ФИО.

## 2. Что проверено и подтверждено (по факту прогонов/кода)

### Безопасность (фокус постановки задачи) — ОК
- **Серверная проверка роли**: GET /api/instructor/dashboard — сессия через
  `_session_user_id` (идентично require_session: нет/неверный/истекший → 401),
  затем SELECT users по id, `role != 'instructor'` → **403**; distinct 401/403
  как в design.md. Проверено кодом (dashboard.py:100–131) и тестами:
  - без токена → 401 `{"ok":false}` (test_dashboard_401_without_token — зеленый);
  - неверный токен → 401 (test_dashboard_401_invalid_token — зеленый);
  - logout → повторный вызов 401 (test_dashboard_401_after_logout — зеленый);
  - student-сессия → 403 (test_dashboard_403_for_student_session — зеленый);
  - инструктор → 200 + ФИО/email (test_dashboard_200_for_instructor_with_fio — зеленый).
- **demo:true** в ответе присутствует и тестируется (assert data["demo"] is True).
- NFR-2: единственный SQL — `SELECT … WHERE id = ?`, параметризован; тест
  test_dashboard_sql_parameterized + визуальная проверка диффа — 0 конкатенаций.
- NFR-3: логирования ответа/заголовков в модуле нет.
- XSS: ФИО подставляется через `textContent` (не innerHTML) — безопасно.
- Доступ к реальным данным БД: эндпоинт отдает только ФИО/email учетки +
  демо-константы; заявки/расписания не выдаются — соответствует design.md
  «Сознательные ограничения».
- Статика /instructor/dashboard физически отдается всем (клиентский редирект
  после 401/403 до отрисовки) — осознанный паттерн проекта, зафиксирован
  arch-review §1.1; замечанием не считаю.

### Фронт (фокус постановки задачи) — ОК с MIN-2/MIN-4
