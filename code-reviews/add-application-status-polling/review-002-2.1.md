# Code review: задача 2.1 (change add-application-status-polling)

Дифф `e11c6d0` (+ сборка роутера `1414b37`) — backend/application_status.py
(НОВЫЙ, 168 строк), include в backend/app.py, публичная фабрика сессии
в backend/auth.py (11 строк). Ревью по трем кругам: (1) design.md пакета
(«Решение СА», «Порядок обмена» п.1–5, таблица эндпоинтов, матрица ошибок,
MAJ-1 arch-review-002), (2) практики/безопасность (404-неразличение,
атомарность MIN-1, минимальность payload, параметризованный SQL, токены вне
URL/логов), (3) интеграция с 1.1 (колонки) и 3.1/4.1 (контракты для экрана).
Факты — по коду и свежим прогонам этой сессии.

Проверено по существу:

- **404-неразличение** — один общий модульный `_NOT_FOUND`
  (backend/application_status.py:53–55, предрендеренное тело) для обоих
  эндпоинтов и всех причин («чужой», «несуществующий», «уже потреблен») —
  тела байт-в-байт идентичны; тест TC-S9BE-005 сравнивает тела foreign vs
  missing для poll_token и exchange_token. Существование чужих заявок не
  раскрывается (NFR-28, наследование NFR-7).
- **Статус — только чтение**: одиночный параметризованный SELECT по частичному
  UNIQUE-индексу, close в finally, ни одной записи; TC-S9BE-002 — после 3
  чтений строка заявки побайтово равна исходной (status/created_at/токены/
  комментарий), exchange_token чтением не потребляется. Маппинг 'deny' →
  'rejected'; reason = review_comment ТОЛЬКО при rejected — при
  waiting/approved reason=None (заметки модерации при approved не утекают).
- **Атомарный обмен (MIN-1)** — порядок design.md п.1–5 воспроизведен:
  SELECT по exchange_token → нет → 404; guard status='approved' → иначе 409
  (токен НЕ потреблен — переходная ветка FR-81); строка users существует →
  иначе 409 («approved без users» — вне контракта модерации); УСЛОВНЫЙ
  UPDATE exchange_token = NULL WHERE exchange_token = ? + проверка rowcount
  (backend/application_status.py:146–153): rowcount != 1 → rollback → 404,
  сессия НЕ выдается; rowcount = 1 → сессия → commit одной транзакцией.
  Два параллельных обмена одним валидным токеном — ровно один 200, второй
  404 (TC-S9BE-007: threading.Barrier, два TestClient на общий файл БД;
  SQLite сериализует запись: второй UPDATE не находит токен).
- **Сессия** — публичная фабрика `auth.issue_session` (backend/auth.py:
  261–271) — обертка над `_session_issue`: тот же реестр _sessions, тот же
  TTL 12 ч, механизм логина не тронут — экспорт фабрики прямо разрешен
  design.md («Порядок обмена» п.5). Ответ — форма ответа логина
  {ok, token, route:'cabinet'} — БЕЗ email/user_id (минимальный payload);
  роль instructor — по строке users, созданной approve (тест: /api/auth/me
  200 по выданному токену + role='instructor' в БД).
- **Терминальный 404 (MAJ-1)** — на уровне API различение сохранено точно:
  потребленный/чужой exchange_token → 404 (триггер терминального состояния
  экрана 4.1), переходные отказы → 409 (экран остается в waiting) — тест
  TC-S9BE-007: повторный обмен 200→404 при сохранении status='approved'
  (poll_token жив после консумации exchange_token).
- **422 на пустые** — отсутствующий/пустой X-Poll-Token и пустой
  exchange_token (включая whitespace-only — .strip()) → контрактный
  {ok:false, error:"<поле-ру>: …"}; смок ревьюера: "   " в заголовке и теле
  → 422 контрактного формата.
- Правило префиксов: оба эндпоинта под /api/instructors/* (до-сессионный
  контур заявителя); include в create_app с комментарием (backend/app.py:
  81–85); контур модерации и /api/instructor/* не затронуты.
- SQL только параметризованный (0 f-конкатенаций — grep по измененным
  модулям); токены в URL не пишутся (заголовок/тело), logging/print в модуле
  нет (grep).

Не является замечанием (соответствует контракту/решениям):

- POST обмена ВООБЩЕ без тела отдает FastAPI-дефолт 422 `{"detail":[...]}`
  вместо контрактного {ok:false, error} (смок ревьюера). Контракт design.md
  задает 422 для «нет/пусто» ЗНАЧЕНИЯ токена — отсутствующее тело за
  границей контракта; механика та же, что во всех контурных моделях
  (register/auth/instructors — прецедент зафиксирован в
  add-auth-cabinet/review-001-1.1.md #4). Дефекта спеки не усматриваю.
- Сессия выдается ДО commit — при отказе транзакции в памяти остается
  «лишняя» сессия без потребленного токена: истечет по TTL, эквивалент
  лишнего логина — решение зафиксировано design.md п.5; rollback-ветка
  (409, переходная) на месте.
- `except Exception` вокруг issue_session+commit — широкий, но правомерно:
  любая ошибка → rollback → 409 (переходная ветка, токен сохранен);
  сужение типа ничего не меняет в поведении.
- rollback в ветке rowcount != 1 — до этого только SELECTы (откатывать
  нечего): защитный вызов, безвреден.
- Серверный rate-limit опроса отсутствует — осознанная точка расширения
  design.md («Сознательные ограничения»), бюджет NFR-28 — контракт клиента.

## Проверенные Scenario (спека StudentFlow, дельта)

- «Экран опрашивает статус по неперебираемому идентификатору» — чтение
  только чтение, без записи/побочных эффектов (TC-S9BE-002).
- «waiting → approved: бесшовный переход в кабинет без ввода пароля» —
  обмен при approved → рабочая сессия role instructor (TC-S9BE-003).
- «Ошибка обмена оставляет экран в waiting» — 409 guard'а и 409 вырожденного
  «approved без users», токен НЕ потреблен, повтор возможен (TC-S9BE-003/007).
- «Обмен вернул 404 (токен потреблен или чужой)…» — консумация → повторный
  404, статус остается approved; ровно один 200 при параллельном обмене
  (TC-S9BE-007, MIN-1).
- «Чужой или несуществующий идентификатор — 404-неразличение» — идентичные
  тела 404 для чужой/несуществующей по обоим токенам + 422 на пустые
  (TC-S9BE-005); зондирующие запросы без побочных эффектов.
- Негативные по контракту: exchange при waiting → 409; при rejected ветка
  того же guard'а (см. замечание о покрытии — review-004-5.1 #1).
