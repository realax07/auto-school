## Находки

### MAJOR-1 — validated-авто: фото/СТС заменяемы без повторной валидации, а UI обещает несуществующий переход «заново на валидацию»
- Где: backend/instructor_cars.py `upload_car_photo_angle` (статус не проверяется) + frontend/js/dashboard-instructor.js `mcRenderGalActs`, ветка validated.
- Факты: (а) upload-эндпоинт принимает замену любого ракурса и СТС у авто в status='validated' — статус остается 'validated', авто продолжает показываться НОВЫМ ученикам в каталоге с бейджем «Проверено», хотя контент после валидации админом мог быть полностью заменен (в т.ч. все 5 ракурсов и СТС — гейт ОВ-4 обходится задним числом, админ повторно ничего не увидит: в validating-фильтре авто не появится). design.md это предполагает только для draft/validating («инструктор дозагружает ракурсы в draft/validating»), но серверно это не enforced. (б) Подсказка в модалке для validated-авто дословно: «Если замените фото или СТС — при желании отправьте авто на валидацию заново (принятые ученики увидят бейдж "Не проверено")» — ОБА утверждения ложны: кнопки отправки в этой ветке нет, а перехода validated→* не существует (submit требует draft → 409, withdraw требует validating → 409; design.md: «validated — терминальный в этом объеме»). Новичок, последовавший подсказке, упрется в 409 без объяснения.
- Почему MAJOR: пользовательский контракт противоречит собственной терминальности статуса и документированной модели дозагрузки; гейт валидации контента фактически одноразовый, при этом UI активно подталкивает к несуществующему сценарию.
- Минимальный фикс (на выбор, достаточно одного): (1) честная копия в validated-ветке («замена фото не возвращает авто на валидацию — статус сохранится») + (2) желательно серверный guard: upload ракурса/СТС по validated → 409 с разъяснением, ЛИБО при замене сбрасывать/маркировать статус по отдельному решению (вне объема — тогда только копия). Ничего в машине статусов не ломает, тесты дополняются точечно.

### MINOR-1 — existence-oracle по car_id для ученика: 403 vs 404
- Где: instructor_cars.py `get_car_photo_angle`, студент-ветка: сначала проверка пары (не из пары → 403), потом draft (→ 404).
- Эффект: любой аутентифицированный ученик перебором car_id отличает существующий авто (403) от несуществующего (404) — раскрытие существования, для инструкторов тот же случай корректно 404-неразличение. Задокументировано в коде и тесте как осознанный контракт, но ослабляет NFR-4 и непоследовательно между ролями; косвенно позволяет зондировать «есть ли у инструктора X авто» до подачи заявки.
- Фикс: для ученика не из пары вернуть 404 (одна строка + правка теста). Не блокирует — канал требует валидной сессии.

### MINOR-2 — instructor_summary: `_pair_car(...)` без viewer для инструкторского виджета
- Где: backend/instructor_summary.py:102 — `_pair_car(conn, row["student_id"], instructor_id or 0)` — дефолт viewer='student'.
- Эффект: в виджете «Занятия сегодня» для draft-авто владельца photo_url не выдастся, что противоречит комментарию «владелец видит свои фото во всех статусах» в booking._car_brief. Сейчас безвредно (виджет photo_url не рендерит — проверено в dashboard-instructor.js), но это латентный шейп-мисматч для следующего, кто начнет показывать фото по этому полю. Фикс: передать viewer="instructor".

### NIT-1 — object URLs без revoke
- frontend/js/cabinet.js `loadImgAuth` (и mcLoadImg в dashboard-instructor.js): URL.createObjectURL без URL.revokeObjectURL при перерисовках раздела — рост памяти при долгой сессии SPA-навигации. Не критично для таймлайна сессии кабинета.

### NIT-2 — дублирование SELECT в admin_cars_completeness
- instructor_cars.py: две почти идентичные ветки SELECT (с фильтром/без) — отличается только WHERE. Можно один запрос с опциональным WHERE. Читаемость, не поведение.

### NIT-3 — `_car_transition` check-then-act вне одной транзакции
- SELECT статуса → UPDATE без guard-условия в WHERE (в отличие от accept/deny в student_requests.py, где гонка закрыта `AND status='new'` + rowcount по тому же мотиву review-001 #7). При single-worker benign (повторный submit валидирующего авто вернет 200 с тем же результатом), но паттерн в кодовой базе уже есть — дешево выровнять: `UPDATE ... WHERE id=? AND status=?` + rowcount→409.

### NIT-4 — файл-сирота при неудачном INSERT
- create_car (multipart) и upload_car_photo_angle пишут файл на диск до INSERT/UPDATE; сбой БД оставляет файл-сироту. Для DELETE-ветки сироты задокументированы как техдолг — расширение того же долга, ок при осознанности.

- openspec/changes/add-car-validation-booking/design.md:110–113 — «validated — терминальный в этом объеме» и «Загрузка/замена фото и СТС статус НЕ меняет»; строка 310 — «Снятие подтверждения (validated→…) — вне объема (терминальный статус)». Код правилен и закомментирован со ссылкой на MAJ-1; но СА-пакет следующей документационной итерации обязан обновить машину статусов и раздел «Сознательные ограничения» в design.md, иначе следующий исполнитель/ревьюер получит противоречивую спецификацию. Не блокирует код-ревью.

### NIT-5 — тост по снимку состояния UI, серверный status из ответа не потребляется
- mcUpload.onDone не прокидывает тело ответа, поэтому тост «авто отправлено на повторную валидацию» строится по снимку `wasValidated` (car.status до клика). При устаревшей вкладке (фото уже заменяли из другой вкладки) тост может соврать, хотя бейджи после openCars() всегда приходят с сервера. Сервер уже возвращает итоговый `status` — дешевое улучшение: прокинуть ответ в onDone и тостить по нему. Не блокирует.

### NIT-6 — остаточный файл-сирота в составной ветке upload
- Guard-UPDATE (validated→validating) не обернут в try/unlink как первый UPDATE: если sqlite3.Error случится именно на нем, commit не выполняется (close откатывает) — но уже сохраненный файл остается на диске. Вероятность исчезающе мала (второй статический UPDATE), фиксировалось только поведение NIT-4. Не блокирует.
