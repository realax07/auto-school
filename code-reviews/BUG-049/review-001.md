## (1) cancel-эндпоинт — guard confirmed, доступ, гонки — OK

`backend/booking.py:453-485`, паттерн 1-в-1 с confirm/reject:

- **Роль/доступ:** `require_role(token, 'instructor')` + ownership через
  `_booking_row` → чужая бронь 404 («только инструктор пары» = владелец
  брони по instructor_id; тест: cancel другим инструктором → 404).
- **Guard-статус:** атомарный `UPDATE … WHERE id=? AND status='confirmed'` +
  `rowcount==0 → 409` — гонок нет. Confirm (guard `'new'`) и cancel (guard
  `'confirmed'`) — взаимоисключающие WHERE-условия, при любом
  чередовании максимум один UPDATE меняет строку; повторный cancel → 409
  (покрыто тестом). Предварительный SELECT вне транзакции TOCTOU не
  создает: instructor_id брони иммутабелен.
- **status='rejected' из-за CHECK:** `db.py:114` — CHECK
  `('new','confirmed','rejected')`, статуса 'cancelled' схема не знает;
  решение легитимно и задокументировано в докстринге. Отказ от миграции
  схемы в bug-ветке — разумный трейд (минус — семантическая перегрузка,
  см. MIN-2).
- **Слот освобождается:** 'rejected' выпадает из частичного индекса
  `uq_booking_active_slot … WHERE status IN ('new','confirmed')` (ОВ-5) —
  тест проверяет повторную бронь ученика на тот же слот → 200.
- **reject_comment:** cancel не трогает колонку; у confirmed-брони он и так
  NULL (reject пишет комментарий только из 'new') — инвариант
  «rejected → комментарий» для cancel сознанно не применяется, тест
  фиксирует `reject_comment is None`.
- **Боковые эффекты согласованы:** 'rejected' выпадает из
  `blocking_bookings` (MAJ-1) и из active-выборок slots-эндпоинта —
  «слот снова свободен» выполняется на всех уровнях, отдельных правок не
  требует.

Находок нет.
