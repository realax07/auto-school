Не является замечанием (соответствует контракту/решениям):
- Единое сообщение об отказе — константа `AUTH_FAIL_MESSAGE = "Неверный email
  или пароль"`, дословно sdd §10.1; одна точка формирования ответа
  (`_login_fail`), одна точка 401 защищенных (`_unauthorized`).
- Анти-брутфорс: порог 5 (в допуске 3–10), база 30 с, удвоение, потолок
  15 мин (R-BF1/R-BF2), окно 15 мин + сброс при успехе + сброс level при
  успехе (R-BF3, включая эскалацию — `_reset_failures` обнуляет и level),
  заблокированный запрос отвечает тем же 401/строкой без проверки кредов
  (R-BF4). Учет в памяти процесса, single-worker — зафиксированное
  допущение design.md. Попытки во время блокировки не эскалируют level —
  нарастание срабатываний, а не попыток; спека Scenario «Длительность
  блокировки нарастает» сравнивает срабатывания — соответствует.
- Параметризованный SQL: оба запроса (`WHERE email = ?`, `WHERE id = ?`)
  через db-слой с `?`-плейсхолдерами (NFR-2), конкатенаций нет.
- bcrypt: `bcrypt.checkpw` против `password_hash` (FR-3), фиктивная проверка
  `_DUMMY_HASH` cost 12 при отсутствующей записи — выравнивание тайминга
  (design.md timing-замечание); замер ревьюера: успешный вход ~350 мс,
  известный vs неизвестный email 328 vs 333 мс — неразличимо, NFR-1 ≤ 500 мс
  в бюджете (теста замера в 1.1 нет — он отнесен к 4.1 по трассировке sdd §13).
- Токен: `secrets.token_urlsafe(32)`, реестр `{token: (expires, user_id)}`,
  TTL 12 ч; истекшие записи вычищаются лениво (design.md поток 4); токен в
  ответах только при 200 login — в 401/422 телах, исключениях и логах
  отсутствует: logging/print в модуле нет вовсе (NFR-3); пароль в логи
  не пишется (покрыто test_password_not_in_logs).
- 422-формат «<поле-ру>: поле обязательно» — в порядке полей §10.1, формат
  Спринта 0 воспроизведен; отклонение тел не-JSON/не-строк типы отдают
  FastAPI-дефолт `422 {detail}` (проверено смоком ревьюера) — спека §10.1
  задает контракт только для пустых/отсутствующих полей, за его пределами
  формат не оговорен (в Спринте 0 то же поведение) — дефект спеки не усматриваю.
- user_id в записи сессии — источник /me (§10.3), удаление записи → 401 /me.

## Проверенные Scenario (спека auth)

- Вход ученика: успешный вход (токен 43 симв. base64url, 200 {ok,token});
  после входа токен принимается /me (через integration-ветку).
- Единое сообщение: неверный пароль, несуществующий email — посимвольно
  идентичные 401 (код+текст), токен не выдается (включая проверку равенства
  текстов в тесте).
- Хранение учетных данных: пароль — только bcrypt-хэш в users (тест смотрит
  в БД через fetch_user); пароль отсутствует в логах (caplog на DEBUG).
- Сессии с TTL: истекший токен (сдвиг времени без sleep) → 401; подделанный
  токен → 401; отсутствующий заголовок → 401.
- Анти-брутфорс: блокировка после порога — отказ без проверки кредов,
  тот же 401/текст даже с верными учетными данными; per-IP изоляция
  (чужой IP входит); нарастание (вторая блокировка длиннее первой) и
  истечение блокировки (сдвиг времени); сброс счетчика после успеха
  (включая level); сброс окном наблюдения R-BF3.
- Выход: logout аннулирует (повторный запрос с токеном → 401); logout без
  валидного токена → 401 {ok:false}.

## Что НЕ проверено (честно)

- Поведение под реальным многопоточным/многорабочим uvicorn (счетчики `_bf`
  и `_sessions` — без локов; спека фиксирует single-worker как допущение,
  гонка не воспроизводилась).
- X-Forwarded-For / обратный прокси: `_client_ip` берет `request.client.host`
  — за прокси все клиенты сольются в один IP (для текущего деплоя без
  прокси — корректно; при появлении прокси потребует пересмотра).
- Долговременная память `_bf`/`_sessions`: записи IP никогда не удаляются
  (не экспоненциальный рост в рамках спринта, но неограниченный рост на
  дистанции большого трафика).
- Замер NFR-1 в CI (теста замера нет — зона 4.1); мой смок: ~350 мс.
- `openspec validate --strict`, flow_check — зона задачи 4.1.
