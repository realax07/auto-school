## Findings (новое — только по фиксу)

### RR-1. TC-S19-011 недетерминирован: keep-строка 13d23h59m59s сама попадает под DELETE в ≈1/3 прогонов (tests/unit/test_s19_ai_chat.py:261–295)

Механика. SQLite `datetime('now')` — секундная точка (дробная часть
отбрасывается вниз). Keep-строка пишется как now(вставки)−13d23h59m59s =
T0−14d+1с, floored → ровно T0−14d+1с. Сон 1.2с ГАРАНТИРУЕТ, что к моменту
запроса floored `now` = T0+1 или T0+2. Выживает строка только при
T_запроса ∈ {T0, T0+1}; при T0+2 граница окна (T0+2−14d) оказывается
ПОЗЖЕ строки (T0+1−14d) → DELETE `<` удаляет ее физически, SELECT `>=`
не показывает → assert :293 падает (`messages == []`). Сон не «делает
строгую границу детерминированной», а переводит keep-сторону в режим
«выживает только если латентность до GET уложилась в одну секундную
границу» — ничем не гарантировано. Замер: 4/11 красных.
Обоснование сна в докстринге («−1 seconds становится строго старше
границы») пусто: delete-строка floored всегда T0−14d−1с < T0−14d ≤
T_запроса−14d — удаляется при любом t1 ≥ t0 безо всякого сна.
Направление фикса (точечное, только тест): убрать `time.sleep(1.2)` —
тогда keep-строка выживает детерминированно при любой реальной латентности
< ~1с (T_запроса = T0 или T0+1), delete-строка удаляется всегда; строгая
граница закрепляется самим секундным floor'ом SQLite, сон для этого не
нужен и вреден.

### RR-2. time.sleep в юнит-носителе вопреки конвенции репо и собственному докстрингу файла (tests/unit/test_s19_ai_chat.py:288 против :46–47; tests/conftest.py:16–17)

нужен — удалить); докстринг носителя привести в соответствие (убрать
обоснование сна, сохранить формулу «старые записи — прямым INSERT с
