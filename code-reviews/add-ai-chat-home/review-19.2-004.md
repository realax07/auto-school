## Оценка regex (по запросу делегирования)

Поведение паттерна — срез от ПЕРВОГО литерала «session_id:» до конца
stdout (DOTALL).

- Перегрез возможен только если ассистент сам напечатает «session_id:» в
  середине ответа. Оценка: на разрешенных темах (ПДД/дорожные ситуации/
  ГИБДД, системный промпт FR-19.6 с вежливым отказом на постороннее)
  неправдоподобно; текст УЧЕНИКА в generate не попадает (только stdout
  ассистента), чужие сообщения каналом не проходят. Худший случай —
  обрезанный хвост видимого ответа (косметика), не безопасность и не
  утечка. Для v1 — допустимо; рассуждение задокументировано в комментарии
  константы.
- Граничные случаи: stdout, начинающийся с «session_id:» (ответа нет) →
  срез всего → пусто → ProviderError → человеческий текст (корректный
  fail-safe); хвост без значения («session_id:» в самом конце без \S) не
  срезается — по наблюдаемому формату hermes недостижимо.
- Рекомендация (MIN-1, не блокирует): при первом же касании файла
  (например, в волне 19.4) анкеровать по ПОСЛЕДНЕМУ вхождению
  (`stdout.rfind("session_id:")` с отсечкой до конца) — хвост всегда
  припасан в конец и снимает класс перегреза полностью, — либо якорить по
  форме хвоста hermes (`session_id:\s*\d{8}_\d{6}_[0-9a-f]+\s*(?:\n.*)*$`),
  что заодно отвергнет срез по «похожей, но не той» строке. Внедрение
  сейчас не требую: текущий риск оценен как приемлемый.
