## По приоритетам делегации (сверено)

1. **Денежные автоматы.** Покрытые пути корректны: двойной release/refund/payout
   отсечен частичными UNIQUE (design.md:96–100) + guard статус+rowcount; release
   при активном споре невозможен (свип: «нет открытого спора», design.md:227–228;
   ручной resolve — единственная дверь); гонка «спор vs свип» на границе 24ч —
   РАЗОБРАНА и корректна: окна не пересекаются (спор при NOW−completed ≤ 24ч,
   свип строго после), оба читают часы в BEGIN IMMEDIATE single-worker —
   кто первый скоммитился, второго честно отклоняет guard (проверено по
   условиям design.md:190/197/227); двойной resolve закрыт (resolution NOT NULL
   + UNIQUE). Комиссия ПОСЛЕ холда — СА решил ЯВНО: «c берется НА МОМЕНТ РЕЛИЗА»
   (design.md:245–248; admin-transactions:97–103 «применяется к последующим
   релизам; существующие не пересчитываются»); оценка — принять: симметрично
   снапшоту цены на бронь (каждая величина фиксируется на своем событии),
   история восстановима из release-строки (gross/fee). Пейаут при недостаче —
   guard на подтверждении, 409, заявка остается, списания нет (design.md:217–222,
   payouts:40–66); гонки закрыты single-worker + BEGIN IMMEDIATE. Математика
   floor: net = gross×(100−c)//100 ≤ gross, fee = gross−net ≥ 0; c=100 → net=0,
   fee=gross; c=0 → fee=0 «факт 0» учат и спека компании (admin-transactions:34–49),
   и сценарий релиза (instructor-management:57–61); gross<100 — целочисленно
   корректно. НЕ покрыто: MAJ-1 (cancel/reject после старта), MAJ-2 (gross=0
   через спор), MIN-1 (инструктор молчит).
2. **Целостность ledger.** Балансы — только SUM, колонок-счетчиков нет
   (design.md:158–169); тождество денег сходится (topup = hold = released gross +
   refund; gross = net + fee; payout ≤ earned_net). Отрицательные невозможны:
   hold проверяет available ≥ hold_amount в той же BEGIN IMMEDIATE до INSERT
   (402 с need_kop/available_kop, бронь не создается); release/refund тратят
   только замороженное, обеспеченное холдом; payout — guard баланса на confirm.
   topup > 0 CHECK; сумма-лимит пополнения (500k ₽, tasks 16.2.1) — задача
   строже спеки, не противоречит.
3. **Легаси-совместимость.** Стратегия корректна: цена NULL → холда нет
   (hold_amount_kop DEFAULT 0 через _COLUMN_MIGRATIONS; легаси-путь 1:1 —
   specs/booking:85–89); status «completed» расширяет CHECK надмножеством — все
   легаси-строки валидны, конфликтов с новыми статусами логики нет;
   uq_booking_active_slot пересоздается на new/confirmed (completed слот не
   занимает — design.md:153–156), _ACTIVE_STATUSES не тронуты; пересоздание
   booking_new — прецедент ADR-010 с переносом строк и проверкой на копии
   прод-подобной БД (16.1.1 готовность); споры — ОТДЕЛЬНАЯ таблица
   booking_disputes, данные броней не трогаются. Претензии проверены: s5 = 27
   тестов ✓, «Платежи» в tests/ = 0 ✓; контрольный полный прогон в 16.3.1 —
   обязательный критерий, правильно поставлен.
