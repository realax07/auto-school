# Требования: Контур «инструктор ↔ ученик» (Спринт 3, Партия A, change add-instructor-student-loop)

> Автор: БА-агент (Флоу 1, Спринт 3, Партия A)
> Статус: **УТВЕРЖДЕН** (Заказчик, 2026-10-15: «Дефолты принимаю» — ОВ-1…ОВ-6 по умолчаниям БА)
> Источник: BACKLOG.md, раздел «Добавлено 2026-10-15, ночь (от Заказчика) — контур «инструктор ↔ ученик»»
> + смежные решения 2026-10-15 (вечер: файлы ВУ + admin-API; поздний вечер: календарь, «Занятия на сегодня»)
> Нумерация FR продолжается после Спринтов 1–2 (последний — FR-22).

## Описание

Контур, замыкающий инструктора и ученика: инструктор заполняет профиль
(автомобили с фото, часы работы), ученик находит инструктора (карточки с
фильтрами), подает заявку, инструктор принимает ее (ученик попадает в
«Мои ученики» с привязкой к автомобилю) или отказывает (с обязательным
комментарием, видимым ученику). Рейтинг инструктора составляется из
отзывов, доступных только реальным (привязанным) ученикам. Дополнительно:
реальная загрузка файлов ВУ в анкете инструктора с выдачей изображения в
admin-API за админ-токеном и виджеты главной кабинета инструктора
(«Привязанные ученики», «Запросы учеников», «Занятия на сегодня» с честным
пустым состоянием).

## Аудитория

- Ученики (выбор инструктора, заявки, свои заявки, отзывы).
- Инструкторы (одобренные, вход по Спринту 2): автомобили, часы работы,
  запросы учеников, мои ученики.
- Администратор школы: карточка инструктора с изображением ВУ.

## Ролевая модель

| Роль | Идентификация | Что доступно в этом объеме |
|---|---|---|
| Гость | без сессии | лендинг, анкета инструктора (заявка) |
| Ученик | сессия users, роль student | кабинет, раздел «Выбор инструктора», подача заявок, свои заявки (вкл. комментарий отказа), отзывы |
| Инструктор | сессия users, роль instructor (approved-заявка, Спринт 2) | кабинет: мои автомобили, календарь часов работы, запросы учеников, мои ученики, виджеты главной |
| Администратор | X-Admin-Token (Спринт 0) | карточка инструктора в админке, включая изображение ВУ |

Механизм сессий и ролей — существующий (/api/auth/login, Спринты 1–2);
новых механизмов аутентификации не вводим.

## Функциональные требования

### Блок 1. Файлы ВУ в анкете + admin-API (задача 3.4)

- FR-23: Анкета инструктора MUST реально сохранять загруженный файл ВУ
  (изображение), а не только фиксировать факт заявки (снимает ограничение
  Спринта 2, requirements-instructor-flow.md).
  - НАМЕРЕНИЕ (GIVEN заявка заполнена и файл изображения выбран WHEN
    анкета отправлена THEN файл сохранен на стороне сервера, заявка
    хранит ссылку на файл; отправка без файла — по правилам
    обязательности полей макета).
- FR-24: admin-API MUST выдавать изображение ВУ только при валидном
  админ-токене (X-Admin-Token, механизм Спринта 0); без токена / с
  неверным токеном — отказ.
  - НАМЕРЕНИЕ (GIVEN заявка с загруженным ВУ WHEN админ запрашивает
    изображение с валидным токеном THEN изображение возвращается;
    GIVEN тот же запрос без токена THEN отказ доступа, изображение не
    возвращается).
- FR-25: Детальная карточка инструктора в админке (клик по строке —
  решение Заказчика 2026-10-15 вечер) MUST открывать форму с полными
  данными заявки, включая загруженное изображение ВУ.
  - НАМЕРЕНИЕ (GIVEN заявка с ВУ в таблице админки WHEN админ кликает
    по строке THEN карточка показывает данные анкеты и изображение ВУ).

### Блок 2. Мои автомобили (задача 3.5)

- FR-26: Кабинет инструктора MUST содержать раздел «Мои автомобили», где
  инструктор заводит автомобили (марка/модель, год, госномер, тип КПП —
  состав полей уточняется мокапом, задача 3.3). Связь автомобиль →
  инструктор — один-ко-многим: у инструктора несколько автомобилей, каждый
  автомобиль принадлежит ровно одному инструктору.
  - НАМЕРЕНИЕ (GIVEN инструктор в разделе WHEN добавляет автомобиль
    THEN он сохраняется в списке автомобилей этого инструктора; другой
    инструктор этот автомобиль не видит).
- FR-27: К автомобилю MUST прикладываться фото (механизм загрузки — как
  у ВУ в анкете). Фото доступно владельцу (в своем кабинете).
  - НАМЕРЕНИЕ (GIVEN автомобиль создан WHEN инструктор загружает фото
    THEN фото привязано к автомобилю и отображается в его разделе).
- FR-28: Инструктор MUST иметь возможность отредактировать и удалить
  свой автомобиль.
  - НАМЕРЕНИЕ (GIVEN есть автомобиль WHEN инструктор удаляет его
    THEN автомобиль исчезает из раздела и из вариантов привязки для
    новых принятых учеников; судьба существующих привязок — ОВ-3).

### Блок 3. Календарь часов работы (задача 3.6)

- FR-29: Раздел «Календарь» в кабинете инструктора MUST позволять
  выбирать часы работы на сетке недели/дня (выбор интервалов — по
  макету, задача 3.3).
  - НАМЕРЕНИЕ (GIVEN инструктор в календаре WHEN выделяет интервалы
    (например, Пн 10:00–14:00) THEN они помечаются как рабочие).
- FR-30: График MUST сохраняться (сущность availability) и
  восстанавливаться при следующем входе инструктора.
  - НАМЕРЕНИЕ (GIVEN график сохранен WHEN инструктор перезаходит в
    кабинет и открывает календарь THEN отмечены те же интервалы).

### Блок 4. Выбор инструктора учеником (задача 3.7)

- FR-31: В кабинете ученика MUST появиться раздел «Выбор инструктора»:
  карточки одобренных инструкторов с профилем (ФИО, стаж, автомобили,
  рейтинг, часы работы).
  - НАМЕРЕНИЕ (GIVEN есть одобренные инструкторы WHEN ученик открывает
    раздел THEN видит их карточки; инструкторы со статусом waiting/deny
    в списке не участвуют).
- FR-32: Список MUST поддерживать фильтры: машина (наличие/тип авто),
  рейтинг, стаж, свободное время (пересечение с availability).
  - НАМЕРЕНИЕ (GIVEN инструкторы с разными атрибутами WHEN ученик
    применяет фильтр THEN остаются только подходящие карточки; пустой
    результат показывает корректное пустое состояние, а не ошибку).
- FR-33: Карта (интеграция с картографическими сервисами) — ВНЕ СКОУПА.
  Фиксируется точка расширения: карточка инструктора и фильтры
  проектируются так, чтобы зона/гео-привязка добавлялась позже без
  переделки требований этого объема.

### Блок 5. Рейтинг и отзывы (задача 3.8)

- FR-34: Отзыв (оценка + текст) MAY оставить только реальный ученик —
  пользователь с подтвержденной связью с этим инструктором (принятая
  заявка); остальные получают отказ действия.
  - НАМЕРЕНИЕ (GIVEN ученик принят инструктором WHEN оставляет отзыв
    THEN он сохраняется и учитывается; GIVEN ученик без принятой заявки
    к этому инструктору WHEN пытается оставить отзыв THEN действие
    отклонено, отзыв не создается).
- FR-35: Карточка инструктора MUST показывать агрегат рейтинга
  (средняя оценка по отзывам + количество).
  - НАМЕРЕНИЕ (GIVEN есть отзывы WHEN карточка открыта THEN показан
    средний рейтинг и число отзывов; GIVEN отзывов нет THEN показано
    «нет отзывов», а не 0.0).

### Блок 6. Заявки учеников и решение инструктора (задачи 3.9, 3.10)

- FR-36: Ученик MUST уметь подать заявку выбранному инструктору из его
  карточки. Заявка попадает инструктору в раздел «Запросы учеников»
  (виджет входящих заявок на главной кабинета).
  - НАМЕРЕНИЕ (GIVEN карточка инструктора WHEN ученик подает заявку
    THEN она появляется у инструктора со статусом «новая»; повторная
    заявка тому же инструктору в активном статусе — не создается
    дубликат).
- FR-37: Инструктор MUST видеть список входящих заявок (ученик, дата,
  профиль-выжимка).
- FR-38: «Отказ» MUST требовать обязательный комментарий (причину);
  без комментария действие недоступно. Статус заявки → «отказана»,
  комментарий виден ученику в разделе «Мои заявки» его кабинета.
  - НАМЕРЕНИЕ (GIVEN входящая заявка WHEN инструктор жмет «Отказать»
    без комментария THEN действие заблокировано; GIVEN комментарий
    введен THEN ученик в своих заявках видит статус «отказана» и текст
    комментария).
- FR-39: «Принять» MUST переводить заявку в «принята», ученик появляется
  в «Моих учениках» инструктора с привязкой к выбранному автомобилю
  инструктора (выбор авто — на шаге принятия, по макету задачи 3.3).
  - НАМЕРЕНИЕ (GIVEN входящая заявка и ≥1 автомобиль инструктора WHEN
    инструктор принимает с выбором авто THEN создается связь
    ученик ↔ инструктор ↔ автомобиль; GIVEN у инструктора 0 автомобилей
    WHEN попытка принятия THEN принятие недоступно до заведения авто
    (ОВ-4)).
- FR-40: Виджет «Привязанные ученики» на главной кабинета MUST
  показывать принятых учеников (после принятия заявки).
- FR-41: Виджет «Занятия на сегодня» MUST показывать список занятий
  инструктора на текущую дату; в этом объеме занятий еще нет (реальное
  расписание — вне скоупа), поэтому — честная заглушка с корректным
  пустым состоянием «Сегодня занятий нет».
  - НАМЕРЕНИЕ (GIVEN реального расписания не существует WHEN главная
    кабинета открыта THEN виджет показывает «Сегодня занятий нет»).

## Нефункциональные требования

- NFR-1 (безопасность, фото): изображение ВУ выдается ТОЛЬКО по
  админ-токену (никогда — ученикам и гостям); фото автомобилей — только
  владельцу-инструктору (в кабинете) и в обезличенном виде на публичной
  карточке инструктора, если мокап задачи 3.3 это предусмотрит (иначе —
  только владельцу). Прямые URL файлов без проверки доступа недопустимы.
- NFR-2 (безопасность, отзывы): сервер MUST проверять наличие
  подтвержденной связи «ученик принят инструктором» при создании отзыва;
  проверка только на UI недостаточна.
- NFR-3: SQL параметризованный (переносится из Спринтов 1–2).
- NFR-4: Токены/секреты не в логах и репозитории (переносится).
- NFR-5 (модель данных): instructor_cars — один-ко-многим к инструктору;
  availability — интервалы, привязанные к инструктору; reviews — уникальная
  пара ученик↔инструктор; student_requests — статусы новая/принята/отказана
  + обязательный комментарий при отказе + ссылка на автомобиль при принятии.
  (Уровень сущностей, не SQL — детали схемы и таблица решений за СА/архитектором, задача 3.2.)
- NFR-6: Загружаемые файлы MUST проверяться по типу (изображение) и
  ограничению размера (порог — ОВ-5); содержимое не исполняется.

## Ограничения / Границы скоупа

НЕ делаем в этом объеме:
- Карта-интеграция (выбор инструктора на карте, гео-фильтры) — отдельная
  задача Заказчика; оставлена точка расширения (FR-33).
- Реальное расписание занятий (создание занятий, слоты бронирования,
  оплата): виджет «Занятия на сегодня» — заглушка с пустым состоянием.
- Долгосрочное планирование: перенос часов работы, отпуска, отмена занятий.
- Чат/переписка ученик↔инструктор (вне контура этого change).
- Уведомления (email/push) о заявках и решениях — backlog «Прочее».
- Новые механизмы аутентификации; используются сессии Спринтов 1–2.
- Модерация отзывов админом — не заявлена Заказчиком (ОВ-6).

## Открытые вопросы (ОВ — на решение Заказчика; после ответов раунд закрывается)

- ОВ-1: Может ли ученик одновременно иметь активные заявки нескольким
  инструкторам? Дефолт при отсутствии ответа: да, но принять может
  только один (принятие закрывает остальные активные заявки ученика).
- ОВ-2: Может ли ученик после отказа повторно подать заявку тому же
  инструктору? Дефолт: да, неограниченно (без троттлинга в этом объеме).
- ОВ-3: Что происходит с существующими привязками «ученик↔авто» при
  удалении инструктором автомобиля? Дефолт: привязка снимается, связь
  ученик↔инструктор сохраняется; инструктор перекрепляет авто вручную.
- ОВ-4: Обязательно ли инструктору завести ≥1 автомобиль до принятия
  учеников? Дефолт: да (принятие требует выбора авто, FR-39).
- ОВ-5: Ограничение размера/форматов загружаемых фото (ВУ, авто)?
  Дефолт: изображения JPEG/PNG, ≤ 5 МБ на файл.
- ОВ-6: Нужна ли админу модерация/удаление отзывов? Дефолт: нет в этом
  объеме (не заявлено в BACKLOG).


## Решения Заказчика (2026-10-15)

Цитата: «Дефолты принимаю» — все шесть открытых вопросов закрыты дефолтами БА:
- ОВ-1: несколько параллельных активных заявок — да; принятие одним закрывает остальные.
- ОВ-2: повторная заявка после отказа — да, без троттлинга.
- ОВ-3: удаление автомобиля инструктором — привязка ученика к авто снимается, связь с инструктором сохраняется.
- ОВ-4: ≥1 автомобиль у инструктора обязателен до принятия ученика — да.
- ОВ-5: фото ВУ/авто — JPEG/PNG, ≤5 МБ.
- ОВ-6: админ-модерация отзывов — нет в этом объёме.
