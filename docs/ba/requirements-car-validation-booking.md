## Описание

Три контура одного объема. (1) Автомобили: жизненный цикл статусов
(черновик → на валидации → проверено) с человеческой валидацией в новой
админ-разделе «Автомобили», модалка автомобиля с галереей 5 ракурсов,
дозагрузка СТС на уже созданном авто (диагностика текущей нерабочей
поведенки — см. FR-64), фото авто в бронировании ученика. (2) Календарь:
раздел «Бронирования» сливается с «Календарем» (брони и запросы
отображаются прямо на слотах), редактирование графика переводится на
модель «Сохранить/Отменить» — изменения применяются только по кнопке.
(3) Навигация и косметика: чистка заглушек админки, единый сайдбар-лейаут
экрана выбора инструктора (BUG-047-прецедент), удаление демо-текста
«ваш следующий маршрут», архитектурный документ связей таблиц.

## Аудитория

- Инструкторы: «Мои автомобили» (модалка, галерея, статусы, СТС на
  созданном авто), календарь с бронями/запросами на слотах и
  «Сохранить/Отменить», главная без демо-текста.
- Ученики: бронирование с фото авто инструктора, выбор инструктора
  в едином лейауте кабинета, календарь своих броней вместо отдельного
  раздела.
- Администраторы: чистый сайдбар без заглушек; новый раздел «Автомобили»
  с фильтром «На валидации» и подтверждением.

## Ролевая модель

|| Роль | Идентификация | Что доступно в этом объеме |
||---|---|---|
|| Гость | без сессии | без изменений; модалки/фото/документы недоступны |
|| Ученик | сессия users, роль student | фото авто инструктора в бронировании; календарь со своими бронями; выбор инструктора в лейауте кабинета |
|| Инструктор | сессия users, роль instructor | модалка/галерея своих авто, статусы, дозагрузка СТС своих авто, календарь с бронями/запросами + Сохранить/Отменить |
|| Администратор | X-Admin-Token | раздел «Автомобили»: все авто, фильтр «На валидации», модалка подтверждения (валидатор-человек, ОВ-1 Спринта 5) |

Механизм сессий и ролей — существующий (Спринты 1–5, правило префиксов
/api/instructor/*, /api/student/*, /api/admin/*); новых механизмов
аутентификации не вводим.

  пункты «Платежи»/«Настройки» не трогаются (в пункте 1 не заявлены).
  - НАМЕРЕНИЕ (GIVEN админ открыл админку THEN в сайдбаре нет
    «Расписания» и «Отношения»; GIVEN клик по оставшимся пунктам THEN

- FR-59: Экран выбора инструктора (frontend/instructor-choice.html)
  MUST быть встроен в единый сайдбар-лейаут кабинета ученика

  Навигация между разделами — через сайдбар; при переходе на экран
  сохраняются сессия/подсветка активного раздела.
  - НАМЕРЕНИЕ (GIVEN ученик с сессией открыл выбор инструктора THEN
    экран показан внутри сайдбар-лейаута кабинета, активный пункт
    подсвечен; GIVEN экран отрисован THEN кнопки/ссылки «в кабинет»

    разделов кабинета).
- FR-62: Главная страница инструктора MUST НЕ содержать текст
  «Ваш следующий маршрут» (сейчас — pin-label в визуальном блоке,
  frontend/instructors.html). Удаляется только текст/подпись; сам
  визуальный блок и остальной лендинг — без изменений.
  - НАМЕРЕНИЕ (GIVEN открыт лендинг/главная инструктора THEN строки
    «ваш следующий маршрут» нет нигде на странице).

### Блок 2. Автомобили (пункты 3, 6, 7, 8)

- FR-60: В бронировании занятия у ученика MUST отображаться фото
  автомобиля, прикрепленного к паре с инструктором
  (student_requests.car_id; источник — ракурсы instructor_cars,
  доступ по правилам FR-42/NFR-7 Спринта 5: ученику пары — да).
  Отсутствие фото/авто (car_id NULL, авто удален/заблокирован) —
  корректный плейсхолдер, не битая картинка (механика MIN-3 Спринта 5).
  - НАМЕРЕНИЕ (GIVEN пара с прикрепленным авто и загруженными фото
    WHEN ученик открывает бронирование THEN фото авто показано;
    GIVEN авто без загруженных ракурсов THEN плейсхолдер).
- FR-63: В разделе «Мои автомобили» клик по автомобилю MUST открывать
  модальное окно с полной информацией об авто (марка, модель, госномер,
  год, КПП) и галереей фотографий — все 5 ракурсов (спереди, сзади,
  салон, слева, справа). Галерея — листание без перезагрузки страницы;
  замена/загрузка ракурса возможна из модалки (существующий контракт
  POST …/photo/{angle}). Модалка — только владельцу (чужое авто
  недостижимо из UI, API-защита — NFR-18).
  - НАМЕРЕНИЕ (GIVEN авто с 3 загруженными ракурсами WHEN владелец
    кликает по плитке THEN модалка с инфо и галереей из 3 фото,
    пустые ракурсы — плейсхолдеры; GIVEN клик по другому авто THEN
    модалка показывает его данные).
- FR-64: Инструктор MUST иметь возможность загрузить/заменить фото СТС
  на УЖЕ созданном автомобиле. СЕЙЧАС НЕ РАБОТАЕТ — диагноз (проверено
  по backend/instructor_cars.py): загрузочного эндпоинта для СТС НЕ
  СУЩЕСТВУЕТ — POST /api/instructor/cars/{id}/photo/{angle} принимает
  только angle из 5 ракурсов (иной angle → 404, kind=car_sts там не
  поддерживается), GET …/sts — только чтение, а legacy POST …/photo
  (одиночное фото Спринта 3) пишет photo_path, не photo_sts. То есть
  это не сломанный вызов, а отсутствующая функция: нужен НОВЫЙ эндпоинт
  (предложение СА: POST /api/instructor/cars/{id}/sts, валидация файла
  как у ракурсов — JPEG/PNG ≤5 МБ, kind car_sts существующего
  uploads.py) и UI-контрол в «Моих автомобилях»/модалке FR-63. Новое
  фото СТС появляется в «Моих документах» (FR-45 Спринта 5).
  - НАМЕРЕНИЕ (GIVEN авто создан до/после Спринта 5 WHEN владелец
    загружает фото СТС THEN файл сохранен, «Мои документы» показывают
    актуальный СТС; GIVEN файл не JPEG/PNG или >5 МБ THEN 422,
    предыдущее фото СТС не затронуто).
- FR-65: Автомобиль MUST иметь статус из фиксированного набора:
  «Черновик» / «На валидации» / «Проверено». Статус отображается
  инструктору-владельцу в «Мои автомобили» (бейдж; «Проверено» —
  зеленая галочка). Переходы: черновик → на валидации (действие
  инструктора — «отправить на валидацию»); на валидации → проверено
  (только админ, FR-66); возврат в черновик/отзыв с валидации — см.
  Границы/ОВ-3. Новое авто создается в статусе «Черновик».
  - НАМЕРЕНИЕ (GIVEN новое авто WHEN создано THEN статус «Черновик»;
    GIVEN владелец отправил авто на валидацию WHEN открывает список
    THEN бейдж «На валидации»; GIVEN админ подтвердил WHEN владелец
    обновляет список THEN бейдж «Проверено» с зеленой галочкой).
- FR-66: В админке MUST появиться новый раздел «Автомобили»: список
  ВСЕХ авто всех инструкторов (марка/модель/госномер, владелец,
  комплектность 5 ракурсов + СТС — переиспользование
  GET /api/admin/cars/completeness), фильтр «На валидации», клик по
  авто → детальная модалка с возможностью ПОДТВЕРДИТЬ авто в статусе
  «На валидации». Валидатор — человек в админке (решение ОВ-1
  Спринта 5: «все обязательны. Валидирует человек в админке»):
  подтверждение доступно только авто с полным комплектом (комплектность
  видна в модалке; подтверждение неполного — заблокировано либо ОВ-4).
  Судьба существующего флага blocked и раздела /admin/cars — ОВ-5.
  - НАМЕРЕНИЕ (GIVEN 2 авто «На валидации» из 5 WHEN применен фильтр
    THEN показаны ровно 2; GIVEN админ открыл модалку авто «На
    валидации» с полным комплектом WHEN нажал «Подтвердить» THEN
    статус «Проверено», авто исчезает из фильтра «На валидации»;
    GIVEN комплект неполный THEN подтверждение недоступно с указанием,
    чего не хватает).

### Блок 3. Архитектура (пункт 4)

- FR-61: Связи таблиц по всем типам данных MUST быть описаны в ОТДЕЛЬНОМ
  документе данных (предложение: architecture/data-model.md), на который
  ссылается architecture/map.md (в map.md — ссылка с аннотацией, сам
  map.md не раздувается). Документ покрывает ВСЕ сущности БД: users,
  instructor_applications, student_requests, instructor_cars, availability,
  booking, reviews — с типами связей (1:N, денормализации), ключами,
  статусными машинами и правилами доступа. Обязательная структура
  документа (заполняет СА/архитектор, задача 7.3):
  1. Перечень сущностей: назначение, ключи, колонки-статусы.
  2. Матрица связей: A → B, кардинальность, внешний ключ/условие
     (в т.ч. связи без FK: student_requests.car_id, booking.availability_id,
     денормализация booking.instructor_id/student_id, пара = 
     student_requests.status='accepted', ракурсы/СТС — колонки
     instructor_cars + kind в data/uploads).
  3. Статусные машины: student_requests (new/accepted/denied),
     booking (new/confirmed/rejected), instructor_cars (draft/validation/
     verified — новый, FR-65), instructor_applications, blocked-флаг.
  4. Правила целостности: частичный UNIQUE booking (NFR-8), запрет
     PUT availability при активных бронях (409), авто-закрытие заявок,
     снятие car_id при удалении авто.
  5. Матрица доступа к данным по ролям (сводка NFR-7 + админ-токен).
  Документ — данные/связи, НЕ компоненты (компоненты остаются в map.md).
  - НАМЕРЕНИЕ (GIVEN СА открыл map.md THEN в разделе компонентов есть
    ссылка на документ данных; GIVEN открыт документ данных THEN каждая
    сущность БД присутствует с ключами и связями; GIVEN новая таблица
    добавлена спринтом THEN документ дополняется — живой документ).

### Блок 4. Календарь и бронирования (пункты 9, 10)

- FR-67: Отдельный раздел «Бронирования» MUST быть удален; его
  функционал сливается с разделом «Календарь» инструктора (и
  календарем ученика): брони и запросы отображаются ПРЯМО на слотах
  календаря. На слоте показывается состояние: свободен / запрос брони
  («новая», с учеником, кнопки подтвердить/отклонить) / подтвержденная
  бронь (с учеником/инструктором, авто пары). Данные — существующие
  GET /api/instructor/bookings, GET /api/student/bookings (разрез
  «календарь» Спринта 5, новых сущностей не заводится). После слияния
  недоступность раздела не ломает прямые ссылки (редирект на календарь
  — механика BUG-047: старые маршруты обслуживаются).
  - НАМЕРЕНИЕ (GIVEN есть запрос брони и подтвержденная бронь WHEN
    инструктор открывает календарь THEN оба видны на своих слотах;
    GIVEN пункт меню «Бронирования» WHEN отображен THEN его нет;
    GIVEN старая ссылка на раздел WHEN открыта THEN ведёт в календарь).
- FR-68: В календаре инструктора при редактировании графика MUST быть
  кнопки «Сохранить» и «Отменить». Изменения графика (добавление/
  удаление/правка слотов) применяются ТОЛЬКО по «Сохранить» (один PUT
  /api/instructor/availability — существующий контракт полной замены);
  «Отменить» возвращает календарь к последнему сохраненному состоянию
  (перезагрузка данных с сервера) без вызова PUT. Решения по броням
  (подтвердить/отклонить на слоте, FR-67) применяются сразу — кнопки
  «Сохранить/Отменить» относятся к ГРАФИКУ, не к броням (уточнение —
  ОВ-6). Защита слотов с активными бронями при «Сохранить» —
  наследование MAJ-1 Спринта 5: 409 с перечнем затронутых слотов,
  график не изменен.
  - НАМЕРЕНИЕ (GIVEN инструктор изменил слоты WHEN нажал «Отменить»
    THEN календарь вернулся к сохраненному, на сервере ничего не
    изменилось; GIVEN изменения WHEN нажал «Сохранить» THEN один PUT,
    календарь отражает новый график; GIVEN удаляемый слот имеет
    активную бронь WHEN «Сохранить» THEN 409 с перечнем, график не
    изменен).

## Нефункциональные требования

- NFR-18 (доступ): модалки и документы — только владельцу (инструктор
  видит свои авто/СТС/график) и админу (X-Admin-Token — раздел
  «Автомобили», подтверждение статуса). Фото авто — владельцу и
  ученикам пары (наследование NFR-7). Проверки — на сервере при каждом
  запросе; UI-скрытие и недостижимость из UI проверкой не считаются.
- NFR-19 (совместимость): введение статусов авто MUST НЕ ломать
  существующие брони, календари, «Мои документы», виджет «Занятия на
  сегодня» и выдачу ученику: авто в любом статусе остается в уже
  созданных парах/бронях с прежним отображением (фото, СТС-доступ
  владельцу). Статус влияет только на НОВЫЕ действия (отправка на
  валидацию, подтверждение админом) — см. ОВ-2.
- NFR-20 (миграция): добавление статусных полей instructor_cars —
  idempotent-миграция (механика db.py, наследование); существующие авто
  при миграции получают дефолтный статус (предложение: «Проверено»,
  чтобы каталог и действующие пары не изменились — ОВ-1).
- NFR-21 (атомарность сохранения графика): «Сохранить» = один PUT,
  применение целиком или ничего (наследование контракта Спринта 3 +
  409-защита MAJ-1 Спринта 5); частично примененный график недопустим.
- Наследуются без изменений: NFR-7…NFR-10 (доступ, гонки броней, лимиты
  фото, параметризованный SQL/логи), NFR-11…NFR-17 (контейнеры) —
  новые эндпоинты подчиняются тем же правилам (префиксы API, magic
  bytes/5 МБ для новых загрузок, {ok:false} формат ошибок).

## Приоритеты (MoSCoW)

- Must: FR-58…FR-68, NFR-18…NFR-21.
- Точки расширения (не Must): возврат авто с «На валидации» в черновик
  силами инструктора; отклонение авто админом (сейчас — только
  подтверждение); «Черновик» как скрытый от каталога черновик публикации.

## Ограничения / Границы скоупа

НЕ делаем в этом объеме (явные границы):
- Удаление legacy-маршрута POST+GET /api/instructor/cars/{id}/photo
  (одиночное фото Спринта 3, photo_path) — судьба определена design.md
  Спринта 5 (удаление при архивации MODIFIED-дельты); в этом change не
  трогаем, чтобы не смешивать с FR-64.
- Уведомления о смене статуса авто (email/push) — backlog.
- Разблокировка авто (blocked) — вне объема (наследование Спринта 5).
- Нарезка слотов, перенос/отмена подтвержденных броней — точки
  расширения Спринта 5, не ревизируются.
- Кнопки «Сохранить/Отменить» — только календарь инструктора; календарь
  ученика read-only (ОВ-6 уточняет охват по броням).
- Ввод новых сущностей «календарь»/«бронь на слот» — не заводится:
  слияние FR-67 — разрез отображения поверх booking (наследование ADR-005).

## Открытые вопросы (ОВ — на решение Заказчика; после ответов раунд закрывается)

- ОВ-1: Какой статус получают СУЩЕСТВУЮЩИЕ авто при миграции? Дефолт:
  «Проверено» (зеленая галочка) — действующие пары, брони и каталог не
  меняются; инструктор может заново отправить авто на валидацию, если
  хочет освежить данные. Альтернатива: всем «На валидации» (админ
  перебирает все авто сразу после релиза — нагрузка на админку).
- ОВ-2: Влияет ли статус авто на видимость у УЖЕ принятых учеников и в
  существующих бронях? Дефолт: нет — NFR-19, авто пары отображается как
  прежде при любом статусе; статус «Черновик»/«На валидации» влияет
  только на каталог для новых учеников (скрыть из каталога — да/нет?
  дефолт: черновик и «На валидации» скрыты из каталога новых учеников,
  «Проверено» — показан).
- ОВ-3: Может ли инструктор ОТМЕНИТЬ отправку на валидацию (вернуть авто
  в «Черновик»)? Дефолт: нет, возврат — только точка расширения; авто
  «зависает» на валидации до решения админа (просто: нет гонок статусов
  с админской модалкой).
- ОВ-4: Что админ делает с авто «На валидации» с НЕполным комплектом?
  Дефолт: кнопка «Подтвердить» заблокирована с перечнем недостающего
  (ракурс/СТС); инструктору виден тот же перечень — досылает и повторно
  отправляет. (Отдельной кнопки «Отклонить» в этом объеме нет.)
- ОВ-5: Судьба существующего раздела админки /admin/cars (комплектность
  + блокировка, Спринт 5) при появлении раздела «Автомобили»? Дефолт:
  слить — новый раздел «Автомобили» ВКЛЮЧает комплектность и кнопку
  блокировки, старый раздел удаляется (один раздел про авто, как
  FR-67 сливает бронирования с календарем).
- ОВ-6: Охват кнопок «Сохранить/Отменить» (п.10): только график
  availability или также решения по броням на слотах? Дефолт: только
  график; решения по броням (подтвердить/отклонить, FR-67) применяются
  немедленно — как в Спринте 5 (бронь — реактивный процесс: ученик ждет
  ответ, откладывание решения кнопкой «Сохранить» скрыло бы слот от
  других учеников без причины).
- ОВ-7: Новые авто, созданные ПОСЛЕ релиза, — обязателен ли полный
  комплект (5 ракурсов + СТС) уже при создании (как в Спринте 5), а
  «Черновик» — только для авто, досылающих документы? Дефолт: создание —
  по действующему контракту (СТС обязателен при создании, ракурсы
  досылаются после), «Черновик» — стартовый статус любого нового авто;
  отправка на валидацию требует полного комплекта (симметрично ОВ-4).
