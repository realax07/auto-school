## Описание

Перевод сервисного контура в контейнеры: собираемый из репо образ
приложения (python-slim, non-root), compose-стек «app + nginx + MinIO»
с именованными томами (БД, загрузки), healthcheck по /api/health,
идемпотентные миграции при старте, прогон тестов внутри того же образа
и сборка образа в CI. Мотивация — INC-001: сегодня рантайм живет
в общемашиночных окружениях (uvicorn исчезал при обновлении тулчейна),
фиксы терялись в рантайм-копиях; контейнер делает окружение артефактом
репозитория, воспроизводимым на любой машине.

Bare-metal systemd-деплой (deploy/) сохраняется рабочим как альтернативный
режим: переключение — окружением (env), без правок кода приложения.

## Аудитория

- ПМ/эксплуатация: подъем стенда одной командой compose; healthcheck
  как признак живости; понятные места данных (тома).
- Dev/QA: воспроизводимое окружение; тесты в том же образе, что и
  прод-код.
- Заказчик: снижение риска повторения INC-001; будущий перенос файлов
  в S3 (MinIO уже в контуре).

## Функциональные требования

### Блок 1. Образ приложения (задача 6.1)

- FR-51: Репозиторий MUST содержать Dockerfile, собирающий образ
  приложения (uvicorn + FastAPI + статика frontend/): база — официальный
  python-slim; зависимости ставятся в виртуальное окружение (.venv)
  через multi-stage-сборку (builder-этап не попадает в финальный образ).
  Приложение в контейнере MUST запускаться от непривилегированного
  пользователя (non-root).
  - НАМЕРЕНИЕ (GIVEN чистая машина с Docker WHEN выполняется сборка
    образа из репо THEN сборка проходит без ручных шагов, образ
    запускается, uvicorn слушает порт, процесс — не от root;
    GIVEN собранный образ WHEN его инспектируют THEN в нем нет
    builder-артефактов (кэшей pip, компиляторов)).
- FR-52: Репозиторий MUST содержать docker-compose-стек из трех сервисов:
  app (образ FR-51), nginx (reverse proxy — эквивалент текущего
  deploy/nginx-autoschool.conf: статика и /api/* проксируются на app,
  TLS по self-signed-сертификатам из файлов вне образа) и MinIO
  (S3-совместимое объектное хранилище — готовит контур под будущий
  перенос файлов из data/uploads, BACKLOG 2026-10-16). Данные БД и
  загрузок MUST лежать на именованных томах (db, uploads) и
  переживать пересоздание контейнеров.
  - НАМЕРЕНИЕ (GIVEN поднятый стек WHEN создается пользователь и
    загружается файл THEN после `docker compose down && up` данные
    доступны без восстановительных действий; GIVEN стек WHEN остановлен
    и поднят заново THEN записи БД и файлы загрузок на месте).

### Блок 2. Жизненный цикл контейнера (задачи 6.1, 6.3)

- FR-53: При старте контейнера app MUST выполняться инициализация БД
  (создание таблиц, миграции колонок) идемпотентно: повторный старт на
  существующей БД не разрушает данные и не дублирует миграции
  (механика init_db/idempotent-миграций db.py уже существует —
  контейнер обязан ее использовать, а не изобретать новую).
  - НАМЕРЕНИЕ (GIVEN volume с БД предыдущей версии WHEN контейнер
    стартует THEN схема доводится до актуальной, данные целы;
    GIVEN тот же volume WHEN контейнер перезапускается THEN старт
    проходит без ошибок повторного применения миграций).
- FR-54: Живость приложения MUST проверяться HTTP-эндпоинтом
  /api/health: healthcheck MUST быть прописан и в образе (HEALTHCHECK),
  и в compose-сервисе app; nginx и внешние оркестраторы могут опираться
  на этот признак.
  - НАМЕРЕНИЕ (GIVEN работающий контейнер app WHEN docker ps /
    compose ps THEN статус healthy; GIVEN процесс uvicorn убит WHEN
    healthcheck отрабатывает THEN статус становится unhealthy).

### Блок 3. CI и тесты в контейнере (задачи 6.1, 6.4)

- FR-55: Тесты MUST прогоняться ВНУТРИ контейнера на том же образе,
  что поставляется (не на отдельном «тестовом» образе): pytest
  выполняется в контейнере с временной БД; локально и в CI — одна
  и та же механика прогона.
  - НАМЕРЕНИЕ (GIVEN собранный образ WHEN выполняется прогон тестов
    внутри контейнера THEN тесты проходят, артефактов прогона в
    постоянных томах не остается; GIVEN тот же образ WHEN он
    используется в compose THEN это тот же digest, на котором гонялись
    тесты).
- FR-56: CI MUST собирать образ приложения на каждый PR и прогонять
  тесты внутри собранного образа; провал сборки или тестов красит PR.
  - НАМЕРЕНИЕ (GIVEN PR с падающим тестом WHEN CI завершается THEN
    статус проверки — ошибка; GIVEN PR с ломающим Dockerfile WHEN CI
    завершается THEN статус проверки — ошибка).

### Блок 4. Обратная совместимость bare-metal (задача 6.1)

- FR-57: Существующий bare-metal-деплой (deploy/autoschool.service,
  deploy/nginx-autoschool.conf) MUST остаться рабочим без изменений
  кода приложения: режим развертывания (контейнер vs systemd) MUST
  определяться окружением и конфигурацией (env-переменные путей БД,
  загрузок и секретов уже изолированы в коде), репозиторий дает
  инструкции по обоим режимам.
  - НАМЕРЕНИЕ (GIVEN машина со старым systemd-деплоем WHEN pull и
    рестарт сервиса THEN сервис работает как раньше; GIVEN контур
    переключен на compose WHEN это сделано THEN код приложения
    не правился — менялись только env/конфиги).

## Нефункциональные требования (NFR-контур)

- NFR-11 (non-root): процессы в контейнерах MUST работать от
  непривилегированного пользователя; файлы томов, создаваемые
  контейнером, не должны требовать root на хосте для обслуживания.
- NFR-12 (pin версий): версии MUST быть зафиксированы — базовый образ
  (python-slim с конкретным тегом, в идеале digest), версии зависимостей
  в requirements.txt (сейчас fastapi/uvicorn/bcrypt и др. — без версий),
  версии образов nginx и MinIO в compose. Сборка воспроизводима:
  пересборка без изменения входов дает то же окружение.
- NFR-13 (healthcheck): контейнер app сообщает живость через
  /api/health (см. FR-54); проверка выполняется средствами, уже
  находящимися в образе (без добавления curl и пр. ради одного
  healthcheck).
- NFR-14 (secrets вне образа): секреты (админ-логин/хеш, ключи MinIO,
  TLS-ключи) MUST попадать в контейнеры только через окружение
  (env_file/секреты compose) и монтируемые файлы; НИ один секрет
  не зашивается в слои образа; .env и deploy/tls/ исключены из
  контекста сборки (.dockerignore) — наследование INC-006 и NFR-3.
- NFR-15 (volumes): состояние — в именованных томах (db — файл БД,
  uploads — каталог загрузок); ничего постоянного не пишется в слои
  контейнера; путь томов переопределяется env (AUTOSCHOOL_DB_PATH,
  AUTOSCHOOL_UPLOADS_DIR — существующие переменные).
- NFR-16 (изоляция сетей): compose-стек разделяется на сети: внешняя
  (nginx ↔ клиенты) и внутренняя (app ↔ MinIO); наружу публикуются
  только порты nginx (80/443); порты app и MinIO не публикуются на хост
  (доступ — только внутри стека).
- NFR-17 (тесты в контейнере): прогон тестов внутри контейнера —
  штатная, документированная процедура (локально и в CI), на том же
  образе, что поставляется (см. FR-55); тесты изолированы от постоянных
  томов (временная БД на время прогона).

## Приоритеты (MoSCoW)

- Must: FR-51…FR-57, NFR-11…NFR-17.
- Точки расширения (не Must): S3-адаптер uploads.py (перенос файлов в
  MinIO — задача 6.3 PLAN, отдельная дельта), TLS не-self-signed,
  оркестрация поверх compose.

## Ограничения / Границы скоупа

НЕ делаем в этом объеме (явные границы):
- Перенос файлов в MinIO (S3-адаптер uploads.py) — задача 6.3,
  отдельный объем: здесь MinIO только поднимается в стеке и готов
  принимать данные; uploads продолжает работать на volume (NFR-15).
- Модульный JS фронтенда — Партия B (slug modular-js), вне этого пакета.
- Изменение поведения API/доменной логики — запрещено: контейнеризация
  не меняет наблюдаемое поведение приложения (кроме адреса/портов
  публикации nginx).
- Миграция с bare-metal как обязательная: systemd-деплой остается
  поддерживаемым режимом (FR-57).
- Автозапуск/мониторинг поверх Docker (watchtower, внешние алерты),
  Kubernetes/сворм — вне скоупа.
- Продовый TLS от центра сертификации — вне скоупа (наследование
  решения Заказчика «ходим по IP, self-signed»).

## Решения-дефолты (утверждены составом Спринта 6)

- База образа: python-slim (не alpine — колеса bcrypt/uvicorn без
  сборочных сюрпризов; не full — размер).
- Зависимости — через .venv в multi-stage (наследование урока INC-001:
  окружение — артефакт репозитория, не общемашиночный тулчейн).
- MinIO включается в стек сразу, адаптер файлов — позже (файловый
  интерфейс уже изолирован в uploads.py).
- Открытых вопросов (ОВ) нет: объем утвержден PLAN; спорные места
  (сеть, порты, имена томов) — решения design.md пакета
  add-containerization.
