## Описание

Спринт 9 собирает три пункта из бэклога (решение Заказчика 2026-11-02).

(1) Политика персональных данных (ПД) — блокер запуска в эксплуатацию: публичная
страница /policy со стандартным шаблоном 152-ФЗ под данные сервиса (ФИО, телефон,
email, фото ВУ/СТС, фото авто); текст политики — ОТДЕЛЬНЫЙ заменяемый артефакт,
не вшитый в HTML страниц: подмена без правки кода (ОВ-1). Согласие — обязательный
чекбокс при регистрации инструктора И в форме регистрации ученика (ОВ-2) со ссылкой
на /policy с обоих мест; согласие фиксируется (дата + версия политики) в заявке
инструктора / записи ученика.

(2) Автоопределение статуса заявки: экран «Ожидание модерации» (/instructors/pending)
сам опрашивает статус заявки без перелогина (интервал опроса в границах 10–15 с):
waiting → approved — автоматический переход в кабинет инструктора; waiting →
rejected — показ причины отказа (без входа). Опрос останавливается при уходе
со страницы.

(3) Миграция на Vue 3 + Vite — старт: ADR на стек и каркас сборки. ЖЕСТКАЯ директива
Заказчика (ОВ-3): сохранить модульную структуру Спринта 6 — библиотеки выносятся
в отдельные chunks (vendor-сплит), страницы мигрируют постранично (не монолитный
SPA), существующие Playwright e2e сохраняются и остаются зелеными на мигрированных
страницах. Пилотная страница — «Ожидание модерации» (ОВ-4); на ней же реализуется
п.2 (синергия задач 9.2 и 9.4).

## Аудитория

- Заявители-инструкторы: при отправке анкеты выражают согласие с политикой; на экране
  ожидания видят актуальный статус без перелогина; при approved — автоматически
  попадают в кабинет; при rejected — видят причину отказа без входа.
- Ученики: при регистрации выражают согласие с политикой; текст политики доступен
  со страницы регистрации.
- Администраторы: контур модерации без изменений (approve / deny с обязательным
  комментарием); комментарий отказа автоматически становится текстом на экране
  ожидания заявителя.
- Владелец сервиса / контент-редактор: подмена текста политики заменой артефакта —
  без участия разработчика и без правки кода.
- Команда разработки / CI: каркас Vue 3 + Vite, постраничная миграция, зеленый набор
  e2e как критерий приема каждого шага миграции.

### Ролевая модель

| Роль | Идентификация | Что доступно в этом объеме |
|---|---|---|
| Гость (заявитель) | идентификатор заявки, выданный при отправке анкеты | /policy; экран ожидания с опросом статуса; причина отказа |
| Ученик | сессия users, роль student | /policy; регистрация с обязательным согласием |
| Инструктор | сессия users, роль instructor | /policy; бесшовный переход в кабинет после approval |
| Администратор | X-Admin-Token | контур модерации без изменений; /policy |
| Контент-редактор | deploy-доступ (замена артефакта) | подмена текста политики без правки кода |

Механизм сессий и ролей — существующий (Спринты 1–8); новых механизмов
аутентификации, кроме бесшовного обмена идентификатора заявки на сессию после
approval (механизм — за СА, см. открытые вопросы), не вводим.

## Функциональные требования

### Блок 1. Политика персональных данных (пункт состава 1; ОВ-1, ОВ-2)

- FR-76: Сервис MUST иметь публичную страницу /policy (без входа, с любого устройства) с текстом политики персональных данных по стандартному шаблону 152-ФЗ под данные, собираемые сервисом: ФИО, телефон, email, фото ВУ/СТС, фото авто (а также остальные поля существующих форм: реквизиты ВУ — номер/категория/дата, госномер, адрес; политика охватывает все данные, запрашиваемые формами сервиса). ТЕКСТ политики MUST поступать из ОТДЕЛЬНОГО заменяемого артефакта (отдельный файл/шаблон вне кода страниц): в исходниках страниц (HTML/JS) текст политики отсутствует; /policy отображает актуальный артефакт и его версию (версия задается метаданными артефакта). Ссылка на /policy MUST быть видна и открываться из обоих мест выражения согласия: анкета инструктора и форма регистрации ученика.
  - НАМЕРЕНИЕ (GIVEN гость открыл /policy THEN показаны текст политики и версия, и текст не найден в HTML/JS-исходниках страниц; GIVEN артефакт заменен новым текстом THEN /policy показывает новый текст и новую версию после подмены артефакта без правки кода; GIVEN открыта анкета инструктора или форма регистрации ученика THEN ссылка на /policy видна и ведет на страницу политики).
- FR-77: Анкета инструктора (frontend/instructor-apply.html, маршрут /instructors/apply) MUST содержать обязательный чекбокс согласия с политикой персональных данных со ссылкой на /policy: отправка анкеты при неустановленном чекбоксе невозможна на клиенте (кнопка сабмита блокирована до установки) и отклоняется на сервере (повторная проверка: заявка без согласия не создается).
  - НАМЕРЕНИЕ (GIVEN чекбокс не установлен THEN кнопка отправки недоступна и заявка не отправляется; GIVEN чекбокс установлен, анкета отправлена THEN заявка создана с фиксацией согласия; GIVEN прямой POST /api/instructors/apply без флага согласия THEN 422 {ok:false}, заявка не создана).
- FR-78: Форма регистрации ученика (модальное окно «Регистрация» на лендинге, POST /api/register) MUST содержать обязательный чекбокс согласия с политикой со ссылкой на /policy: правила те же, что для анкеты инструктора — сабмит без чекбокса блокирован на клиенте и отклоняется на сервере (регистрация без согласия не создается).
  - НАМЕРЕНИЕ (GIVEN чекбокс не установлен THEN регистрация не выполняется; GIVEN чекбокс установлен, форма отправлена THEN пользователь создан с фиксацией согласия; GIVEN прямой POST /api/register без флага согласия THEN 422 {ok:false}, пользователь не создан).
- FR-79: Согласие MUST фиксироваться в данных заявки/регистрации: при успешной отправке анкеты инструктора в заявке сохраняются дата согласия (UTC сервера) и версия политики; при успешной регистрации ученика — те же поля в записи пользователя. Версия берется на момент сабмита из метаданных артефакта политики; ранее созданные заявки/пользователи сохраняют версию на момент своего сабмита.
  - НАМЕРЕНИЕ (GIVEN заявка создана THEN в ее данных есть дата и версия политики; GIVEN после релиза текст политики заменен на новую версию THEN новые заявки фиксируют новую версию, прежние — свою сохраненную).

### Блок 2. Автоопределение статуса заявки (пункт состава 2)

- FR-80: Экран «Ожидание модерации» (/instructors/pending) MUST автоматически опрашивать статус своей заявки без перелогина; интервал опроса — 12 с (допустимый диапазон 10–15 с — решение Заказчика). Идентификация заявки без сессии: при успешной отправке анкеты сервис выдает неперебираемый идентификатор заявки; экран ожидания сохраняет его локально и опрашивает статус по нему. При открытии экрана без сохраненного идентификатора (прямая ссылка) экран работает в текущем статическом режиме — без опроса и без ошибок.
  - НАМЕРЕНИЕ (GIVEN анкета отправлена, заявка waiting THEN экран показывает «на рассмотрении» и продолжает опрос; GIVEN статус сменен админом THEN экран отражает изменение не позднее одного интервала (≤ 15 с) без действий пользователя; GIVEN экран открыт без идентификатора THEN статический текст, запросов статуса нет).
- FR-81: При переходе waiting → approved экран MUST автоматически переводить заявителя в кабинет инструктора без повторного ввода пароля (бесшовный обмен идентификатора заявки на существующую сессию users с ролью instructor; механизм обмена — решение СА, см. открытые вопросы). При ошибке обмена экран остается в waiting и продолжает опрос.
  - НАМЕРЕНИЕ (GIVEN админ одобрил заявку WHEN проходит очередной интервал THEN заявитель оказывается в кабинете инструктора, сессия users создана, роль instructor; GIVEN обмен не удался THEN экран остается в «на рассмотрении», опрос продолжается по графику).
- FR-82: При переходе waiting → rejected экран MUST показывать статус «заявка отклонена» и причину отказа (комментарий админа — обязательный комментарий из контура модерации Спринта 2) — без входа и без перелогина. Для исторических заявок без комментария показывается нейтральный текст отказа без причины.
  - НАМЕРЕНИЕ (GIVEN админ отклонил заявку с комментарием «нечитаемое фото ВУ» THEN на экране ожидания виден статус отказа и этот текст; GIVEN комментарий отсутствует THEN виден нейтральный текст отказа; вход для просмотра не требуется).
- FR-83: Опрос статуса MUST останавливаться при уходе со страницы: закрытие вкладки, переход по любой ссылке, скрытие вкладки — после ухода новые запросы статуса не отправляются (нет фоновых таймеров, переживающих страницу). При сетевой ошибке на очередном тике экран остается в waiting и продолжает опрос с тем же интервалом (без учащения, без всплывающих ошибок пользователю).
  - НАМЕРЕНИЕ (GIVEN вкладка закрыта THEN запросы статуса прекращены; GIVEN пользователь ушел на /instructors THEN опрос остановлен, таймеры не существуют; GIVEN один тик не удался по сети THEN пользователь ничего не видит, следующий тик по графику 12 с).

### Блок 3. Миграция на Vue 3 + Vite — старт (пункт состава 3; ОВ-3, ОВ-4)

- FR-84: MUST быть принят ADR на стек (Vue 3 + Vite — решение Заказчика) и создан каркас сборки, сохраняющий модульную структуру Спринта 6: библиотеки выносятся в ОТДЕЛЬНЫЕ chunks (vendor-сплит — runtime Vue и любые сторонние библиотеки живут собственными чанками и не инлайнятся в чанки страниц); страницы мигрируют ПОСТРАНИЧНО (каждая страница — самостоятельная точка входа/чанк; монолитный SPA запрещен директивой ОВ-3); ADR фиксирует постраничный план миграции (очередность страниц на Спринты 9–11) и правила vendor-сплита.
  - НАМЕРЕНИЕ (GIVEN сборка выполнена THEN в артефактах сборки есть отдельные vendor-чанки и чанк пилотной страницы, вендорный код отсутствует внутри чанка страницы; GIVEN открыта пилотная страница THEN загружаются только ее чанк и требуемые vendor-чанки; GIVEN открыт ADR THEN в нем стек, план страниц, правила сплита и критерий приема e2e).
- FR-85: Существующие Playwright e2e (tests/test_ui_playwright.py — 49 сценариев) MUST сохраниться и оставаться зелеными на мигрированных страницах: сценарии не переписываются под новый стек (селекторы, маршруты, ожидания — без правок); шаг миграции принимается только при зеленом прогоне всего набора e2e.
  - НАМЕРЕНИЕ (GIVEN пилотная страница мигрирована THEN полный прогон набора e2e зеленый без правок сценариев; GIVEN сценарий «анкета → /instructors/pending» THEN проходит на мигрированной странице без изменений кода сценария).
- FR-86: Пилотная страница миграции — «Ожидание модерации» (ОВ-4): страница /instructors/pending переводится на Vue 3 + Vite и реализует на новом стеке весь блок 2 — опрос статуса, переходы waiting→approved/rejected, остановку опроса при уходе (синергия задач 9.2 и 9.4). Визуальный результат — эквивалент текущего экрана.
  - НАМЕРЕНИЕ (GIVEN страница открыта THEN она обслуживается новым каркасом (чанк страницы + vendor-чанки Vue); GIVEN все сценарии блока 2 THEN выполняются на Vue-версии страницы; GIVEN сравнение с текущим экраном THEN визуальная эквивалентность без редизайна).

## Нефункциональные требования

- NFR-25 (заменяемость политики): подмена текста политики выполняется заменой ОДНОГО артефакта (файла/шаблона) без правки исходников HTML/JS и без пересборки фронтенд-бандлов; проверка: поиск по исходникам страниц не находит ни одной строки текста политики; операция подмены (замена артефакта + перезапуск/редеплой сервиса) выполняется в пределах 15 минут без участия разработчика. Механизм хранения (файл в образе с точкой монтирования vs volume) — решение СА в границах этого требования.
- NFR-26 (бюджет бандлов): каждый vendor-чанк — не более 150 КБ в gzip; суммарный JavaScript первого захода пилотной страницы (чанк страницы + загружаемые vendor-чанки) — не более 200 КБ в gzip; страница загружает только свои чанки и требуемые vendor-чанки (код немигрированных страниц в бандл пилотной страницы не попадает). Бюджет проверяется на артефактах сборки (размеры чанков в dist) на приемке.
- NFR-27 (e2e-совместимость): миграция не меняет ни один существующий e2e-сценарий; полный набор e2e зеленый до и после каждого шага миграции (критерий приема — зеленый прогон всего набора в том же CI-контуре, что до миграции). Маршруты страниц и публичные API-контракты (/api/instructors/apply, /api/register и существующие контуры статусов) не меняются ломающим образом; новые поля добавляются обратно-совместимо.
- NFR-28 (нагрузка от опроса): один открытый экран ожидания создает не более 5 запросов статуса в минуту (интервал 12 с); после ухода со страницы запросы прекращаются (остановка — по функциональному требованию блока 2); при сетевой ошибке интервал не уменьшается. Эндпоинт статуса — только чтение (одиночный SELECT по идентификатору заявки), без записи и побочных эффектов. Идентификатор заявки — неперебираемый (случайный): перебор чужих заявок невозможен, чужой/несуществующий идентификатор — 404-неразличение. Латентность отображения смены статуса — не позднее одного интервала (≤ 15 с) после изменения статуса админом.
- Наследуются без изменений: NFR-7…NFR-10 (доступ, гонки броней, лимиты фото, параметризованный SQL/логи), NFR-11…NFR-24 (контейнеры, idempotent-миграции, совместимость) — новые поля (фиксация согласия, идентификатор опроса) и новый эндпоинт статуса подчиняются тем же правилам (префиксы API, формат ошибок {ok:false}, серверные проверки; изменения схемы БД — idempotent-миграцией по механике db.py).

## Приоритеты (MoSCoW)

- Must: весь состав Спринта 9, без частичного приема: блок «Политика ПД» (страница /policy из отдельного артефакта; обязательные чекбоксы и ссылки в обоих контурах регистрации; фиксация даты/версии согласия), блок «Статус заявки» (polling с интервалом 10–15 с; переходы waiting→approved — бесшовно в кабинет, waiting→rejected — с причиной отказа; остановка опроса при уходе), блок «Миграция» (ADR + каркас Vue 3/Vite; vendor-сплит; постраничная миграция; пилотная страница ожидания; зеленые e2e без правок); все нефункциональные требования документа (заменяемость политики, бюджет чанков, e2e-совместимость, нагрузка опроса).

## Ограничения / Границы скоупа

НЕ делаем в этом объеме (явные границы):
- Юридическая экспертиза и кастомизация текста политики: стандартный шаблон 152-ФЗ (ОВ-1);
  замена текста на собственный — операция подмены артефакта силами владельца сервиса,
  вне участия команды.
- Повторное согласие у УЖЕ зарегистрированных инструкторов/учеников при смене версии
  политики — вне объема (фиксация только в момент регистрации; консент-журнал — точка
  расширения).
- Email-уведомления о смене статуса заявки — backlog (пункт 4), не в Спринте 9.
- Миграция остальных страниц (лендинг, анкета инструктора, кабинет инструктора,
  кабинет ученика, админка) — Спринты 9–11 по плану ADR; в Спринте 9 мигрирует только
  пилотная страница /instructors/pending.
- Стек: React, Svelte и иные фреймворки не рассматриваются (решение Заказчика —
  Vue 3 + Vite); включение библиотек в чанки страниц и монолитный SPA запрещены
  директивой ОВ-3.
- Контур модерации (статусы заявок, обязательный комментарий отказа, админ-маршруты) —
  без изменений; блок 2 только читает статус и причину отказа.
- Ревизия состава собираемых данных анкет — не в объеме; политика описывает данные,
  собираемые существующими формами.
- Бесшовная аутентификация вне цепочки «анкета → ожидание → кабинет» (автовход для
  учеников и др.) — вне объема.

## Открытые вопросы (непринципиальные — решение за ПМ; новый раунд Заказчику не требуется: ОВ-1..ОВ-4 закрыты 2026-11-02)

- Механизм бесшовного входа после approval (переход в кабинет без повторного ввода
  пароля): дефолт — вместе с идентификатором опроса при отправке анкеты выдается
  одноразовый неперебираемый токен; при approved он обменивается на сессию users
  (роль instructor); решение за ПМ/СА (в границах существующей сессионной модели).
- Хранение артефакта политики: дефолт — файл в контуре деплоя с точкой монтирования;
  подмена = замена файла + перезапуск контейнера, без пересборки образа; решение
  за ПМ (совместно с СА по деплой-контракту).
- Формат версии политики в метаданных артефакта: дефолт — строка версии и дата
  в шапке артефакта (первая версия — на дату релиза Спринта 9); решение за ПМ.
- Показ номера заявки на экране ожидания (для обращений в поддержку): дефолт —
  показывать рядом со статусом; решение за ПМ.
- Ссылка на политику в футере лендинга/кабинетов помимо двух обязательных мест
  согласия: дефолт — не в объеме (точка расширения); решение за ПМ.
