## Первичный источник (формулировка Заказчика, 2026-10-31 — 7 пунктов)

1. СТС-дозагрузка на созданном авто (диагностика: сейчас POST
   /api/instructor/cars/{id}/photo kind=car_sts не работает / не подключен
   на UI — нужен FR на починку + UI).
2. ВУ: загрузка + предупреждение о замене; замена применяется ТОЛЬКО после
   верификации в админке (статусная модель документов: ВУ →
   pending-revalidation при замене; админ подтверждает) — FR на
   документ-статусы.
3. «Мои документы»: кнопка загрузки + возможность загружать/заменять
   (ВУ и СТС по авто).
4. «Мои автомобили»/«Мои документы» — БЕЗ виджетов (привязанные ученики /
   запросы / занятия на сегодня) — явные исключения.
5. Календарь: запросы учеников отображаются РОВНО на выбранных слотах;
   раздел «Бронирования» удалить.
6. «Мои ученики»: привязанные ученики, по каждому — следующее плановое
   занятие, количество плановых дальше, количество проведенных; «Запросы
   учеников» — подраздел «Мои ученики».

## Описание

Доработка контуров, созданных в Спринтах 5–7, по замечаниям эксплуатации.
(1) Документы: починка дозагрузки СТС на уже созданном авто (функция из
FR-64 Спринта 7 не заработала в UI — требуется повторная диагностика
корня и доводка эндпоинта + контрола) и единая статусная модель
ДОКУМЕНТОВ по образцу статусной модели авто: замена ВУ (и СТС — ОВ-2)
создает версию «на верификации»; до решения админа действует предыдущая
версия. (2) Экраны «Мои автомобили» и «Мои документы» очищаются от
виджетов (привязанные ученики, запросы, занятия на сегодня) — целевые
экраны без дашборд-шума. (3) Календарь: добивка слияния Спринта 7 —
запросы учеников строго на выбранных слотах, без остатков раздела
«Бронирования». (4) «Мои ученики» — новый состав раздела: карточки
учеников со счетчиками занятий; «Запросы учеников» становится
подразделом.

## Аудитория

- Инструкторы: дозагрузка/замена СТС и ВУ («Мои автомобили», «Мои
  документы»), чистые экраны без виджетов, календарь с запросами на
  слотах, раздел «Мои ученики» со счетчиками.
- Администраторы: верификация замененных документов (ВУ/СТС) в админке.
- Ученики: без изменений в этом объеме; косвенно — корректный календарь
  инструктора (запросы на своих слотах).

## Ролевая модель

|| Роль | Идентификация | Что доступно в этом объеме |
||---|---|---|
|| Гость | без сессии | без изменений; документы/ученики/календарь недоступны |
|| Ученик | сессия users, роль student | без нового; видит календарь инструктора без своих запросов на чужих слотах (наследование FR-67/ОВ-6 Спринта 7) |
|| Инструктор | сессия users, роль instructor | СТС/ВУ загрузка+замена, «Мои документы» с загрузкой, чистые экраны, календарь, «Мои ученики» |
|| Администратор | X-Admin-Token | верификация документов (подтвердить/отклонить замену) |

Механизм сессий и ролей — существующий (Спринты 1–7, префиксы
/api/instructor/*, /api/student/*, /api/admin/*); новых механизмов
аутентификации не вводим.

## Функциональные требования

### Блок 1. Документы: СТС и статусная модель (пункты 1, 2)

- FR-69: Инструктор MUST иметь рабочую возможность загрузить/заменить
  фото СТС на УЖЕ созданном автомобиле (из модалки авто и/или «Моих
  документов»). ДИАГНОСТИКА (обязательна ДО фикса, фиксируется в отчете
  задачи): заявленный симптом — POST /api/instructor/cars/{id}/photo
  с kind=car_sts не работает / не подключен на UI; по design.md Спринта 7
  целевой маршрут — POST /api/instructor/cars/{id}/photo/sts (angle='sts'
  → photo_sts), а legacy POST …/photo (без ракурса) предписано удалить.
  Задача диагностики проверяет цепочку по звеньям: (а) существует ли в
  коде параметризованный sts-маршрут и заполняет ли он photo_sts;
  (б) какой маршрут фактически вызывает UI «Моих автомобилей»/модалки
  (frontend/js/*) — не остается ли вызов legacy …/photo с kind=car_sts;
  (в) воспроизводится ли симптом повторной загрузкой. Починка: рабочий
  эндпоинт записи photo_sts (валидация JPEG/PNG ≤5 МБ — NFR-9) + UI-контрол
  в модалке авто. Замена СТС НЕ меняет статус авто (наследование машины
  статусов Спринта 7) — судьба статуса при замене СТС у validated-авто —
  ОВ-6.
  - НАМЕРЕНИЕ (GIVEN авто создан до/после Спринта 5 WHEN владелец
    загружает СТС через модалку THEN файл сохранен в photo_sts, «Мои
    документы» (FR-45 Спринта 5) показывают актуальный СТС; GIVEN файл
    не JPEG/PNG или >5 МБ THEN 422, предыдущее СТС не затронуто;
    GIVEN диагностика завершена THEN корень симптома зафиксирован в
    отчете задачи ДО фикса).
- FR-70: Документы инструктора MUST иметь статусную модель (по образцу
  статусной модели авто Спринта 7). Объекты: ВУ (документ анкеты,
  instructor_applications-контур Спринта 3) и СТС по каждому авто
  (охват СТС статусной моделью — ОВ-2). Статусы: verified (действует) /
  pending-revalidation (заменен, ждет верификации админом) / rejected
  (замена отклонена админом). Правила:
  - при загрузке ЗАМЕНЫ действующего документа новая версия получает
    pending-revalidation; ПРЕДЫДУЩАЯ версия остается verified и
    продолжает действовать до решения админа (документ «не мигает»);
  - верификация — ТОЛЬКО человек в админке (наследование ОВ-1 Спринта 5):
    подтверждение → новая версия verified, предыдущая — архив; отклонение
    → новая версия rejected, предыдущая ОСТАЕТСЯ verified (инструктор не
    остается без документа) — поведение при отклонении уточняет ОВ-1;
  - пока замена в pending-revalidation, повторная загрузка новой версии
    замещает ожидающую (в очереди одна ожидающая версия на документ);
  - СТАТУСЫ ДОКУМЕНТОВ не влияют на статус авто (разные машины состояний;
    связь — только через ОВ-6).
  - НАМЕРЕНИЕ (GIVEN инструктор загрузил замену ВУ WHEN открывает «Мои
    документы» THEN виден действующий старый документ с пометкой
    «Ожидает проверки замены»; GIVEN админ подтвердил WHEN инструктор
    обновляет экран THEN действует новая версия; GIVEN админ отклонил
    THEN продолжает действовать предыдущая версия).
- FR-71: При инициировании замены ВУ (и СТС — по ОВ-2) UI MUST показывать
  предупреждение: замена НЕ вступает в силу сразу — только после
  проверки администратором; до подтверждения действует предыдущая версия.
  Кнопка подтверждения замены в диалоге — явная («Заменить»), загрузка
  без клика по ней не создает ожидающую версию.
  - НАМЕРЕНИЕ (GIVEN инструктор нажал «Заменить ВУ» THEN показан текст
    предупреждения; GIVEN отменил диалог THEN файл не загружен, статус
    документа не изменен; GIVEN подтвердил THEN создана версия
    pending-revalidation).

### Блок 2. «Мои документы» (пункт 3)

- FR-72: Раздел «Мои документы» MUST иметь кнопку загрузки и позволять
  загружать/заменять документы: ВУ (личный документ) и СТС по каждому
  авто владельца. Сегодня раздел — только просмотр/скачивание (FR-45
  Спринта 5; досыл/замена явно исключены Спринтом 5). Загрузка/замена
  из «Моих документов» идет через те же эндпоинты и статусную модель
  FR-69/FR-70 (отдельного контура не заводится); после загрузки список
  обновляется с актуальным статусом версии.
  - НАМЕРЕНИЕ (GIVEN инструктор в «Моих документах» WHEN нажимает
    загрузку у авто THEN загружается/заменяется СТС этого авто (как
    FR-69); GIVEN загружает ВУ THEN применима модель FR-70 с
    предупреждением FR-71; GIVEN замена в ожидании THEN в списке виден
    статус ожидающей версии).

### Блок 3. Экраны без виджетов (пункт 4)

- FR-73: Экраны «Мои автомобили» и «Мои документы» MUST НЕ содержать
  виджеты: «привязанные ученики», «запросы учеников», «занятия на
  сегодня» (виджеты Спринта 3, FR-контур PR#60). Исключения ЯВНЫЕ:
  перечисленные три виджета удаляются с этих двух экранов; места им —
  главная кабинета инструктора (остается без изменений) и новый раздел
  «Мои ученики» (FR-75). Остальные элементы экранов (таблица авто,
  модалка, список документов) — без изменений.
  - НАМЕРЕНИЕ (GIVEN инструктор открыл «Мои автомобили» THEN ни один из
    трех виджетов не отображен; GIVEN открыл «Мои документы» THEN
    аналогично; GIVEN открыл главную кабинета THEN виджеты на месте).

### Блок 4. Календарь (пункт 5)

- FR-74: В календаре инструктора запросы учеников MUST отображаться
  РОВНО на выбранных учеником слотах (дата+время запроса совпадают со
  слотом availability, на который отправлен запрос; никаких
  агрегированных списков «рядом с календарем» и попаданий на соседние
  слоты). Раздел «Бронирования» MUST быть удален без остатков: пункт
  меню, страница, маршруты. Спринт 7 слит функционал (FR-67, PR#95);
  этот пункт — добивка: верификация соответствия «запрос ↔ слот» и
  удаление остаточных UI-следов (пункты меню/прямые ссылки). Старые
  ссылки обслуживаются редиректом на календарь (механика BUG-047).
  Кнопки «Сохранить/Отменить» графика и немедленные решения по броням —
  наследование FR-68/ОВ-6 Спринта 7 без изменений.
  - НАМЕРЕНИЕ (GIVEN ученик отправил запрос на слот 14:00–15:00 WHEN
    инструктор открывает календарь на эту дату THEN запрос показан
    именно на слоте 14:00–15:00 с кнопками подтвердить/отклонить;
    GIVEN пункт меню «Бронирования» WHEN отображен THEN его нет;
    GIVEN старая ссылка WHEN открыта THEN редирект в календарь).

### Блок 5. «Мои ученики» (пункт 6)

- FR-75: Раздел «Мои ученики» MUST показывать привязанных учеников
  (пары = student_requests.status='accepted') — по каждому:
  1) следующее плановое занятие (ближайшая подтвержденная бронь с датой
  ≥ сегодня; при отсутствии — «нет»); 2) количество плановых занятий
  дальше (подтвержденные брони после следующей); 3) количество
  проведенных (подтвержденные брони с датой < сегодня; правило
  материализации lesson_date — наследование MIN-1 Спринта 5, локальная
  дата сервера). «Запросы учеников» (контур Спринта 3) MUST стать
  ПОДРАЗДЕЛОМ «Моих учеников» (внутри раздела, не отдельным пунктом
  сайдбара); функционал принятия/отказа — без изменений (наследование
  FR Спринта 3, ОВ-1…6 Спринта 3). Встречаемость учеников в списке
  «Мои ученики» и в подразделе запросов — по существующим связям пар;
  новые сущности не заводятся (чтение поверх booking/student_requests —
  наследование ADR-005).
  - НАМЕРЕНИЕ (GIVEN пара принята, есть 1 бронь на завтра и 2 на
    следующей неделе, 3 в прошлом THEN карточка ученика показывает:
    следующее — завтра, плановых дальше — 2, проведенных — 3;
    GIVEN пара без броней THEN следующее — «нет», счетчики 0/0;
    GIVEN есть новый запрос WHEN открыт «Мои ученики» THEN запрос виден
    в подразделе «Запросы учеников»; GIVEN запрос принят THEN ученик
    появляется в основном списке).

## Нефункциональные требования

- NFR-22 (доступ): документы (загрузка/замена/чтение), «Мои ученики» и
  календарь — только владельцу-инструктору; верификация документов —
  только админу (X-Admin-Token). Проверки — на сервере при каждом
  запросе (наследование NFR-7/NFR-18): UI-скрытие и недостижимость из UI
  проверкой не считаются; чужой документ/ученик — 404-неразличение.
- NFR-23 (совместимость): статусная модель документов (FR-70) и все
  изменения экранов MUST НЕ ломать существующие брони, календари, пары,
  каталог и выдачу ученику: pending-revalidation у ВУ/СТС не блокирует
  инструктора, не скрывает его из каталога и не меняет существующие
  брони/занятия (влияние на новые действия — ОВ-3). Удаление виджетов
  (FR-73) и раздела «Бронирования» (FR-74) не меняет API-контрактов
  брони/availability.
- NFR-24 (миграция): введение статусов документов — idempotent-миграция
  (механика db.py, наследование Спринтов 6–7); существующие документы
  (ВУ всех инструкторов, СТС всех авто) при миграции получают
  verified — никто не «зависает» на верификации после релиза (симметрично
  NFR-20/ОВ-1 Спринта 7). Механизм хранения версий (колонки vs таблица
  версий) — решение СА в границах этого требования.
- Наследуются без изменений: NFR-7…NFR-10 (доступ, гонки броней, лимиты
  фото: JPEG/PNG magic bytes ≤5 МБ, параметризованный SQL/логи),
  NFR-11…NFR-21 (контейнеры, атомарность графика) — новые эндпоинты
  подчиняются тем же правилам (префиксы API, {ok:false} формат ошибок).

## Приоритеты (MoSCoW)

- Must: FR-69…FR-75, NFR-22…NFR-24.
- Точки расширения (не Must): причина отказа при отклонении замены
  админом (комментарий, как в заявках Спринта 3); история версий
  документа с просмотром архива; пакетное подтверждение документов
  админом.

## Ограничения / Границы скоупа

НЕ делаем в этом объеме (явные границы):
- Статусная модель АВТО не пересматривается (draft/validating/validated,
  ОВ-1…7 Спринта 7 — закрыты); правки только там, где затронуты
  документы (ОВ-6).
- Уведомления (email/push) о верификации документов и о запросах —
  backlog.
- Отказ админа для АВТО (validating→отклонено) — точка расширения
  Спринта 7, не ревизируется.
- Нарезка слотов, перенос/отмена подтвержденных броней — точки
  расширения Спринта 5, не ревизируются.
- Календарь ученика — read-only, изменений нет (наследование ОВ-6
  Спринта 7).
- Кабинет ученика, каталог, админ-разделы кроме верификации документов —
  вне объема.
- Новые сущности «плановое занятие»/«расписание курса» — не заводятся:
  счетчики FR-75 — разрез поверх booking.

## Открытые вопросы (ОВ — на решение Заказчика; после ответов раунд закрывается)

- ОВ-1: Что происходит при ОТКЛОНЕНИИ админом замененной версии
  документа? Дефолт: замененная версия получает rejected (видна
  инструктору с пометкой), предыдущая ОСТАЕТСЯ verified и действует;
  инструктор может заменить повторно. Причина отказа — точка расширения
  (не Must).
- ОВ-2: Распространяется ли статусная модель (pending-revalidation +
  верификация админом) на СТС, или только на ВУ (как дословно в п.2)?
  Дефолт: ДА, единая модель для ВУ и СТС по авто — иначе два механизма
  для одинаковых по сути документов; пункты 1 и 3 требуют замены СТС
  так или иначе.
- ОВ-3: Влияет ли pending-revalidation (или rejected замены) ВУ/СТС на
  новые действия инструктора — видимость в каталоге, новые заявки
  учеников, отправку авто на валидацию? Дефолт: НЕ влияет —
  инструктор остается полностью активным (NFR-23); влияние — точка
  расширения после первого эксплуатационного опыта.
- ОВ-4: Что видит админ для верификации документов и в каком месте
  админки? Дефолт: новый раздел «Документы»: список ожидающих версий

  ожидающих версий, историю не трогаем.
- ОВ-5: «Следующее плановое занятие» и счетчики (FR-75) — учитывать
  только ПОДТВЕРЖДЕННЫЕ брони или также новые ЗАПРОСЫ учеников?

  отклонен и счетчиками обещать его нельзя; запросы видны в подразделе

- ОВ-6: Замена СТС у validated-авто — сбрасывать ли статус авто в

  сбрасывать — статус авто и статус документа независимы (машины
  состояний разные, FR-70); повторная валидация авто — отдельное
  действие инструктора submit, как в Спринте 7.
- ОВ-7: Повторная загрузка ожидающей версии (пока первая замена в

  замещает ожидающую версию (в очереди одна ожидающая версия на
  документ); «отозвать замену» отдельной кнопкой — точка расширения.
