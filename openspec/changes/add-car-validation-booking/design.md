## Модель данных (NFR-наследование; DDL уточняет dev в границах)

Расширение `instructor_cars` (миграция idempotent — механика users.role):

- `status TEXT NOT NULL DEFAULT 'validated'` — статус валидации.
  РЕШЕНИЕ (значение DEFAULT): существующие строки при миграции получают
  'validated' — автомобиль, живший до статусной модели, не должен
  исчезнуть из каталога и пар (обратная совместимость каталога);
  НОВЫЕ авто создаются в 'draft' — create_car пишет статус ЯВНО в INSERT,
  DEFAULT в новом коде не используется (защита от «молчаливого validated»
  при будущих INSERT).
- `blocked INTEGER` (Спринт 5) объявляется УСТАРЕВШЕЙ: новые эндпоинты ее
  не читают и не пишут; скрытие от учеников регулируется status.
  Данные не мигрируют. Эффект по существующим броням (MIN-2 арх-ревью):
  брони всех авто — в том числе заблокированных в Спринте 5 —
  СОХРАНЯЮТСЯ (не аннулируются), видимость авто и его фото в
  существующих бронях после миграции определяется статусом по ОВ-2
  (существующие строки → validated, «Проверено»).
- `photo_path` (Спринт 3) — устаревшая, без изменений (наследование).

Состав ракурсов и СТС — БЕЗ структурных изменений: photo_front/rear/
interior/left/right, photo_sts (Спринт 5).

Таблица booking, availability, student_requests, users — без структурных
изменений.

## Машина статусов (норма объема)

```
            submit (инструктор)         validate (админ)
  draft ────────────────► validating ────────► validated
    ▲                         │
    └─────────────────────────┘
          withdraw (инструктор, ОВ-3)
```

- Начальный статус нового авто — draft.
- draft→validating: `POST /api/instructor/cars/{id}/submit`, только
  владелец; авто в другом статусе → 409.
- validating→draft: `POST /api/instructor/cars/{id}/withdraw`, только
  владелец (ОВ-3 — отзыв возвращает авто в черновик, скрывает его от
  учеников); авто не в validating → 409.
- validating→validated: `POST /api/admin/cars/{id}/validate`
  (X-Admin-Token); предусловие ОВ-4: загружено ЛЮБЫЕ 3 ракурса из 5
  (COUNT непустых колонок ракурсов ≥ 3) И photo_sts NOT NULL — иначе 409
  с перечнем недостающего; авто не в validating → 409.
- validated — терминальный в этом объеме (переход вниз — точка
  расширения, см. proposal).
- Загрузка/замена фото и СТС статус НЕ меняет (инструктор дозагружает
  ракурсы в draft/validating; после замены комплекта повторная отправка —
  через submit/withdraw-цикл).

## Видимость по статусу (ОВ-2) — матрица

|| Поверхность | draft | validating | validated |
|---|---|---|---|
| Плитки/список владельца («Мои автомобили») | виден, статус «Черновик» | виден, «На проверке» | виден, «Проверено» |
| Карточки каталога новых учеников (выбор инструктора, авто-фильтры) | НЕ участвует | НЕ участвует | участвует |
| Карточка авто у ученика ПАРЫ | скрыт (404-неразличение выдачи) | виден, желтый бейдж «Не проверено» | виден, «Проверено» + зеленая галочка |
| Фото ракурсов ученику пары (GET photo/{angle}) | 404 | выдается | выдается |
| Фото авто в брони ученика (календарь) | без фото (плейсхолдер) | с фото | с фото |
| СТС | только владельцу | только владельцу | только владельцу |

Правила реализации:
- видимость применяется СЕРВЕРНО на каждом запросе выдачи (каталог,
  карточки, фото, брони) — параметризованный SELECT по status; UI-скрытие
  не считается (наследование NFR-7);
- отказ по draft для ученика — 404-неразличение (не раскрываем
  существование авто; наследование NFR-4);
- у инструктора-владельца свои авто видны во ВСЕХ статусах (управление
  черновиком — необходимость для дозагрузки и отправки);
- админ видит все авто всех статусов.

## Баг 5.2 — диагностика выдачи фото (плитки инструктора и ученика)

Симптом: фото сохраненного авто не отображается в плитке инструктора и
у ученика. Наблюдаемое требование — в спеке (MODIFIED «Фото автомобиля
доступно владельцу»); способ починки спека не предписывает. Диагностическая
задача (tasks.md 3.1) проверяет цепочку по звеньям и фиксирует корень в
отчете задачи:

- (а) выдача: GET /api/instructor/cars — возвращает ли payload с
  фото-URL ракурсов; GET …/photo/{angle} — отдает ли image/* владельцу
  и ученику пары (матрица кодов Спринта 5);
- (б) клиент: какой URL строит плитка (frontend/js/dashboard-instructor.js)
  и карточка ученика (cabinet.html / booking) — совпадает ли с реальным
  маршрутом; не подставляется ли файловый путь data/uploads/… (статикой
  не раздается) вместо URL эндпоинта; не остается ли плитка на
  устаревшем одиночном поле photo_path (устаревшая колонка);
- (в) состояние: воспроизводится ли после перезагрузки и повторного
  входа; при отсутствии фото — плейсхолдер, не битая картинка.

## СТС существующего авто — диагностика симптома «POST photo kind=car_sts»

Наблюдение по коду (уточняется задачей диагностики, tasks.md 4.1): в
backend/instructor_cars.py существует legacy-пара POST+GET
`/api/instructor/cars/{id}/photo` (БЕЗ ракурса, хвост Спринта 5 —
design.md предписывал удалить, в коде остался), которая пишет в
устаревшую photo_path и игнорирует kind — вызов с kind=car_sts НЕ
заполняет photo_sts; параметризованный POST …/photo/{angle} принимает
только 5 ракурсов. Итог: СТС на созданном авто загрузить нельзя.

Решение:
- РАСШИРЕНИЕ списка ракурсов значением `sts`: POST
  `/api/instructor/cars/{id}/photo/sts` → валидация как у фото (JPEG/PNG
  magic bytes, ≤5 МБ) → запись в photo_sts; GET …/photo/sts — только
  владелец (эквивалент существующего GET …/sts, который сохраняется для
  совместимости «Моих документов»);
- legacy POST+GET `/api/instructor/cars/{id}/photo` (одиночное фото,
  photo_path) УДАЛЯЮТСЯ вместе с фиксацией (REMOVED-дельта «Одиночное
  фото автомобиля без ракурса (фото-контракт Спринта 3)» — MIN-4
  арх-ревью); фото-кластер тестов Спринта 3 (tests/test_s3_backend.py,
  TC-S3BE-008 — 12+ проверок legacy-маршрута) подлежит обновлению на
  параметризованный маршрут в задаче 4.1; диагностика проверяет и
  фиксирует в отчете задачи всех клиентов legacy-маршрута (фронт и
  тесты), чтобы удаление не сломало выдачу; мастер-спека приведется при
  архивации;
- диагностика обязана подтвердить корень (kind теряется / пишет не в ту
  колонку) воспроизведением и зафиксировать в отчете задачи ДО фикса.

## Замена контура блокировки (Спринт 5) — обоснование

Требование Спринта 5 «Комплектность фото автомобиля проверяет
администратор» решала ту же задачу («человек в админке валидирует
комплект») через БЛОКИРОВАНИЕ авто с неполным комплектом. Статусная
модель покрывает ее полностью и добавляет недостающее позитивное
подтверждение: неполный комплект теперь живет в draft/validating и так
скрыт от учеников — отдельная блокировка дублирует скрытие с худшей
эргономикой (нет пути к validated). Поэтому: требование блокировки
замещается (MODIFIED-дельта), эндпоинт POST /api/admin/cars/{id}/block
УДАЛЯЕТСЯ, колонка blocked — устаревшая (см. «Модель данных»).
Поведение «заблокированный/неполный авто недоступен ученикам»
сохраняется через draft (сценарий дельты).

## API-эндпоинты (методы / роли / валидации)

Формат ответов — механика Спринтов 1–5: 200 {ok:true, …}; ошибки
{ok:false, error:"<по-русски>"}; 401/403/404/409/422 — как в design.md
Спринта 5. SQL параметризованный (NFR-10←NFR-3); токены/персональные
данные в логах запрещены.

## Фронт (без новых страниц)

- `instructor-dashboard.html` + `js/dashboard-instructor.js`: плитки авто —
  бейдж статуса («Черновик»/«На проверке»/«Проверено»), кнопки
  «Отправить на проверку» (draft) / «Отозвать» (validating), счетчик
  комплекта; плитка строится от URL авторизованного эндпоинта (не от
  файлового пути) — фикс 5.2; календарь графика — кнопки
  «Сохранить»/«Отменить» (FR-68): «Сохранить» = один PUT полной замены,
  «Отменить» = перезагрузка GET без PUT (ОВ-6 — брони решаются мимо
  кнопок), 409 с перечнем затронутых интервалов показывается с
  сохраненным графиком.
- `admin-dashboard.html` + `js/admin-dashboard.js`: новый раздел
  «Автомобили» — таблица всех авто (владелец, марка/модель/госномер,
  статус, комплектность), фильтр «На валидации», модалка подтверждения
  с чек-листом комплектности (5 ракурсов + СТС); кнопка «Подтвердить»
  ЗАБЛОКИРОВАНА, пока ракурсов <3 или нет СТС (ОВ-4) — дублируется
  серверной проверкой 409; перечень недостающего виден и инструктору
  (counters в GET /api/instructor/cars); старый админ-раздел /admin/cars
  (комплектность + блокировка, Спринт 5) СЛИТ в раздел «Автомобили» и
  удален — один раздел про авто (ОВ-5, как FR-67 сливает бронирования
  с календарем); навигация — без «Отношения»/«Расписания».
- `cabinet.html` + `js/cabinet.js`: карточки авто — бейджи по статусу;

## Решения по НФТ

- NFR-7: матрица видимости выше; серверная проверка статуса на каждом
  запросе выдачи; СТС и далее только владельцу.
- NFR-9: uploads.py без изменений (magic bytes, ≤5 МБ, uuid-имена) —
  sts-ракурс идет через существующую механику.
- NFR-10: параметризованный SQL во всех новых запросах (grep-контроль —
  задача приемки); статусы/токены/персональные данные в логах запрещены.
- Миграции: idempotent (механика users.role); безопасны на существующем
  volume контейнерного стенда (init_db через lifespan — наследование
  add-containerization).

## Сознательные ограничения (задокументированы)

- Отказ админа (validating→draft/отклонено с причиной) — точка
  расширения: машина статусов допускает добавление перехода без
  переделки; в этом объеме его нет (инструктору доступен отзыв — ОВ-3).
- Снятие подтверждения (validated→…) — вне объема (терминальный статус).
- Порог «3 ракурса» — только для ПОДТВЕРЖДЕНИЯ; обязательность полного
  набора из Спринта 5 (создание с СТС, 5 загружаемых ракурсов) не
  пересматривается.
- Колонки blocked/photo_path — устаревшие без миграции данных;
  cleanup-миграции (удаление колонок) — вне объема.
- Уведомления о смене статуса — вне объема.
- In-memory сессии/токены, single-worker, статика без серверной защиты
  страниц — наследованные ограничения, не revisiting.

## Соответствие ADR-004

Отступлений нет: ФИО — только в users; файлы — data/uploads/ вне статики,
выдача авторизованными эндпоинтами; связь «пара» — статус accepted
student_requests; рейтинг не затронут. Новое решение объема — колонка
status с миграцией существующих строк в validated и удалением
блокировочного контура; ADR/карта архитектуры обновляются архитектором
при ревью пакета (вне этого пакета).
