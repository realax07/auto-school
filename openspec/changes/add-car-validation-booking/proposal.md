# Change: add-car-validation-booking

## Why (Зачем)

Спринт 7. После Спринта 5 автомобиль инструктора существует в двух
состояниях — «есть в БД» и «есть в БД», без различия «данные загружены»
и «данные проверены школой»: только что созданный автомобиль (одна
анкета без фото) виден ученику так же, как полностью укомплектованный.
При этом админ-контур комплектности (Спринт 5) умел только БЛОКИРОВАТЬ
авто с неполным комплектом — позитивного пути «проверили и подтвердили»
нет. Параллельно живут хвосты выдачи: фото сохраненного авто не
отображается в плитке инструктора и у ученика (баг 5.2 — регрессия
выдачи), СТС на УЖЕ созданном авто загрузить нельзя (эндпоинт принимает
только ракурсы, legacy-маршрут пишет в устаревшую photo_path, kind=car_sts
теряется). Навигация перегружена демо-заглушками («Отношения»,
«Расписания» в админке, «Ваш следующий маршрут» на главной инструктора,
кнопка «← В кабинет» вместо единого сайдбара у ученика — BUG-047).
И, наконец, бронирование: в календаре ученика автомобиль пары показан
текстом, без фото.

Решение — статусная модель валидации автомобиля: draft / validating /
validated с серверными переходами, статусной видимостью для учеников и
подтверждением человеком в админке (порог: любые 3 ракурса + СТС).

Источник требований: `docs/ba/requirements-car-validation-booking.md`
(УТВЕРЖДЕН; решения Заказчика ОВ-1…ОВ-7 — в конце документа). Задействованные
в этом пакете решения: ОВ-2 (видимость/бейджи статусов), ОВ-3 (отзыв
инструктором возвращает авто в draft), ОВ-4 (подтверждение админом:
любые 3 ракурса + СТС).

## What Changes (Что меняет)

- Домен `instructor-cars` (MODIFIED + ADDED):
  - статус валидации автомобиля: draft / validating / validated; все
    существующие авто мигрируют в validated, новые создаются в draft;
  - переходы: draft→validating — инструктор отправляет на проверку;
    validating→draft — инструктор отзывает (ОВ-3); validating→validated —
    админ подтверждает, требуется ЛЮБЫЕ 3 ракурса из 5 + СТС (ОВ-4);
    некорректный переход отклоняется (409);
  - видимость для учеников (ОВ-2): draft — скрыт; validating — виден
    (ученику пары) с желтым бейджем «Не проверено»; validated — бейдж
    «Проверено» + зеленая галочка; каталог новых учеников — только
    validated;
  - фикс выдачи (баг 5.2): фото сохраненного авто отображается в плитке
    инструктора и в карточке у ученика после перезагрузки и повторного
    входа; без фото — плейсхолдер;
  - СТС существующего автомобиля: загрузка/замена СТС на созданном авто
    работает (диагностика симптома «POST photo kind=car_sts не
    сохраняет» — в tasks.md, корень фиксируется отчетом задачи);
  - админ-контур: вместо блокировки — подтверждение валидации; раздел
    «Автомобили» админки: все авто, фильтр «На валидации», модалка
    подтверждения с комплектностью; кнопка подтверждения заблокирована,
    пока ракурсов <3 или нет СТС (ОВ-4). Блокировка (Спринт 5) и
    legacy-одиночное фото (хвост Спринта 5) удаляются вместе со своими
    требованиями.
- Домен `instructor-documents` (MODIFIED): «Мои документы» — выдача
  ТОЛЬКО владельцу (как прежде) + СТС по каждому авто независимо от
  статуса валидации; дозагрузка СТС существующему авто появляется в
  разделе.
- Домен `booking` (MODIFIED): в календаре ученика у подтвержденной брони
  отображается ФОТО прикрепленного авто инструктора (draft-авто — без
  фото, скрыт; авто удален — корректное пустое состояние «—», наследие
  MIN-3).
- Домен `student-instructor-choice` (MODIFIED): в карточках каталога и
  авто-фильтрах участвуют только validated-автомобили.
- Навигация (ADDED-возможность `navigation`): админка — без демо-пунктов
  «Расписание»/«Отношения»; ученик — «Выбор инструктора» без кнопки
  «← В кабинет», единый сайдбар кабинета (BUG-047); главная инструктора —
  без декоративного «Ваш следующий маршрут».

Модульная архитектура (директива Заказчика, наследуется): новый код
статусов — в существующем домене `backend/instructor_cars.py` (свой
домен, не раздувается чужими concerns); выдача ученикам — точечные
расширения существующих модулей; фронт — существующие ES-модули
`frontend/js/*` без новых сборочных единиц, кроме минимальных правок.

## Impact (Последствия)

- Код: РАСШИРЕНИЯ `backend/instructor_cars.py` (статусы, submit/withdraw,
  admin validate, angle='sts', status в выдаче), `backend/db.py`
  (idempotent-миграция колонки status; существующие строки → validated),
  `backend/uploads.py` (без изменений — kinds уже есть), `backend/booking.py`

  (include/статика — без новых страниц). УДАЛЕНИЕ хвостов: legacy
  POST+GET `/api/instructor/cars/{id}/photo` (одиночное фото, photo_path)
  и POST `/api/admin/cars/{id}/block`. Фронт: `frontend/js/dashboard-instructor.js`
  + `instructor-dashboard.html` (статусы, кнопки отправить/отозвать,
  плитки), `frontend/admin-dashboard.html` + `frontend/js/admin-dashboard.js`
  (раздел «Автомобили», модалка, чистка навигации), `frontend/cabinet.html`
  + `frontend/js/cabinet.js` (бейджи, фото авто в бронях, сайдбар),
  `frontend/instructor-choice.html` + `frontend/js/instructor-choice.js`
  (сайдбар, каталог validated), `frontend/instructors.html` (без «маршрута»).
  Тесты в `tests/`.
- Хранилище: без новых подкаталогов; миграция колонки — idempotent,
  выполняется при старте приложения (init_db, в т.ч. на существующем
  volume контейнерного стенда — см. design add-containerization).
- Master-spec: MODIFIED — `instructor-cars` («Фото автомобиля доступно
  владельцу»), `instructor-documents` (1), `booking` (1),
  `student-instructor-choice` (1); REMOVED — `instructor-cars`
  («Комплектность фото автомобиля проверяет администратор» — заменена

- API-контракты и модель данных — design.md настоящего пакета; sdd.md
  (раздел «Спринт 7») дополняется задачей приемки.

## Out of scope / допущения

- Отклонение авто админом (validating→отказ с причиной) — НЕ в объеме:
  требование фиксирует только подтверждение; инструктору доступен отзыв
  (ОВ-3). Точка расширения: статусы и переходы допускают новую
  админ-операцию без переделки модели.
- Разблокировка/повторная блокировка: контур блокировки Спринта 5
  заменяется статусной моделью и удаляется (обоснование — design.md);
  отдельной операции «снять подтверждение» (validated→…) в объеме нет.
- Уведомления инструктору/админу о статусах (email/push/in-app) — вне
  скоупа.
- Ограничение «3 ракурса» — порог ПОДТВЕРЖДЕНИЯ админом; загрузка всех
  5 ракурсов и правило обязательности набора из Спринта 5 не меняются
  (5 ракурсов остаются загружаемыми, замена каждого — независимая).
- Диагностика бага 5.2 и СТС-симптома: наблюдаемые требования фиксируют
  спеки; корень вскрывается диагностическими задачами tasks.md (план —
  design.md), способ починки спекой не предписан.
- Колонка photo_path (Спринт 3) остается устаревшей без миграции данных
  (наследование Спринта 5).
