# Design: add-ai-chat-home

## Context

Стек (sdd.md): FastAPI-монолит backend/app.py (include_router по доменным
модулям backend/{auth,student,instructor,wallet,policy}), SQLite
data/app.db (WAL, только параметризованные ?-запросы, схема — CREATE
TABLE IF NOT EXISTS при старте backend/core/db.py), сессии ученика —
in-memory dict TTL 12 ч, заголовок X-Session-Token (backend/auth/auth.py,
_session_user_id). Фронтенд — Vue multi-entry MPA: кабинет —
frontend/vue/cabinet.html + src/pages/cabinet/App.vue (плоский wiring в
onMounted), HTTP-обертка src/shared/api.js (X-Session-Token из
sessionStorage 'session_token'). Раздел «Главная» — #sec-home: .greet,
чат-бар .assistant (заглушка), .quick, .services-title/.tiles.
Макеты утверждены Заказчиком 2026-11-18 — эталоны дословных текстов:
design/mocks/mobile/mobile-home-chat.html (390px: приветствие по центру,
композер над таб-баром) и design/mocks/home-chat-web.html (1440px: левое
меню, приветствие по центру, композер внизу). Клиент hermes доступен на
хосте (`hermes chat -q`, oneshot) — временный инференс по решению
Заказчика (BACKLOG #5 в редакции requirements-ai-chat-home.md).

## Цели и не-цели

Цели: «Главная» кабинета = ИИ-чат по макетам (обе версии), рабочий
POST /api/ai/chat с серверной историей и retention 14 дней, ограничение
тем системным промптом, носители/e2e/design-guard в том же цикле.

Не-цели: внешний инференс (только подготовленный под замену контракт),
вложения «+», чат вне кабинета ученика, правки сайдбара/таб-бара,
контрактов остальных API, мокапов и content/pdd.

## Решение 1: контракт API и адаптер провайдера (backend/ai)

Один доменный модуль backend/ai/ (прецедент backend/student/*):

- POST /api/ai/chat — auth X-Session-Token ученика, 401 без валидной
  сессии; запрос {message}; ответ {reply}; роутер включается
  include_router в backend/app.py.
- GET /api/ai/chat/history — история текущей учетки за последние 14 дней
  (массив сообщений role/text/created_at для рендера пузырей, обе версии
  представления подхватывают один и тот же серверный журнал).
- Генерация ответа — ТОЛЬКО через адаптер провайдера внутри модуля
  (внутренний интерфейс вида generate(messages) -> reply). Временный
  провайдер — сессия hermes: CLI `hermes chat` oneshot с системным
  промптом «ГигаЧат — помощник по обучению ПДД» + темы (ПДД, дорожные
  ситуации в России, ГИБДД), знания content/pdd + интернет. Передача
  текста сообщения — через `--query-file` (stdin/файл), НЕ argv:
  argv процесса виден в process-list хоста (ps) весь ход генерации;
  системный промпт — тоже мимо argv. Смена на внешний инференс =
  замена провайдера внутри backend/ai/ — фронтенд не правится
  (ограничение Заказчика, требования-19, раздел «Ограничения»).
- Бюджет ответа ≤30 с (NFR): `--run-budget SECONDS` вызова hermes +
  собственный таймаут ≤30 с; ошибка/таймаут → человеческий текст у
  поля (без кодов и стеков). Секреты и служебные argv в логи не
  попадают (NFR-3-семейство).

Отвергнутые альтернативы: внешний инференс сразу (вне спринта по решению
Заказчика); вызов модели из фронтенда (секреты и промпт у клиента).

## Решение 2: история чата в SQLite, retention 14 дней

Таблица ai_messages (id, user_id, role user|assistant, text, created_at)
в схеме backend/core/db.py — CREATE TABLE IF NOT EXISTS при старте
(прецедент wallets С16); только ?-плейсхолдеры (NFR-2). Подхват при
открытии чата: GET-история выборкой по user_id токена, упорядочивание по
времени, глубина 14 дней (условие по created_at). Retention — серверная
механика: DELETE записей старше 14 дней при чтении истории (и
опционально фоновая чистка на lifespan приложения); клиентской глубине
не доверять (NFR). Изоляция: выборка строго по user_id сессии
(параметризованно) — чужая история недоступна.

## Решение 3: фронтенд — замена #sec-home

Контент #sec-home заменяется по макетам, дословно:

- Удаляются .quick (3 быстрые кнопки) и .services-title/.tiles (все 4
  плитки, включая рабочие #tile-instructor/#tile-requests — навигация к
  «Найти водителя»/«Мои заявки» остается через сайдбар/таб-бар; молчаливая
  потеря раздела = дефект, FR-19.2). Удаляется .greet («ЛИЧНЫЙ КАБИНЕТ /
  Добро пожаловать, Иван!», App.vue:47) — приветствие «Главной» становится
  чатовым; ФИО остается в блоке учетки сайдбара и профиле таб-бара
  (MODIFIED cabinet, FR-5 сохраняется).

- Новая структура: spark-иконка (SVG дословно из макета), «Добрый день!»,
  подсказка «Спроси что угодно про обучение, экзамен или ПДД — помогу
  подготовиться»; композер прижат к низу (мобилка — над таб-баром):
  поле с плейсхолдером «Спроси что угодно про обучение, экзамен или
  ПДД...», кнопка «+» (disabled, подпись «Скоро»), рабочая кнопка
  отправки (стрелка вверх, как в макете).
- Состояния: пустая история (нет сообщений за 14 дней) → приветствие по
  центру (макет); есть история → переписка пузырями user/assistant
  вместо приветствия (FR-19.4).
- Отправка: POST /api/ai/chat через src/shared/api.js (X-Session-Token);
  на время ожидания — индикатор (не «висит» молча); ответ → пузырь
  assistant; ошибка/таймаут — человеческий текст у поля, без кодов.
- Сайдбар/таб-бар, остальные секции, хеш-навигация, sessionStorage-ключи
  — без изменений.

## Решение 4: носители и дизайн-контроль в том же цикле

Правило Заказчика: изменения макета/поведения UI несут обновление
e2e/design-guard в том же цикле (зона задач 19.3, СА не пишет):

- tests/web/test_cabinet_page.py — вербатим-гарды #sec-home (MOCKUP
  cabinet-student.html) переводятся на новые макеты БЕЗ ослаблений
  (фрагменты дословно; сами мокапы не синхронизируются).
- tests/web/test_ui_playwright.py — e2e чата (вход → чат → отправка →
  история; вьюпорты 390×844 и 1440×900) + design-guard перенос.
- Носитель TC-UI-060 (tests/web/test_ui_playwright.py:4708, BUG-060,
  решение Заказчика 2026-11-06) — судьба названа явно: тест машинно
  требует видимые/кликабельные #tile-instructor/#tile-requests и
  становится красным от удаления .tiles. Носитель переписывается на
  навигацию сайдбар/таб-бар (аналог сценария «Навигация не потеряна»
  specs/ai-chat); в тесте фиксируется замена решения BUG-060 решением
  Заказчика 2026-11-18 — «Да, убираем все кнопки с этого экрана и
  оставь только гигагаишника. Не только в могилке, но и на веб версии
  тоже» (требования-19, «Решения Заказчика»;
  decisions/2026-11-18-s19-ai-chat-home.md). Новая проверка — без
  ослаблений (переходы «Найти водителя»/«Мои заявки» обязаны работать).
- tests/api/test_s19_ai_chat.py (зона 19.2) — API/история/retention/
  изоляция/темы, TC-S19-NNN в docstring с трассировкой на Requirements
  specs/ai-chat/spec.md (прецедент test_s16_backend.py).
- QA (19.4): test-model/checklists/add-ai-chat-home.md → кейсы →
  автоматизация, design check по макетам, полный regress.

## Риски / сознательные ограничения

- Временный провайдер — внешний CLI: latency/доступность нестабильны.
  Смягчение: таймаут ≤30 с + человеческая ошибка у поля (NFR).
- Гарантия отказа на посторонние темы — свойство системного промпта
  (best effort); спека фиксирует видимое поведение (FR-19.6), тест
  сценарием на типовых вопросах.
- Удаление .greet задевает носитель ФИО кабинета — MODIFIED cabinet +
  адаптация носителей в 19.3; регресс ФИО в сайдбаре закрывается
  существующим прогоном test_cabinet_page/test_sidebar_unified.
- Латency-прогон провайдера не входит в unit-гейты (внешний процесс) —
  QA-кейс на боевой сессии (19.4).
- Конкурентные вызовы провайдера — ЯВНОЕ допущение: sync-хендлер
  FastAPI уходит в threadpool, при одновременных запросах двух учеников
  возможны параллельные hermes-процессы. Нагрузки спринта малы —
  параллелизм не ограничиваем (семафор/очередь в backend/ai не
  вводим); поведение при параллельных запросах на 19.4 НЕ проверяется
  (нагрузочного сценария в плане прогонов нет).
