## 1. Целевые проверки (фокус ревью)

### 1.1 Проверка role='instructor' на бэке — ДА, корректно

- Доступ к кабинету защищается не фронтом, а серверным эндпоинтом данных
  GET /api/instructor/me: require_session (401) → SELECT users по user_id
  (401 при отсутствии записи) → role != 'instructor' → 403 (design.md
  «Доступ и проверка роли», sdd.md §20.1, задача 1.1). Механика
  подтверждена по коду: require_session (auth.py:97–106) возвращает user_id
  из реестра {token: (expires, user_id)} с ленивой чисткой истекших; роли в
  users хватает (db.py миграция role, DEFAULT 'student').
- Distinct 401/403 корректен: 403 = «сессия валидна, роль не та» — сценарий
  «сессия ученика» покрыт спекой и задачей 1.1 (тест student → 403).
- Альтернатива «расширить /api/auth/me ключом role и фильтровать на фронте»
  отклонена обоснованно (research.md §2): это была бы проверка фронтом плюс
  регресс контракта Спринтов 1–2.1.
- Техдолг Спринта 2.1 закрывается: design.md add-instructor-flow (поток 4)
  требовал «при реальном кабинете — обязательная серверная проверка роли
  (require_session + role)» — выполняется этим эндпоинтом. Вторая половина
  той же записи («ключ role в /api/auth/me») не реализуется сознательно:
  с выделенным эндпоинтом кабинета ключ role в /me больше не нужен
  (фронт различает роли по 403 от /api/instructor/me). Запись в map.md
  обновлена соответствующе (см. правку карты).
- Замечание (не замечание к пакету — фиксация факта): HTML
  /instructor/dashboard, как и вся статика проекта, доставляется всем;
  FR-18 «страница не показывается» достигается клиентским редиректом после
  401/403 от API, до отрисовки (wiring: вызов до render). Это осознанный
  паттерн статики без сборки, зафиксированный в map.md со Спринта 1
  (/cabinet) и распространенный на cabinet-stub в 2.1. Консистентно;
  данных в разметке нет — только демо.

### 1.2 Демо-данные vs реальные — разделение корректное, один риск

- Архитектурно реальные данные в кабинет не попадают: единственный эндпоинт
  возвращает только {id, surname, name, patronymic, email} (состав §10.3);
  заявки (license_category и пр.) кабинету не выдаются; всё содержимое
  карточек — статика мокапа. Обратная путаница («реальное приняли за демо»)
  невозможна — реальных бизнес-данных в объеме нет.
- Проверено по мокапу: футер «Демонстрационный интерфейс · Все данные
  вымышлены» присутствует (dashboard-instructor.html:83); navTo дает
  toast «следующий экран в концепции кабинета» (:90); демо-персона
  «Михаил Самойлов»/«МС»/«Инструктор · Категория B» — :29. Задача 2.1
  требует сохранения футера и пометок — контроль в design check (4.1) есть.
- MIN-1: «Мой день» — главный вид, открывается первым — без пометки «демо»
  (design.md: «у разделов (кроме „Мой день“)»). При этом именно на нем
  реальное ФИО из учетки стоит вплотную к фиктивным занятиям, ученикам и
  доходам — самый вероятный момент путаницы. FR-21 говорит «разделы помечены
  как демо-данные» без исключения для «Мой день». Требуется: либо пометку
  «демо» на содержимом «Мой день» тоже (маленький бейдж, дословности
  ключевых блоков FR-19 не мешает), либо явная ссылка на решение
  Заказчика/рекомендацию макета, почему главный вид исключен.

### 1.3 Достаточность контракта /api/auth/me (ФИО, инициалы) — ДА

- /api/auth/me возвращает {id, surname, name, patronymic, email}
  (auth.py:264–292) — для FR-20 достаточно: ФИО = «{surname} {name}
  {patronymic}», инициалы = первые буквы фамилии и имени (обоих полей
  достаточно по определению инициалов; отчество в инициалы не входит).
- Полнота данных гарантирована схемой: register.py требует patronymic,
  instructor_applications имеет surname/name/patronymic NOT NULL →
  вырожденный случай «нет отчества» не воспроизводим.
- Пакет правильно НЕ расширяет /api/auth/me: кабинет берет те же поля из
  GET /api/instructor/me (тот же состав, но с серверной проверкой роли) —
  контракт Спринтов 1–2.1 без регресса. Согласовано: design.md, sdd.md
  §20.1/§20.2, задача 1.1.

## 3. Minor-замечания

### MIN-1: «Мой день» без пометки «демо» — главный вид уязвим к путанице

См. §1.2. Требование: в design.md/задаче 2.1 либо добавить пометку «демо»
на содержимом «Мой день», либо заменить молчаливое исключение на явную
ссылку на источник (решение Заказчика / рекомендация макета).

### MIN-2: противоречие THEN «переход после входа» между двумя активными дельтами

Спека instructor-auth (add-instructor-flow)Scenario «вход успешен → THEN
попадает на /instructor/cabinet-stub» остается в дереве изменений, а новая
спека instructor-dashboard задает «route='cabinet' → /instructor/dashboard».
Proposal объясняет отказ от дельты по instructor-auth, но до архивации
add-instructor-flow оба требования активны и противоречат друг другу.
Требование: при архивации Спринта 2.1 (или в этом пакете) оформить смену
назначения как MODIFIED requirement домена instructor-auth либо явную
заметку superseded, чтобы в specs не остались два взаимоисключающих THEN.

### MIN-3: разрыв неймсейса /api/instructors/* vs /api/instructor/me

Публичный домен анкеты живет под /api/instructors/apply (мн. число), новый
эндпоинт кабинета — /api/instructor/me (ед. число). Функционально безвредно
(разные домены), но это две конвенции для одной сущности. Требование:
зафиксировать в sdd.md §26 (вне спринта) правило выбора префикса для
следующих эндпоинтов кабинета, чтобы неймсейс не разъезжался дальше.

### MIN-4: битая ссылка на задачу в design.md

design.md «Доступ и проверка роли» заканчивается «пометка в
architecture/map.md — задача реализации (5.2)» — задачи 5.2 в tasks.md нет;
пометка карты выполняется в задаче 4.1 (приемка). Требование: поправить
«(5.2)» → «(4.1)». Правка документальная, до старта работ.
