# Research: add-instructor-cabinet

Наследуются техрешения Спринтов 0–2.1: FastAPI + SQLite, фронт — статика из
design/mocks без сборки, сессии — in-memory токен TTL 12 ч (require_session),
me / logout контракты Спринта 1, route-механика §15.5. Ниже — альтернативы по
новым решениям объема (E12).

## 1. Проверка доступа к кабинету: только фронт vs серверная проверка роли

|| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Серверная проверка: require_session + роль на эндпоинте данных кабинета** | Ключ role уже в users; GET /api/auth/me (§10.3) уже отдает ФИО по сессии — данные для кабинета доступны защищенно; student-сессия не проходит | Новый эндпоинт (или расширение /me ключом role) | **ВЫБРАНО** — прямое следствие FR-18 и design.md add-instructor-flow (поток 4: «при реальном кабинете — обязательная серверная проверка роли (require_session + role)»; этот объем тот самый случай). Техдолг заглушки §15.5/design.md закрывается здесь |
| Только фронт-проверка (JS: 401 от /api/auth/me) | Ноль бэка | Сессия ученика проходит проверку (role в /me не возвращается) — student видит кабинет инструктора; нарушает FR-18 | Отклонено (нарушение FR-18) |
| Проверка роли middleware'ом на маршруте статики /instructor/dashboard | Защита до отдачи HTML | Статика отдается без сессий в текущей архитектуре (токен в sessionStorage, не в cookie) — механику пришлось бы изобретать; не защищает API | Отклонено (ломает модель авторизации Спринта 1) |

## 2. Данные ФИО для кабинета: reuse /api/auth/me vs новый эндпоинт

|| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|---|
| **Новый GET /api/instructor/me: require_session + role='instructor', ответ как /me** | Серверная проверка роли (FR-18) в одной точке; контракт /me (§10.3) не меняется — нет регресса Спринтов 1–2.1; кабинет не отдает данные ученику | Один новый маленький эндпоинт | **ВЫБРАНО** |
| Расширить /api/auth/me ключом role и фильтровать на фронте | Меньше эндпоинтов | Меняет существующий контракт (Спринты 1–2.1 читают ответ); роль по факту не проверяет — токен ученика валиден; «фильтрация на фронте» = проверка фронтом | Отклонено (регресс контракта + не выполняет FR-18) |

## 3. Назначение route='cabinet': вести в dashboard vs оставить заглушку

|| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|---|
| **Wiring фронта: route='cabinet' → /instructor/dashboard** | Кабинет достижим из флоу входа (иначе весь объем недостижим); контракт login §15.5 не меняется (ключ route как есть) | Заглушка перестает быть назначением маршрута (страница остается) | **ВЫБРАНО** |
| Оставить route='cabinet' → /instructor/cabinet-stub, кабинет открывать вручную | Ноль правок входа | Новый кабинет недостижим после входа — объем теряет смысл; заглушка существовала именно как временное назначение до этого объема | Отклонено |

## 4. Сайдбар макета: разделы по FR-19 vs строго исходник HTML

Макет dashboard-instructor.html не содержит nav-кнопок (стили .nav и функция
navTo заданы, кнопки в исходнике отсутствуют), FR-19 перечисляет разделы
явно. Разделы сайдбара строятся по перечню FR-19 в стилистике макета
(использование готовых .nav-стилей и navTo — дословность текстов/структуры/
стилей ключевых блоков из FR-19 не затрагивается). Альтернатива «точно
воспроизвести исходник» сделала бы FR-19 неисполнимым. Альтернативы — одна;
зафиксировано как допущение в proposal.md.

## 5. Инкрементальные мелочи

Схема БД не меняется (users §4/§16 достаточна). Демо-данные — статика
фронта. Выход — механика logout §10.2 без изменений. Альтернативы не
рассматривались — инкремент тривиален.
