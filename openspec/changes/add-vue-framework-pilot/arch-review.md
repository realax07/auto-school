## 1. Разбор по пунктам проверки (1–6)

### 1.1. Multi-entry вместо SPA-монолита — работает на плане задач

Проверено по коду, не по тексту пакета: маршрут — одна строка словаря
`_PAGE_ROUTES` (backend/app.py:42 `/instructors/pending: instructor-pending.html`);
задача 2.3 заменяет целевой файл на `frontend/vue/dist/instructors-pending.html`,
остальные 12 записей словаря и все `/api/*` не затрагиваются — «мигрированная
страница заменяет монолит, остальные не ломаются» конструктивно верно: у
бэкенда нет общего шаблонизатора/сборки, каждая страница — независимый файл,
переключение строго локально. План миграции С9→С10→С11 сверен со списком
файлов: 1 + 5 + 7 = ровно 13 страниц `frontend/*.html`, пропусков и дублей
нет. E2e-якорь существует в заявленном виде: TC-UI-004
(tests/test_ui_playwright.py:358–360) — `wait_for_url("**/instructors/pending")`
+ `expect(h1).to_have_text("Заявка на рассмотрении")`; `to_have_text` —
автождение, момент гидрации Vue покрыт. Отказ от vue-router/pinia — прямо
в границах ОВ-3. ЗАМЕЧАНИЕ: у legacy-файла есть потребитель вне Playwright и
вне `_PAGE_ROUTES` — **MAJ-1** (§2).

### 1.2. Vendor-чанки и бюджеты NFR-26 — достижимы

Механика штатная для Vite/Rollup: `manualChunks` (runtime vue → чанк `vue`,
сторонние пакеты → чанки по пакетам, общий код страниц → `shared`) +
multi-entry — вендорный код в чанках страниц не появляется, страница грузит
только свой static-import graph (это и есть критерий 4.1в). Арифметика
бюджета: пилот без единой библиотеки сверх Vue; runtime Vue 3 (tree-shaken
prod-build) — порядка 16–30 КБ gzip, чанк страницы + shared у экрана без
форм — единицы–десятки КБ; суммарно ~40–70 КБ gzip против лимита 200 КБ —
запас многократный; вендорный бюджет 150 КБ при одном vue-чанке не
напрягается. Заявка ADR-008 «~20 КБ gzip» — оценка, не факт; окончательно
решает замер на артефактах (4.1: `gzip -c | wc -c`, сумма static-import
graph) — методика корректна, и она же (задача 4.1) повторяется на приемке
каждого шага миграции, так что дрейф бюджетов контролируем. Регламент
«новая зависимость — только с оценкой бюджета чанка» отвечает ОВ-3 на
будущее. Возражений нет.

### 1.3. E2e-совместимость (NFR-27) и доставка dist — контур не ломается

Маршруты: все остальные страницы продолжают отдаваться из `frontend/` как
есть — немигрированные не зависят от сборки. Раздача нового префикса:
nginx в ОБОИХ контурах — catch-all `proxy_pass` на app
(deploy/container/nginx.conf `location / → app:8390`;
deploy/nginx-autoschool.conf `location / → 127.0.0.1:8390`), значит
`/vue/assets/*` доходит без единой правки nginx/compose — «БЕЗ ИЗМЕНЕНИЙ»
в пакете соответствует фактам. Dockerfile: node builder-этап перед python
builder + `COPY --from` в runtime наследует multi-stage ADR-006; compose
(`build: .`) в пересборке образа, отдельного механизма не нужно. Прогон e2e
против собранного dist (npm ci && npm run build → pytest) — честная приемка
(исследовательская альтернатива «гонять e2e по legacy» отклонена
обоснованно). Режим отказа задокументирован: забытая сборка = 404
пилотного маршрута → красный прогон с понятной причиной (ADR-008,
последствия). Нюансы реализации — **MIN-1** (bare-metal Node-prerequisite),
**MIN-2** (COPY-порядок/dist в .dockerignore), §2.

### 1.4. Пилот: зависимость от add-application-status-polling и NFR-28

Декларация зависимости корректна и согласована по всем слоям (proposal
«Impact», design «Интеграция», шапка tasks, задача 3.1, раздел
«Зависимости»): контракт — неперебираемый идентификатор, интервал 12 с,
waiting→approved (обмен на сессию) / waiting→rejected (причина), остановка
опроса при уходе — в точности FR-80…83/NFR-28; клиент пилота объявлен
потребителем, серверная сторона (эндпоинт статуса, обмен) — норма
polling-пакета; риск «двух конкурирующих реализаций опроса на одной
странице» назван, точка слияния — приемка 9.5. NFR-28 архитектуре не
противоречит: ≤5 запросов/мин с открытого экрана, эндпоинт read-only
(одиночный SELECT), остановка таймера на unmount/скрытие вкладки —
нагрузочный класс незначимый для single-worker + SQLite WAL, таймер не
переживает страницу (FR-83) — фоновых процессов не возникает. ЗАМЕЧАНИЕ:
исполнимость старта задачи 3.1 как написано — **MAJ-2** (§2): пакета
add-application-status-polling в дереве нет (параллельный worktree), а 3.1
требует «писать против его design.md» и включает сетевой смоук блока 2,
которому нужна серверная часть того пакета.

### 1.5. Модульная директива Заказчика (ОВ-3) — отвечает, монолита не создает

Структура построже буквы директивы: страница = отдельная точка входа и
свой чанк; библиотеки — только собственными vendor-чанками, инлайн в
страницы запрещен спекой; SPA/vue-router/pinia запрещены явно (research
п.2/п.8 с аргументами); общее СВОЕ код страниц — отдельный shared-чанк,
сознательно НЕ смешанный с вендорным (корректно: бюджет вендора не
расходуется на свой код, но shared считается в бюджете первого захода —
двойного учета нет). Регламент для будущих шагов (зависимость = оценка
чанка; >150 КБ gzip — отклонение или lazy) — прямой ответ на «выносы
библиотек и прочее». Каждая страница-вход физически не может втащить код
чужих страниц (multi-entry). Двойное ведение шапки/футера (12 legacy-монолитов
× Vue-компоненты) на время С9–С11 — задокументированный временный техдолг
ADR-008, исчезает по завершении миграции; это цена постраничности, а не
новый монолит.

## 2. Findings

### Blocker — нет

### Major

**MAJ-1 — противоречие пакета по судьбе legacy-файла: тест-потребитель не
запланирован.** Design «Отдача мигрированных страниц» утверждает:
«ссылок и маршрутов на файл вне `_PAGE_ROUTES` нет (grep-контроль — задача
2.3)» — факт не соответствует репо: tests/test_instructor_pages.py:256–268
(`test_pending_page_exists_and_text`) читает legacy-файл напрямую через
локальный helper `page("instructor-pending.html")` (строка 24) и при
удалении файла (задача 2.3) падает. Готовность 2.3 требует одновременно
«файл удален, grep — ссылок нет» И «pytest tests/test_instructor_pages.py
зеленые» — совместимо только правкой этого теста, но правка нигде не
запланирована: зона файлов 2.3 — только backend/app.py, а NFR-27 защищает
лишь tests/test_ui_playwright.py. Дев, дойдя до 2.3, обнаружит
самопротиворечащиеся критерии и будет импровизировать правку теста без
мандата — в пакете, где «0 правок в тестах» является приемочным аргументом
(5.1). Это тот же класс нестандартных допущений, что прецедент DEF-002:
факт проверяется чтением репо, а не повторением в тексте.

**MAJ-2 — зависимость от add-application-status-polling заявлена, но
условия исполнимости 3.1 не зафиксированы.** Пакета в дереве нет
(openspec/changes/ — 8 пакетов; polling параллелится в отдельном worktree,
решение 2026-11-02-s9-application-status-polling-go есть, пакета — нет),
при этом tasks 3.1 предписывает «писать 3.1 против его design.md», а
готовность 3.1 включает сетевой смоук блока 2 (запрос раз в ~12 с,
approved → кабинет, rejected → причина) — ему нужна СЕРВЕРНАЯ часть
polling-пакета (эндпоинт статуса, обмен идентификатора на сессию). По
воротам J46 dev_task стартует по этому пакету независимо от судьбы
соседнего: без зафиксированного предусловия 3.1 стартует без контракта —
дев либо блокируется, либо изобретает контракт (ровно те «две конкурирующие
реализации», которых пакет объявил недопустимыми). «Детали за ПМ» (слияние
на 9.5) — легитимная точка, но предусловие старта и условие смоука должны
быть записаны в пакете, а не удерживаться в голове оркестратора.

## 6. Основание вердикта

Ядро пакета архитектурно состоятельно и сверено с кодом, а не с текстом:
multi-entry ложится на фактическую механику `_PAGE_ROUTES` (замена
локальна, 12 страниц не затрагиваются); бюджеты NFR-26 достижимы с
многократным запасом и проверяются на артефактах, а не обещаниями;
catch-all nginx/compose подтверждает «доставку без изменений», Dockerfile
наследует ADR-006; зависимость от polling-пакета декларирована по всем
слоям, NFR-28 совместим с single-worker контуром; ОВ-3 выполнена строже
буквы (SPA/vue-router/pinia запрещены, регламент будущих зависимостей).
ADR-008 соответствует формату и содержанию пакета; карта обновлена.

Доработка — из-за двух major: пакет в двух местах делает утверждения,
опровергаемые текущим состоянием репо/дерева (потребитель legacy-файла;
доступность design.md polling-пакета), и готовности задач 2.3/3.1 при этом
самопротиворечивы — дев получит невыполнимый чек-лист и будет достраивать
контракт на ходу. Обе правки — точечные (design/tasks), на решения не
влияют. **доработка**: СА правит по §5, затем повторное ревью (J46);
dev_task до approve не стартует.
