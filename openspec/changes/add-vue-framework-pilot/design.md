# Design: add-vue-framework-pilot

Источники решений: docs/ba/requirements-sprint9.md (УТВЕРЖДЕН — блок 3
FR-84…FR-86, NFR-26 бюджеты 150/200 КБ gzip, NFR-27 e2e-совместимость);
решения Заказчика ОВ-3/ОВ-4 от 2026-11-02 (decisions/2026-11-02-sprint9-scope.md,
decisions/2026-11-02-s9-vue-framework-pilot-go.md); существующий контур —
ADR-001 (статика тем же сервисом), ADR-006 (multi-stage образ, compose,
pinned-образы), карта архитектуры; модульный JS Спринта 6 (frontend/js/*);
альтернативы — research.md настоящего пакета. Стек фиксирован ADR-008
(architecture/adr/008-vue3-vite-migration.md — создается задачей 1.1).

## Baseline (что есть, без миграции не меняется)

- 13 HTML-монолитов `frontend/*.html` + ES-модули `frontend/js/*`
  (Спринт 6); сборки нет.
- Маршруты страниц — словарь `_PAGE_ROUTES` в `backend/app.py`
  (FileResponse из `frontend/`); статика JS — `GET /js/{filename}` с явным
  content-type.
- Контур: nginx (reverse proxy 80/443) → app:8390 (ADR-006);
  bare-metal systemd — тот же app (FR-57). e2e: `pytest
  tests/test_ui_playwright.py` поднимает `uvicorn backend.app:app` из
  репозитория (фикстура `server`) — 49 сценариев, прогон идет по РЕАЛЬНОЙ
  статике репо/образа, моков страниц нет.

## Архитектура каркаса (решения ADR-008)

1. **Multi-entry MPA: страница = отдельная точка входа.** Каждая
   мигрированная страница — собственный HTML-вход Vite
   (`rollupOptions.input` по одному html на страницу) и собственный чанк
   страницы. Клиентский роутер НЕ вводится; навигация между страницами —
   обычные ссылки. SPA-монолит запрещен (ОВ-3).
2. **Vendor-сплит (правила, наследуемые всеми шагами миграции).**
   `build.rollupOptions.output.manualChunks` выделяет библиотеки в
   собственные чанки: runtime Vue → vendor-чанк `vue`; любой будущий
   сторонний пакет → отдельный vendor-чанк по пакету. Вендорный код НЕ
   инлайнится в чанки страниц (ОВ-3: «выносы библиотек»). Общий код
   страниц (api-клиент, утилиты) — отдельный чанк `shared` (свой код, не
   библиотека; на бюджет vendor-чанков не расходуется, но учитывается в
   JS первого захода).
3. **Бюджеты NFR-26:** каждый vendor-чанк ≤ 150 КБ gzip; суммарный
   JavaScript первого захода пилотной страницы (чанк страницы + все
   загружаемые им чанки: shared + vendor) ≤ 200 КБ gzip; страница
   загружает только свои чанки и требуемые vendor-чанки. Контроль — на
   артефактах сборки (задача 4.1). Vue 3 runtime (~20 КБ gzip) дает запас;
   в пилот не подключается ни одной лишней библиотеки (без pinia/vue-router —
   research.md п.8). Регламент для будущих шагов миграции: новая
   зависимость — только с оценкой бюджета чанка; чанк > 150 КБ gzip —
   отклонение или lazy-подключение.
4. **Постраничная миграция:** мигрированная страница ЗАМЕНЯЕТ HTML-монолит
   целиком (маршрут начинает отдавать каркасный вход, legacy-файл
   удаляется); немигрированные страницы живут как есть, без сборки и
   правок.

### План постраничной миграции (FR-84, Спринты 9–11)

| Этап | Страницы | Основание |
|---|---|---|
| Спринт 9 (этот пакет) | `/instructors/pending` (пилот, ОВ-4) | Простейший статусный экран, ноль форм; синергия с блоком 2 (задача 9.2) — функциональность проверяется на пилоте |
| Спринт 10 | `/instructors/rejected`, `/registered`, `/admin-login`, `/instructor/cabinet-stub`, `/review` | Одноцелевые статусные экраны и простые формы — тот же паттерн «экран = точка входа» без сложного состояния |
| Спринт 11 | `/`, `/instructors`, `/instructors/apply`, `/cabinet`, `/instructor-choice`, `/instructor/dashboard`, `/admin-dashboard` | Лендинги, анкета с multipart, кабинеты — наибольшая сложность; постранично, каждый шаг принимается зеленым полным e2e (NFR-27) |

Очередность: от простых экранов к сложным формам и кабинетам; окончательная
нарезка по спринтам — за ПМ (план зафиксирован, состав этапов уточняется в
спринтах; план страниц — норма ADR-008).

## Каталоги и сборка

```
frontend/
  *.html, js/            ← немигрированные монолиты (не трогаются)
  vue/                   ← workspace Vue/Vite (НОВЫЙ)
    package.json         ← vue, vite, @vitejs/plugin-vue — версии pinned
                           (наследование практики ADR-006); scripts: dev/build
    vite.config.mjs      ← multi-entry; manualChunks (vue → 'vue', сторонние
                           пакеты → чанки по пакетам, общий код → 'shared');
                           base '/vue/'; outDir 'dist'; hashed assets
    instructors-pending.html   ← вход пилотной страницы: статическая
                           разметка экрана (эквивалент legacy) + модуль-скрипт
    src/
      pages/instructor-pending/  ← пилот: main.js (createApp + таймер опроса),
                           App.vue, компоненты, стили
      shared/api.js      ← перенос fetch-обертки frontend/js/api.js
                           (контракты вызовов НЕ меняются)
    dist/                ← артефакт сборки: instructors-pending.html +
                           assets/*.{js,css} с хэшами (в .gitignore, в git НЕ
                           коммитится)
```

- `base: '/vue/'` — ассеты ссылаются на `/vue/assets/...`; префикс
  `/vue/` не пересекается с существующей статикой (`/js/*`, html-входы).
- Имя входа сохраняется Vite: `instructors-pending.html` →
  `dist/instructors-pending.html` (коллизий с legacy
  `instructor-pending.html` нет — он удаляется на том же шаге, tasks 2.3).
- Каталог `frontend/vue/` (а не верхнеуровневый `app/`): весь фронт живет
  в frontend/ — зонирование репозитория сохраняется, Docker-контекст и
  .dockerignore единые; верхнеуровневый app/ смешался бы с backend/app.py
  (research.md п.4).

## Доставка сборки в образ/контейнер и dev-режим

- **Dockerfile — добавляется node builder-этап** перед python builder
  (наследование multi-stage ADR-006):
  - `FROM node:22-slim@<digest> AS frontend-builder` (pinned, как python) →
    `COPY frontend/vue/package*.json` → `npm ci` (layer-cache по манифесту) →
    `COPY frontend/vue/` → `npm run build` (dist внутри этапа);
  - runtime-этап: `COPY --from=frontend-builder /app/frontend/vue/dist
    ./frontend/vue/dist`. node_modules и dev-зависимости в прод-образ НЕ
    попадают; владелец/права appuser не меняются.
- **docker-compose.yml — БЕЗ ИЗМЕНЕНИЙ** (`build: .` остается; nginx —
  reverse proxy без изменений, статика по-прежнему тем же сервисом —
  ADR-001; обе сети и порты не трогаются).
- **.dockerignore — дополняется**: `frontend/vue/node_modules/`
  (сборка идет в образе из манифестов), локальный `frontend/vue/dist/`.
- **bare-metal (FR-57):** перед деплоем выполняется `npm ci && npm run
  build` (тот же артефакт, что в образе) — порядок фиксируется задачей 2.2
  в комментарии Dockerfile; отдельного entrypoint/механики не вводится.
- **Dev-режим:** `npm run dev` (Vite dev server) для разработки страницы:
  быстрая итерация по SFC без пересборки; вызовы `/api/*` проксируются на
  локальный `uvicorn backend.app:app` (поле `server.proxy` в
  vite.config.mjs). Прод-эквивалент проверяется только на собранном dist —
  e2e и приемка идут против сборки, не против dev-сервера.
- **gitignore дополняется**: `frontend/vue/dist/`,
  `frontend/vue/node_modules/`.

## Отдача мигрированных страниц (backend/app.py)

- Маршрут `/instructors/pending` — FileResponse
  `frontend/vue/dist/instructors-pending.html` (media_type
  `text/html; charset=utf-8`). Остальные маршруты `_PAGE_ROUTES` — без
  изменений.
- НОВАЯ статика: `GET /vue/assets/{path}` — FileResponse из
  `frontend/vue/dist/assets`, content-type по суффиксу явно
  (`application/javascript` / `text/css` — паттерн `/js/{filename}`, не
  зависеть от системных mimetypes). Обхода каталогов нет (паттерн проверки
  `/`/`..` у js-маршрута).
- Legacy `frontend/instructor-pending.html` удаляется (замена монолита
  целиком, FR-86/ОВ-4). Известный потребитель файла вне `_PAGE_ROUTES` —
  tests/test_instructor_pages.py: `test_pending_page_exists_and_text`
  (строки 256–268) читает файл напрямую через helper `page()` (строка 24).
  Тест мигрируется на вход пилотной страницы В СОСТАВЕ задачи 2.3 — см.
  раздел «Миграция legacy-тестов страницы ожидания»; grep-контроль
  отсутствия ссылок на legacy-файл выполняется после этой правки
  (задача 2.3).
- `/api/*` не затрагиваются (NFR-27: контракты без ломающих изменений).

## Пилотная страница «Ожидание модерации» (FR-86, ОВ-4)

- **Визуальный перенос 1:1** instructor-pending.html: шапка (бренд «Сбер
  Автошкола», ссылка «← Вернуться на лендинг»), карточка статуса (иконка,
  kicker «Заявка инструктора», h1 — ТОЧНЫЙ текст «Заявка на рассмотрении»,
  пояснение), блок шагов 01/02/03, кнопки «На главную» / «О лендинге для
  инструкторов», футер. Стили переносятся в компонент/подключаемый css без
  редизайна. Тексты — без изменений (языковой зонинг: RU).
  Якорь e2e: TC-UI-004 (`tests/test_ui_playwright.py:334`) —
  `page.wait_for_url("**/instructors/pending")` + h1 == «Заявка на
  рассмотрении»; `expect(...).to_have_text` автодождем покрывает момент
  гидрации Vue.
- **Блок 2 на новом стеке — потребитель контракта change
  add-application-status-polling (ЗАВИСИМОСТЬ, задача 9.2):**
  - опрос статуса по сохраненному неперебираемому идентификатору заявки,
    интервал 12 с (FR-80; NFR-28: ≤5 запросов/мин);
  - waiting → approved: обмен идентификатора на сессию (контракт
    polling-пакета) → редирект в кабинет инструктора; ошибка обмена —
    остаться в waiting, опрос продолжается (FR-81);
  - waiting → rejected: статус «заявка отклонена» + причина отказа
    (FR-82; историческая заявка без комментария — нейтральный текст);
  - остановка опроса при уходе со страницы: unmount/закрытие вкладки,
    скрытие вкладки — таймер отменяется, новые запросы не уходят (FR-83);
    сетевая ошибка тика — тихо, интервал не меняется (FR-83, NFR-28);
  - без сохраненного идентификатора — статический режим как сегодня:
    без запросов и без ошибок (FR-80).
- **Клиентская механика:** таймер опроса и его отмена — в одном месте
  страницы (setup/onUnmounted компонента; `visibilitychange` — пауза
  тиков при скрытой вкладке в границах FR-83 «нет фоновых таймеров,
  переживающих страницу»). Данные — локальное состояние SFC; pinia и
  vue-router НЕ вводятся (research.md п.8).
- **Интеграция с add-application-status-polling:** контракт API (формат
  ответа статуса, эндпоинт, обмен на сессию) — норма того пакета; чтобы на
  одной странице не оказались две конкурирующие реализации опроса, после
  миграции пилот реализует блок 2 на Vue и legacy-JS-механика опроса для
  /instructors/pending не используется (контракт API общий). Очередность
  и точку слияния сводит приемка Спринта 9 (задача 9.5) — детали за ПМ.

### Зависимости

- **change `add-application-status-polling`** — серверная сторона
  контракта опроса: эндпоинт статуса по неперебираемому токену (GET
  /api/instructors/application-status, poll_token — только чтение) и
  обмен идентификатора на сессию (POST
  /api/instructors/application-exchange, одноразовый exchange_token);
  требование спеки того пакета — «Автоопределение статуса заявки на
  экране ожидания» (дельта StudentFlow). Пилотная страница — ПОТРЕБИТЕЛЬ
  этого контракта (клиент опроса блока 2 на Vue); эндпоинты и форматы
  ответов пилот сам не определяет. Пакет существует — ветка
  feat/s9-polling-package (создан коммитом 7b433d9).
- **Предусловие dev (старт задачи 3.1):** задачи опроса polling-пакета
  (backend: эндпоинт статуса + обмен) смержены до старта пилотной
  страницы ЛИБО пилот пишет 3.1 против design.md polling-пакета
  параллельно (примечание СА; порядок слияния — за ПМ). Сетевой смоук
  готовности 3.1 выполняется против серверной части polling-пакета
  после ее слияния; если слияния к моменту готовности 3.1 нет — смоук
  переносится в критерии приемки 9.5 (готовность 3.1 без него:
  статический контроль контракта по design.md polling-пакета + зеленый
  TC-UI-004).

## e2e-совместимость (FR-85, NFR-27)

- Сценарии `tests/test_ui_playwright.py` (49) не переписываются:
  селекторы, маршруты, ожидания — без правок; критерий шага миграции —
  зеленый полный прогон.
- **Порядок прогона (новый обязательный шаг контура):** `npm ci && npm run
  build` → `pytest tests/test_ui_playwright.py` — фикстура `server`
  поднимает тот же `uvicorn backend.app:app`, который после миграции
  отдает Vue-вход из dist; сценарий «анкета → /instructors/pending»
  проходит по реальной мигрированной странице. CI добавляет шаг сборки
  перед e2e (та же команда, что в Dockerfile — один способ сборки).
- Маршруты страниц не меняются; публичные API не затрагиваются; новая
  статика `/vue/assets/*` — добавление, не изменение контрактов
  (обратно-совместимо, NFR-27).

## Миграция legacy-тестов страницы ожидания

- **tests/test_instructor_pages.py** — известный потребитель legacy-файла
  вне `_PAGE_ROUTES`: `test_pending_page_exists_and_text` (строки 256–268)
  читает `frontend/instructor-pending.html` напрямую через локальный
  helper `page()` (строка 24). Судьба — ПЕРЕВОД на новую Vue-страницу в
  составе задачи 2.3 (не отдельная волна; тест не удаляется): источник
  чтения переключается с legacy-файла на вход пилотной страницы
  (`frontend/vue/instructors-pending.html`); проверяемые тексты,
  селекторы и URL НЕ меняются — маршруты сохраняются
  (`/instructors/pending` отдает тот же экран, h1 «Заявка на
  рассмотрении»). Контроль текстов/структуры остается статическим — e2e
  не дублируется (сквозной сценарий уже покрывает TC-UI-004).
- **TC-UI-004** (tests/test_ui_playwright.py:358–360, «анкета →
  /instructors/pending») — продолжает работать на новом стеке без правок:
  маршруты те же; `page.wait_for_url("**/instructors/pending")` +
  `expect(h1).to_have_text("Заявка на рассмотрении")` — автожидание
  покрывает момент гидрации Vue. Сценарий не переписывается (NFR-27).
- **Разграничение с NFR-27:** «0 правок в тестах» касается ТОЛЬКО
  tests/test_ui_playwright.py; правка tests/test_instructor_pages.py —
  разрешенная и ожидаемая работа пакета (задача 2.3), критерии 5.1/6.1
  читаются в этих границах.

## Решения по НФТ

- **NFR-26:** бюджеты проверяются на артефактах сборки (gzip-размеры
  файлов dist, задача 4.1: каждый чанк `gzip -c | wc -c`; сумма JS первого
  захода пилота — page-чанк + static-import graph). Страница загружает
  только свои чанки (multi-entry) — код немигрированных страниц в бандл
  пилота физически не попадает.
- **NFR-27:** см. раздел e2e; селекторы/тексты/маршруты сохранены.
- **NFR-28** (нагрузка опроса) — интервал и остановка опроса на клиенте
  пилота; серверная часть — пакет add-application-status-polling.
- Наследуются без изменений: ADR-001 (статика тем же сервисом), FR-57
  (bare-metal/compose — один код), ADR-006 (multi-stage, pinned-образы,
  non-root appuser, секреты вне образа), NFR-13/14 (healthcheck, TLS — не
  затрагиваются).

## Сознательные ограничения (задокументированы)

- dist и node_modules — не в git (артефакты; .gitignore).
- Хэшированные имена ассетов Vite дают автоматическую cache-инвалидность;
  серверные заголовки кэширования не вводятся (паттерн остальной статики).
- Сборка npm ci удорожает docker build — принято (layer-cache по
  package*.json); второй pinned базовый образ (node) — принятая цена
  multi-stage ADR-006.
- План миграции определяет этапы по спринтам, не дедлайн внутри спринта;
  состав этапов Спринтов 10–11 — за ПМ.
- Заголовки/тексты страниц при будущей миграции — только перенос текущих
  (директива «без большого переписывания»; редизайн — вне миграции).
- Общий код страниц (shared-чанк) растет по мере миграции; контроль — тот
  же бюджет первого захода (задача 4.1 на каждом шаге миграции).

## Соответствие ADR-001/006/007 (формат архива)

Отступлений нет: статика — тем же сервисом (ADR-001, отдача через app.py);
multi-stage образ с pinned-базами и правами appuser сохраняется (ADR-006);
ADR-008 пишется по эталону формата ADR-007 (контекст/решение/альтернативы/
последствия) задачей 1.1; карта архитектуры обновляется архитектором при
ревью пакета (прецедент ADR-007).
