# Design: add-auth-cabinet

Источники решений: research.md (настоящий пакет), утвержденный дизайн
Спринта 0 (docs/superpowers/specs/2026-10-08-registration-admin-design.md),
утвержденный мокап design/mocks/cabinet-student.html. Детальные контракты
API — в `sdd.md` (раздел «Спринт 1»).

## Компоненты

```
Браузер
  │  статика (/, /cabinet; модалка «Вход» на лендинге)
  │  fetch JSON API (заголовок X-Session-Token)
  ▼
FastAPI-сервис (uvicorn, single-worker)
  ├── app.py      — + роутер auth, + маршрут /cabinet
  ├── auth.py     — НОВЫЙ модуль (домен auth):
  │                 POST /api/auth/login, POST /api/auth/logout, GET /api/auth/me;
  │                 in-memory реестр сессий {token: (expires, user_id)} TTL 12ч;
  │                 зависимость require_session
  ├── register.py — БЕЗ ИЗМЕНЕНИЙ (регистрация Спринта 0)
  ├── admin.py    — БЕЗ ИЗМЕНЕНИЙ (админ-контур Спринта 0)
  ├── db.py       — get_conn (уже используется; схема users не меняется)
  └── config.py   — без изменений
  ▼
SQLite data/app.db (WAL) — таблица users (email UNIQUE + password_hash)
```

Авторизация — отдельный модуль backend/auth.py (ограничение ТЗ); register.py
и admin.py не затрагиваются. Таблица users — та же, что у регистрации:
логин = email, проверка пароля = bcrypt.checkpw против password_hash.

## Потоки

### Поток 1: вход ученика (FR-1…FR-3)

```
Лендинг → модалка «Вход» (m-login) → POST /api/auth/login {email, password}
  → SELECT по email (параметризованный)
    → запись не найдена: 401 {ok:false, error:"Неверный email или пароль"}
    → bcrypt.checkpw(password, password_hash):
        fail → 401 с ТОЙ ЖЕ строкой ошибки (FR-2, без раскрытия деталей)
        ok   → токен = secrets.token_urlsafe(32),
               реестр {token: (now + 12ч, user_id)}
               → 200 {ok:true, token}
               → JS: sessionStorage, редирект /cabinet
```

Единое сообщение об отказе — константа, одна для всех причин (FR-2).
Timing-замечание: SELECT «нет записи» пропускает bcrypt — для выравнивания
времени ответа допустима фиктивная проверка хэша (деталь реализации, тест
NFR-1 по верхней границе).

### Поток 2: кабинет (FR-4…FR-7, FR-9)

```
/cabinet → cabinet.html (перенос мокапа дословно)
  → JS читает токен из sessionStorage; GET /api/auth/me (X-Session-Token)
      401 → редирект на страницу входа (лендинг с открытой модалкой m-login) (FR-7)
      200 → подстановка ФИО: uname = «{surname} {name} {patronymic}»,
            greet = «Добро пожаловать, {name}!» (FR-5)
  → плитки, чат-бар, quick-кнопки — заглушки (как в мокапе): клик НЕ выполняет
    сервисного действия (FR-6); поведение клика — как в мокапе
  → «Выйти» → POST /api/auth/logout (X-Session-Token) → очистка sessionStorage
    → редирект на главную / (FR-8)
```

Тексты и стили — дословно из мокапа; отличия ТОЛЬКО: wiring (fetch, редиректы)
и подстановка ФИО вместо примера «Иван Иванов»/«Добро пожаловать, Иван!»
(FR-9, допущение зафиксировано в proposal).

### Поток 3: выход (FR-8)

```
POST /api/auth/logout (X-Session-Token)
  → токен в реестре? удалить → 200 {ok:true}
  → нет/истек → 401 {ok:false} (аннулировать нечего; JS всё равно чистит сессию)
После любого ответа JS: очистить sessionStorage, location.href = '/'
```

### Поток 4: защита ресурса (FR-7)

```
require_session (зависимость auth.py): заголовок X-Session-Token есть?
  токен в реестре? не истек (TTL 12ч)?
  → ok: обработка запроса; fail: 401 {ok:false}
  (запись сессии {token: (expires, user_id)}: user_id — источник данных
  GET /api/auth/me, sdd §10.3)
Истекающие записи вычищаются лениво при проверке (неактуальные токены
не накапливаются функционально: истекший = отклоненный).
```

## Обработка ошибок

| Ситуация | Ответ/поведение | Требование |
|---|---|---|
| Вход: неверный email / неверный пароль / нет учетной записи | 401 `{"ok": false, "error": "<единое сообщение>"}` — одна строка на все причины; токен не выдается | FR-2 |
| Отсутствует/пустое тело запроса входа | 422 `{"ok": false, "error": "<поле-ру>: поле обязательно"}` (формат Спринта 0, хендлерная валидация как MAJ-1) | — |
| /api/auth/me, /api/auth/logout без/с неверным/истекшим/аннулированным токеном | 401 `{"ok": false}`, данных нет | FR-7, FR-8 |
| Внутренняя ошибка | 500 `{"ok": false, "error": "Внутренняя ошибка"}`; детали — в лог, пароли и токены в лог не пишутся (NFR-3) | NFR-3 |

## Решения по НФТ

- NFR-1 (ответ авторизации ≤ 500 мс): bcrypt cost 12 ~250 мс на проверку —
  в бюджете; SELECT по индексируемому UNIQUE email — миллисекунды; контроль —
  тест замера времени POST /api/auth/login.
- NFR-2 (параметризованный SQL): единственный запрос домена (SELECT по email)
  — через db-слой с `?`-плейсхолдером.
- NFR-3 (токены и секреты не в репозитории и логах): токен — только в
  sessionStorage и памяти процесса; пароли не логируются; .env-механика
  Спринта 0 не меняется.

## Минимальная анти-брутфорс защита /api/auth/login (решение Заказчика, вариант (б))

Публичный endpoint подбора пароля реальных пользователей — поверхность атаки
качественно иная, чем у единственного админа Спринта 0, поэтому отсутствие
защиты не принимается как техдолг (arch-review MAJ-3). Спецификация уровня
требований — механизм имплементации (in-memory, БД, middleware и т.п.) на
усмотрение разработчика задачи 1.1:

- Требование R-BF1 (ограничение попыток): после 5 (порог, точное значение
  фиксируется разработчиком в пределах 3–10) неудачных попыток входа подряд
  с одного IP-адреса сервис MUST временно блокировать обработку попыток
  входа с этого IP: на каждый новый запрос отвечать отказом входа с тем же
  единым сообщением (FR-2), не выполняя проверку учетных данных.
- Требование R-BF2 (нарастающая длительность): длительность блокировки MUST
  нарастать с каждым следующим превышением порога (минимум: 30 с после
  первого срабатывания, удвоение за каждое следующее, верхняя граница 15 мин).
  Точные значения — решение разработчика в указанных пределах; фиксируются в
  sdd.md при имплементации.
- Требование R-BF3 (сброс счетчика): успешный вход или истечение окна
  наблюдения (не менее 15 минут без неудачных попыток) MUST сбрасывать
  счетчик неудачных попыток для IP.
- Требование R-BF4 (единообразие отказа): заблокированный запрос MUST
  возвращать тот же ответ 401 с единой строкой ошибки, что и неверные
  учетные данные (FR-2) — блокировка не раскрывает свое существование и не
  создает оракула перебора.
- Границы: защита — только для /api/auth/login; /api/admin/login остается
  в рамках задокументированного техдолга Спринта 0 (map.md «Техдолг
  спринта-0»). Учет попыток — в памяти процесса (тот же single-worker
  компромисс, что у сессий; рестарт сбрасывает счетчики — документированное
  ограничение).

## Сознательные ограничения (задокументированы)

- Сессии в памяти: потеря при рестарте (пере-вход), single-worker —
  тот же документированный компромисс, что у админ-токена Спринта 0.
- Вход только по email (телефон-логин — вне спринта; placeholder мокапа
  сохраняется дословно, см. proposal).
- Водители: модель данных не расширяется (вне спринта, решение Заказчика).
