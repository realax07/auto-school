## Проверка закрытия замечаний первого ревью (по фактам диффа f6b56ac..HEAD)

### MAJ-1 — ЗАКРЫТ (все 4 требованных правки на месте)

1. **Постоянный vs переходный отказ в design-машине состояний — разведено.**
   Ветви обмена после `status approved`:
   - ok → sessionStorage 'session_token' → **удалить application_poll_token и
     application_exchange_token из localStorage ДО редиректа** → redirect route
     'cabinet' → /instructor/dashboard; polling остановлен (терминальное);
     оговорено: возврат на /instructors/pending после чистки — токенов нет →
     STATIC, 0 запросов;
   - **ПЕРЕХОДНЫЙ отказ** (409: guard статуса / вырожденное «approved без
     users»; сетевая ошибка; токен НЕ потреблен) → экран в waiting, опрос
     продолжается, повтор обмена на следующем тике (FR-81);
   - **ПОСТОЯННЫЙ отказ** (404-неразличение: не найден / уже потреблен / чужой)
     → **ТЕРМИНАЛЬНОЕ**: таймер снят, оба ключа localStorage удалены,
     нейтральная подсказка «войдите с email и паролем» (без деталей о
     токене/заявке — 404-неразличение сохраняется). Обоснование «почему НЕ
     waiting» вписано в дизайн дословно по формулировке MAJ-1: повтор
     невозможен по построению, продолжение опроса — вечный цикл «тик →
     approved → обмен → 404» и ложный статус «на рассмотрении»; последующий
     вход на /instructors/pending — STATIC. Матрица ответов дополнена строкой
     терминального 404 с той же логикой.
2. **Чистка localStorage при УСПЕШНОМ обмене ДО редиректа — внесена в трех
   местах согласованно**: ok-ветка машины состояний (см. выше), проза раздела
   обмена («ПЕРЕД редиректом фронт удаляет … потребленный exchange_token не
   должен остаться источником повторных обменов при back-навигации или во
   второй вкладке (MAJ-1)») и матрица ответов. Источник стейла (в) из MAJ-1
   устранен.
3. **Спека**: сценарий «Ошибка обмена оставляет экран в waiting»
   переформулирован — GIVEN теперь ТОЛЬКО переходные причины (409 guard /
   вырожденное «approved без users», сетевая ошибка, токен НЕ потреблен), THEN
   — «токен сохранен — повторный обмен возможен на следующем тике» с прямой
   отсылкой к отдельному терминальному сценарию; ложное для потребленного
   токена обещание из первого ревью убрано. Добавлен сценарий «Обмен вернул 404
   (токен потреблен или чужой) — терминальное состояние с подсказкой входа»:
   опрос остановлен, оба ключа удалены, нейтральная подсказка, возврат на
   /instructors/pending — статичный режим без запросов. Требование уровня
   Requirement закреплено в MUST-абзаце («успешный обмен удаляет
   идентификаторы с экрана; 404 обмена — терминально, с нейтральной подсказкой
   входа»).
4. **tasks обновлены**: 4.1 — машина состояний переписана (ok с чисткой ДО
   редиректа; переходная/постоянная ветви; терминальная подсказка); 5.2 —
   TC-UI-049 расширен («back-навигация на /instructors/pending после успешного
   бесшовного перехода (токены удалены при успехе) — статичный режим,
   0 запросов опроса»), добавлен TC-UI-050 (терминальное 404: подсказка входа,
   опрос остановлен, токены localStorage удалены, «второй контекст после
   успеха — back-навигация/вторая вкладка»); сквозная нумерация TC-UI-043…050
   согласована в 5.2, 7.1 и «Прогоне 2»; список сценариев §1 tasks дополнен
   новым сценарием 1:1 с заголовком спеки.

Три пути воспроизведения из MAJ-1 закрыты: (а) back-навигация после успеха —
токены удалены при успехе → STATIC, 0 запросов (TC-UI-049); (б) вторая вкладка
после успеха первой — терминальный 404 с корректным экраном и без опроса
(сценарий спеки + TC-UI-050); (в) неочищенные ключи как источник повторных
обменов — чистка при успехе и в терминальном 404.

### MIN-1 — ЗАКРЫТ (атомарность потребления + тест параллельных обменов)

- design, «Порядок обмена» п.4: **УСЛОВНЫЙ UPDATE exchange_token = NULL WHERE
  exchange_token = ? + проверка rowcount** — атомарное потребление; rowcount=1
  — токен захвачен ЭТИМ запросом, rowcount=0 — уже потреблен (в т.ч.
  параллельным обменом) → 404-неразличение, сессия НЕ выдается; паттерн MIN-1
  Спринта 8 назван, мотивировка гонки приведена (sync-эндпоинты в threadpool,
  интерливинг SELECT-проверки и UPDATE не свободен); инвариант закреплен:
  «два параллельных обмена одним валидным токеном — ровно один 200, второй
  404 (SQLite сериализует запись)». Согласовано по всем сечениям design:
  описание exchange_token, блок architecture (application_status.py),
  таблица эндпоинтов, матрица ответов. Отказ транзакции → rollback — повтор
  возможен (не возвращенная сессия in-memory безвредна, истечет по TTL).
- tasks 2.1: механика в тексте задачи + тест в «Готовности»: «два
  параллельных обмена одним валидным токеном — ровно один 200, второй 404».

### MIN-2 — ЗАКРЫТ (ветки IntegrityError разведены + тесты)

- design: ветки разведены **по сообщению/имени индекса**: гонка дубля email
  (UNIQUE instructor_applications.email, Спринт 2) → контрактная 422 БЕЗ
  регенерации и повторной вставки; коллизия poll_token/exchange_token
  (частичные UNIQUE) → регенерация + повторная вставка БЕЗ 422; последствие
  смешения названо (email уходит в цикл регенерации, токен — в ложную 422).
  Строка apply в таблице эндпоинтов дополнена тем же правилом.
- tasks 1.1: механика в тексте + тесты обоих исходов IntegrityError в
  «Готовности»: «параллельный дубль email → 422 (заявка одна, цикла
  регенерации нет)» и «коллизия токена → регенерация, заявка создана».

### MIN-3 — ЗАКРЫТ (pageshow-ре-арм)

- design, машина состояний (раздел bfcache): pageshow persisted=true → таймер
  **ПЕРЕВООРУЖАЕТСЯ**, опрос по обычному графику БЕЗ немедленного тика
  (бюджет NFR-28 держится); ре-арм — только в состоянии POLLING (терминальное
  и статичное состояния ре-арма не требуют).
- спека: сценарий «Опрос останавливается при уходе со страницы» дополнен
  (pageshow persisted=true → перевооружение по обычному графику).
- tasks 4.1 (машина) и TC-UI-046 (кейс возврата из bfcache) — внесены.

### MIN-4 — ЗАКРЫТ (оговорка видимости в спеке)

- спека, сценарий «Экран опрашивает статус…»: WHEN — «экран **ВИДИМ** (вкладка
  активна)»; THEN — «при видимом экране изменение отражается не позднее одного
  интервала (≤15 с)… (скрытая вкладка — опрос остановлен FR-83; латентность
  отсчитывается с возврата видимости)» — противоречие с FR-83 снято;
  TC-UI-043 — «на видимом экране». Oговорка продублирована и в разделе NFR-28
  design (латентность ≤1 интервала ПРИ ВИДИМОМ ЭКРАНЕ).

### MIN-5 — ЗАКРЫТ (exchange_token в «Сознательных ограничениях»)

- design, «Сознательные ограничения»: новый пункт — exchange_token в
  localStorage (application_exchange_token, рядом с poll_token) осознанно, НЕ
  sessionStorage: хранение обязано переживать перезагрузки (approve может
  прийти через часы и после перезагрузок); уровень риска эквивалентен
  sessionStorage-сессии того же пользователя (токен одноразовый, ведет только
  к своей заявке и сессии своей строки users); удаляется при успешном обмене и
  в терминальном 404. В «точках расширения» ротация/отзыв расширена до
  «poll_token И exchange_token».
