## Разбор по пунктам проверки

### 1. Неперебираемый идентификатор и 404-неразличение — выдержано

- **Механизм**: два артефакта (poll_token многоразовый / exchange_token одноразовый),
  оба `secrets.token_urlsafe(32)` — 256 бит энтропии, тот же генератор, что у
  сессий Спринта 1 (auth.py:246,257). Перебор невозможен физически; частичные
  UNIQUE-индексы (`WHERE … IS NOT NULL`) дают точечный lookup и защиту от дублей,
  регенерация при коллизии. Выдача — один раз при apply, 422 токенов не выдает.
- **Хранение/миграция**: две колонки ALTER TABLE по механике `_COLUMN_MIGRATIONS`
  db.py (guard pragma table_info, init_db через lifespan, существующий volume) —
  idempotent; backfill отсутствует осознанно, исторические строки (NULL) дают
  статичный режим экрана — согласовано с FR-80 («экран без идентификатора —
  без запросов»).
- **404-неразличение**: поиск по токену — «чужой» и «несуществующий» проходя́т
  один и тот же промах по индексу → идентичный 404; ответ статуса несет
  {status, reason|null}, без номера заявки/email/метаданных. Токены в заголовке
  (X-Poll-Token) и теле POST — access-логи (path+query) чистые. Timing-канал
  незначим (в отличие от логина, bcrypt в контуре опроса не участвует; чтобы
  увидеть 409 обмена, нужно уже обладать валидным токеном — это сам заявитель).
- Причина отказа (review_comment) видна только носителю poll_token — это сам
  заявитель; утечки существования чужих заявок нет.

### 2. Обмен токена на сессию — привязка однозначна, безопасность выдержана

- **Однозначность привязки**: UNIQUE instructor_applications.email (MAJ-1
  Спринта 2) → заявка по exchange_token ровно одна; approve (instructor_admin.py)
  создает users тем же email одной транзакцией с UPDATE статуса (MIN-3) —
  следовательно «approved» возможен только при существующей строке users,
  созданной ИМЕННО из этой заявки. Обратные пути проверены: student-регистрация
  на email ожидающей заявки (register.py проверяет только users) проходит, но
  тогда approve падает по UNIQUE users.email → rollback → заявка остается
  waiting → guard обмена (status='approved') не пропускает; после approve
  повторная регистрация на тот же email отсечена проверкой users. Сессию ЧУЖОГО
  инструктора по токену получить нельзя — токен ведет только к своей заявке и
  ее собственной строке users; вырожденный случай вне контракта → 409.
- **Одноразовость**: потребление UPDATE exchange_token=NULL той же транзакцией;
  сессия in-memory не транзакционна с БД, но дубль сессии того же пользователя
  безвреден (эквивалент двух логинов) — дизайн это фиксирует. Race двух
  параллельных обменов одним валидным токеном: механизм атомарности не назван —
  MIN-1 (следствие безвредно, но инвариант «ровно один 200» надо закрепить).
- **Альтернативы** (один токен, JWT-style, автовход по учетным данным) —
  отклонены обоснованно: одноразовость vs многоразовость неразделима одним
  артефактом; JWT — новая сессионная механика вопреки границе ТЗ; автовход —
  перебираем и хуже по всем осям. Решение в границах существующей модели
  (ADR-002/003), revisiting модели не требуется. Роль в выдаче — 'instructor'
  через строку users, route 'cabinet' — форма ответа логина, фронт переиспользует
  механику landing.js/api.js. НО: терминальное состояние после потребления
  токена машиной экрана не обработано — MAJ-1 (см. §Замечания).

### 3. NFR-28 — бюджет, остановка, только чтение: реализуемо

- **Математика бюджета верна**: тики 0/12/24/36/48/60 с при скользящем окне
  60 с — максимум 5 запросов; планирование следующего тика ПОСЛЕ завершения
  предыдущего запроса исключает наложение и только сдвигает тики позже.
  Возобновление после visible без немедленного тика — бюджет держится при
  частом переключении вкладок.
- **Остановка при уходе**: visibilitychange hidden/pagehide/beforeunload —
  корректный набор; нюанс восстановления из bfcache (back-навигация) — MIN-3.
- **Только чтение**: одиночный параметризованный SELECT по частичному индексу,
  без записи и побочных эффектов; payload минимальен ({status, reason|null}).
  Нагрузка на single-worker SQLite — тривиальна (5 req/мин на экран, O(log n)
  lookup); серверный rate-limiter не нужен — решение осознанное, точка
  расширения зафиксирована.
- **Латентность ≤15 с**: первый тик немедленный, смена статуса видна ≤1
  интервала (12 с < 15 с) при видимом экране; сценарий спеки не оговаривает
  условие видимости — MIN-4 (иначе противоречие с FR-83: опрос при скрытой
  вкладке остановлен по требованию).

### 4. Зависимость от add-vue-framework-pilot — контракт общий, порядок не блокирует

- Контракт опроса сформулирован фреймворк-независимо: HTTP-эндпоинты (дизайн
  этого пакета) + ключи localStorage (application_poll_token/exchange_token,
  пишет vanilla apply.js — задача 3.1, читает Vue-страница — 4.1) +
  sessionStorage handoff ('instructor_rejected_reason'/'session_token' —
  механика api.js/landing.js). Ни одна строка контракта не предполагает стек
  потребителя — пилот на Vue и текущий HTML-экран живут на одном контракте;
  бэкенд-задачи 1.1/2.1/3.1 [P] от каркаса не зависят.
- Порядок внедрения зафиксирован (PLAN 9.3 → 9.4 → фронт-задача 4.1 этого
  пакета), зависимость однонаправленная, цикла нет; e2e-критерий совместный
  (49 существующих сценариев без правок, NFR-27/FR-85) — приемка 9.2+9.4.
- Факт: пакет add-vue-framework-pilot в openspec/changes/ еще НЕ создан
  (решение create_change от 2026-11-02 есть). Для этого пакета это не блокер —
  контракты фронт-задачи 4.1 определены здесь, каркас получит собственное
  arch-ревью; но фронт-блок блока 2 не может стартовать до его появления.
- NFR-26 (бюджеты чанков) не дублируется — остался в объеме каркасного пакета,
  интерфейс («страница не добавляет библиотек сверх каркаса») зафиксирован.

### 5. Дублирование vanilla vs Vue на переходный период — допустимо

- Внутри пакета дублирования логики опроса нет: polling реализуется ОДИН раз
  (Vue на пилотной странице); vanilla-часть (apply.js) только сохраняет токены
  перед существующим редиректом — это не дублирование, а разделение контракта
  по шву localStorage.
- Переиспользование (экран отказа /instructors/rejected с механикой
  sessionStorage, route 'cabinet' → /instructor/dashboard, api.js) устраняет
  второй UI и второй путь показа отказа — то, что ревью обычно ловит как
  расползание, здесь сведено конструктивно.
- Переходное сосуществование двух механизмов раздачи фронтенда (статика
  frontend/ + Vite-чанки каркаса) — осознанная цена пилота, владелец — пакет
  add-vue-framework-pilot; на контракты этого пакета не влияет. Допустимо.

## Вердикт: доработка

Правило: blocker/major = 0 требовалось для approve. Обнаружен один major —
машина состояний экрана не обрабатывает терминальное состояние «approved +
exchange_token потреблен», воспроизводимое штатной навигацией пользователя
(MAJ-1); исправление требует правок design.md (машина состояний),
specs/StudentFlow (сценарий «Ошибка обмена…») и tasks (4.1/5.2) — т.е.
доработки СА, а не только реализации. Повторное ревью — после устранения
MAJ-1 (minor'ы переносить не требуется, они контролируются в задачах).

## Замечания

### Blocker — нет

### Major — 1

| # | Замечание | Основание / место контроля |
|---|---|---|
| MAJ-1 | Терминальное состояние «approved + exchange_token потреблен» не обработано: машина состояний знает только «ошибка (409/сеть) → waiting + опрос продолжается», а 404 (токен уже потреблен/чужой) в нее не внесен. Сценарий воспроизводится штатно: (а) бесшовный переход в кабинет успешен → Back-навигация на /instructors/pending → localStorage-токены на месте → тик: approved → обмен → 404 → «на рассмотрении» + опрос — вечный цикл для УЖЕ одобренного заявителя; (б) вторая вкладка экрана после успеха первой; (в) ключи localStorage не чистятся и после УСПЕШНОГО обмена (источник стейла). Следствия: бесконечный цикл попыток обмена (5×GET + 5×POST в минуту с одного экрана — двойной трафик против духа бюджета NFR-28), ложный статус «на рассмотрении» неограниченно долго. Спецификация закрепляет ошибочное ожидание: сценарий «Ошибка обмена оставляет экран в waiting» — «повторный обмен возможен на следующем тике» — для потребленного токена это ложь по построению. Требуется: 1) в design-машине состояний отделить постоянный отказ обмена (404 при approved: сессия уже выдана ранее, повтор невозможен) от переходного (409/сеть): 404 — терминально (таймер снят, оба ключа localStorage удалены, нейтральная подсказка «войдите с email и паролем»); 2) удалять application_poll_token/application_exchange_token из localStorage при успешном обмене (перед редиректом); 3) скорректировать сценарий спеки (переходные ошибки) и добавить терминальную ветку; 4) задачи 4.1 (машина состояний) и 5.2 (TC-UI: back-навигация после успешного перехода — 0 запросов; сценарий «Экран без сохраненного идентификатора — статичный режим» накрывает кейс после чистки) | design.md «Машина состояний экрана», «Обработка ошибок»; specs/StudentFlow сценарий «Ошибка обмена…»; tasks 4.1, 5.2 |

## Основание вердикта

Пункты 1–3 по существу выдержаны: неперебираемость (256 бит, тот же генератор,
что у сессий) и 404-неразличение конструктивны; привязка «токен → своя заявка →
своя строка users» однозначна (UNIQUE email + транзакционный approve; обратные
пути — регистрация ученика на email заявки и вырожденный approve — закрыты
guard'ами и UNIQUE); бюджет NFR-28 математически верен и реализуем. Зависимость
от Vue-пилота и переходное дублирование — чистые (контракт фреймворк-независим,
дублирования логики нет). Единственный major — MAJ-1: необработанное терминальное
состояние обмена дает вечный цикл «обмен → 404» на штатной Back-навигации после
бесшовного перехода — это ядро поставляемой функциональности (FR-81), правится
на уровне design/specs/tasks, поэтому **доработка**: СА устраняет MAJ-1 (minor'ы
MIN-1…MIN-5 — попутно/в задачах), повторное арх-ревью, затем dev_task.
Карта и ADR не пишутся — механизм не принят.
