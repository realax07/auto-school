## 1. Модель recurring/one_off: совместимость, миграция, коллизии

**Совместимость и миграция — принято.** Д1/Д2 (research R1-A, ADR-010 решения
1–2): тип на записи availability, не новая сущность — booking.availability_id,
GET/PUT, индексы и все потребители сохраняются; легаси-строки становятся
recurring самим DEFAULT-определением колонки (без перезаписи — FR-97
выполняется конструктивно). Rebuild: SQLite не снимает табличный UNIQUE через
ALTER — одна транзакция BEGIN IMMEDIATE, INSERT…SELECT сохраняет id и
created_at (ссылки броней валидны; FK booking→availability в db.py
подтвержденно отсутствует — DROP безопасен), guard по колонке slot_type →
повторный запуск no-op (NFR-30), fresh-БД получает новый DDL из _SCHEMA.
Проверено по существующему коду: механика guard-миграций наследуется
(_COLUMN_MIGRATIONS, init_db через lifespan, Спринты 6–9) — новый rebuild ей
не противоречит. Частичный индекс booking переиндексируется на
(availability_id, lesson_date): данные совместимы (старый индекс строже),
DROP IF EXISTS + CREATE IF NOT EXISTS — idempotent. Задача 1.1 неделима и
содержит тесты на предсозданной БД (TC-S10BE-001) — достаточный контроль.

**Коллизии recurring+one_off в одну ячейку — НЕ сведено (см. MAJ-1).**
UNIQUE (…, slot_date) допускает одну one_off на дату+время и recurring-серию
того же дня/времени одновременно (обе строки в БД — design это явно
фиксирует, FR-90 требует показывать один слот). Для отображения дедупликация
задана (инструктор — тип one_off приоритетен), но: (а) уровень хранилища —
см. MAJ-1; (б) дедупликация выдачи GET slots?date= для совпавших экземпляров
(design задает instances отдельно по recurring и one_off) не pinned — при
совпадении ученик получит два экземпляра на одну дату+время с независимо
вычисленными состояниями. Оценка: MAJ-1.

**GET availability «все recurring + все one_off независимо от дат»** —
корректно и для NFR-32 (инструктор листает недели без сети), и для
запрет-прошлого правила (б): клиент возвращает прошедшие one_off в payload
без изменений. Поля slot_type/date — аддитивны, тесты s3/s7 читают
weekday/start/end — NFR-29 по GET выполняется.

## 2. MAJ-1 (Спринт 5) сохранен и перенесен на экземпляры

Закон Спринта 5 (409 с перечнем, график не изменен, брони не меняются)
сохранен по всем слоям: specs/instructor-availability MODIFIED — сценарии
409/только-rejected/прошедшие-не-блокируют; design — helper
blocking_bookings поднимается до экземпляров (конфликт, если активная бронь
('new'/'confirmed') на (lesson_date, start, end) не покрыта НИ одной строкой
нового графика — one_off или серией), 409 conflicts[{…, date}] аддитивно к
формату Спринта 7 (UI Спринта 7 читает weekday/время/статусы — не ломается);
транзакция BEGIN IMMEDIATE до проверки (наследование M-3 review-001,
сериализация с create_booking) — окно TOCTOU «проверка → удаление» закрыто,
как и прежде. Кейс «one_off на слот с бронью» — 409 с датой (TC-S10BE-003/004);
«удаление recurring с бронями» — 409 с перечнем всех затронутых дат серии.
Прошедшие экземпляры (начало < NOW) не блокируют и не изменяются — согласовано
с FR-92/NFR-31 и сценарием «Прошедшие экземпляры не блокируют замену».
Замечание вне MAJ: формулировка design «для recurring-экземпляров без
брони-привязки к дате поле date = null» — фактически мертвая ветка (lesson_date
NOT NULL у всех броней); безвредна, аддитивна — не требует действия.

## 3. Запрет правки < текущей даты/времени: серверная валидация

Сервер — единственный арбитр (NFR-31): проверка каждого PUT (422 «Прошедшие
слоты не подлежат изменению») и каждого POST брони (422), клиентская
блокировка попапа/кнопки — только UX; дизайн прямо повторяет «клиентское
скрытие проверкой не считается». Таймзона: NOW = локальное время сервера
(МСК) — наследование nowMoscow/MIN-1, клиент вычисляет МСК как UTC+3
(единая точка). Граница — по НАЧАЛУ слота, асимметрия дословно по Заказчику:
инструктор ≥ NOW (начавшийся серийный слот правит), ученик > NOW (начавшийся
не бронирует) — открытый вопрос требований закрыт дефолтом БА, зафиксирован
в design и R5. Два замечания: (а) само правило границы записано в design
двояко «начало ≤ NOW» (заголовок) против «начало < NOW → прошедший» (текст
правила) и клиентского «≥ NOW редактируема» — MIN-1; (б) «локальное время
сервера = МСК» — допущение, не проверено деплоем: TZ не закреплен нигде
(grep Dockerfile/compose/deploy — пусто; контейнер получит UTC, граница
сместится на 3 часа, FR-93/FR-96 нарушатся для утренних слотов; прецедент —
MIN-4 review-001, MIN-1 Спринта 5: UTC vs локальная дата) — MIN-2.

## 4. Ученический вид: разворот серий, производительность, будущее/прошлое

Разворот — серверный (Д7, R4-C обоснованно: ученику недоступны определения
графика — 403-наследование; честные free/busy/pending по (id, date) считает
только сервер). Производительность: экземпляры ОДНОЙ недели по запросу —
≤ 7×(число серий)+one_off недели, SQLite single-instructor — запас
многократный; бесконечного разворота нет (горизонт ±12 месяцев — клиентский
лимит листания; сервер лимитирует только по неделям запросами). NFR-32:
решетка и подпись — локально сразу, экземпляры — асинхронно (≤ 500 мс), у
инструктора — нулевая сеть на листании (полный GET определений) — контракт
достижим. Бронирование только будущих: серверная проверка
lesson_date+start_time > NOW (МСК), 422; легаси-путь без date —
materialize_lesson_date (ближайшая дата серии, MIN-1), сужение «сегодня, но
уже начался → 422» задокументировано с контролем время-зависимости тестов
s5 на приемке (задача 7.1) — корректно. Прошлые недели — история: статусы
своих броней/запросов по lesson_date (GET bookings без изменений,
наследование FR-74), действий нет. Следствие Д8 (история серий не хранится):
время прошедших броней отображается по JOIN с ТЕКУЩИМ состоянием availability
— после смены времени серии прошедшая бронь показывается с новым временем
(фактически занятие было в старое); в пакете это следствие не названо —
MIN-3 (сознательное ограничение должно быть зафиксировано явно).

## 5. Попап-редактор над ячейкой: клиентский контракт

Контракт (Д10) не ломает существующий контур: попап — оверлей поверх страницы
у ячейки (не сдвигает/не переполняет сетку, сдвиг внутрь у границ вьюпорта,
Esc/клик вне — закрытие без изменений); тип индивидуален ячейке, применяется
к несохраненным правкам по подтверждению (индикатор #cal-changed, наследование
«Сохранить/Отменить» FR-68); отрисовка локальная ≤ 200 мс. Наложение с
существующим поведением сведено: клик по слоту с запросом/бронью открывает
решение (#m-bk) немедленно, мимо «Сохранить» (наследование ОВ-6/FR-74 —
задача 5.1 пункт (г) повторяет явно); «Сохранить график» — по-прежнему один
PUT полного графика (типы+даты), «Отменить» — перезагрузка GET; 409 с датами
в перечне показывается с сохраненным графиком. Нарезка задач корректна: попап
и сетка недели — один рендер-контур, одна задача 5.1 (правильное «НЕЛЬЗЯ
делить» из tasks.md); ключи calSelected «weekday-hour» меняются на
неделе-привязанные — ломать нечего вне 5.1. Прошедшие ячейки/недели — попап
не открывается (стиль просмотра, cursor по умолчанию) — клиентская часть
FR-93, сервер дублирует (§3).

## 6. Реальный календарь: правила рендера

Д9/FR-88: неделя = 7 последовательных реальных дат от понедельника, якорь
±7 дней, «эта неделя» — точка возврата; попадание в день недели — по самому
числу (арифметика Date, никаких фиксированных решеток). Проверочные факты
требований подтверждены прогоном в этой системе: 2026-11-30 → Mon (Пн),
2026-12-31 → Thu (Чт), 2028-02-29 → Tue (Вт) — в табличных фактах design/
tasks ошибок нет; неделя 28.12.2026–03.01.2027 — Mon→Sun (граница года
корректна). Длины месяцев 28/29/30/31 и переходы — следствия арифметики дат;
подпись диапазона с обеими частями («30 ноября — 6 декабря 2026», «28 декабря
2026 — 3 января 2027») обновляется атомарно с колонками (NFR-32 «подпись
никогда не противоречит колонкам»). «Сегодня»/«сейчас» — МСК = UTC+3
фиксированно (MSK без DST с 2011 — допущение устойчиво); локальная таймзона
браузера не используется — единая точка с сервером. Факты включены в e2e
(TC-S10UI-002/008, приемка 7.1) — контроль воспроизводим. Замечаний нет;
граница «правка в момент наступления времени» (гонка правки и часов) —
дефолт задокументирован (422 + перезагрузка сохраненного).
