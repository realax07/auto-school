## 1. Целевые проверки (фокус ревью)

### 1.1 Модель брони и гонки (NFR-8) — корректны

- Таблица booking: student_id/instructor_id → users, availability_id →
  availability (слот = интервал графика ЦЕЛИКОМ, ОВ-3), статусы
  new/confirmed/rejected (CHECK), reject_comment с инвариантом обязательности
  при rejected (кодом — та же механика, что student_requests.deny_comment,
  допустимо при SQLite без PRAGMA foreign_keys — единственная линия защиты
  и для владельца/пары, precedent ревью 3A). Отдельная таблица пар не
  заводится — связь «принят» = student_requests.status='accepted',
  прямое наследование ADR-004 (решение 4). Соответствует ТЗ.
- **Гарантия единственности — частичный уникальный индекс** `uq_booking_active_slot
  ON booking(availability_id) WHERE status IN ('new','confirmed')`:
  механика выбрана правильно и по делу. Альтернативы отклонены обоснованно
  (research.md §2): простой SELECT перед INSERT проигрывает гонкам; полный
  UNIQUE(availability_id) блокировал бы повторный запрос после отклонения
  (ОВ-5). Отклоненные выпадают из индекса — повторный запрос допустим,
  ровно буква ОВ-5. BEGIN IMMEDIATE на POST create и confirm — корректный
  уровень лока для SQLite WAL; confirm конкуренции не имеет (бронь уже
  держит слот индексом) — рассуждение design.md («Гонки бронирования»)
  верное. Проигравший в гонке INSERT получает 409 без записи — «отказ
  конфликта, а не молчаливая порча», дословно NFR-8.
- Денормализация instructor_id в booking (прямые выборки календарей со
  сверкой с availability.instructor_id при создании) — допустима: пара
  иммутабельна в этом объеме (отвязки ученика нет), рассинхрон
  недостижим. lesson_date материализацией ближайшей будущей даты weekday —
  допущение зафиксировано в proposal.md как явное, повторение слота —
  точка расширения (замечание по семантике даты — MIN-1).
- Статусная модель открыта для точки расширения «перенос/отмена»
  (новый статус/операция без переделки) — требование Границ ТЗ выполнено.

### 1.2 Доступ участников пары (NFR-7) — корректен, полон

- Слоты: серверная проверка пары на GET /api/student/instructors/{id}/slots
  — «и при прямом вызове API» покрыто и текстом Requirement, и сценарием;
  UI-скрытие проверкой не считается — дословно FR-46/NFR-7. Постороннему
  ученику занятость видна как «занято» без раскрытия, кем (сценарий есть).
- Фото ракурсов: владелец + ученики пары; гость 401 / иная роль 403 /
  чужой или несуществующий 404 / не из пары 403 — матрица MIN-2 ревью 3A
  перенесена на новый параметризованный маршрут /photo/{angle} полностью.
- СТС: отдельный эндпоинт только владельцу; ученику пары и всем прочим —
  отказ; «СТС ученикам не выдается» покрыто сценарием спеки. Правило
  FR-44/NFR-7 выполнено разделением kinds (car_photo vs car_sts) —
  учиться на одном kind с флагом публикации не пришлось, поверхность
  ошибки меньше.
- Брони: GET ученика — только свои (по сессии), GET инструктора — только
  своего контура, confirm/reject чужой брони → 404 (сценарий «Чужую бронь
  решить нельзя»); «Мои документы» — только владельцу (сценарий с
  перечислением всех чужих ролей). Прямые URL исключены конструктивно —
  data/uploads/ вне статики, наследование NFR-1 (ADR-004, решение 2).
  Замечаний нет.

### 1.3 «Мои документы», комплектность в админке, модульность — соответствуют

- «Мои документы» (FR-45): единый список ВУ (из instructor_applications)

  анкете без файла — сценарий есть, досыл вне объема — соответствует

  допустимо (Content-Disposition — деталь dev, корректно не спекифицировано).
- Комплектность (ОВ-1): выбран ровно вариант Заказчика — сервер хранит
  факт (колонки ракурсов NULL/NOT NULL + флаг blocked), валидирует человек

  комплектом НЕ введена — правильно: она противоречила бы буквальной
  цитате «Валидирует человек в админке». Разблокировка вне объема —
  зафиксировано как сознательное ограничение design.md.
- Модульность (директива Заказчика): booking.py и instructor_documents.py —

## 3. Major-замечания

### MAJ-1: PUT /api/instructor/availability (полная замена графика) не согласовани с booking — висячие ссылки на слоты достижимы

См. §2 (последняя строка). Design.md объявляет: availability — «БЕЗ
структурных изменений», instructor_availability.py — в списке «без
изменений». При этом существующий контракт Спринта 3 — PUT с ПОЛНОЙ
заменой графика одной транзакцией (архитектурная карта, компонент
instructor_availability.py): инструктор в любой момент может удалить или
заменить интервал. booking.availability_id NOT NULL ссылается на строку
availability логически (внешние ключи в схеме не включены — фикс ревью
3A). Достижимый сценарий без единой новой строчки в этом пакете: ученик
отправил запрос / инструктор подтвердил бронь → инструктор правит график
(PUT без этого слота) → строка availability удалена, бронь осталась:
календари FR-49 теряют дату/время занятия (JOIN пуст), слот исчезает из
выдачи, ученик видит подтвержденное занятие-призрак; защита «на уровне
хранилища» (NFR-8) для этого случая не работает — нарушение не через
гонку, а через несогласованное изменение основания. Ни design.md, ни
specs/booking, ни tasks.md этот случай не называют. Требование к СА:
определить взаимодействие PUT с активными/подтвержденными бронями —
рекомендую запрет (PUT отклоняется 409 с перечнем затронутых слотов, пока
у них есть брони в 'new'/'confirmed'; инструктор сначала решает брони) как
минимально-сюрпризный и соответствующий духу NFR-8 («не молчаливая
порча»); допустимая альтернатива — каскад (брони удаляемых слотов →
'rejected' с системным комментарием, механика авто-закрытия заявок 3A).
Выбранный вариант зафиксировать: design.md (раздел модели данных/блок C),
сценарий в specs/booking/spec.md, тест в задачу 4.1, сверка контракта PUT —
в 5.1.

## 4. Minor-замечания

### MIN-1: семантика даты lesson_date / «Занятия на сегодня» — часовой пояс не определен
«Ближайшая будущая дата weekday» и «lesson_date = today» зависят от
календаря/пояса, а унаследованный техдолг спринта-0 — времена UTC vs
локальная дата (MIN-4 review-001, архитектурная карта). На границе недели
два правила дадут разные брони и разные виджеты. Одна строка в design.md:
фиксировать единое правило (рекомендую локальную дату сервера — в ее
показаниях живут календари) + тест границы в 4.1/4.2.

### MIN-2: blocked-автомобиль × брони — эффект блокировки на контур брони не определен
Эффект block описан для каталога/карточек/выдачи фото (скрыт от учеников),
но не для брони: видит ли ученик пары автомобиль в подтвержденной брони,
если авто пары заблокировали (ОВ-6 говорит «следует за перекреплением», но
авто удалено из выдачи ученику — конфликт наблюдений); можно ли создавать
новые брони при заблокированном авто пары. Зафиксировать одну строку в
design.md (рекомендую: блокировка не трогает существующие брони и их
отображение — блокируется автомобиль как объект каталога, не календарь) и
тест в 2.2/4.1.

### MIN-3: car_id NULL в календарях — пустое состояние не определено
Удаление авто снимает car_id принятой заявки при сохранении пары (ОВ-3
Спринта 3 — закреплено master-спекой instructor-cars). Календарь ученика,
календарь инструктора и today_lessons (ОВ-6) обязаны показывать
«автомобиль» — при car_id NULL (авто удален) отображение не определено.
Одна строка в design.md (рекомендую: место авто — корректное пустое
состояние, не ошибка) + тест.

### MIN-4: судьба устаревшего фото-контракта Спринта 3 не объявлена
Устаревшей объявлена только колонка instructor_cars.photo_path. Но в
Спринте 3 существовал и эндпоинт POST+GET
/api/instructor/cars/{id}/photo (одиночное фото, без ракурса) — design.md
блок A вводит /photo/{angle} молча, судьба старого маршрута (удаление /
совместимость) не указана; после архивации дельты старый эндпоинт останется
без спечного основания. Аналогично master-требование «Добавление
автомобиля» не упоминает СТС. Одна строка в design.md: старый
/photo-маршрут удаляется (или объявляется устаревшим) одновременно с
photo_path; в master-спеку совместность требований решится при архивации.

### 7.2 Новое наблюдение (не блокирует)

**MIN-5 (примечание, некритично):** новый Requirement «Замена графика при
активных бронях отклоняется» размещен в ADDED-дельте booking, тогда как сам
контракт PUT /api/instructor/availability принадлежит домену
instructor-availability. При архивации ограничение ляжет в
openspec/specs/booking/spec.md, а контракт PUT останется в
specs/instructor-availability — расщепление одного контракта по двум спекам.
Поведение однозначно и не противоречит master-спеке (валидации --strict
проходят), поэтому правка пакета не требуется: рекомендую при архивации
перенести требование в instructor-availability (MODIFIED/ADDED-дельтой) либо
зафиксировать перекрестную ссылку; текущая сверка контракта PUT в tasks 5.1
уже страхует рассинхрон.
