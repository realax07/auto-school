## Модель данных (NFR-24; DDL уточняет dev в границах)

Новая таблица `document_versions` (миграция idempotent — механика
users.role / instructor_cars.status):

- `id INTEGER PRIMARY KEY AUTOINCREMENT`
- `target_type TEXT NOT NULL CHECK (target_type IN ('license','car_sts'))`
  — тип документа: ВУ (личный документ анкеты) / СТС автомобиля
  (единая модель ВУ+СТС — ОВ-2; СТС — по одному на каждую машину,
  у инструктора машин много → СТС много)
- `target_id INTEGER NOT NULL` — instructor_applications.id (для
  license) / instructor_cars.id (для car_sts)
- `version INTEGER NOT NULL` — порядковый номер версии документа
- `file_path TEXT NOT NULL` — файл в data/uploads/ (uuid-имя, вне
  статики — ADR-004)
- `status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN
  ('pending','verified','rejected'))`
- `reject_reason TEXT` — причина отказа; CHECK
  `(status <> 'rejected' OR (reject_reason IS NOT NULL AND
  reject_reason <> ''))` — при rejected причина обязательна на уровне
  схемы (ОВ-1)
- `uploaded_at TEXT NOT NULL` — момент загрузки версии
- `decided_at TEXT` — момент verify/reject
- `UNIQUE (target_type, target_id, version)`; частичный уникальный
  индекс `UNIQUE (target_type, target_id) WHERE status = 'pending'` —
  одна ожидающая версия на документ (ОВ-7) на уровне схемы

Таблица instructor_applications (license_photo_path) и instructor_cars
(photo_sts) — БЕЗ структурных изменений: канонические колонки
хранят файл ДЕЙСТВУЮЩЕЙ версии (совместимость со всеми существующими
потребителями: GET …/sts, GET …/photo/sts, admin completeness, карточка
анкеты). Pending-версия живет ТОЛЬКО в document_versions; при verify
каноническая колонка переключается на файл новой версии.

### Seed-миграция существующих документов (NFR-24)

Для каждой анкеты с непустым license_photo_path — строка
(license, application_id, version=1, file=license_photo_path,
status='verified', uploaded_at=created_at анкеты); для каждого авто с
непустым photo_sts — (car_sts, car_id, version=1, file=photo_sts,
status='verified', uploaded_at=created_at авто). Idempotent: seed
только при отсутствии строк документа (SELECT по
target_type+target_id); повторный запуск ничего не меняет; на
существующем volume контейнерного стенда выполняется init_db через
lifespan (наследование add-containerization). Эффект: после релиза ни
один документ не «зависает» на верификации, выдача файлов
не меняется (действующая версия = тот же файл). Анкета без ВУ /
авто без СТС — строк не создают (пустые состояния сохраняются).

## Машина статусов документа (норма объема; по образцу авто Спринта 7)

```
                 загрузка/замена (инструктор, FR-71/72)
  (нет версии) ────────────────────────────► pending ─── verify ───► verified (действует)
                                                 │  ▲                    │ (архив при новой
                                      повторная  │  │ повторная          │  verified-версии)
                                      загрузка   └──┘ загрузки          │
                                      замещает (ОВ-7)                   │ reject (причина
                                                                        ▼ обязательна, ОВ-1)
                                                                     rejected
                                                 предыдущая verified
                                                 ОСТАЕТСЯ действующей
```

- Действующая версия документа — последняя verified (до первой
  верификации действующего файла нет: первичный СТС — photo_sts,
  первичное ВУ — license_photo_path, см. «Первичная загрузка vs
  замена»).
- pending — ровно одна на документ (частичный UNIQUE-индекс);
  повторная загрузка замещает ожидающую (файл + uploaded_at той же
  строки, version не растет до верификации) — ОВ-7.
- verify (только админ, X-Admin-Token): pending → verified; предыдущая
  verified остается в истории как архив; каноническая колонка
  (license_photo_path / photo_sts) переключается на файл новой версии.
- reject (только админ): pending → rejected С ОБЯЗАТЕЛЬНОЙ причиной
  (ОВ-1: без причины — 422; пустая причина = 422); предыдущая
  verified ОСТАЕТСЯ действующей — инструктор не остается без
  документа; rejected-версия видна инструктору с причиной («Мои
  документы»); инструктор может заменить повторно (новая pending).
- Статусы документов НЕ влияют на статус авто (разные машины
  состояний; связь — только через ОВ-6, см. ниже) и НЕ влияют на
  активность инструктора (ОВ-3: каталог, новые заявки, submit — без
  изменений, NFR-23).
- «Отозвать pending» — НЕ реализуется (ОВ-7 — только замещение;
  точка расширения).

### Первичная загрузка vs замена (решение СА)

- СТС у авто БЕЗ действующего СТС (легаси/дозагрузка, FR-69): файл
  пишется в photo_sts напрямую + создается verified v1 — как в
  Спринте 7; проверка файла — валидатором авто при validate (гейт
  ОВ-4/MAJ-1 Спринта 7); двойная human-верификация одного файла не
  вводится.
- СТС при ДЕЙСТВУЮЩЕМ (verified v1 существует): замена → pending-
  версия, photo_sts НЕ перезаписывается до верификации — «документ
  не мигает» (FR-70).
- ВУ при анкете БЕЗ ВУ (первичная, досыл из FR-72): pending-версия —
  верификация только человеком (наследование ОВ-1 Спринта 5);
  verify переключает license_photo_path. При анкете С ВУ — всегда
  замена → pending.

## Правило ОВ-6: замена СТС и статус валидации авто

- POST …/cars/{id}/photo/sts при status='validated': статус НЕ
  меняется (validated остается validated) — статусы документа и авто
  независимы, повторная валидация авто — отдельное действие submit
  (ОВ-6). Текущее поведение Спринта 7 (MAJ-1: ЛЮБАЯ замена, включая
  sts, возвращает validated → validating) УТОЧНЯЕТСЯ: правило MAJ-1
  остается ТОЛЬКО для 5 ракурсов (validated → validating при замене
  любого ракурса — без изменений, валидатор обязан видеть актуальные
  фото); для sts-ветки сброса нет.
- Замена СТС не трогает ракурсы и комплектность-гейт: photo_sts
  остается непустым (действующая версия), флаг has_sts и счетчики
  комплектности не меняются; админ видит замену в разделе «Документы»,
  а не в разделе «Автомобили».

## Диагностика: СТС-дозагрузка на созданном авто не работает (FR-69)

Симптом Заказчика (п.1): СТС-дозагрузка на созданном авто в UI не
работает. Спринт 7 завел параметризованный POST
/api/instructor/cars/{id}/photo/sts (запись в photo_sts подтверждена
кодом) — симптом сохраняется, значит корень сместился. Задача
диагностики (tasks.md 3.1) проверяет цепочку по звеньям и фиксирует
корень в отчете задачи ДО фикса:

- (а) эндпоинт: воспроизведением подтвердить, что POST
  …/photo/sts принимает JPEG/PNG ≤5 МБ и заполняет photo_sts (и —
  после введения версий — создает правильную версию документа);
- (б) клиент: какой маршрут фактически вызывают «Мои автомобили»
  (модалка авто) и «Мои документы» (frontend/js/dashboard-instructor.js)
  — не остается ли вызов legacy POST …/photo с kind=car_sts (маршрут
  удален в Спринте 7 → 404/405), не вызывается ли sts-загрузка только
  при СОЗДАНИИ авто (поле sts_photo модалки создания), а у
  существующего авто контрол отсутствует/неактивен; проверить все
  места вызова (модалка авто, секция документов);
- (в) состояние: воспроизводится ли повторной загрузкой; что в сетевых
  запросах браузера (код ответа, payload — поле файла, angle).

Фикс: рабочий контрол загрузки/замены СТС в модалке авто и «Моих
документах» (единый эндпоинт POST …/photo/sts), с учетом статусной
модели документов (замена → pending, ОВ-6 — без сброса статуса авто).

{ok:false, error:"<по-русски>"}; 401/403/404/409/422 — как в design.md
Спринта 5. SQL параметризованный (NFR-10); файлы/ФИО/статусы в логах
запрещены.

## Видимость и доступ (NFR-22) — матрица

|| Поверхность | Кто видит |
|---|---|
| Список «Мои документы» + версии/статусы/причины отказа | только владелец-инструктор |
| Файл действующей версии документа | только владелец (ВУ — только владелец; СТС — только владелец, наследование) |
| Загрузка/замена ВУ и СТС | только владелец (чужой авто/документ → 404-неразличение) |
| GET /api/admin/documents (+file, verify, reject) | только X-Admin-Token; инструктор/ученик/гость → 401/403 |
| «Мои ученики» (карточки, счетчики) | только владелец-инструктор; чужие пары не выдаются |
| Виджеты «привязанные ученики»/«запросы»/«занятия на сегодня» | главная кабинета — остаются; «Мои автомобили»/«Мои документы» — ОТСУТСТВУЮТ (FR-73, UI-правило: серверная выдача не меняется) |

Правила реализации: проверки — на сервере при каждом запросе
(владелец документа/пары вычисляется серверно — механика
instructor_documents.py); UI-скрытие проверкой не считается; отказ —
404-неразличение (не раскрываем существование документа/пары).

## Календарь (FR-74) — фронт, без изменений бэкенда

- Запросы (booking.status='new') и брони (confirmed) отображаются
  ВНУТРИ ячейки выбранного слота: дата+время запроса совпадают со
  слотом availability (booking привязан к availability_id — данные
  уже есть в GET /api/instructor/bookings; агрегированных списков
  «рядом с календарем» нет, попаданий на соседние слоты нет).
- Кнопки решений по запросу/брони — на слоте, немедленно, мимо
  «Сохранить» (наследование ОВ-6 Спринта 7); «Сохранить» = один PUT
  полной замены графика, «Отменить» = перезагрузка GET без PUT;
  409 (интервал с активной бронью, MAJ-1) — показывается с
  сохраненным графиком. Контур availability — без изменений кода.
- Раздел «Бронирования» удаляется БЕЗ остатков: пункт меню, секция
  #sec-bookings, JS-контур; старая ссылка #/bookings — редирект в
  календарь (механика BUG-047).

## «Мои ученики» (FR-75, ОВ-5) — счетчики

- Источник пар: student_requests.status='accepted' (новых сущностей
  нет — чтение поверх booking/student_requests, наследование ADR-005).
- next_lesson: ближайшая бронь status='confirmed' с lesson_date ≥
  сегодня; отсутствует → «нет». planned_count: confirmed после
  следующей. completed_count: confirmed с датой < сегодня (правило
  материализации lesson_date — наследование MIN-1 Спринта 5,
  ЛОКАЛЬНАЯ дата сервера; таймзона клиента не участвует).
- ТОЛЬКО confirmed (ОВ-5): запросы (new) в счетчиках и «следующем»
  не участвуют — запрос может быть отклонен; запросы видны в
  подразделе «Запросы учеников» (вкладка/окно ПО ТРЕБОВАНИЮ, внутри
  раздела «Мои ученики»; отдельного пункта сайдбара больше нет).
- Пустые состояния: пара без броней — «нет», 0/0; нет пар —
  корректное пустое состояние раздела.

## Фронт (без новых страниц)

- `instructor-dashboard.html` + `js/dashboard-instructor.js`:
  - «Мои документы»: у ВУ и у каждого СТС — кнопки загрузки/замены
    (multipart на POST /api/instructor/documents/license и
    POST …/cars/{id}/photo/sts), предупреждение FR-71 (текст: замена
    вступит в силу только после проверки администратором; до

    «Заменить» в диалоге — без клика файл не отправляется; бейджи:
    «Ожидает проверки замены» (pending), «Отклонено» с текстом причины
    (ОВ-1), действует; после загрузки список перезагружается;
  - экраны «Мои автомобили» и «Мои документы» — БЕЗ виджетов
    (привязанные ученики, запросы учеников, занятия на сегодня
    удалены с этих экранов; главная — без изменений, FR-73);
  - календарь: запросы/брони на слотах (ячейка слота), решения
    немедленно, «Сохранить/Отменить»; раздел «Бронирования» удален

- `admin-dashboard.html` + `js/admin-dashboard.js`: раздел

  пункт «Документы» добавляется, остальное без изменений.

## Обработка ошибок (сводка)

|| Ситуация | Ответ | Требование/решение |
|---|---|---|
| reject без причины / пустая причина | 422 | ОВ-1 |
| verify/reject не-pending версии | 409 | машина статусов документа |
| verify/reject без админ-токена | 401 | механика Спринта 0 |
| Файл не JPEG/PNG / >5 МБ (ВУ и СТС) | 422, прежний файл не затронут | NFR-9, FR-69 |
| Чужой документ/авто/пара (загрузка, чтение, файл) | 404-неразличение | NFR-22, NFR-7 |
| Повторная загрузка при pending | 200 — замещает ожидающую (не ошибка) | ОВ-7 |
| Замена СТС у validated-авто | 200, status авто не меняется | ОВ-6 |
| PUT availability удаляет интервал с активной бронью | 409 с перечнем (наследование, без изменений) | MAJ-1 Спринта 5/7 |

## Решения по НФТ

- NFR-22: матрица выше; серверная проверка владельца/токена на каждом
  запросе; 404-неразличение.
- NFR-23: pending/rejected документов не блокирует инструктора, не
  скрывает из каталога, не меняет брони/занятия (ОВ-3); удаление
  виджетов и раздела «Бронирования» — UI-правки, API-контракты
  booking/availability не меняются; канонические колонки
  photo_sts/license_photo_path сохранены — все существующие
  потребители (sts-выдача, completeness, карточка анкеты) работают
  без переделки.
- NFR-24: seed-миграция idempotent (см. «Модель данных») —
  существующие документы сразу verified; механизм хранения — ТАБЛИЦА
  версий (решение СА в границах NFR-24: канонические колонки остаются
  указателем действующего файла, история — в document_versions).
- NFR-9/10: uploads.py без изменений (magic bytes, ≤5 МБ, uuid);
  параметризованный SQL во всех новых запросах (grep-контроль —
  задача приемки); документы/ФИО/токены/причины не логируются.
- Миграции: безопасны на существующем volume (init_db через lifespan
  — наследование add-containerization).

## Сознательные ограничения (задокументированы)

- «Отозвать pending» — точка расширения (ОВ-7: только замещение).
- История версий с просмотром архива, пакетное подтверждение — точки
  расширения; админ работает только с ожидающими версиями.
- Влияние статусов документов на активность инструктора — точка
  расширения (ОВ-3: «не влияет пока что»).
- Первичное СТС (авто без СТС) не проходит документную верификацию —
  обоснование в «Первичная загрузка vs замена»; ВУ при анкете без ВУ —
  через pending (асимметрия задокументирована).
- Колонки license_photo_path/photo_sts остаются каноническими
  указателями действующей версии; перенос указателя в
  document_versions с удалением колонок — вне объема.
- Уведомления о верификации/запросах — backlog. In-memory сессии/
  токены, single-worker — наследованные ограничения, не revisiting.

## Соответствие ADR-004

Отступлений нет: ФИО — только из users (админ-выдача); файлы —
data/uploads/ вне статики, выдача авторизованными эндпоинтами
(владелец/админ); связь «пара» — статус accepted student_requests;
рейтинг не затронут. Новое решение объема — таблица document_versions
с seed-миграцией verified v1; ADR/карта архитектуры обновляются
архитектором при ревью пакета (вне этого пакета).
