# Research: add-instructor-flow

Наследуются техрешения Спринтов 0–1: FastAPI + SQLite, фронт — статика из
design/mocks без сборки, пароли — bcrypt cost 12, сессии — in-memory токен
TTL 12 ч, админ-API — X-Admin-Token. Ниже — альтернативы по новым решениям
Спринта 2 (E12).

## 1. Пароль в заявке: хэш при отправке vs повторный ввод при approve

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **bcrypt-хэш сохраняется в заявке (FR-11.1); при approve переносится в users как есть** | Хэш уже стойкий — повторное хэширование не требуется (и невозможно: открытый пароль нигде больше нет); approve — один INSERT без криптографии; пароль НЕ хранится и НЕ логируется в открытом виде ни в какой момент времени | bcrypt-хэш в таблице заявок (виден при компрометации БД — но это верно и для users) | **ВЫБРАНО** (прямое требование FR-11.1 и дословное ТЗ: «в заявке на аппрев все данные, включая хэш пароля») |
| Открытый пароль хранится в заявке до approve, хэшируется при одобрении | Не нужен хэш в заявке | Открытый пароль персистентно хранится неопределенное время — нарушение NFR-3 и духа FR-11.1; приказной порядок не меняет факта хранения | Отклонено (нарушение требований) |
| Повторный ввод пароля инструктором при одобрении (письмо/звонок) | Хэш в заявке не нужен | Новый UX вне ТЗ; инструктор может не быть доступен; FR-11.1 явно описывает перенос хэша | Отклонено (вне ТЗ) |

## 2. Разделение ролей: флаг роли в users vs отдельная таблица

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Колонка role в users** (значения: student / instructor; заявка до approve — только в instructor_applications) | Единая таблица учетных данных, /api/auth/login не меняет механизм проверки; роутинг после входа (FR-13) решается одним SELECT; ТЗ допускает «флаг роли в данных заявки/пользователя» | Модификация схемы users (additive, NULL-safe с дефолтом student — ученики Спринтов 0–1 не ломаются) | **ВЫБРАНО** |
| Отдельная таблица instructors с дублем email/хэша | Явное разделение доменов | Дублирование учетных данных и синхронизация; вход (единый /api/auth/login) требовал бы SELECT по двум таблицам; противоречит FR-16 («создавать пользователя в users») | Отклонено |
| Роль определяется наличием записи в instructor_applications | Ноль изменений схемы | Роль становится динамическим выводом ( approved заявка удалена/нет — роль плавает); явный флаг проще и устойчивее | Отклонено |

## 3. Получение id созданной записи при approve (INSERT в users)

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **cursor.lastrowid после INSERT** | Ноль доп. запросов; стандартный sqlite3 API, уже используется в register.py (Спринт 0) | Работает только сразу после INSERT тем же курсором (здесь — так и есть) | **ВЫБРАНО** (консистентность с register.py) |
| Отдельный SELECT по email после INSERT | Не зависит от курсора | Лишний запрос; гонка не исключена избыточно (UNIQUE + lastrowid атомарны в одном соединении) | Отклонено |

## 4. Идентификация статуса при входе (FR-13)

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **После успешной проверки пароля в users: SELECT по email в instructor_applications** | Логика целиком на бэкенде: 200-ответ дополняется полем маршрута (cabinet/pending/rejected + причина); фронт просто следует контракту | Один доп. параметризованный SELECT | **ВЫБРАНО** (детали — sdd.md §15) |
| Фронт после входа сам запрашивает статус отдельным эндпоинтом | Разделение concern'ов | Второй запрос + временное окно рассинхрона; статусные экраны требуются сразу по факту входа | Отклонено |

## 5. Инкрементальные мелочи

Формат ответов API, хендлерная валидация (дефолты вместо Pydantic-required),
анти-брутфорс на /api/auth/login, единое сообщение об отказе входа —
наследуются Спринтов 0–1 без альтернатив. Таблица заявок — только хранение
(паттерн 5 map.md). Альтернативы не рассматривались — инкремент тривиален.
