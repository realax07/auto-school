# Delta: booking

## MODIFIED Requirements

### Requirement: Запрос брони на слот

Ученик пары MUST уметь выбрать слот графика инструктора (интервал
целиком, ОВ-3) и отправить запрос брони («новая»). Бронь
MUST быть только на будущих экземплярах — начало строго позже текущего
момента МСК, иначе отклонение сервером (FR-96/NFR-31); бронь MUST
фиксироваться на дате экземпляра (разовый — его дата; повторяющийся —
дата недели брони; поле даты аддитивно, без даты — ближайший будущий
экземпляр). Повторный запрос на занятый слот не создается; после
отклонения — допустим (ОВ-3…ОВ-5).

С ЭКОНОМИКОЙ (Спринт 16): если у инструктора задана цена часа, при
создании брони в НЕЙ ЖЕ транзакции фиксируется СНАПШОТ цены и создается
ХОЛД (транзакция журнала, привязанная к брони; ровно один холд на бронь —
частичный UNIQUE) на сумму цена_снапшот × длительность слота (целые
копейки); средства ученика переходят из «доступно» в «заморожено»,
инструктору НЕ принадлежат (дословно Заказчика: «При бронировании
занятия, деньги блокируются, но еще у инструктора»). Если доступного
баланса недостаточно, бронь НЕ создается (ни записи брони, ни холда) —
сервер отклоняет запрос с суммами для UI (недостаточно средств,
пополните кошелек). Если цена инструктором не задана — бронирование
работает как прежде, без холда (обратная совместимость).

Источник: requirements-booking-docs.md FR-47…49, FR-95/96, NFR-8/31;
решение Заказчика 2026-11-14; docs/ba/requirements-sprint16.md FR-101…103.

#### Scenario: Запрос создается со статусом «новая» и виден инструктору

- **GIVEN** пара создана и у инструктора есть свободный будущий слот
- **WHEN** ученик выбирает слот и отправляет запрос брони
- **THEN** запрос создан со статусом «новая» и появляется у инструктора в запросах брони

#### Scenario: Занятый слот не бронируется повторно

- **GIVEN** у слота есть активный запрос или подтвержденная бронь одного ученика пары
- **WHEN** другой ученик той же пары пытается забронировать этот слот
- **THEN** действие отклонено, дублирующий запрос не создан

#### Scenario: Слот бронируется целиком

- **GIVEN** у инструктора есть интервал графика 10:00–14:00
- **WHEN** ученик бронирует этот слот
- **THEN** занятием считается весь интервал 10:00–14:00 (нарезка на подынтервалы не выполняется)

#### Scenario: Повторный запрос после отклонения допустим

- **GIVEN** запрос брони ученика на слот отклонен инструктором (с комментарием)
- **WHEN** ученик снова отправляет запрос на этот же слот
- **THEN** новый запрос создается (повторная подача не ограничена)

#### Scenario: Бронь фиксируется на конкретной дате экземпляра

- **GIVEN** повторяющийся слот «Чт 16:00–18:00», ученик бронирует экземпляр на 12 ноября
- **WHEN** запрос брони отправлен с этой датой
- **THEN** бронь создана именно на 12 ноября 16:00–18:00 (дата экземпляра зафиксирована в записи брони); запрос с датой, не попадающей на день недели серии (или не равной дате разового слота), отклоняется сервером

#### Scenario: Запрос брони на прошедший или начавшийся слот отклоняется сервером

- **GIVEN** слот сегодня 10:00–12:00 при текущем времени 14:30 (или дата слота прошла)
- **WHEN** запрос брони на этот слот отправлен, в том числе прямым вызовом API в обход UI
- **THEN** сервер отклоняет запрос ({ok:false}), записи нет; в UI слот отображается без кнопки брони

#### Scenario: Запрос в старом формате (без даты) продолжает приниматься

- **GIVEN** клиент отправляет POST {availability_id} без поля даты на будущий слот
- **WHEN** сервер обрабатывает запрос
- **THEN** запрос принимается без ошибки: бронь создается на ближайшую будущую дату экземпляра серии (прежнее поведение), остальные проверки прежние

#### Scenario: Бронь с ценой создает холд и снапшот

- **GIVEN** у инструктора задана цена часа, у ученика достаточно средств
- **WHEN** ученик бронирует слот длительностью N часов
- **THEN** в одной транзакции созданы бронь (снапшот цены, hold_amount = цена×100×N копеек) и холд журнала; «доступно» ученика уменьшилось, «заморожено» увеличилось на hold_amount; инструктору средства не зачислены; ровно один холд на бронь

#### Scenario: Недостаточно средств — бронь не создается

- **GIVEN** у инструктора задана цена часа, доступного баланса ученика меньше суммы холда
- **WHEN** ученик отправляет запрос брони (в том числе прямым вызовом API)
- **THEN** сервер отклоняет запрос с сообщением о недостатке средств и суммами для пополнения; записи брони и холда НЕ созданы (состояние кошелька не изменилось)

#### Scenario: Бронь у инструктора без цены — без холда (обратная совместимость)

- **GIVEN** инструктор не задавал цену часа
- **WHEN** ученик бронирует слот (легаси-поведение)
- **THEN** бронь создана без холда и снапшота-суммы (hold_amount = 0); все существующие проверки и коды ответов прежние

#### Scenario: Повторная бронь того же экземпляра не дублирует холд

- **GIVEN** на экземпляр уже есть бронь с холдом (или гонка двух параллельных запросов)
- **WHEN** второй запрос обрабатывается
- **THEN** отклонение без второй брони и без второго холда (частичный UNIQUE холда на бронь; занятость — прежние гарантии)

## ADDED Requirements

### Requirement: Размороз при отклонении или отмене брони до старта

Отклонение инструктором запроса брони и отмена подтвержденной брони до
старта MUST выполнять ПОЛНЫЙ размороз холда: заморожено уменьшается,
доступно ученика возвращается (транзакция refund журнала, привязанная к
брони). Размороз MUST выполняться в той же транзакции, что смена статуса
брони; ровно один refund на бронь (частичный UNIQUE). Брони без холда
(цена не задана) размороз не создают.

Источник: решение Заказчика 2026-11-14; docs/ba/requirements-sprint16.md
FR-104; NFR-34/35.

#### Scenario: Отклонение запроса возвращает средства

- **GIVEN** бронь «новая» с холдом
- **WHEN** инструктор отклоняет запрос (с обязательным комментарием)
- **THEN** статус «отклонена»; холд закрыт refund-транзакцией: заморожено уменьшилось, доступно вернулось на сумму холда

#### Scenario: Отмена подтвержденной брони возвращает средства

- **GIVEN** подтвержденная бронь с холдом до старта занятия
- **WHEN** инструктор отменяет бронь
- **THEN** статус «отклонена» (механика BUG-049); холд закрыт refund-транзакцией, средства ученика полностью в «доступно»

#### Scenario: Повторный размороз невозможен

- **GIVEN** бронь, холд которой уже закрыт refund-ом
- **WHEN** повторные отмены/действия по этой брони
- **THEN** второй refund-транзакции нет (частичный UNIQUE), балансы не искажены

### Requirement: Проведенное занятие и авто-релиз холда через 24 часа

Через 24 часа после отметки «проведено», ЕСЛИ ученик не оспорил, холд
MUST закрываться автоматически (релиз): инструктору — net по текущей
комиссии, платформе — fee; ровно одна транзакция release с полями
gross/fee/net. Ровно один release на бронь; открытый спор блокирует
авто-релиз; брони без холда релиза не создают.

Источник: решение Заказчика 2026-11-14; FR-106; NFR-34/35.

#### Scenario: Авто-релиз после окна без спора

- **GIVEN** бронь «проведена» (hold_amount > 0), спора нет, с момента отметки прошло 24 часа
- **WHEN** выполняется свип авто-релиза (при чтении кошельков/админ-раздела)
- **THEN** создана ровно одна release-транзакция (gross = сумма холда, fee по комиссии, net инструктору); заморожено ученика обнулилось по этой брони; баланс инструктора вырос на net

#### Scenario: До истечения окна релиза нет

- **GIVEN** бронь «проведена», с отметки прошло меньше 24 часов
- **WHEN** выполняется свип
- **THEN** релиза нет; холд остается замороженным

#### Scenario: Открытый спор блокирует авто-релиз

- **GIVEN** бронь «проведена» с открытым спором, окно 24 часов истекло
- **WHEN** выполняется свип
- **THEN** авто-релиза нет; холд закрывается только решением оператора по спору

### Requirement: Оспаривание учеником и решение оператора

Ученик MUST уметь оспорить проведенное занятие в окне 24 часа от отметки
(обязательный комментарий); холд остается замороженным до решения
оператора. Повторный спор при открытом или решенном споре отклоняется.
Оператор MUST уметь решить спор: release инструктору или refund ученику —
с обязательным комментарием; решение закрывает спор и холд ровно одной
журнальной транзакцией.

Источник: решение Заказчика 2026-11-14 («…и отсутсвии жалоб от ученика»);
FR-107/108; NFR-34/35.

#### Scenario: Ученик оспаривает в окне 24 часов

- **GIVEN** бронь «проведена» менее 24 часов назад
- **WHEN** ученик отправляет спор с комментарием
- **THEN** спор зафиксирован; холд остался замороженным; авто-релиз не выполняется

#### Scenario: Спор вне окна отклоняется

- **GIVEN** с отметки «проведено» прошло более 24 часов (спора нет, релиз выполнен/ожидается)
- **WHEN** ученик пытается оспорить
- **THEN** сервер отклоняет (окно закрыто); холд/релиз не меняются

#### Scenario: Повторный спор при открытом отклоняется

- **GIVEN** по брони уже есть открытый спор
- **WHEN** ученик отправляет еще один спор
- **THEN** сервер отклоняет (конфликт); второго открытого спора нет (частичный UNIQUE)

#### Scenario: Решение оператора закрывает холд

- **GIVEN** открытый спор по брони с холдом
- **WHEN** оператор решает «перевести инструктору» или «вернуть ученику» (с обязательным комментарием)
- **THEN** создана ровно одна транзакция release (fee/net по комиссии) или refund (полный возврат); спор закрыт с решением и комментарием; без комментария решение недоступно; повторное решение отклоняется

### Requirement: Статусы брони расширяются статусом «проведена»

Модель статусов расширяется: подтвержденная бронь MUST переходить в
«проведена» по отметке инструктора; прочие статусы и контракты — без
изменений. «Проведена» MUST не занимать слот для новых броней (индекс
активных — прежний) и не мешать замене графика. Ответы API дополняются
новыми полями без удаления существующих (обратная совместимость).

Источник: решение Заказчика 2026-11-14; FR-105; NFR-35 (MAJ-1-наследование).

#### Scenario: Проведенная бронь не занимает будущие экземпляры серии

- **GIVEN** проведенная бронь экземпляра 12 ноября повторяющегося слота
- **WHEN** ученик смотрит будущие недели (например, 19 ноября)
- **THEN** экземпляры серии доступны для бронирования как прежде

#### Scenario: Существующие бронирования и решения работают как прежде

- **GIVEN** контур бронирования без цен (инструкторы без цены)
- **WHEN** выполняются существующие сценарии (создание, confirm/reject/cancel, MAJ-1, NFR-8)
- **THEN** поведение и коды ответов не изменились (контроль — зеленый прогон существующих тестов бронирования)
