# Delta: admin

## ADDED Requirements

### Requirement: Вход администратора

Администратор MUST входить в админку по логину и паролю, заданным в
конфигурации окружения (ADMIN_USER + ADMIN_PASSWORD_HASH, bcrypt). Вход с
неверными учетными данными MUST отклоняться (трассировка: FR-5).

Источник: requirements.md FR-5.

#### Scenario: Успешный вход администратора

- **GIVEN** администратор открывает страницу входа в админку
- **WHEN** он вводит логин и пароль, соответствующие ADMIN_USER и хэшу ADMIN_PASSWORD_HASH
- **THEN** система подтверждает вход, выдает авторизационный токен и открывает доступ к админке

#### Scenario: Вход с неверным паролем

- **GIVEN** администратор открывает страницу входа в админку
- **WHEN** он вводит корректный логин, но неверный пароль
- **THEN** система отклоняет вход, токен не выдается, доступ к админке не открывается

#### Scenario: Вход с неизвестным логином

- **GIVEN** администратор открывает страницу входа в админку
- **WHEN** он вводит логин, не совпадающий с ADMIN_USER
- **THEN** система отклоняет вход, токен не выдается

### Requirement: Список зарегистрированных пользователей

Админка MUST показывать список зарегистрированных пользователей: ФИО, email,
телефон, дата регистрации; свежие записи сверху; при совпадении даты/времени
регистрации порядок MUST быть детерминированным (тай-брейк по id по убыванию)
(трассировка: FR-6).

Источник: requirements.md FR-6.

#### Scenario: Просмотр списка пользователей

- **GIVEN** администратор вошел в админку и в системе есть зарегистрированные пользователи
- **WHEN** он открывает список пользователей
- **THEN** для каждого пользователя показаны ФИО, email, телефон и дата регистрации

#### Scenario: Свежие записи сверху

- **GIVEN** администратор вошел в админку
- **WHEN** зарегистрированы два пользователя: первый — раньше, второй — позже (в том числе обе записи созданы в одну и ту же секунду)
- **THEN** в списке пользователей запись второго (более свежего) отображается выше записи первого

### Requirement: Выгрузка CSV

Админка MUST выгружать список зарегистрированных пользователей в CSV-файл:
кодировка с BOM, разделитель «;», колонки ФИО;Email;Телефон;Роль;Дата
регистрации; значения пользовательских полей, начинающиеся с `=`, `+`, `-`,
`@`, MUST получать префикс `'` (санитизация CSV-инъекции); дата регистрации
MUST выводиться в локальном времени (пересчет из UTC при выводе)
(трассировка: FR-7).

Источник: requirements.md FR-7.

#### Scenario: Выгрузка CSV с корректным форматом

- **GIVEN** администратор вошел в админку и в системе есть зарегистрированные пользователи
- **WHEN** он запускает выгрузку CSV
- **THEN** загружается CSV-файл с BOM и разделителем «;», заголовок колонок — ФИО;Email;Телефон;Роль;Дата регистрации, по строке на каждого пользователя; в колонке «Роль» — значение ученика

#### Scenario: Санитизация опасных значений в CSV

- **GIVEN** администратор вошел в админку и зарегистрирован пользователь, у которого значение пользовательского поля начинается с опасного префикса (например, ФИО или email вида `=1+1`)
- **WHEN** он запускает выгрузку CSV
- **THEN** такая ячейка в CSV содержит значение с префиксом `'` (например, `'=1+1`), формула при открытии файла в Excel/LibreOffice не исполняется

#### Scenario: Дата регистрации в CSV в локальном времени

- **GIVEN** администратор вошел в админку и зарегистрирован пользователь, время регистрации которого в UTC и в локальной зоне попадает на разные календарные дни
- **WHEN** он запускает выгрузку CSV
- **THEN** в колонке «Дата регистрации» указан локальный календарный день регистрации

#### Scenario: CSV пуст при отсутствии пользователей

- **GIVEN** администратор вошел в админку и в системе нет зарегистрированных пользователей
- **WHEN** он запускает выгрузку CSV
- **THEN** загружается CSV-файл с корректным BOM, разделителем и заголовком колонок, без строк данных

### Requirement: Токен доступа к админ-API

Админ-API MUST требовать авторизационный токен; токен MUST выдаваться только
после успешного входа администратора. Запросы админ-API без токена, с
неверным или истекшим токеном MUST отклоняться (трассировка: FR-8).

Источник: requirements.md FR-8.

#### Scenario: Доступ с валидным токеном

- **GIVEN** администратор успешно вошел и получил токен
- **WHEN** он обращается к админ-API, передавая этот токен
- **THEN** система обрабатывает запрос и возвращает данные

#### Scenario: Запрос без токена

- **GIVEN** пользователь не выполнял вход администратора
- **WHEN** он обращается к админ-API без токена
- **THEN** система отклоняет запрос как неавторизованный и данные не возвращает

#### Scenario: Запрос с неверным токеном

- **GIVEN** истек срок действия токена администратора (или токен подделан)
- **WHEN** он обращается к админ-API с этим токеном
- **THEN** система отклоняет запрос как неавторизованный и данные не возвращает
