# Delta: auth

## ADDED Requirements

### Requirement: Вход ученика

Сервис авторизации MUST принимать логин (email) и пароль и при совпадении с
учетной записью ученика выдавать сессионный токен (трассировка: FR-1).

Источник: requirements.md FR-1.

#### Scenario: Успешный вход ученика

- **GIVEN** в системе зарегистрирован ученик с email E и паролем P (пароль хранится в виде bcrypt-хэша)
- **WHEN** он отправляет форму входа с email E и паролем P
- **THEN** система выдает сессионный токен и пользователь попадает в личный кабинет /cabinet

#### Scenario: После входа открыт кабинет

- **GIVEN** ученик успешно вошел и получил сессионный токен
- **WHEN** система завершает вход
- **THEN** пользователь оказывается на странице /cabinet

### Requirement: Единое сообщение об отказе входа

Сервис авторизации MUST отклонять вход при неверном email, неверном пароле
или отсутствующей учетной записи и MUST выдавать единое сообщение об ошибке,
не раскрывающее, какая именно из причин имела место (трассировка: FR-2).

Источник: requirements.md FR-2.

#### Scenario: Вход с неверным паролем

- **GIVEN** в системе зарегистрирован ученик с email E
- **WHEN** он отправляет форму входа с email E и неверным паролем
- **THEN** система отклоняет вход с единым сообщением о неверных учетных данных, токен не выдается

#### Scenario: Вход с несуществующим email

- **GIVEN** в системе нет учетной записи с email X
- **WHEN** пользователь отправляет форму входа с email X и любым паролем
- **THEN** система отклоняет вход с тем же единым сообщением, что и при неверном пароле, токен не выдается

#### Scenario: Сообщение об отказе не раскрывает причину

- **GIVEN** выполнены вход с неверным паролем и вход с несуществующим email
- **WHEN** сравниваются ответы системы на оба отказа
- **THEN** сообщения об ошибке идентичны (одинаковый текст, одинаковый код ответа)

### Requirement: Хранение учетных данных

Учетные данные MUST храниться в таблице users; пароль MUST храниться только
в виде bcrypt-хэша; открытый пароль MUST NEVER сохраняться и MUST NEVER
попадать в логи (трассировка: FR-3).

Источник: requirements.md FR-3.

#### Scenario: Проверка пароля против хэша

- **GIVEN** ученик зарегистрирован, и в таблице users для его email хранится bcrypt-хэш пароля
- **WHEN** выполняется вход с корректным паролем
- **THEN** система проверяет пароль сравнением с bcrypt-хэшем и разрешает вход

#### Scenario: Открытый пароль отсутствует в хранилище и логах

- **GIVEN** выполнены регистрация и вход ученика с паролем P
- **WHEN** выполняется прямой просмотр таблицы users и журналов сервиса
- **THEN** строка P отсутствует и в хранилище, и в логах; в таблице только bcrypt-хэш

### Requirement: Сессии с ограниченным сроком действия

Сессионный токен MUST выдаваться только после успешного входа и MUST иметь
ограниченный срок действия (TTL); запрос с истекшим токеном MUST
отклоняться (трассировка: FR-1, FR-7).

Источник: requirements.md FR-1, FR-7.

#### Scenario: Запрос с истекшим токеном

- **GIVEN** ученик вошел в систему и получил сессионный токен
- **WHEN** срок действия токена (TTL) истек, и выполняется запрос к защищенному ресурсу с этим токеном
- **THEN** система отклоняет запрос как неавторизованный и возвращает пользователя на страницу входа

#### Scenario: Запрос с подделанным токеном

- **GIVEN** пользователь не выполнял успешный вход
- **WHEN** он обращается к защищенному ресурсу с произвольной строкой вместо токена
- **THEN** система отклоняет запрос как неавторизованный

### Requirement: Ограничение попыток входа (анти-брутфорс)

Сервис авторизации MUST ограничивать число неудачных попыток входа подряд
с одного IP-адреса и после превышения порога временно блокировать попытки
входа с этого IP (трассировка: FR-2, решение Заказчика — вариант (б) по
arch-review MAJ-3).

Источник: requirements.md FR-2; design.md «Минимальная анти-брутфорс защита
/api/auth/login».

#### Scenario: Блокировка после превышения порога попыток

- **GIVEN** с одного IP-адреса подряд выполнено больше допустимого порога неудачных попыток входа
- **WHEN** с этого же IP поступает очередная попытка входа (с любыми учетными данными)
- **THEN** система отклоняет попытку без проверки учетных данных и с тем же единым сообщением об отказе, что и при неверных учетных данных, токен не выдается

#### Scenario: Длительность блокировки нарастает

- **GIVEN** блокировка входа с IP уже срабатывала ранее, и порог неудачных попыток превышен снова
- **WHEN** сравнивается длительность новой блокировки с предыдущей
- **THEN** новая блокировка длится не меньше (дольше) предыдущей — длительность нарастает с каждым срабатыванием

#### Scenario: Счетчик сбрасывается после успешного входа

- **GIVEN** с IP выполнено несколько неудачных попыток входа (меньше порога блокировки)
- **WHEN** с этого же IP выполняется успешный вход
- **THEN** счетчик неудачных попыток для этого IP обнуляется, и последующие изолированные неудачные попытки не приводят к блокировке

#### Scenario: Заблокированная попытка не раскрывает блокировку

- **GIVEN** вход с IP заблокирован по превышению порога неудачных попыток
- **WHEN** с этого IP выполняется попытка входа с корректными учетными данными существующего ученика
- **THEN** ответ идентичен отказу при неверных учетных данных (тот же код, тот же текст), токен не выдается

### Requirement: Выход ученика

Выход MUST аннулировать действующий сессионный токен и возвращать
пользователя на главную страницу; после выхода токен MUST перестать
приниматься системой (трассировка: FR-8).

Источник: requirements.md FR-8.

#### Scenario: Успешный выход

- **GIVEN** ученик вошел в систему и находится в кабинете
- **WHEN** он нажимает «Выйти»
- **THEN** сессионный токен аннулируется и пользователь попадает на главную страницу

#### Scenario: Токен не принимается после выхода

- **GIVEN** ученик выполнил выход, и его токен аннулирован
- **WHEN** выполняется запрос к защищенному ресурсу с этим токеном
- **THEN** система отклоняет запрос как неавторизованный
