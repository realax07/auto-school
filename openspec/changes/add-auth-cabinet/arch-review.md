- Риск: разработка стартует против отсутствующих контрактов; задача 2.1

- Требование: восстановить раздел «Спринт 1» в sdd.md в main (из stash 62b6e2e

  MAJ-2 ниже.

### MAJ-2: противоречие design.md ↔ sdd.md (stash) по составу записи сессии

- Факт: design.md (Компоненты, Поток 1/4) трижды фиксирует реестр сессий как
  `{token: expires}`. sdd §10.3 (stash): «Источник — запись users по id,
  привязанному к сессии» — то есть `{token: (expires, user_id)}`.
  GET /api/auth/me без user_id в записи сессии нереализуем без SELECT по
  токену, которого в схеме нет.
- Риск: разработчик 1.1, читающий design.md, реализует реестр без привязки —
  /me не сможет вернуть ФИО (FR-5), либо появится самодеятельная доработка
  контракта на этапе кода.
- Требование: привести design.md к одному составу записи
  (`{token: (expires, user_id)}`) во всех трех местах (состав записи — деталь
  дизайна, место ей в design/sdd, не в спеке).

### MAJ-3: публичный /api/auth/login без анти-брутфорса — техдолг не зафиксирован в пакете

- Факт: в Спринте 0 отсутствие rate-limit на /api/admin/login было осознанно
  задокументировано (map.md «Техдолг спринта-0», review-001). Спринт 1
  добавляет публичный endpoint подбора пароля реальных пользователей —
  поверхность атаки качественно иная, чем у одного админа. Ни design.md
  («Сознательные ограничения»), ни research.md, ни proposal.md этот пункт
  не упоминают: долг не принят и не отклонен — он невидим.
- Сопутствующее: фиктивная bcrypt-проверка при отсутствующей записи
  («допустима», design Поток 1 / sdd §10.1) — при необязательности время
  ответа раскрывает существование учетной записи, усиливая перебор (см.
  MIN-1 — связаны).
- Требование (любой из вариантов, выбор за СА/ПМ): (а) зафиксировать в
  design.md «Сознательные ограничения» как осознанный принятый техдолг с
  формулировкой риска (как это сделано для admin-login в Спринте 0) —
  минимальный достаточный вариант для границ спринта; (б) либо включить в
  пакет минимальную защиту (пауза/лимит попыток на email+IP). Отсутствие
  упоминания — не принимается.

в рамках минимальности варианта — фиксирую как известное свойство, а не
замечание. Пересмотр уместен только при появлении реальных инцидентов.
