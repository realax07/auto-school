# Research: add-instructor-student-loop

Наследуются техрешения Спринтов 0–2.2: FastAPI + SQLite WAL (single-worker),
bcrypt, сессии in-memory {token: (expires, user_id)} TTL 12 ч
(require_session), admin-токен in-memory (X-Admin-Token), статика тем же
сервисом без сборки, параметризованный SQL. Ниже — альтернативы по новым
решениям объема (E12).

## 1. Хранение загруженных файлов (ВУ, фото авто): каталог вне статики vs раздача как StaticFiles

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Каталог data/uploads/ вне frontend/, выдача только через авторизованные эндпоинты** | Прямой URL не работает в принципе (NFR-1 «прямые URL без проверки доступа недопустимы»); доступ проверяется кодом (админ-токен / владелец) | Нужны эндпоинты-раздачи | **ВЫБРАНО** — единственный вариант, исполняющий NFR-1 дословно |
| Сохранять в frontend/uploads/ и раздавать статикой | Ноль кода раздачи | Любой, кто узнает/подберет URL, получает изображение ВУ — прямое нарушение NFR-1 | Отклонено (нарушение NFR-1) |
| Хранить изображения BLOB-ами в SQLite | Один носитель | Раздача все равно требует авторизованного эндпоинта; BLOB раздувает БД и бэкапы; выигрыша нет | Отклонено (без преимуществ) |

## 2. Связь «ученик принят инструктором»: материализованная таблица vs вычисление из заявок

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Связь = заявка в статусе «принята» (student_requests.accepted; car_id — привязка к авто)** | Одна сущность вместо двух синхронизируемых; ОВ-1 (закрытие остальных заявок) и ОВ-3 (снятие привязки к авто без разрыва связи) ложатся естественно; NFR-5 описывает ровно эту сущность | Выборка принятых — по индексу (instructor_id + status) | **ВЫБРАНО** |
| Отдельная таблица students_instructors + заявки отдельно | «Классическая» нормализация | Две сущности об одном факте; рассинхрон при отказе/удалении авто; ОВ-3 требует править обе | Отклонено (дублирование факта) |

## 3. График availability: интервалы-записи vs булева сетка (ячейки по 30 мин)

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Записи-интервалы (weekday, start_time, end_time)** | Прямо соответствует NFR-5 («availability — интервалы»); выбор «свободное время» — пересечение интервалов SQL-условием | Сетка UI собирает интервалы из ячеек (логика на фронте) | **ВЫБРАНО** |
| Булева сетка ячеек по 30 мин (7×48 флагов) | Тривиальный UI-маппинг | Не «интервалы» по NFR-5; фильтр пересечения — перебор ячеек; миграция при смене шага сетки | Отклонено |

## 4. Агрегат рейтинга: вычисление на лету vs денормализация (колонка rating в users)

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **AVG/COUNT по reviews на лету** | Всегда консистентно; отзывы не «горячие» (запись редка); отзывов у инструктора — единицы | Агрегат на каждый список карточек | **ВЫБРАНО** (объемы спринта малы; индекс по instructor_id) |
| Денормализация в users.rating_avg | Список дешевле | Инвариант «средняя = AVG(отзывы)» приходится поддерживать вручную в трех местах (создание отзыва, удаление, правки) — источник рассинхронов | Отклонено |

## 5. Правило префиксов API (MIN-3 arch-review add-instructor-cabinet)

Двойной нейсеймс /api/instructors/* (анкета) и /api/instructor/* (кабинет)
зафиксирован ревью как техдолг «зафиксировать до следующих эндпоинтов
кабинета». Правило (design.md настоящего пакета): `/api/instructors/*` —
публичная анкета инструктора (существующий, не расширяется); `/api/instructor/*`
— эндпоинты кабинета инструктора (сессия + role='instructor');
`/api/student/*` — эндпоинты кабинета ученика (сессия + role='student');
`/api/admin/*` — админ-API (X-Admin-Token). Альтернатива «унифицировать
все под /api/instructors/» отклонена: ломает существующие контракты
Спринтов 1–2 ради косметики.

## 6. Инкрементальные мелочи

Миграция license_photo_path — idempotent ALTER (механика users.role,
Спринт 2). Виджеты главной кабинета — один агрегирующий эндпоинт
GET /api/instructor/summary, а не три мелких. Ответы ошибок — формат
{ok:false} Спринтов 1–2. По этим пунктам альтернативы не рассматривались —
инкремент тривиален.
