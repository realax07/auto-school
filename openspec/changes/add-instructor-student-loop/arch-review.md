## 1. Целевые проверки (фокус ревью)

### 1.1 Целостность модели данных — корректна, кроме стажа (MAJ-3)

- instructor_cars: один-ко-многим к users (instructor_id NOT NULL, индекс),
  transmission CHECK IN ('manual','automatic'), photo_path NULL —
  соответствует NFR-5 и FR-26. Владелец проверяется кодом на каждом
  мутирующем эндпоинте (чужой → 404) — при SQLite без PRAGMA foreign_keys
  это единственная линия защиты, достаточная для single-worker.
- availability: интервалы (weekday 0..6, start<end), UNIQUE-кортеж + индекс
  по instructor_id под фильтр «свободное время» — соответствует NFR-5,
  research.md §3 (отклонение булевой сетки обоснованно).
- reviews: UNIQUE(instructor_id, student_id), rating CHECK 1..5 — NFR-5.
- student_requests: три статуса, deny_comment (инвариант обязательности —
  кодом), car_id NULL→заполняется при принятии, индексы под оба списка —
  NFR-5. Связь «принят» = строка student_requests.status='accepted'
  (research.md §2) — одна сущность вместо двух синхронизируемых, ОВ-1/ОВ-3
  ложатся естественно. Решение принято.
- **MAJ-3: стаж (experience) в модели данных пакета отсутствует.** FR-31
  требует на карточке «стаж», FR-32 — фильтр `min_experience` (лет).
  Источник стажа в существующей схеме — instructor_applications.experience
  (TEXT, свободный формат), который approve в users НЕ переносит (sdd.md
  §16: копируются только surname, name, patronymic, email, phone,
  password_hash). Новые таблицы пакета (instructor_cars, availability,
  reviews, student_requests) стажа не содержат; миграций под него нет.
  GET /api/student/instructors и фильтр min_experience (design.md, блок 4;
  задача 4.1) не реализуемы без материализации стажа. Требование к СА:
  добавить колонку (минимально — `experience_years INTEGER NOT NULL
  DEFAULT 0` в users + idempotent-миграция + перенос при approve, либо
  отдельное решение), валидацию числом при анкете и фиксацию в design.md/
  задачах 1.1/4.1. Свободный текст заявки к фильтру «≥ N лет» непригоден.

### 1.2 API-контракты — роли, валидации, коды ошибок — корректны, один пробел (MAJ-2)

- Правило префиксов (design.md) закрывает MIN-3 arch-review
  add-instructor-cabinet дословно: /api/instructors/* — публичная анкета
  (не расширяется), /api/instructor/* — кабинет (сессия+роль),
  /api/student/* — кабинет ученика, /api/admin/* — токен. Все 15 новых
  эндпоинтов правилу подчиняются, исключений нет.
- Матрица 401/403/404/409/422 последовательна и совпадает с механикой
  Спринтов 1–2 ({ok:false, error}; 404 «не раскрываем существование»).
  Ролевые проверки всех блоков соответствуют таблице ролей ТЗ.
- Валидации по блокам: файлы — magic bytes + ≤5 МБ до записи (ОВ-5);
  авто — покомпонентно 422; availability — start<end, дубликаты схлопнуть,
  полная замена транзакцией; отзыв — серверная проверка связи (NFR-2),
  1..5, ≤1000, повторный 409; заявки — дубликат 409 без записи, отказ без
  комментария 422, чужой car_id 422, 0 авто 409 (ОВ-4). Покрытие FR-23…FR-41
  и NFR полное (трассировка — задача 8.1, допустимо по tasks.md).
- **MAJ-2: перекрепление автомобиля (ОВ-3) не обеспечено API-контрактом.**
  design.md («Жизненный цикл», удаление автомобиля) требует «инструктор
  перекрепляет авто вручную (минимально: выбор авто у принятого ученика)»,
  задача 6.4 включает перекрепление во фронт — но в таблицах эндпоинтов
  (блоки 2, 6) такого эндпоинта нет, задачи 6.1/6.2 его не реализуют.
  Фронт 6.4 остается без бэкенда. Требование к СА: добавить эндпоинт
  (например, PATCH /api/instructor/students/{id}/car: car_id — свое авто,
  иначе 422) в контракт и в задачу 6.1/6.2.

### 1.3 Безопасность фото — соответствует NFR-1/NFR-6

- Хранение data/uploads/{license,cars}/<uuid>.<ext> вне frontend/, статикой
  не раздается, имена генерирует сервер — прямой URL исключен конструктивно
  (исследовано research.md §1; BLOB-альтернатива отклонена обоснованно).
- Валидация по содержимому (JPEG FF D8 FF / PNG 89 50 4E 47) до записи,
  Content-Type клиента не доверенный, лимит 5 МБ — NFR-6, ОВ-5.
- Выдача: изображение ВУ — только X-Admin-Token (сценарии «ученическая
  сессия → отказ» и «прямой URL → 404» покрыты спекой и задачей 1.2);
  фото авто — только владельцу по сессии; публичная карточка —
  характеристики без фото и госномера (допущение proposal, совместимо с
  NFR-1). Замечаний нет; матрицу кодов GET фото — MIN-2.

### 1.4 Миграции SQLite — корректны

- Одна additive-колонка license_photo_path TEXT NULL (NULL = заявка без ВУ)
  + 4 CREATE TABLE IF NOT EXISTS — механика idempotent-миграции users.role
  (Спринт 2, sdd.md §16) переиспользуется; регресс Спринтов 0–2.2
  контролируется задачей 7.1. Точки правки существующего кода (db.py,
  app.py, instructors.py, instructor_admin.py) перечислены и минимальны.
- WAL + single-worker: новые таблицы инвариант не нарушают; in-memory
  сессии/токены наследуются без изменений (research.md, design.md
  «Сознательные ограничения»).

### 1.5 Жизненный цикл заявок — механизм системного отказа допустим, объем закрытия — нет (MAJ-1)

- Системный отказ «принят другим инструктором» (решение СА): авто-закрытие
  остальных заявок ученика переводится в существующий статус 'denied' с
  системным deny_comment — четвертый статус не вводится (NFR-5 сохранен),
  комментарий виден ученику (механика FR-38 переиспользуется), решение
  Заказчика по ОВ-1 не отменяет, а исполняет. Допустимость механизма —
  подтверждаю; фиксация как допущения в proposal.md + design.md корректна.
- **MAJ-1: закрытие охватывает только 'new', инвариант ОВ-1 нарушается.**
  ОВ-1 (утвержденный дефолт): «принять может только один (принятие
  закрывает остальные активные заявки ученика)»; активные статусы в
  design.md — new И accepted. Достижимый сценарий: ученик подал А и Б →
  Б принял (заявка А осталась 'new') → ученик повторно подала А (ОВ-2 —
  разрешено) → А принимает. Design.md закрывает «остальные 'new'-заявки» —
  их нет; ученик остается принят у двух инструкторов одновременно,
  связь «принят» (основа отзывов, «Моих учеников», виджета) перестает быть
  уникальной. Спека student-requests словами покрывает случай
  («остальные активные»), сценарий тестирует только new/new — дыра
  проталкивается в тесты. Требование к СА: довести дизайн до буквы ОВ-1 —
  accept закрывает ВСЕ остальные активные заявки ученика (accepted →
  denied с тем же системным комментарием; альтернатива «409 при наличии
  accepted-связи у ученика» хуже: механизма отвязки в объеме нет —
  ученик блокируется навсегда), добавить сценарий «accepted у Б + accept
  у А» в specs/student-requests и в задачу 6.1.

## 4. Minor-замечания

### MIN-1: семантика фильтра min_rating при отсутствии отзывов
У инструктора без отзывов агрегат {has_reviews:false}; попадает ли он в
выборку при min_rating>0 — design.md не определяет. Рекомендация: без
отзывов инструктор фильтру min_rating>0 не удовлетворяет (в min_rating=0 —
удовлетворяет); зафиксировать одной строкой в design.md и тестом 4.1.

### MIN-2: матрица кодов GET /api/instructor/cars/{id}/photo
«чужому/гостю — 401/403/404» — недоопределено. Рекомендация: гость 401,
чужая роль 403, чужой/несуществующий автомобиль 404 (симметрично остальным
блокам); зафиксировать в design.md.

### MIN-3: файлы-сироты в data/uploads/
DELETE автомобиля и обработка заявки не удаляют файлы с диска (осиротевшие
photo_path/license_photo_path). Для объема допустимо, но зафиксировать как
осознанный техдолг (cleanup — вне скоупа) в design.md «Сознательные
ограничения», чтобы не всплыло как дефект на ревью кода.

### MIN-4: answers-файл раунда вопросов отсутствует
Контракт 1 (artifact_contract.md): раунд вопросов обязан оставлять
docs/ba/answers_roundN.md с дословными цитатами. В docs/ba/ только
requirements-файл; решения ОВ-1…ОВ-6 процитированы в самом ТЗ (раздел
«Решения Заказчика»). По существу решение зафиксировано, но условие входа
контракта 2 формально не выполнено — БА дописать answers-файл (цитата
«Дефолты принимаю» + связь ОВ-N → ТЗ), к дизайну пакета не относится.
