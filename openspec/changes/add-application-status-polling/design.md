# Design: add-application-status-polling

Источники решений: docs/ba/requirements-sprint9.md (УТВЕРЖДЕН, блок 2
FR-80…FR-83 + NFR-28; открытые вопросы п.1 — механизм бесшовного входа,
решение за СА); decisions/2026-11-02-s9-application-status-polling-go.md
(create_change, PLAN.md 9.2). Существующий контур заявок (brownfield):
backend/instructors.py — POST /api/instructors/apply создает заявку
status='waiting' и отвечает {"ok": true}; backend/auth.py — login §15.5:
waiting → route 'pending', deny → route 'rejected' + review_comment;
сессии — in-memory реестр {token: (expires, user_id)}, TTL 12 ч,
secrets.token_urlsafe(32), фабрика _session_issue (register.py);
backend/instructor_admin.py — approve: INSERT users role='instructor' +
UPDATE status='approved' ОДНОЙ транзакцией (MIN-3), deny: status='deny' +
обязательный review_comment. Экраны: frontend/instructor-pending.html —
статичный («проверка при логине»), /instructors/pending и
/instructors/rejected — маршруты _PAGE_ROUTES backend/app.py; механика
логина (frontend/js/landing.js): route 'cabinet' → /instructor/dashboard,
route 'rejected' → sessionStorage 'instructor_rejected_reason' +
/instructors/rejected; сессия — sessionStorage 'session_token'
(frontend/js/api.js TOKEN_KEY). Зависимость: change
add-vue-framework-pilot (каркас Vue 3 + Vite, vendor-сплит — пилотная
страница ОВ-4, FR-86).

## Решение СА: обмен идентификатора на сессию (открытый вопрос п.1)

Рассмотрено и ОТВЕРГНУТО:
- ОДИН токен и на опрос, и на обмен — отвергнуто: опрос требует
  многоразовость (тик каждые 12 с часами, переживает перезагрузки
  экрана), обмен — одноразовость (анти-replay). Один артефакт либо
  потребляется и убивает опрос, либо не потребляется и допускает
  повторный обмен сессии.
- Self-contained подписанный токен (JWT-стиль) — отвергнуто: новая
  сессионная механика вопреки requirements §Ролевая модель («новых
  механизмов аутентификации… не вводим») и существующей модели
  (in-memory реестр, TTL 12 ч — наследуемое ограничение Спринтов 1–8,
  не revisiting).
- Автовход по email/паролю заявки — отвергнуто: перебираемо, требует
  хранения учетных данных на экране — хуже по всем осям безопасности.

ПРИНЯТО — ДВА артефакта, выдаются ВМЕСТЕ при успешной отправке анкеты
(дефолт открытого вопроса п.1, зафиксирован СА):
- poll_token — многоразовый неперебираемый идентификатор опроса
  (secrets.token_urlsafe(32), 256 бит энтропии): ТОЛЬКО чтение статуса,
  НЕ потребляется, действителен до и после решения (чтение статуса не
  дает прав — read-only эндпоинт);
- exchange_token — одноразовый неперебираемый токен обмена: при approved
  обменивается на СУЩЕСТВУЮЩУЮ сессию users (роль instructor);
  потребляется той же транзакцией (UPDATE … SET exchange_token = NULL);
  повторный обмен/чужой токен → 404-неразличение; при НЕУДАЧНОМ обмене
  токен сохраняется — повтор возможен на следующем тике (FR-81).

Порядок обмена (POST /api/instructors/application-exchange):
1. SELECT заявки по exchange_token (параметризованный); нет/потреблен →
   404-неразличение.
2. Guard: status='approved' (симметрично guard'ам модерации) — иначе 409.
3. Строка users СУЩЕСТВУЕТ: создана approve (instructor_admin.py —
   INSERT users + UPDATE статуса одной транзакцией; email заявки = email
   users). Вырожденный случай «approved без users» (вне контракта
   модерации) → 409, экран остается в waiting.
4. Сессия — фабрика auth.py (единый реестр _sessions, TTL 12 ч;
   переиспользование _session_issue — при необходимости экспорт в
   публичную фабрику в границах задачи, МЕХАНИКА не меняется).
5. UPDATE exchange_token = NULL — потребление фиксируется той же
   транзакцией БД; отказ транзакции → сессия не считается выданной
   (повтор обмена возможен).
Ответ — форма ответа логина: {ok:true, token, route:'cabinet'} — фронт
переиспользует механику маршрутизации логина (route 'cabinet' →
/instructor/dashboard; sessionStorage 'session_token' — ключ api.js
TOKEN_KEY). FR-81 («сессия users создана, роль instructor», без ввода
пароля) выполняется: сессия выдается по одноразовому неперебираемому
токену, а не по учетным данным.

## Модель данных (NFR-11…24; DDL уточняет dev в границах)

ALTER TABLE instructor_applications (idempotent-миграция механики db.py:
guard по pragma table_info; init_db через lifespan — существующий volume):

- `poll_token TEXT` — идентификатор опроса; частичный UNIQUE-индекс
  (WHERE poll_token IS NOT NULL) — точечный параметризованный SELECT;
- `exchange_token TEXT` — одноразовый токен обмена; частичный
  UNIQUE-индекс (WHERE exchange_token IS NOT NULL) — защита от дублей и
  точечный lookup.

Правила:

- Генерация — secrets.token_urlsafe(32) (тот же генератор, что у сессий
  Спринта 1): 256 бит энтропии — неперебираемость NFR-28; коллизия
  (перекрытие индекса) — регенерация до вставки, вероятность пренебрежима.
- Токены выдаются ОДИН РАЗ — при создании заявки (apply); poll_token НЕ
  ротируется и НЕ потребляется чтениями; exchange_token потребляется
  обменом (NULL) и не восстанавливается.
- Backfill НЕТ: существующие строки остаются NULL → экран для них в
  прежнем статичном режиме (статус по логину — как сегодня, FR-80).
  Обоснование: токен ценен только если выдан заявителю при сабмите;
  историческим заявителям выдать его некому.
- Токены в логах ЗАПРЕЩЕНЫ (наследование стиля NFR-3/NFR-10): poll_token
  передается заголовком X-Poll-Token, exchange_token — телом POST; в URL
  НЕ пишутся — access-логи (path+query) токенов не содержат.

## Эндпоинты (методы / роли / валидации)

Формат ответов — механика Спринтов 1–8: 200 {ok:true, …}; ошибки
{ok:false, error:"<по-русски>"}; 404-неразличение — как в контурах
Спринта 3+. SQL параметризованный (NFR-10).

| Метод и путь | Роль | Валидации / поведение |
|---|---|---|
| POST /api/instructors/apply | гость | БЕЗ ИЗМЕНЕНИЙ контракта валидаций; РАСШИРЕНИЕ УСПЕШНОГО ответа: {ok:true, poll_token, exchange_token} (новые поля — старые потребители игнорируют, NFR-27); при 422 (ошибка валидации/дубль email) токены НЕ выдаются и заявка не создается |
| GET /api/instructors/application-status | гость по X-Poll-Token | заголовок отсутствует/пуст → 422; заявки по poll_token нет → 404-неразличение (одинаковый ответ для «чужой» и «несуществующий», NFR-28); найдено → одиночный SELECT по индексу, БЕЗ записи и побочных эффектов (NFR-28): {ok:true, status:'waiting'|'approved'|'rejected', reason:string|null} — внутренний статус 'deny' маппится в 'rejected', reason = review_comment ТОЛЬКО при rejected (при waiting/approved reason=null); статус при approved после выдачи сессии НЕ меняется (approved — терминальный) |
| POST /api/instructors/application-exchange | гость по body | body {exchange_token}: нет/пусто → 422; токен не найден/уже потреблен (NULL) → 404-неразличение; guard status='approved' → иначе 409 {ok:false}; успех → сессия фабрикой auth.py (единый реестр, TTL 12 ч, роль instructor через строку users) + UPDATE exchange_token=NULL одной транзакцией; ответ {ok:true, token, route:'cabinet'} — форма ответа логина |

## Машина состояний экрана ожидания (FR-80…FR-83, NFR-28)

```
  нет токенов в localStorage
        └──────────────────────────► STATIC: прежний экран, запросов НЕТ (FR-80)
 anketa 200: apply.js кладет токены
        │
        ▼
  POLLING (waiting): первый тик — сразу при загрузке,
        далее тик каждые 12 с ПОСЛЕ завершения предыдущего запроса
        (наложения запросов нет; допустимый диапазон 10–15 с, решение 12 с)
        │
        ├── status waiting ──► следующий тик через 12 с; экран «на рассмотрении»
        │
        ├── status approved ─► POST application-exchange (exchange_token)
        │                        ├─ ok ──► sessionStorage 'session_token' = token
        │                        │        (механика api.js) → редирект route
        │                        │        'cabinet' → /instructor/dashboard;
        │                        │        polling ОСТАНОВЛЕН (терминальное)
        │                        └─ ошибка (409/сеть) ─► экран остается в
        │                                 waiting, опрос ПРОДОЛЖАЕТСЯ (FR-81)
        │
        └── status rejected ─► sessionStorage 'instructor_rejected_reason' =
                                 reason → /instructors/rejected (тот же экран
                                 и механика, что после логина route 'rejected',
                                 Спринт 2; БЕЗ входа, FR-82);
                                 polling ОСТАНОВЛЕН (терминальное)

  ОСТАНОВКА/ПАУЗА (FR-83, NFR-28):
  visibilitychange → hidden: запросы прекращаются НЕМЕДЛЕННО (нет тика,
    уже ушедшего в полете запроса не отменяем — ответ игнорируется после
    возврата, если статус уже получен);
  visibilitychange → visible: опрос возобновляется ПО ОБЫЧНОМУ ГРАФИКУ
    (БЕЗ немедленного тика — бюджет ≤5/мин держится при частом
    переключении вкладок);
  pagehide / beforeunload: таймер снят — фоновых таймеров, переживающих
    страницу, НЕТ;
  сетевая ошибка тика: пользователь ничего не видит (без всплывающих
    ошибок), следующий тик через те же 12 с — БЕЗ учащения и без backoff-
    экспонент (FR-83, NFR-28).
```

Бюджет NFR-28 (математика): первый тик t=0, далее 12/24/36/48/60… — в
любом скользящем окне 60 с максимум 5 запросов → «не более 5 запросов в
минуту» выполняется и при немедленном первом тике. Латентность
отображения смены статуса — не позднее одного интервала (≤15 с) после
решения админа при видимом экране (NFR-28).

## Переход waiting → rejected: переиспользование экрана отказа (решение СА)

Причина отказа показывается БЕЗ входа переходом на СУЩЕСТВУЮЩИЙ экран
/instructors/rejected с передачей причины через sessionStorage
'instructor_rejected_reason' — ТО ЖЕ, что делает логин при route
'rejected' (frontend/js/landing.js:56). Обоснование: единый путь показа
отказа (логин и опрос ведут на один экран — заявитель видит одно и то же
независимо от способа проверки), ноль нового UI, существующие сценарии
экрана отказа (нейтральный текст при пустом комментарии — поведение
Спринта 2) сохраняются. Альтернатива «rejected-состояние инлайн на
Vue-странице ожидания» отвергнута: дублирование экрана отказа и второй
путь показа причины. FR-82 соблюден: статус и причина видны без входа и
перелогина; пустой/исторический комментарий → нейтральный текст отказа.

## Видимость и доступ — матрица

| Поверхность | Кто видит |
|---|---|
| Статус заявки (waiting/approved/rejected) | только носитель poll_token (идентификатор выдан заявителю при сабмите, неперебираем) |
| Причина отказа (review_comment) | только носитель poll_token того же контура (это сам заявитель); 404-неразличение не раскрывает существование чужих заявок |
| Обмен на сессию | только носитель exchange_token при approved; сессия role='instructor' — та же модель, что логин |
| Контур модерации (approve/deny) | только X-Admin-Token — БЕЗ ИЗМЕНЕНИЙ |

Правила реализации: проверки — на сервере при каждом запросе
(поиск по токену из заголовка/тела, НЕ из URL); UI-скрытие проверкой не
считается; отказ — 404-неразличение (NFR-28, наследование NFR-7).

## Обработка ошибок (сводка)

| Ситуация | Ответ | Требование/решение |
|---|---|---|
| GET статуса без/с пустым X-Poll-Token | 422 {ok:false} | контракт формата запроса |
| Чужой/несуществующий poll_token | 404-неразличение {ok:false} | NFR-28 |
| POST обмена без/с пустым exchange_token | 422 {ok:false} | контракт формата запроса |
| Чужой/несуществующий/уже потребленный exchange_token | 404-неразличение {ok:false} | одноразовость, решение СА |
| Обмен при статусе ≠ approved (waiting/rejected) | 409 {ok:false} | guard, симметричен модерации |
| Вырожденное «approved без строки users» | 409 {ok:false} | вне контракта модерации; экран остается в waiting (FR-81) |
| Сетевая ошибка тика на экране | без ответа пользователю, тик через 12 с | FR-83, NFR-28 |
| 422 apply (валидация/дубль email) | заявка не создана, токены не выдаются | наследование Спринта 2 |

## Решения по НФТ

- NFR-28: интервал 12 с (диапазон 10–15) — 5 тиков в скользящем окне
  60 с максимум (математика выше); после ухода запросов нет; при
  сетевой ошибке интервал не уменьшается; эндпоинт — только чтение
  (одиночный SELECT по индексу, без записи и побочных эффектов);
  poll_token/exchange_token — случайные 256-битные (token_urlsafe(32))
  — перебор невозможен; чужой/несуществующий — 404-неразличение;
  латентность отображения — ≤1 интервала.
- NFR-27 (совместимость): apply расширяется ДОБАВЛЕНИЕМ полей в
  успешный ответ (контракт не ломается); login/logout/me, контур
  модерации, /api/instructor/* и прочие префиксы — без изменений;
  существующие Playwright e2e (49 сценариев) сохраняются без правок —
  сценарий «анкета → /instructors/pending» проходит на мигрированной
  странице (проверка — задачи сборки/приемки).
- NFR-11…24 (наследование): миграция idempotent механикой db.py на
  существующем volume (init_db через lifespan); параметризованный SQL во
  всех новых запросах; токены/причины/пароли в логах не фигурируют
  (poll_token в заголовке, exchange_token в теле — URL чист);
  формат ошибок {ok:false}; single-worker/in-memory — наследованные
  ограничения, не revisiting (сессии после рестарта процесса теряются —
  как и сегодня для логина; на контракт блока 2 не влияет: экран
  продолжает опрос, перелогин не требуется).
- NFR-26 (бюджеты чанков) — объем каркаса add-vue-framework-pilot;
  интерфейс с этим пакетом: страница ожидания не добавляет библиотек
  сверх каркаса (polling — свой код на Vue, без новых зависимостей).

## Сознательные ограничения (задокументированы)

- Показ номера заявки на экране ожидания (открытый вопрос п.4) — НЕ в
  объеме; ответ статуса не содержит номера (решение за ПМ отдельно).
- Ротация/отзыв poll_token, «отвязать экран» — точки расширения (не Must).
- Серверный rate-limit опроса — точка расширения: бюджет NFR-28 —
  контракт клиента, проверяется тестами/приемкой.
- Опрос исторических заявок (NULL-токены) — не реализуется (см. модель
  данных); их путь — логин, как сегодня.
- Уведомления о смене статуса — backlog.
- Сессии in-memory с TTL 12 ч — наследуемое ограничение; повторный
  вход по сессии после рестарта сервиса не гарантируется (как и
  сегодня), на контракт опроса не влияет.

## Соответствие ADR/карте архитектуры

Отступлений нет: новые маршруты — под существующим префиксом
/api/instructors/* (до-сессионный контур заявителя); сессионная модель,
формат ошибок, миграционная механика, каталог data/uploads — без
изменений (uploads не затрагивается); никаких новых файлов статики вне
каркаса Vue (объем add-vue-framework-pilot). ADR по механизму обмена —
в границах этого design.md; карта архитектуры/ADR-каталог обновляются
архитектором при ревью пакета (вне этого пакета).
