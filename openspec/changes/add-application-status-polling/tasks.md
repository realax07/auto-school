## 1. Миграция + выдача неперебираемых токенов при apply (backend)

- [x] 1.1 [P] [migration][code] backend/db.py + backend/instructors.py —
      ALTER TABLE instructor_applications: колонки poll_token TEXT и
      exchange_token TEXT (частичные UNIQUE-индексы WHERE … IS NOT NULL);
      idempotent-миграция механики db.py (guard pragma table_info;
      init_db через lifespan — существующий volume); backfill НЕ делается
      (исторические строки NULL → статичный режим экрана). POST
      /api/instructors/apply: генерация poll_token и exchange_token
      (secrets.token_urlsafe(32), регенерация при коллизии индекса),
      запись в заявку той же транзакцией, расширение успешного ответа
      {ok, poll_token, exchange_token} (обратно-совместимо — старые
      потребители игнорируют новые поля, NFR-27); при 422 (валидация/
      дубль email) — заявка не создана, токены не выдаются;
      IntegrityError РАЗВЕДЕН по веткам (MIN-2, по сообщению/имени
      индекса): гонка дубля email (UNIQUE email, Спринт 2) → 422 БЕЗ
      регенерации токенов, коллизия токена (частичный UNIQUE) →
      регенерация + повторная вставка БЕЗ 422 (смешение веток
      недопустимо — гонка email не должна уходить в цикл регенерации);
      токены в логи не пишутся.
      Готовность: тесты — apply 200 содержит оба токена, оба
      сохранены в заявке, токены двух заявок не совпадают и имеют
      достаточную длину/энтропию (неперебираемость); 422 apply токенов
      не выдает; параллельный дубль email → 422 (заявка одна, цикла
      регенерации нет) и коллизия токена → регенерация, заявка создана
      (MIN-2 — оба исхода IntegrityError); миграция на предсозданной
      БД со старыми заявками:
      колонки есть, старые строки NULL, повторный запуск ничего не
      меняет; существующий e2e «анкета → /instructors/pending» зелен
      без правок сценария.
      FR: FR-80. NFR: NFR-27, NFR-28 (неперебираемость), NFR-11…24.
      Зависит от: —.

## 2. Эндпоинт статуса (read-only) + обмен токена на сессию (backend)

- [x] 2.1 [P] [code] НОВЫЙ backend/application_status.py + include в
      backend/app.py — GET /api/instructors/application-status
      (заголовок X-Poll-Token: нет/пуст → 422; заявки нет →
      404-неразличение, одинаковый для «чужой»/«несуществующий»;
      успех — одиночный параметризованный SELECT по индексу, БЕЗ записи
      и побочных эффектов: {ok, status:'waiting'|'approved'|'rejected',
      reason} — внутренний 'deny' маппится в 'rejected', reason =
      review_comment ТОЛЬКО при rejected, иначе null) и POST
      /api/instructors/application-exchange (body {exchange_token}:
      нет/пуст → 422; не найден/уже потреблен → 404-неразличение;
      guard status='approved' → иначе 409; успех — сессия фабрикой
      auth.py (единый реестр _sessions, TTL 12 ч, роль instructor по
      строке users; вырожденное «approved без users» → 409) +
      УСЛОВНЫЙ UPDATE exchange_token = NULL WHERE exchange_token = ? +
      проверка rowcount — атомарное потребление одной транзакцией
      (паттерн MIN-1 Спринта 8): rowcount = 0 — токен уже потреблен, в
      том числе параллельным обменом → 404, сессия не выдается;
      ответ
      {ok, token, route:'cabinet'} — форма ответа логина). Контракты —
      design.md (таблицы эндпоинтов, «Решение СА»).
      Готовность: тесты — статусы waiting/approved/rejected('deny'+причина)
      по токену; чтение НЕ меняет заявку (status/created_at/токены
      неизменны после N чтений — только чтение); чужой/несуществующий
      poll_token и exchange_token → одинаковый 404; обмен при approved
      выдает рабочую сессию (GET /api/auth/me → role instructor),
      exchange_token потреблен (повторный обмен → 404); два
      параллельных обмена одним валидным токеном — ровно один 200,
      второй 404 (MIN-1: одноразовость — ровно один исход); обмен при
      waiting/rejected → 409; пустые заголовок/токен → 422.
      FR: FR-80, FR-81, FR-82, NFR-28. NFR: NFR-10, NFR-7, NFR-27.
      Зависит от: 1.1 (контракт колонок).
