# Delta: instructor-auth

## ADDED Requirements

### Requirement: Вход инструктора через общий механизм авторизации

Вход инструктора MUST выполняться по логину (email) и паролю через
существующий /api/auth/login — тот же механизм проверки пароля (bcrypt),
сессий и единого сообщения об отказе, что у учеников (Спринт 1). Анти-брутфорс
защита входа действует для инструкторов так же, как для учеников (трассировка:
FR-13).

Источник: requirements-instructor-flow.md FR-13.

#### Scenario: Вход одобренного инструктора

- **GIVEN** заявка одобрена, пользователь с email E и хэшем пароля P существует в users
- **WHEN** он входит по email E и паролю P через /api/auth/login
- **THEN** вход успешен, сессия выдана

#### Scenario: Единое сообщение при отсутствии и пользователя, и заявки

- **GIVEN** email X отсутствует и в users, и в заявках
- **WHEN** выполняется вход по email X с любым паролем
- **THEN** система выдает то же единое сообщение об отказе входа, что и при неверных учетных данных ученика (текст и код ответа идентичны), сессия не выдается

#### Scenario: Неверный пароль отклоняется единым сообщением

- **GIVEN** одобренный инструктор с email E и паролем P существует
- **WHEN** выполняется вход по email E с неверным паролем
- **THEN** система выдает то же единое сообщение об отказе входа, сессия не выдается

### Requirement: Роутинг после входа по статусу

После успешной проверки пароля система MUST направлять пользователя по
состоянию его учетной записи/заявки: пользователь существует (заявка
approved) → заглушка личного кабинета /instructor/cabinet-stub («кабинет
скоро»); заявка в статусе waiting → экран ожидания /instructors/pending;
заявка в статусе deny → экран отказа /instructors/rejected с причиной
(комментарием из админки) (трассировка: FR-13).

Источник: requirements-instructor-flow.md FR-13.

#### Scenario: Пользователь найден — заглушка кабинета

- **GIVEN** заявка одобрена, пользователь с email E существует в users
- **WHEN** он успешно входит по email E и паролю
- **THEN** он попадает на /instructor/cabinet-stub с заглушкой «кабинет скоро»

#### Scenario: Заявка waiting — экран ожидания

- **GIVEN** отправлена заявка с email E (статус waiting, записи в users нет)
- **WHEN** выполняется вход по email E с паролем из анкеты
- **THEN** пользователь попадает на экран ожидания /instructors/pending («заявка на рассмотрении»), сессия не выдается

#### Scenario: Заявка deny — экран отказа с причиной

- **GIVEN** заявка с email E отклонена администратором с комментарием C
- **WHEN** выполняется вход по email E с паролем из анкеты
- **THEN** пользователь попадает на экран отказа /instructors/rejected, на котором видна причина отказа C; сессия не выдается

#### Scenario: Статусный экран недоступен без проверки пароля

- **GIVEN** существует заявка в статусе deny с комментарием C
- **WHEN** выполняется попытка открыть /instructors/rejected напрямую (без входа с паролем)
- **THEN** причина отказа C не раскрывается: прямой доступ к статусному экрану без успешной проверки логина/пароля не показывает данные заявки

### Requirement: Заглушка кабинета инструктора

Страница /instructor/cabinet-stub MUST показывать заглушку «кабинет скоро» и
MUST NOT содержать функциональность кабинета инструктора (макет
dashboard-instructor.html — следующий объем). Доступ к странице — только с
действующей сессией, полученной входом; без сессии — возврат на вход
(трассировка: FR-13, ограничение ТЗ).

Источник: requirements-instructor-flow.md FR-13; раздел «Ограничения».

#### Scenario: Заглушка вместо кабинета

- **GIVEN** одобренный инструктор успешно вошел в систему
- **WHEN** он попадает на /instructor/cabinet-stub
- **THEN** отображается заглушка «кабинет скоро»; функциональные элементы кабинета (расписание, статистика, доходы) отсутствуют

#### Scenario: Страница заглушки без сессии отклоняется

- **GIVEN** пользователь не выполнял успешный вход
- **WHEN** он открывает /instructor/cabinet-stub напрямую
- **THEN** страница не открывается — пользователь возвращается на вход (как в механизме защиты кабинета ученика)
