# Delta: admin-moderation

## ADDED Requirements

### Requirement: Раздел заявок инструкторов в админке

В админ-панели MUST появиться раздел «Заявки инструкторов»: таблица всех
заявок с данными анкеты; клик по строке открывает действия «Одобрить» и
«Отклонить». Доступ — только с валидным админ-токеном (X-Admin-Token);
без него — отказ как неавторизованный. bcrypt-хэш пароля хранится в заявке,
но не выдается API и не отображается в UI (решение Заказчика
2026-10-12-hash-not-rendered; трассировка: FR-14).

Источник: requirements-instructor-flow.md FR-14; decisions/2026-10-12-hash-not-rendered.md.

#### Scenario: Администратор видит все заявки

- **GIVEN** администратор вошел в админку (валидный админ-токен) и в системе есть заявки со статусами waiting, approved и deny
- **WHEN** он открывает раздел «Заявки инструкторов»
- **THEN** таблица показывает все заявки (включая уже обработанные) с данными анкеты; password_hash в ответе API и в UI отсутствует (хэш хранится в заявке, но не выдается и не рендерится; ответ GET не логируется)

#### Scenario: Клик по строке открывает действия

- **GIVEN** в таблице заявок есть хотя бы одна заявка
- **WHEN** администратор нажимает на строку заявки
- **THEN** становятся доступны действия «Одобрить» и «Отклонить»

#### Scenario: Доступ без админ-токена отклоняется

- **GIVEN** у клиента нет валидного админ-токена (отсутствует, неизвестен, истек)
- **WHEN** выполняется запрос списка заявок или действия над заявкой
- **THEN** система отвечает отказом как неавторизованный, данные заявок не выдаются, действия не выполняются

### Requirement: Отклонение заявки с обязательным комментарием

Действие «Отклонить» MUST требовать обязательный комментарий (причину);
без комментария действие MUST быть недоступно. При отклонении статус заявки
меняется на deny, комментарий сохраняется и в дальнейшем показывается
инструктору при входе (см. домен instructor-auth, FR-13) (трассировка: FR-15).

Источник: requirements-instructor-flow.md FR-15.

#### Scenario: Отклонение без комментария недоступно

- **GIVEN** администратор выбрал заявку в статусе waiting и нажал «Отклонить»
- **WHEN** поле комментария пусто
- **THEN** действие отклонения недоступно/не выполняется, статус заявки остается waiting

#### Scenario: Отклонение с комментарием

- **GIVEN** администратор выбрал заявку в статусе waiting и ввел комментарий C
- **WHEN** он подтверждает «Отклонить»
- **THEN** статус заявки становится deny, комментарий C сохраняется в заявке

#### Scenario: Повторное отклонение не меняет уже сохраненную причину

- **GIVEN** заявка уже в статусе deny с комментарием C
- **WHEN** администратор просматривает заявку
- **THEN** сохраненная причина C остается доступной (не теряется при последующих действиях в админке)

#### Scenario: Отклонение не-waiting заявки отклоняется сервером

- **GIVEN** заявка в статусе approved (создана запись users role='instructor') или уже deny
- **WHEN** выполняется прямой POST deny с валидным админ-токеном (кнопка в UI скрыта, API-защита — guard статуса)
- **THEN** сервер отвечает 409 («Заявка уже одобрена» / «Заявка уже отклонена»), статус заявки НЕ меняется, запись users остается без изменений (рассинхрон исключен; симметрично guard approve)

### Requirement: Одобрение заявки создает пользователя

Действие «Одобрить» MUST создавать пользователя в users из данных заявки
(email и уже готовый bcrypt-хэш из заявки) и менять статус заявки на
approved. Повторное одобрение MUST быть недоступно (кнопка скрыта для
уже одобренной заявки) (трассировка: FR-16).

Источник: requirements-instructor-flow.md FR-16.

#### Scenario: Одобрение заявки waiting

- **GIVEN** заявка в статусе waiting с email E и bcrypt-хэшем H
- **WHEN** администратор нажимает «Одобрить»
- **THEN** в users создается запись с email E и password_hash H, статус заявки становится approved

#### Scenario: Одобренная заявка не одобряется повторно

- **GIVEN** заявка в статусе approved
- **WHEN** администратор открывает заявку
- **THEN** действие «Одобрить» недоступно (кнопка скрыта); повторного создания пользователя не происходит

#### Scenario: Вход одобренного инструктора с паролем из анкеты

- **GIVEN** заявка одобрена, в users создан пользователь с хэшем, перенесенным из заявки
- **WHEN** инструктор входит по email и паролю, указанному в анкете
- **THEN** вход успешен (проверка пароля против перенесенного хэша)

### Requirement: Созданный пользователь получает роль инструктора

При одобрении созданная запись в users MUST помечаться ролью инструктора,
отличимой от роли ученика (ученики, созданные регистрацией Спринта 0,
сохраняют роль ученика) (трассировка: FR-16, ограничение ТЗ о разделе
«ученик/инструктор»).

Источник: requirements-instructor-flow.md, раздел «Ограничения»;
FR-16.

#### Scenario: Роль одобренного инструктора отличима от роли ученика

- **GIVEN** одобрена заявка с email E, и существует ученик, зарегистрированный через /api/register
- **WHEN** сравниваются записи users обоих
- **THEN** запись инструктора помечена ролью инструктора, запись ученика — ролью ученика
