# Delta: instructor-application

## ADDED Requirements

### Requirement: Лендинг инструкторов по прямой ссылке

Страница /instructors MUST быть доступна по прямой ссылке без авторизации и
MUST соответствовать утвержденному макету landing-instructors.html; кнопки
CTA лендинга MUST вести на анкету заявки /instructors/apply (трассировка:
FR-10).

Источник: requirements-instructor-flow.md FR-10.

#### Scenario: Прямой переход по ссылке

- **GIVEN** сервис запущен
- **WHEN** пользователь открывает /instructors по прямой ссылке без авторизации
- **THEN** отдается лендинг инструкторов, соответствующий макету landing-instructors.html

#### Scenario: CTA ведут на анкету

- **GIVEN** открыт лендинг /instructors
- **WHEN** пользователь нажимает кнопку CTA («Стать инструктором» / выбор формата работы)
- **THEN** выполняется переход на страницу анкеты /instructors/apply

### Requirement: Анкета заявки инструктора

Страница /instructors/apply MUST соответствовать макету
registration-instructor.html и MUST собирать: ФИО, телефон, email, адрес
фактического проживания, формат работы (свой авто / авто Сбера),
государственный номер (если свой автомобиль), номер и дату выдачи ВУ,
категорию прав, стаж вождения, пароль и подтверждение пароля. Обязательные
поля — отмеченные звездочкой в макете, плюс пароль и подтверждение
(трассировка: FR-11).

Источник: requirements-instructor-flow.md FR-11.

#### Scenario: Анкета соответствует макету и собирает все поля

- **GIVEN** пользователь открыл /instructors/apply
- **WHEN** страница отображается
- **THEN** на форме есть поля ФИО, телефон, email, адрес, переключатель формата работы (свой авто / авто Сбера), госномер (виден/активен при «свой автомобиль»), номер ВУ, дата выдачи ВУ, категория, стаж, пароль, подтверждение пароля; обязательность полей соответствует отметкам звездочкой макета плюс пароль с подтверждением

#### Scenario: Переключение формата работы меняет доступность госномера

- **GIVEN** открыта анкета /instructors/apply
- **WHEN** выбран формат «автомобиль Сбера»
- **THEN** поле госномера становится недоступным для ввода (по поведению макета); при возврате на «свой автомобиль» поле снова доступно

### Requirement: Сохранение заявки со статусом waiting

Отправка корректно заполненной анкеты MUST создавать заявку инструктора со
статусом waiting и переводить пользователя на экран ожидания
/instructors/pending (трассировка: FR-12).

Источник: requirements-instructor-flow.md FR-12.

#### Scenario: Успешная отправка анкеты

- **GIVEN** анкета /instructors/apply заполнена корректно (все обязательные поля, пароли совпадают, email свободен)
- **WHEN** пользователь отправляет анкету
- **THEN** создается заявка со статусом waiting и всеми введенными данными, и пользователь попадает на экран ожидания /instructors/pending («заявка на рассмотрении»)

#### Scenario: Отклонение анкеты с email существующего пользователя

- **GIVEN** в системе существует пользователь с email E (users)
- **WHEN** отправляется анкета с email E и корректными остальными данными
- **THEN** заявка НЕ создается, пользователь видит единое сообщение об ошибке отправки, экран ожидания не показывается

#### Scenario: Отклонение некорректно заполненной анкеты

- **GIVEN** анкета заполнена с пустым обязательным полем, или несовпадающими паролем/подтверждением, или коротким паролем
- **WHEN** пользователь отправляет анкету
- **THEN** заявка НЕ создается, показывается сообщение с указанием первой ошибки валидации

### Requirement: Хранение пароля заявки только в виде bcrypt-хэша

Пароль из анкеты MUST храниться только как bcrypt-хэш (тот же механизм, что
регистрация ученика: cost не ниже 12); открытый пароль MUST NEVER сохраняться
в хранилище и MUST NEVER попадать в логи. Хэш сохраняется в самой заявке и
при одобрении переносится в users без повторного хэширования (трассировка:
FR-11.1).

Источник: requirements-instructor-flow.md FR-11.1.

#### Scenario: В заявке хранится только хэш

- **GIVEN** отправлена анкета с паролем P
- **WHEN** выполняется прямой просмотр записи заявки и журналов сервиса
- **THEN** строка P отсутствует и в записи заявки, и в логах; в заявке хранится только bcrypt-хэш

#### Scenario: Одобренная заявка переносит хэш без повторного хэширования

- **GIVEN** заявка содержит bcrypt-хэш пароля P, отправленного при регистрации заявки
- **WHEN** администратор одобряет заявку
- **THEN** пользователь в users создается с тем же значением хэша (значение хэша в users совпадает со значением в заявке), и вход с паролем P по /api/auth/login успешен

### Requirement: Данные ВУ-файла не сохраняются

Загрузка файла ВУ в анкете НЕ выполняется: элемент присутствует как
визуальный (соответствие макету), файл НЕ сохраняется, факт отправки анкеты
фиксируется без файла. Система SHALL NOT запрашивать, принимать или хранить
файл ВУ (трассировка: FR-11, ограничение ТЗ).

Источник: requirements-instructor-flow.md, раздел «Ограничения».

#### Scenario: Файл не загружается на сервер

- **GIVEN** открытая анкета /instructors/apply
- **WHEN** пользователь выбирает файл ВУ и отправляет анкету
- **THEN** файл не сохраняется системой, заявка создается без него (поле файла не входит в данные заявки)
