## 2. Major-замечания

### MAJ-1: instructor_applications.email без UNIQUE — проверка apply осталась без второй линии защиты

- Факт: design.md «Модель данных» и sdd.md §16 задают email TEXT NOT NULL
  без UNIQUE; защита дубликата — только SELECT-проверки в /api/instructors/apply
  (шаги 8–9). Собственный принцип пакета нарушен: «users.email остается
  UNIQUE — вторая линия защиты после SELECT-проверки (та же механика
  register.py)». В register.py второй линией действительно служит
  UNIQUE + catch sqlite3.IntegrityError (register.py:104); в apply — ловить
  нечего, INSERT пройдет.
- Гонка реальна: uvicorn single-worker исполняет sync-хендлеры в threadpool —
  два одновременных сабмита одной анкеты проходят SELECT до чужого INSERT,
  и обе заявки waiting создаются на один email.
- Риск: вход waiting-инструктора (sdd §15.5) делает SELECT по email и
  fetchone — строка выбирается недетерминированно из двух; deny одной заявки
  не меняет статус второй — инструктор с отказом видит экран ожидания
  (нарушение FR-13). Плюс две строки учетных хэшей на один email.
- Требование: в design.md и sdd.md §16 добавить
  `email TEXT NOT NULL UNIQUE` в CREATE TABLE instructor_applications;
  в контракте §15.1 и задаче 1.1 — обработка sqlite3.IntegrityError как
  той же контрактной 422 «Email: уже зарегистрирован» (симметрично
  register.py); в задаче 1.2 — тест гонки (два apply одного email
  параллельно → ровно одна заявка).

## 3. Minor-замечания

### MIN-1: deny без статусного guard — одобренную заявку можно «отклонить» через API

sdd §15.4 меняет статус на deny без проверки текущего. Кнопка в UI скрыта,
но прямой POST с валидным админ-токеном переводит approved-заявку в deny,
оставляя запись users role='instructor' (рассинхрон). Требование: guard
«только waiting, иначе 409» симметрично approve (sdd §15.3) + сценарий в
спеке admin-moderation.

### MIN-2: обязательный чекбокс согласия макета не попал в контракт анкеты

В registration-instructor.html чекбокс «Я подтверждаю… обработку персональных
данных» отмечен звездочкой и required. FR-11: «Обязательные поля — по макету
(со звездочкой) + пароль». В sdd §15.1 и задаче 1.1 списка обязательных полей
чекбокса нет. Требование: либо включить согласие в обязательную валидацию
(буквальное прочтение FR-11), либо зафиксировать в proposal обратную
интерпретацию отдельным допущением с эскалацией ПМ→Заказчик — сейчас это
тихое расхождение спеки с ТЗ.

### MIN-3: approve — INSERT в users и UPDATE статуса не зафиксированы как одна транзакция

sdd §15.3 описывает последовательность, но не атомарность. При падении между
INSERT и UPDATE заявка остается waiting при существующем пользователе:
повторный approve даст 409 «Email: уже зарегистрирован» — админ не сможет
завершить операцию. Требование: одна транзакция (INSERT + UPDATE + commit,
симметрично register.py) — одна строка в design.md «Поток 2» и sdd §15.3.

### MIN-4: роль не проверяется серверно; /api/auth/me не возвращает role

Роутинг по role — только на фронте (§15.5); /api/auth/me (§10.3) роль не
отдает, поэтому сессия ученика проходит проверку 401 и на
/instructor/cabinet-stub. Для заглушки без данных — приемлемо, но решение
надо зафиксировать явно (design.md «Поток 4» + техдолг map.md): при
реальном кабинете инструктора — обязательная серверная проверка роли
(require_session + role) и ключ role в /api/auth/me.

### MIN-5: возражение архитектора по FR-14 (хэш в выдаче админ-API) — исполняем, риск фиксируем

Решение Заказчика (FR-14: таблица заявок «включая bcrypt-хэш») худшее
альтернативы, но исполнимо: bcrypt необратим, админ и так создан иметь
данные заявок. Объективное возражение (роль 2 architect_agent): хэш не нужен
для принятия решения о заявке и не должен рендериться в UI как обычное поле
— минимизируйте поверхность (не показывать/скрыть за действием, не копировать
в буфер, не логировать ответ GET). Возражение передать ПМ Заказчику вместе с
этим ревью; в реализацию — без изменения контракта, но с запретом вывода хэша
в access-логи (NFR-3). Зафиксировано в ADR-003.

## 4. Проверка фокусов задачи (безопасность и консистентность)

- Хэш bcrypt в заявке (доступ админа, логи): хранение хэша в заявке —
  решение Заказчика (FR-11.1 дословно), альтернатив, не нарушающих ТЗ,
  нет (research.md §1 корректно отклонил открытый пароль и повторный ввод).
  Риски доступа админа и логов — MIN-5 и NFR-3-контроль задачи 6.1
  (password_hash выдается только админ-API; тест логов). После deny хэш
  остается в отклоненной заявке (уснувший credential-материал) — принято,
  зафиксировано в ADR-003 «Последствия»; возврат к вопросу (обнуление хэша
  обработанных заявок) — при первом изменении требований FR-14.
- IntegrityError-гонки при approve: покрыты пакетом (409 от UNIQUE,
  design «Поток 2», sdd §15.3, задача 2.1) — с оговоркой MIN-3 о
  транзакционности. Гонка apply — НЕ покрыта (MAJ-1).
- Разделение ролей ученик/инструктор: флаг role в users — корректен
  (research §2; ADR-002 явно откладывал колонку до появления второго типа
  учеток — момент настал, противоречия с ADR-002 нет, это его оговоренное
  развитие). Ученики Спринтов 0–1 накрываются дефолтом 'student' (additive
  миграция, тест задачи 1.2). Дыра серверной проверки роли — MIN-4.

## 5. Согласованность со смежными артефактами

- sdd.md §15–19 стилистически и структурно продолжают §3/§9–14; механизм
  §10.1 переиспользуется без изменения (анти-брутфорс, единое сообщение,
  фиктивная bcrypt-проверка — расширены на проверку против заявок, тайминг
  сохранен).
- Ответ login дополняется ключом route/reason без ломания контракта
  Спринта 1 (обратная совместимость оговорена в §15.5).
- Контракт 7 (карта): изменение контракта /api/auth/login — additive,
  оформлено внутри дельты, отдельной не требует.
- ADR-002 «колонка role — отложено до спринта водителей» — актуализируется
  ADR-003 (роль появляется раньше водителей, по другому поводу); противоречие
  не блокирующее, ADR-002 остается историей решений на свою дату.
