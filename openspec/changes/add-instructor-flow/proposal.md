# Change: add-instructor-flow

## Why (Зачем)

Спринт 2, часть 1: поток подключения инструктора. Сейчас инструктор не может
ни оставить заявку, ни отслеживать ее статус — платформа обслуживает только
учеников (Спринты 0–1). Нужны: лендинг инструкторов (прямая ссылка), анкета
заявки, модерация заявок в админке (одобрить/отклонить с причиной) и экраны
ожидания/отказа после входа по логину/паролю.

Источник требований: `requirements-instructor-flow.md` (УТВЕРЖДЕН,
FR-10…FR-17 + FR-11.1, NFR-2…NFR-4, все Must). Дословное ТЗ Заказчика —
`decisions/2026-10-12-instructor-flow-create-change.md`.

## What Changes (Что меняет)

Новые возможности (все — ADDED; существующие домены registration/auth/cabinet/
admin Спринтов 0–1 поведением для учеников не меняются):

- Домен `instructor-application`:
  - лендинг инструкторов по прямой ссылке /instructors (мокап
    landing-instructors.html), CTA ведут на анкету;
  - анкета /instructors/apply (мокап registration-instructor.html): ФИО,
    телефон, email, адрес, формат работы, госномер (если свой), номер и дата
    ВУ, категория, стаж, пароль + подтверждение; обязательность — по макету
    (звездочка) + пароль;
  - отправка анкеты создает заявку со статусом waiting; пароль хранится
    ТОЛЬКО как bcrypt-хэш (cost ≥ 12, механизм register.py) в самой заявке;
  - заявка с email, уже существующим в users, отклоняется на этапе отправки
    единым сообщением (users.email остается UNIQUE);
  - экран ожидания /instructors/pending после отправки анкеты.
- Домен `admin-moderation`:
  - раздел «Заявки инструкторов» в админке: таблица всех заявок с данными
    анкеты (включая bcrypt-хэш); клик по строке → «Одобрить»/«Отклонить»;
  - «Отклонить» требует обязательный комментарий (причина); статус → deny,
    причина сохраняется;
  - «Одобрить» создает пользователя в users из данных заявки (email + уже
    готовый bcrypt-хэш), статус → approved; повторное одобрение недоступно.
- Домен `instructor-auth`:
  - вход инструктора — через существующий /api/auth/login (логин = email,
    тот же механизм сессий, что у учеников, Спринт 1);
  - роутинг после входа по состоянию: пользователь найден (approved) →
    заглушка «кабинет скоро» /instructor/cabinet-stub; заявка waiting →
    /instructors/pending; заявка deny → /instructors/rejected с причиной
    (комментарием из админки); ни пользователя, ни заявки — единое сообщение
    об отказе входа (как у учеников, FR-13).

## Impact (Последствия)

- Код: новые модули `backend/instructors.py` (публичная анкета) и
  `backend/instructor_admin.py` (модерация); расширение `backend/auth.py`
  (роутинг входа по статусу заявки); схема БД — новая таблица
  `instructor_applications` + колонка роли в `users` (§16 sdd.md); новые
  страницы `frontend/instructors.html`, `frontend/instructor-apply.html`,
  `frontend/instructor-pending.html`, `frontend/instructor-rejected.html`,
  `frontend/instructor-cabinet-stub.html`; тесты в `tests/`.
- Master-spec: домены `instructor-application`, `admin-moderation`,
  `instructor-auth` создаются этой дельтой; существующие домены не
  модифицируются (поведение учеников и админ-контур Спринтов 0–1 без
  изменений).
- API-контракты и модель данных фиксируются в `sdd.md` (раздел
  «Спринт 2, часть 1»); изменение контракта — отдельная дельта.

## Out of scope / допущения

- **Кабинет инструктора (dashboard) — вне объема** (решение Заказчика):
  макет design/mocks/dashboard-instructor.html сохранен, реализация —
  следующий объем. В этом объеме — только заглушка «кабинет скоро».
- **Загрузка файла ВУ — не реализуется** (поле макета, помечено «макет без
  реальной загрузки»); факт заявки фиксируется, файл не сохраняется.
- **Вход водителей через футер лендинга — вне объема** (ТЗ Спринта 2,
  часть 1): футер лендинга инструкторов — визуал мокапа, отдельного входа
  для водителей в этом объеме нет.
- Допущение (интерпретация FR-16): повторная отправка анкеты с email, по
  которому уже есть заявка (даже waiting), отклоняется тем же единым
  сообщением, что и занятый email в users, — иначе вход по email был бы
  недетерминированным (несколько заявок на один email). Требование FR-16
  при этом не меняется: проверка users (UNIQUE) остается обязательной.
- Допущение (FR-13): статусные экраны (waiting/deny) показываются БЕЗ выдачи
  сессионного токена — сессия инструктору без записи в users не выдается
  (защищать нечего); доступ к статусным экранам возможен только через
  успешную проверку логина/пароля (claim по email без пароля отклонен
  Заказчиком).
- Допущение (FR-11): поля «дата выдачи ВУ» и «стаж» на макете без звездочки —
  необязательные; сохраняются как есть (пустые — пустые строки).
