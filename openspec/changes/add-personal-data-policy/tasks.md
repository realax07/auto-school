## 2. Раздача политики: GET /api/policy + страница /policy (backend + фронт)

- [ ] 2.1 backend/policy.py (НОВЫЙ модуль) + backend/app.py +
      frontend/policy.html — модуль домена PersonalData:
      read_policy() — чтение артефакта по POLICY_FILE (дефолт
      deploy/policy/policy.md) НА КАЖДЫЙ запрос (без кэша), парсинг
      шапки (policy-version, policy-date до `---`) и текста после
      разделителя; нарушение формата/чтения → ошибка-статус (контракт
      design.md); GET /api/policy — публичный (без авторизации,
      механика /api/health): 200 {ok:true, version, date, text} /
      500 {ok:false, error:"Политика: временно недоступна"} (содержимое
      артефакта в ответе/логах не раскрывается — NFR-10); страница
      /policy: policy.html в _PAGE_ROUTES — оболочка БЕЗ текста
      политики, fetch GET /api/policy при загрузке, версия+дата в шапке
      страницы, абзацы — текстовыми узлами (textContent/createTextNode,
      НЕ innerHTML), ошибка API → честное сообщение в контейнере
      текста; include роутера policy в create_app.
      Готовность: тесты — GET /api/policy отдает текст и метаданные из
      артефакта; страница /policy открыта без входа (гость) и после
      загрузки показывает текст и версию, при этом в HTML страницы
      текста политики нет (проверка исходника + рендера); подмена
      артефакта (временный файл с новым version/text) → /api/policy и
      /policy показывают новый текст и версию БЕЗ правки кода;
      отсутствующий/битый артефакт → 500 {ok:false} и сообщение на
      странице, сервис не падает.
      Типы: [code]. FR: FR-76. NFR: NFR-25, NFR-10. Зависит от: 1.1.

## 3. Фиксация согласия инструктора + миграция БД (backend)

- [ ] 3.1 [P] backend/db.py + backend/instructors.py — миграция: 4
      колонки через _COLUMN_MIGRATIONS (idempotent, механика
      users.role; init_db через lifespan — существующий volume):
      users.consent_at, users.consent_policy_version,
      instructor_applications.consent_at,
      instructor_applications.consent_policy_version (TEXT NULL —
      легаси-строки с NULL, БЕЗ seed/backfill); instructors.py: при
      успехе apply INSERT получает consent_at (UTC сервера, формат
      'YYYY-MM-DD HH:MM:SS') и consent_policy_version (version из
      артефакта на момент сабмита — хелпер backend/policy.py, задачи
      2.1; клиентской версии не доверять); артефакт недоступен в
      момент сабмита → 500 {ok:false}, заявка НЕ создается; проверки
      и multipart-нормализация consent — БЕЗ изменений (MIN-2).
      Готовность: тесты — предсозданная БД со старыми строками:
      миграция добавляет колонки (легаси — NULL), повторный init_db
      ничего не меняет; валидный POST → заявка создана, оба поля
      непустые и равны метаданным артефакта; POST без consent → 422
      «Согласие: поле обязательно», заявки нет (регресс MIN-2);
      подмена артефакта → новая заявка фиксирует новую версию, прежняя
      — свою (FR-79).
      Типы: [code][migration]. FR: FR-77 (серверная часть), FR-79.
      NFR: NFR-10, NFR-27. Зависит от: 1.1 (формат), 2.1 (хелпер
      read_policy).

## 4. Согласие ученика: /api/register (backend)

- [ ] 4.1 [P] backend/register.py — модель RegisterRequest + поле
      consent (bool = False, механика MAJ-1 — дефолты, валидация в
      хендлере); проверка 1a (после обязательных полей, до проверки
      email): consent is not True → 422 {ok:false, error:"Согласие:
      поле обязательно"} (формулировка/механика — как instructors.py);
      при успехе INSERT users + consent_at (UTC сервера) +
      consent_policy_version (артефакт на момент сабмита, хелпер 2.1);
      артефакт недоступен → 500 {ok:false}, пользователь НЕ создается;
      ответ {ok:true, token} — БЕЗ изменений (сессия — механика
      auth._session_issue, как было).
      Готовность: тесты — POST со всеми полями + consent:true → 200,
      в users consent_at и версия непустые и равны метаданным
      артефакта; POST без consent и с consent:false → 422 «Согласие:
      поле обязательно», пользователя нет; пустая фамилия при
      consent:true → «Фамилия: поле обязательно» (порядок проверок
      1 → 1a сохранен); повторная регистрация email → 422 «Email: уже
      зарегистрирован» (регресс).
      Типы: [code]. FR: FR-78 (серверная часть), FR-79. NFR: NFR-10.
      Зависит от: 2.1 (хелпер read_policy).
