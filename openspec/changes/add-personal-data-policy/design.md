## Артефакт политики — решение СА (границы NFR-25)

NFR-25 оставляет механизм хранения за СА («файл в образе с точкой
монтирования vs volume»). Решение: ФАЙЛ В КОНТУРЕ ДЕПЛОЯ С ТОЧКОЙ
МОНТИРОВАНИЯ (дефолт открытого вопроса требований, подтвержден):

- Путь по умолчанию: `deploy/policy/policy.md` (относительно корня
  репозитория/WORKDIR — та же механика, что AUTOSCHOOL_DB_PATH);
  переопределяется переменной окружения `POLICY_FILE`. deploy/ выбран
  (а не data/ — служебные данные в git не хранятся, NFR-3): артефакт —
  часть контура деплоя, как deploy/container/nginx.conf (прецедент
  монтирования :ro).
- Подмена = замена файла на хосте + перезапуск backend-контейнера.
  Образ НЕ пересобирается, исходники HTML/JS НЕ правятся. Бюджет
  NFR-25 (≤ 15 минут, без разработчика) выполняется с запасом.
- Файл читается с диска НА КАЖДЫЙ запрос (никакого кэша в процессе):
  актуальность после подмены не зависит от рестарта (рестарт — страховка,
  не обязательный шаг); O-размер артефакта — десятки КБ, чтение дешево.
- В контуре: монтирование `./deploy/policy` → read-only в backend-
  контейнер + `POLICY_FILE` (см. «Deploy-контур»).

### Формат артефакта (метаданные версии — шапка файла)

Дефолт открытого вопроса требований: «строка версии и дата в шапке
артефакта». Формат (UTF-8 plain text, без разметки — рендер без
HTML-инъекций):

```
policy-version: 1.0
policy-date: 2026-11-10
---
<текст политики: абзацы, разделенные пустой строкой>
```

- Шапка — строки `ключ: значение` ДО первой строки `---`;
  обязательные ключи: `policy-version` (непустая строка версии,
  например `1.0`) и `policy-date` (дата версии, YYYY-MM-DD).
  Неизвестные ключи шапки игнорируются (расширяемость).
- После `---` — текст политики; НЕпустой (пустой текст = артефакт
  поврежден).
- Нарушение любого правила (нет шапки, нет обязательных ключей, нет
  разделителя, пустой текст, файл отсутствует/нечитаем) → артефакт
  считается ПОВРЕЖДЕННЫМ (см. «Обработка ошибок»).
- Парсер — единственный, в backend/policy.py; им пользуются раздача
  (/api/policy, страница /policy) и фиксация согласия (apply/register).
  Формат даты в шапке — ДОКУМЕНТАЛЬНЫЙ (показывается на /policy);
  дата СОГЛАСИЯ фиксируется сервером отдельно (consent_at — момент
  сабмита, UTC), из шапки не берется.

## API-контракты

Формат ответов — механика Спринтов 1–8: 200 {ok:true, …}; ошибки
{ok:false, error:"<по-русски>"}; 422/500 — как в design.md Спринта 5.
SQL параметризованный (NFR-10); текст политики, ПД и согласия в логах
запрещены.

### GET /api/policy (НОВЫЙ, публичный)

|| Метод и путь | Роль | Поведение |
|---|---|---|
| GET /api/policy | гость (без авторизации) | чтение артефакта НА КАЖДЫЙ запрос; 200 {ok:true, version:"1.0", date:"2026-11-10", text:"<текст>"}; артефакт поврежден/отсутствует → 500 {ok:false, error:"Политика: временно недоступна"} (текст артефакта и его содержимое в ответе/логах не раскрываются) |

### POST /api/instructors/apply (УТОЧНЕНИЕ — обратно-совместимо)

|| Аспект | Изменение |
|---|---|
| Тело | БЕЗ изменений (consent уже был — MIN-2; multipart-нормализация consent true/1/on/да — без изменений, instructors.py:174) |
| Проверки | БЕЗ изменений (порядок sdd §15.1; позиция 1a «Согласие: поле обязательно» → 422) |
| Эффект | при УСПЕХЕ: INSERT + consent_at = момент сабмита (UTC сервера, формат created_at-совместимый 'YYYY-MM-DD HH:MM:SS') и consent_policy_version = policy-version артефакта НА МОМЕНТ САБМИТА (сервер читает артефакт сам — клиентской версии не доверять, FR-79) |
| Ответ | БЕЗ изменений {ok:true} |

### POST /api/register (УТОЧНЕНИЕ — новое обязательное поле)

|| Аспект | Изменение |
|---|---|
| Тело | + consent (bool, дефолт False — механика MAJ-1: дефолты вместо Pydantic-required, валидация в хендлере) |
| Проверки | позиция 1a (после обязательных полей, до проверки email): consent is not True → 422 {ok:false, error:"Согласие: поле обязательно"} — формулировка и механика как instructors.py (MIN-2) |
| Эффект | при УСПЕХЕ: INSERT users + consent_at (UTC сервера) + consent_policy_version (артефакт на момент сабмита) |
| Ответ | БЕЗ изменений {ok:true, token} |

Внимание (NFR-27, честная фиксация): consent в /api/register —
ОБЯЗАТЕЛЬНОЕ поле (FR-78: «прямой POST /api/register без флага согласия
THEN 422», Must). Старые клиенты, не отправляющие consent, получат 422 —
это ТРЕБУЕМОЕ изменение поведения (как проверка consent в apply Спринта 3),
а не регресс: маршруты, шейпы ответов и остальные поля обратно-совместимы.

## Модель данных (NFR-27; DDL уточняет dev в границах)

4 колонки через _COLUMN_MIGRATIONS (idempotent — механика users.role /
instructor_cars.status; PRAGMA table_info → ALTER TABLE при отсутствии):

- users.consent_at TEXT (NULL) — дата/время согласия ученика
- users.consent_policy_version TEXT (NULL) — версия политики при регистрации
- instructor_applications.consent_at TEXT (NULL) — то же для заявки
- instructor_applications.consent_policy_version TEXT (NULL)

- Формат consent_at — как created_at ('YYYY-MM-DD HH:MM:SS', UTC
  сервера; SQLite datetime('now')-совместимый).
- NULL-семантика: запись создана ДО введения фиксации (легаси). SEED/
  BACKFILL НЕ ДЕЛАЕТСЯ (сознательно, в отличие от document_versions
  Спринта 8): дату/версию согласия легаси-записей взять неоткуда —
  повторное согласие у зарегистрированных вне объема (границы
  требований). Новые записи — ОБА поля всегда непустые (сервер
  заполняет из артефакта в одной транзакции с INSERT).
- Проверки целостности на уровне колонок НЕ вводятся (NULL у легаси —
  допустимое состояние); обязанность непустоты у новых записей —
  серверная (задача тестов).
- Изменения схемы — только эти 4 колонки: новых таблиц нет (согласие —
  атрибут самой заявки/записи, консент-журнал — точка расширения).

## Фронт

- `frontend/policy.html` (НОВАЯ) + `/policy` в _PAGE_ROUTES:
  оболочка — шапка (название, «Версия: … от …»), контейнер текста,
  ссылка «Назад»; ТЕКСТ ПОЛИТИКИ в HTML/JS ОТСУТСТВУЕТ (grep-контроль
  NFR-25); текст и метаданные — fetch GET /api/policy при загрузке;
  абзацы (разбиение по пустой строке) — текстовыми узлами; 500/сетевая
  ошибка → сообщение «Политика временно недоступна. Попробуйте позже»
  (честная ошибка, без имитации текста).
- `frontend/instructor-apply.html` + `frontend/js/apply.js` (FR-77):
  текст чекбокса дополняется явной ссылкой «политикой персональных
  данных» → /policy (target="_blank" — чтобы не терять заполненную
  анкету); надпись-заглушка «Перед запуском здесь должна быть ссылка…»
  удаляется; кнопка «Продолжить →» disabled до установки чекбокса
  (change-listener; атрибут required чекбокса сохраняется вторым
  рубежом); consent в multipart отправляется как было (apply.js:68).
- `frontend/index.html` + `frontend/js/landing.js` (FR-78): в модалке
  «Регистрация» перед кнопками — обязательный чекбокс «Я согласен(на) с
  политикой персональных данных» со ссылкой на /policy (target="_blank");
  #reg-submit disabled до установки; payload дополняется
  consent: <true/false>; ответ 422 «Согласие: поле обязательно» —
  в существующий канал #reg-error (без изменения остальной логики
  модалки: вход, переключение регистраций, закрытие — как было).

## Решения по НФТ

- NFR-25: артефакт deploy/policy/policy.md + POLICY_FILE + точка
  монтирования (:ro); подмена = замена файла (+ рестарт) ≤ 15 мин без
  разработчика; чтение на каждый запрос — текст/версия актуальны сразу
  после подмены даже без рестарта; grep-контроль «в исходниках страниц
  (HTML/JS) нет ни одной строки текста политики» — задача приемки
  (frontend/**.html, frontend/js/**, собранные бандлы, если появятся).
- NFR-10: параметризованный SQL во всех новых запросах (новых таблиц
  нет — только ALTER/INSERT-колонки); текст политики, ПД, согласия и
  содержимое артефакта в логах запрещены; ошибка артефакта логируется
  БЕЗ содержимого.
- NFR-27: маршруты не меняются; /api/instructors/apply и
  /api/register — только добавление фиксации/поля consent (обратно-
  совместимо, кроме требуемой обязательности consent — см. контракт
  register); новые колонки NULL-able — существующие SELECT-«*»
  потребители и INSERT других модулей не ломаются; миграция idempotent
  на существующем volume (init_db через lifespan — наследование
  add-containerization, NFR-24-механика).
- Нагрузочные/контейнерные НФТ Спринта 9 (NFR-26/28) — вне блока 1,
  не затрагиваются.

## Deploy-контур

- docker-compose (backend-сервис): монтирование
  `${POLICY_DIR:-./deploy/policy}:/app/deploy/policy:ro` + env
  `POLICY_FILE=/app/deploy/policy/policy.md`; локальный контур —
  дефолтный относительный путь работает без env (repo checkout).
  Точные пути/имена — за dev/infra в границах механики (RUNBOOK
  фиксирует фактические значения).
- deploy/RUNBOOK.md: операция «Подмена политики» — (1) положить новый
  файл с поднятым policy-version (и датой) в deploy/policy/ на хосте;
  (2) перезапустить backend-контейнер; (3) контроль: GET /api/policy
  показывает новую версию, /policy — новый текст. Время — минуты,
  без разработчика (NFR-25); без правки кода и пересборки образа.

## Сознательные ограничения (задокументированы)

- Повторное согласие при смене версии, консент-журнал — точки
  расширения (фиксация только в момент регистрации).
- История версий артефакта не хранится: артефакт один, всегда
  «актуальный»; прежние заявки ссылаются на версию СТРОКОЙ
  (consent_policy_version), сам текст той версии не сохраняется
  (точка расширения при появлении требования аудита).
- Скачивание PDF, ссылка в футерах — точки расширения (MoSCoW).
- Markdown/HTML-разметка в артефакте НЕ поддерживается (plain text +
  абзацы) — рендер без HTML-инъекций; форматирование текста —
  задача шаблона, не движка.
- Кэширование артефакта в процессе не вводится (per-request read) —
  простота и мгновенная актуальность против микроскопической нагрузки
  чтения файла.
- In-memory сессии, single-worker — наследованные ограничения, не
  revisiting.

## Соответствие ADR / карты архитектуры

Новый домен PersonalData (backend/policy.py) — точка расширения по
правилу «домен — отдельный модуль» (Спринт 6, директива Заказчика).
Отступлений от ADR-004 (файлы/ПД вне статики) нет: артефакт политики —
не ПД пользователей, лежит в deploy-контуре, выдается публичным
эндпоинтом по замыслу. ADR/карта обновляются архитектором при ревью
пакета (вне этого пакета).
