## 2. Разбор по пунктам ревью (1–5)

### 2.1 NFR-25 заменяемость артефакта — механизм подтвержден

Решение СА: файл в контуре деплоя с точкой монтирования (дефолт открытого
вопроса ТЗ) — `deploy/policy/policy.md`, переопределение `POLICY_FILE`.
Проверка по фактам кодовой базы:

- **Подмена без правки кода и пересборки — да.** Dockerfile COPY выполняет
  только backend/, frontend/, design/, .env.example, requirements.txt —
  deploy/ в образ НЕ попадает, артефакт не запекается в образ физически.
  Подмена = замена файла на хосте + рестарт backend-контейнера; парсер
  читает файл НА КАЖДЫЙ запрос (кэш в процессе не вводится) — новый текст
  и версия актуальны сразу, рестарт заявлен страховкой, не обязательным
  шагом. Участие разработчика, правки HTML/JS, пересборка бандлов — не
  требуются ни на одном шаге; бюджет ≤ 15 минут выполняется с запасом
  (замена + `docker compose restart app` + контроль GET /api/policy).
- **Точка монтирования в compose прописана — да** (design «Deploy-контур»,
  реализация — задача 6.1): `${POLICY_DIR:-./deploy/policy}:/app/deploy/policy:ro`
  + `POLICY_FILE=/app/deploy/policy/policy.md`. Путь согласован с фактом
  WORKDIR /app: дефолтный относительный путь `deploy/policy/policy.md`
  кода резолвится ровно в точку монтирования; bare-metal systemd-режим
  (repo checkout) работает по тому же дефолту без env — механика
  AUTOSCHOOL_DB_PATH (config.py/db.py), переключение окружением без правок
  кода (FR-57, ADR-006) сохранено.
- **Выбор «host bind :ro» vs volume vs образ — корректен.** Образ нарушал
  бы NFR-25 (подмена = пересборка). Named volume отклонен обоснованно:
  артефакт — не «состояние» (в отличие от db/uploads — паттерн ADR-006),
  а контент с источником истины в git (шаблон v1.0 версионируется
  репозиторием, задача 1.1); том уводит «что сейчас развернуто» от
  репозитория и ломает аудит. Bind-mount :ro — точный прецедент
  deploy/container/nginx.conf и ${TLS_DIR} того же compose-стека (монтирования
  контура деплоя вне образов, INC-006). deploy/ выбран против data/
  обоснованно: data/ — служебные данные вне git (NFR-3), шаблон политики —
  часть контура деплоя.
- **Безопасное направление отказа:** отсутствующий/битый артефакт —
  fail-closed: /api/policy → 500 {ok:false} без раскрытия содержимого
  (NFR-10); apply/register → 500 и запись НЕ создается (сервис не создает
  запись без согласия на конкретную версию — FR-79, сценарий spec «Поврежденный
  артефакт — записи не создаются»). Эксплуатационное следствие
  (зависимость регистраций от файла при зеленом /api/health) — MIN-1.

### 2.2 Фиксация согласия — схема согласована с моделью данных, миграция idempotent

- **Схема:** consent — атрибут самой записи (users, instructor_applications),
  НЕ новая таблица — соответствует паттерну 5 карты («в БД только хранение»,
  без преждевременной сущности консент-журнала; журнал назван точкой
  расширения). 4 колонки: users.consent_at / consent_policy_version +
  те же в instructor_applications, TEXT NULL.
- **Миграция idempotent по механике db.py — да:** точное продолжение
  `_COLUMN_MIGRATIONS` (существующий паттерн: users.role, experience_years,
  photo_*, instructor_cars.status — PRAGMA table_info → ALTER TABLE при
  отсутствии, один commit в init_db; init_db через lifespan — наследование
  add-containerization, поднимается на существующем volume). NULL-семантика
  легаси-строк — прямое следствие ALTER TABLE ADD COLUMN; отказ от
  seed/backfill обоснован (в отличие от seed verified v1 Спринта 8/ADR-007,
  где данные-источник существовали: дату/версию согласия легаси-записей
  взять неоткуда) и закреплен сценарием spec «Записи до введения фиксации
  не переписываются» + тестом повторного init_db (задача 3.1).
- **Версия из артефакта на момент сабмита, сервером:** клиентской версии
  не доверять (FR-79) — парсер один (read_policy в policy.py), им пользуются
  и раздача, и фиксация → показанная на /policy версия и записанная в
  заявку/запись не могут разойтись в пределах запроса. Single-worker
  (наследованный инвариант) гонок чтения артефакта не создает.
- **Обратная совместимость контрактов:** /api/instructors/apply — тело,
  проверки (позиция 1a MIN-2, instructors.py:101–103 подтверждена) и ответ
  {ok:true} без изменений, добавляется только фиксация при INSERT.
  /api/register — новое поле consent: bool = False по механике MAJ-1
  (дефолты вместо Pydantic-required, валидация в хендлере — точно как
  существующие 7 полей register.py), позиция 1a после обязательных полей и
  ДО проверки email (симметрично instructors.py; порядок «1 → 1a» закреплен
  тестом задачи 4.1). Обязательность consent — ломающее изменение для
  старых клиентов (422), и design это называет честно: требуемое поведение
  FR-78 (Must, «прямой POST без флага → 422»), прецедент — введение consent
  в apply Спринтом 3; NFR-27 выполнен в части маршрутов/шейпов/ответов
  ({ok:true, token} без изменений). Правка тестовой поддержки (conftest
  valid_body → consent:true, Playwright-клик чекбокса) — легитимна и
  выделена в задачу 7.2 с явной оговоркой про FR-85 (запрет правки e2e —
  шаги миграции блока 3, на настоящий change не распространяется; сценарии
  не удаляются и не переписываются) — граница проведена корректно.
- **Атомарность фиксации:** consent_at/consent_policy_version добавляются
  в колонки того же INSERT (одна транзакция с созданием записи, как
  существующая связка INSERT+UPDATE license_photo_path в instructors.py) —
  «запись без фиксации» недостижима для новых строк; недоступный артефакт
  отсекается ДО INSERT (500, записи нет).

### 2.3 Чекбоксы в двух контурах — серверная валидация есть в обоих

- **Инструктор:** серверная проверка существует с Спринта 3 (MIN-2,
  instructors.py: «consent is not True → 422 "Согласие: поле обязательно"»,
  позиция 1a; multipart-нормализация true/1/on/да — instructors.py:174,
  подтверждена) — пакет НЕ трогает ее (правильно: регресс-тест задачи 3.1
  «POST без consent → 422, заявки нет» фиксирует наследование). Клиентская
  часть: кнопка disabled до установки (change-listener), required чекбокса
  сохраняется вторым рубежом (атрибут в checkline instructor-apply.html:32
  подтвержден), consent в multipart — apply.js:68 без изменений.
- **Ученик:** серверная проверка НОВАЯ (422 {ok:false, error:"Согласие:
  поле обязательно"} — формат ошибок по конвенции Спринтов 1–8, формулировка
  и механика — как instructors.py); клиентская — чекбокс + disabled #reg-submit
  + payload consent; канал ошибок #reg-error в модалке существует
  (index.html:79, wiring landing.js:18–19 — design-факт подтвержден, новой
  поверхности ошибок не вводится).
- **Чекбокс — не единственная защита в обоих контурах:** spec содержит
  сценарии прямого POST без согласия для apply и register (422, запись не
  создается) — клиентский гейт (disabled) является удобством, сервер —
  контролем; структура сценариев обязывает тесты к прямым POST (задачи
  3.1/4.1/7.1). Клиентский disabled сам по себе не считается защитой —
  корректная архитектура защиты.

### 2.4 Раздача /policy — маршрут, кэширование, попадание в контур без ломания

- **Страница /policy:** новая запись в _PAGE_ROUTES (механика app.py:33–54,
  112–119 — file-response по словарю, закрытие пути) — маршрут уникален,
  с существующими 13 страницами и _PAGE_REDIRECTS не пересекается; grep по
  backend/frontend следов /policy, policy.html, /api/policy, POLICY_FILE,
  consent_at не дал — коллизий и следов преждевременной реализации нет.
- **API GET /api/policy:** публичный без префикса роли, механика /api/health
  (app.py:96–98). Правило префиксов API (design, таблица) соблюдено без
  исключений: ни один ролевой префикс (/api/instructor|student|admin|instructors)
  не расширяется; /api/policy — рядом с /api/register и /api/health
  (публичные до регистрации — обоснование в design: политика читается
  гостем ДО любой регистрации). Новый публичный эндпоинт попадает под
  унаследованное отсутствие rate-limit — осознанно (MIN, техдолг спринта-9).
- **nginx не трогается — и не должен:** deploy/container/nginx.conf —
  `location / { proxy_pass http://app:8390; }` — и страница, и API доезжают
  до app без правок конфига; маршрутизация существующих контуров не меняется.
- **Кэширование — отсутствует на всем пути, и это правильно для NFR-25:**
  proxy_cache в nginx нет; FileResponse страниц без агрессивных заголовков;
  текст страницы получает через fetch при каждой загрузке; артефакт читается
  с диска на каждый запрос. Актуальность после подмены — мгновенная,
  устаревание невозможно по построению. Нагрузка (десятки КБ чтения на
  запрос) — незначимая при single-worker и малом трафике публичной страницы;
  микрокэш отклонен обоснованно (простота против микроскопического выигрыша).
- **XSS-гигиена:** артефакт plain-text без HTML/markdown (format design),
  рендер текстовыми узлами (textContent/createTextNode, НЕ innerHTML),
  метаданные из шапки — в текстовые узлы; ошибка API → честное сообщение в
  контейнере текста (не пустая страница — сценарий spec). Текст политики
  отсутствует в исходниках страниц (grep-контроль — задача приемки 9.1).

### 2.5 Модульность Спринта 6 и масштабируемость решения

- **Домен — отдельный модуль:** backend/policy.py (парсер + раздача + хелпер

  точечные расширения (поле/фиксация), не раздуваются; явный список 15

- **Файлы пакета ограничены и разнесены:** backend policy.py (новый) +
  app.py/db.py/register.py/instructors.py (точечно); frontend policy.html
  (новый) + index.html/landing.js (5.2) + instructor-apply.html/apply.js
  (5.1) — зоны файлов в tasks «Рекомендации к нарезке» разнесены по
  задачам без пересечений (db.py — целиком 3.1; app.py — 2.1; 8.1 сверяет;
  прецедент коллизий 3.2/4.1 учтен). Расхождение формулировки 8.1 с
  «только сверяет» — MIN-5 (не структурно).
- **Без фанатизма:** новых таблиц/сервисов/страниц (кроме обязательной
  /policy) нет; consent — колонки существующих записей, а не новая сущность;
  раздача — тот же FastAPI-сервис (ADR-001: статика тем же сервисом),
  отдельный статический веб-сервер для одного файла не вводится.
- **Масштабируемость (будущие изменения политики):** смена текста/версии —

  меняются — это ровно NFR-25; расширения (повторное согласие, консент-журнал,
  архив текстов версий, PDF, футеры) названы и не блокируют текущую форму.
- **Соседние пакеты Спринта 9:** по декларированным экранам requirements

  этом дереве пакеты 9.2/9.3 отсутствуют (отдельные ветки) — файловая
  коллизия исключается нарезкой PLAN.

Оба решения Заказчика (ОВ-1/ОВ-2) покрыты дословно и согласованно по

ПМ; MIN-2 — сознательное ограничение с точкой расширения). **approve** —
dev_task может стартовать; повторного цикла ревью не требуется.
