# Change: add-s8-cars-docs-booking

## Why (Зачем)

Спринт 8. Доработка контуров Спринтов 5–7 по замечаниям эксплуатации
(решение Заказчика 2026-10-31 — 7 пунктов, requirements-sprint8.md
УТВЕРЖДЕН с решениями ОВ-1…ОВ-7 от 2026-11-01):

1. Документы живут без статусной модели: замена ВУ/СТС сегодня либо
   невозможна («Мои документы» — только просмотр/скачивание, досыл
   явно исключен Спринтом 5), либо (СТС) перезаписывает файл мимо
   всякой верификации. Замена должна вступать в силу ТОЛЬКО после
   проверки админом, до решения — действует предыдущая версия.
2. СТС-дозагрузка на уже созданном авто в UI не работает (симптом
   п.1 Заказчика; Спринт 7 завел параметризованный
   POST …/photo/sts — требуется повторная диагностика цепочки
   «эндпоинт ↔ UI-контрол» и доводка).
3. Экраны «Мои автомобили»/«Мои документы» перегружены виджетами
   (привязанные ученики, запросы, занятия на сегодня).
4. Календарь: остатки слияния Спринта 7 — раздел «Бронирования» еще
   существует (пункт меню, секция, хэш #/bookings), запросы/брони
   должны быть РОВНО на выбранных учеником слотах.
5. «Мои ученики» — демо-заглушка вместо карточек учеников со
   счетчиками занятий; «Запросы учеников» — отдельный пункт сайдбара
   вместо подраздела.

Решение — единая статусная модель ДОКУМЕНТОВ (ВУ + СТС, ОВ-2) по
образцу статусной модели авто Спринта 7: версии документа
pending / verified / rejected, одна ожидающая версия на документ,
предыдущая verified действует до решения админа; причина отказа
обязательна (ОВ-1); замена СТС НЕ сбрасывает валидацию авто (ОВ-6).

Источник требований: `docs/ba/requirements-sprint8.md` (УТВЕРЖДЕН;
решения Заказчика ОВ-1…ОВ-7 — в конце документа). Задействованные
решения: ОВ-1 (reject с обязательной причиной), ОВ-2 (единая модель
ВУ+СТС, СТС по 1 на авто), ОВ-3 (pending/rejected не влияет на
активность инструктора), ОВ-4 (админ-раздел «Документы», предпросмотр
изображений ДОЛЖЕН открываться), ОВ-5 (счетчики — только confirmed;
запросы — по требованию), ОВ-6 (замена СТС не сбрасывает авто),
ОВ-7 (повторная загрузка замещает ожидающую версию).

## What Changes (Что меняет)

- Домен `instructor-documents` (MODIFIED + ADDED):
  - статусная модель документов: новая таблица `document_versions`
    (target_type: license/car_sts, target_id, version, file, статус
    pending/verified/rejected, reject_reason — обязателен при reject);
    действующая версия — последняя verified, предыдущие verified —
    архив; ожидающая — одна на документ, повторная загрузка ее
    замещает (ОВ-7); rejected-версия видна инструктору с причиной
    (ОВ-1);
  - миграция существующих документов: ВУ (license_photo_path анкеты)
    и СТС (photo_sts авто) получают verified-версию v1 — никто не
    «зависает» на верификации после релиза (NFR-24);
  - загрузка/замена инструктором (FR-71, FR-72): ВУ — POST
    /api/instructor/documents/license (multipart); СТС — существующий
    POST /api/instructor/cars/{id}/photo/sts; замена создает
    pending-версию, ПРЕДЫДУЩАЯ действует до решения админа; UI
    показывает предупреждение и явную кнопку «Заменить»;
  - «Мои документы» (GET /api/instructor/documents) — РАСШИРЕНИЕ:
    версии + статусы (действует / «Ожидает проверки замены» /
    отклонено с причиной); файл выдается от действующей версии;
  - верификация админом (ОВ-4): GET /api/admin/documents?status=pending
    (ВУ — с ФИО инструктора, СТС — с авто и госномером), предпросмотр
    файла версии (изображение ДОЛЖНО открываться), POST verify /
    reject; reject — причина обязательна (422 без нее, ОВ-1),
    отклонение НЕ трогает действующую версию.
- Домен `instructor-cars` (MODIFIED, ОВ-6): замена СТС у авто в
  validated НЕ возвращает его в validating — статус авто и статус
  документа независимы (повторная валидация авто — отдельное действие
  submit, как в Спринте 7). Правило ракурсов (validated → validating
  при замене любого из 5 ракурсов, MAJ-1 Спринта 7) — БЕЗ изменений.
  Диагностика СТС-симптома (п.1 Заказчика) — обязательна ДО фикса,
  корень фиксируется в отчете задачи.
- Домен `student-requests` (MODIFIED + ADDED): новый раздел «Мои
  ученики» — карточки принятых учеников (пары status='accepted'):
  следующее плановое занятие, количество плановых дальше, количество
  проведенных — ТОЛЬКО подтвержденные (confirmed) брони (ОВ-5);
  «Запросы учеников» становится подразделом «Мои ученики» (вкладка/
  окно по требованию), функционал принятия/отказа — без изменений.
  Виджеты «Привязанные ученики» и «Занятия на сегодня» остаются
  ТОЛЬКО на главной кабинета.
- Экраны «Мои автомобили» и «Мои документы» (MODIFIED, FR-73) —
  БЕЗ виджетов: «привязанные ученики», «запросы учеников», «занятия
  на сегодня» удаляются с этих двух экранов (явные исключения);
  главная кабинета — без изменений.
- Календарь (ADDED, FR-74): запросы и брони учеников отображаются
  РОВНО на выбранных слотах (дата+время запроса = слоту availability);
  раздел «Бронирования» удаляется без остатков (пункт меню, секция,
  маршруты); старые ссылки (#/bookings) — редирект в календарь
  (механика BUG-047); кнопки «Сохранить/Отменить» графика и
  немедленные решения по броням — наследование FR-68/ОВ-6 Спринта 7.

Модульная архитектура (директива Заказчика, наследуется): модель
версий документов — внутри домена `backend/instructor_documents.py`;
точечные расширения `instructor_cars.py` (только sts-ветка);
выдача «Мои ученики» — расширение `student_requests.py`; фронт —
правки существующих ES-модулей `frontend/js/*`, новых страниц нет.

## Out of scope / допущения

- «Отозвать pending» отдельной кнопкой — НЕ в объеме: ОВ-7 — повторная
  загрузка замещает ожидающую версию; отзыв — точка расширения.
- Влияние pending/rejected документов на активность инструктора
  (каталог, новые заявки, submit авто) — НЕ реализуется: ОВ-3 — «не
  влияет пока что», точка расширения.
- История версий с просмотром архива, пакетное подтверждение — точки
  расширения (MoSCoW: не Must); админ работает только с ожидающими
  версиями, историю не трогает.
- Статусная модель АВТО не пересматривается; отказ админа для авто,
  снятие подтверждения — вне объема (наследование Спринта 7).
- Уведомления (email/push) о верификации документов и запросах —
  backlog.
- Календарь ученика — read-only, без изменений; нарезка слотов,
  перенос/отмена подтвержденных броней — вне объема.
- Новые сущности «плановое занятие»/«расписание курса» не заводятся:
  счетчики «Мои ученики» — разрез поверх booking.
