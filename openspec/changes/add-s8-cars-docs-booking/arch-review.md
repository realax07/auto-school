## 2. Ключевые архитектурные решения — оценка

1. **Таблица document_versions + канонические колонки как указатель
   действующей версии** — принято. Инварианты (одна pending на документ,
   reject без причины невозможен) вынесены на уровень схемы (частичный
   UNIQUE + CHECK), а не дисциплины кода — тот же подход, что дал
   «один слот = одна бронь» (ADR-005, частичный UNIQUE + BEGIN IMMEDIATE).
   Сохранение license_photo_path/photo_sts как канонических указателей
   означает: все существующие потребители (sts-выдача, GET …/photo/sts,
   admin completeness, карточка анкеты) работают без переделки — NFR-23
   выполняется конструктивно, а не оговоркой. Механизм хранения — решение
   СА в границах NFR-24 (там это прямо делегировано), зафиксировано в
   ADR-007.
2. **Seed-миграция verified v1 (NFR-24)** — принято. Idempotent (seed
   только при отсутствии строк документа), init_db через lifespan на
   существующем volume (наследование add-containerization); эффект — ни
   один документ не «зависает» на верификации после релиза, выдача файлов
   не меняется. Симметрично NFR-20/ОВ-1 Спринта 7. Задача 1.1 требует
   тестов на повторный запуск и на частичный индекс — достаточный контроль.
3. **Асимметрия первичной загрузки (СТС → verified сразу, ВУ → pending)** —
   принято, обоснование СА корректно. СТС первичной дозагрузки проходит
   человеческий гейт Спринта 7 (валидатор авто при validate, комплектность
   — человек в админке): вторая human-верификация того же файла не дает
   ничего, кроме двойной очереди. ВУ вне гейта авто — другого человеческого
   контура нет, поэтому pending обязателен (наследование ОВ-1 Спринта 5).
   Асимметрия задокументирована как сознательное ограничение, зафиксирована
   в ADR-007 (решение 3).
4. **Независимость ОВ-6** — принято и проведено последовательно: sts-ветка
   не сбрасывает статус авто и не трогает ракурсы/has_sts/комплектность;
   правило MAJ-1 («validated → validating») сохранено ТОЛЬКО за 5 ракурсами
   с явным регресс-сценарием в specs/instructor-cars. Уточнение поведения
   Спринта 7 (раньше sts-замена тоже сбрасывала) — именно то, что ordered
   ОВ-6; конфликт с открытым change Спринта 7 сведен порядком архивации
   (Спринт 7 → Спринт 8, сводит СА) — приемлемо, зафиксировано в proposal.
5. **Календарь и «Мои ученики» — фронт/чтение без новых сущностей** —
   принято. Запросы/брони на слотах: booking уже привязан к availability_id,
   данные есть в GET /api/instructor/bookings — бэкенд не меняется (NFR-23).
   Счетчики — разрез поверх booking/student_requests (наследование
   ADR-005), только confirmed (ОВ-5), локальная дата сервера (наследование
   MIN-1) — согласовано с существующей механикой lesson_date.
6. **Модульность (директива Заказчика)** — соблюдена: версии документов —
   внутри instructor_documents.py; точечные расширения instructor_cars.py
   (только sts-ветка) и student_requests.py; новых страниц/роутеров нет;
   префиксы API — без исключений.
