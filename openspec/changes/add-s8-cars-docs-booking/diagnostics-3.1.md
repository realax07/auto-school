## 2. Воспроизведение по звеньям (план design.md)

### (а) Эндпоинт: что реально делает POST …/photo/sts и куда уходит legacy

| Прогон | legacy POST …/photo (kind=car_sts) | POST …/photo/sts (JPEG) | PDF → …/photo/sts |
|---|---|---|---|
| ДО фикса (1d40a46) | **HTTP 404**, photo_sts остался None | HTTP 200 `{ok,url,status:"draft"}`, **photo_sts заполнен** | HTTP 422 |
| ПОСЛЕ фиксa (b473703) | HTTP 404 | HTTP 200, photo_sts заполнен + версии СТС `[(1,'verified')]` | HTTP 422 |

Дословно (ДО фикса):

```
[ДО-фикса(1d40a46)] создано авто id=1, photo_sts=None
[ДО-фикса(1d40a46)] (а) legacy POST …/photo kind=car_sts -> HTTP 404 (photo_sts после: None)
[ДО-фикса(1d40a46)] (а) POST …/photo/sts JPEG -> HTTP 200 {"ok":true,"url":"/api/instructor/cars/1/photo/sts","status":"draft"}
[ДО-фикса(1d40a46)] (а) photo_sts после дозагрузки: True
[ДО-фикса(1d40a46)] (а) POST …/photo/sts PDF -> HTTP 422
```

Вывод по (а): маршрут `POST …/photo kind=car_sts` действительно не
существует — он удален в Спринте 7 (заменен параметризованным
`/photo/{angle}`, `UPLOAD_ANGLES = ANGLES + ("sts",)`), любой вызов по
нему → 404/405. НО гипотеза «эндпоинт не записывает photo_sts» НЕ
подтвердилась: актуальный sts-маршрут заполнял photo_sts уже в Спринте 7.
Корень сместился (как и предполагал design.md).

### (б) Клиент: какой маршрут фактически вызывают модалка авто и «Мои документы»

Статический анализ frontend (дерево до фикса = Спринт 7; фронтовая волна
Спринта 8 в это дерево не входит):

- Вызовов legacy `kind=car_sts` во всем frontend НЕТ (grep `kind` по
  frontend/js/*.js и frontend/*.html — 0 совпадений с car_sts). Значит,
  «не подключен на UI» в актуальном коде — не через kind.
- Модалка авто (галерея, «Мои автомобили»): ЕДИНСТВЕННЫЙ вызов загрузки
  фото — `mcUpload('/api/instructor/cars/'+t.carId+'/photo/'+t.angle, …)`
  (frontend/js/dashboard-instructor.js:812, вызывается из change-обработчика
  `gal-file`), angle включает `'sts'` (mcGalKeys — 5 ракурсов + 'sts';
  клик по большому окну/рамке СТС → mcPickGal → выбор файла → POST
  `/photo/sts`). То есть у СУЩЕСТВУЮЩЕГО авто контрол СТС в модалке БЫЛ
  (создание авто отдельно шлет обязательный `sts_photo` — FR-44).
- «Мои документы» (раздел FR-45, dashboard-instructor.js:977–1040): ТОЛЬКО
  просмотр — `GET /api/instructor/documents` (apiGet) и выдача картинок
  `GET /api/instructor/documents/{doc_id}/file` (mcLoadImg). КОНТРОЛА
  загрузки/замены СТС (и ВУ) в разделе НЕТ. Заявленный Заказчиком второй
  путь дозагрузки («Мои документы») физически недоступен в UI до фикса.

### (в) Состояние: воспроизводимость и побочный эффект статуса авто

- Повторная загрузка воспроизводима: 2-я и 3-я загрузки по …/photo/sts —
  стабильно HTTP 200 (и до, и после фикса); поведение детерминировано,
  гонок/рассинхрона не наблюдается.
- ПОБОЧНЫЙ ЭФФЕКТ, подтвержденный воспроизведением (ДО фикса): замена СТС
  у авто в `validated` СБРАСЫВАЛА статус авто → `validating` (правило
  MAJ-1 Спринта 7 применялось к ЛЮБОЙ замене, включая СТС):

```
[ДО-фикса(1d40a46)] (б) повторная загрузка (у validated) -> HTTP 200 {…,"status":"validating"}
```

  Эксплуатационно это выглядит как «дозагрузка СТС ломает авто» (авто
  уходит на повторную валидацию и скрывается из каталога новых учеников),
  а сам файл при этом подменялся НАПРЯМУЮ (photo_sts перезаписывался
  сразу, без верификации админом — документной модели не существовало).
- Контроль после фикса (тот же сценарий): замена СТС у validated →
  HTTP 200, `status:"validated"` (сброса нет — ОВ-6), документ → pending
  v2 (photo_sts не перезаписан):

```
[ПОСЛЕ-фикса(b473703)] (б) повторная загрузка (у validated) -> HTTP 200 {…,"status":"validated","document":{"status":"pending","version":2,…}}
```

## 3. Корень (зафиксирован)

Симптом «СТС-дозагрузка на созданном авто не работает» — составной, три
слагаемых:

1. **Legacy-маршрут удален**: `POST /api/instructor/cars/{id}/photo` с
   `kind=car_sts` не существует с Спринта 7 → 404 (воспроизведено).
   Инструкции/клиент, следующие формулировке симптома, стабильно получают
   отказ — это буквальный корень заявленного «kind=car_sts не работает».
2. **UI-поверхность «Мои документы» не имела контрола загрузки** (FR-45
   была просмотр/скачивание): из раздела документов дозагрузить/заменить
   СТС было невозможно в принципе — путь, заявленный Заказчиком как
   основной для документов, отсутствовал на UI.
3. **Статусная модель документов отсутствовала**: модалка авто умела
   отправить СТС по `/photo/sts`, но (i) замена СТС у validated-авто
   сбрасывала валидацию (MAJ-1 без исключения для СТС) — воспринимается
   как поломка; (ii) фото СТС подменялось напрямую без версии и верификации
   админом — «загрузил и мгновенно подменено» без контроля (FR-70 не
   существовало до Спринта 8).

## 4. Что именно чинено

Backend, итерация 1 (b473703, волна feat/s8-backend) — sts-ветка
`POST …/cars/{id}/photo/sts` (instructor_cars.py) + документные версии
(instructor_documents.py, таблица document_versions):

- первичная дозагрузка (авто без действующего СТС) → photo_sts +
  **verified v1** сразу (FR-69; двойная human-верификация не вводится);
- ЗАМЕНА при действующем СТС → **pending-версия**, photo_sts НЕ
  перезаписывается до верификации («документ не мигает», FR-70),
  повторная загрузка замещает ожидающую (ОВ-7);
- статус авто при замене СТС **НЕ меняется** — validated остается
  validated (ОВ-6); правило MAJ-1 «validated → validating» осталось
  ТОЛЬКО для 5 ракурсов (регресс TC-S7BE-019);
- тесты: TC-S8BE-003 (дозагрузка/замена/ОВ-7/админ-контур), TC-S8BE-004
  (ОВ-6 + MAJ-1 ракурсов), TC-S8BE-001 (миграция/seed).

Фронтовая часть корня №2 (контролы загрузки/замены СТС в «Моих
документах», диалог FR-71 с явной «Заменить») — волна frontend
(04fb133, задачи 5.1/6.1); замечание review-003 #2 про обход FR-71 через
галерейный путь модалки адресовано фронтовой волне — в этой backend-волне
не трогается. Корень №1 закрывается документированием целевого маршрута
(этот отчет + sdd.md задачи 11.1): legacy `kind=car_sts` не
восстанавливается (design.md Спринта 7 — маршрут удален намеренно).
