## Модель данных (NFR-5→NFR-10 наследование; DDL уточняет dev в границах)

Существующие таблицы — БЕЗ структурных изменений: availability,
student_requests, users, instructor_applications. Колонка
instructor_cars.photo_path (Спринт 3, одиночное фото) объявляется
устаревшей: новые эндпоинты ее не читают и не пишут, данные не мигрируют
(файлы-сироты — унаследованный техдолг, cleanup вне объема). СУДЬБА
СТАРОГО ФОТО-МАРШРУТА (MIN-4): эндпоинт Спринта 3 POST+GET
/api/instructor/cars/{id}/photo (одиночное фото, без ракурса) УДАЛЯЕТСЯ
одновременно с photo_path — его заменяют параметризованные POST+GET
/photo/{angle}; совместимость не сохраняется (мастер-спека приведется
при архивации MODIFIED-дельты).

Расширение `instructor_cars` (все миграции idempotent):

- `photo_front TEXT NULL`, `photo_rear TEXT NULL`, `photo_interior TEXT NULL`,
  `photo_left TEXT NULL`, `photo_right TEXT NULL` — пути фото ракурсов
  (спереди/сзади/салон/слева/справа; ОВ-1 — все 5 обязательны);
- `photo_sts TEXT NULL` — путь фото СТС (обязателен при создании — FR-44,
  поэтому у созданных этим объемом авто NOT NULL по факту; NULL — только
  у авто, созданных до миграции);
- `blocked INTEGER NOT NULL DEFAULT 0` — блокировка авто админом
  (ОВ-1: комплектность валидирует человек в админке).

Выбор «6 колонок вместо kind-таблицы» — research.md: ракурсов конечное
число, фиксированный состав, никаких метаданных по каждому фото не нужно;
таблица-справочник дала бы JOIN без выигрыша.

Новая таблица `booking` (домен booking, модуль backend/booking.py):

- `id` PK; `student_id` NOT NULL → users(id); `instructor_id` NOT NULL →
  users(id) (денормализация пары для прямых выборок календаря; сверяется
  с availability.instructor_id при создании);
- `availability_id` NOT NULL → availability(id) — слот = интервал графика
  ЦЕЛИКОМ (ОВ-3), без нарезки;
- `lesson_date` NOT NULL (ISO-дата) — материализованная дата занятия:
  ближайшая будущая дата weekday слота на момент создания брони
  (availability без дат, а календари FR-49 показывают дату; допущение
  proposal.md). ЕДИНОЕ ПРАВИЛО ДАТЫ (MIN-1): даты везде считаются по
  ЛОКАЛЬНОЙ ДАТЕ СЕРВЕРА — и материализация lesson_date, и «today»
  виджета «Занятия на сегодня» (календари живут в показаниях серверных
  часов); времена UTC в БД на выбор даты не влияют (техдолг MIN-4
  review-001 не ретранслируется в контур брони);
- `status` NOT NULL CHECK IN ('new','confirmed','rejected'), DEFAULT 'new';
- `reject_comment` NULL — обязателен при 'rejected' (инвариант кодом, как
  student_requests.deny_comment);
- `created_at`, `decided_at` NULL; индексы по (instructor_id, status),
  (student_id, status);
- **Гарантия единственности (NFR-8)**: частичный уникальный индекс
  `CREATE UNIQUE INDEX uq_booking_active_slot ON booking(availability_id)
  WHERE status IN ('new','confirmed')` — на слоте максимум одна активная/
  подтвержденная бронь; отклоненные не мешают повторному запросу (ОВ-5).
  SQLite partial index — доступен в используемой версии.

Связь «ученик принят» — как в Спринте 3: наличие
student_requests(student, instructor, status='accepted'); новая таблица
пар НЕ заводится (решение ТЗ).

## PUT /api/instructor/availability × активные брони (MAJ-1)

Существующий контракт PUT — ПОЛНАЯ замена графика одной транзакцией.
Правило согласования с booking (выбранный вариант — ЗАПРЕТ, по
рекомендации арх-ревью MAJ-1; альтернатива «каскадный reject с системным
комментарием» отклонена — см. research.md п.7: отклонение брони — решение
инструктора с его комментарием (ОВ-2), автоматическое отклонение за него
— молчаливая порча решений, против духа NFR-8):

- PUT выполняется как прежде, ЕСЛИ новый график содержит все слоты
  (weekday+интервал), у которых есть брони в статусах 'new'/'confirmed';
- ЕСЛИ новый график не содержит хотя бы один такой слот — PUT
  отклоняется: 409 {ok:false, error «В графике есть слоты с активными
  бронями…»} с ПЕРЕЧНЕМ затронутых слотов (weekday, интервал, статус
  брони); график НЕ изменяется (замена целиком не выполняется);
- инструктор сначала решает брони (confirm/reject с комментарием —
  контракты блока C), затем повторяет сохранение графика;
- слоты, у которых брони только в статусе 'rejected', замене не мешают;
- реализация: проверка в backend/booking.py (helper по таблице booking),
  вызывается из instructor_availability.py перед заменой; тест — задача
  4.1, сверка контракта PUT — задача 5.1.

Структура availability при этом не меняется (таблица БЕЗ структурных
изменений — см. выше), меняется только поведенческий контракт PUT.

## Эффект блокировки авто на контур брони (MIN-2)

Блокировка авто админом (blocked=1) НЕ ретроактивна для броней: она
блокирует автомобиль как объект КАТАЛОГА (скрытие от учеников —
карточки/выдача фото), но не календарь — существующие брони (в т.ч.
подтвержденные) сохраняются и отображаются как прежде, авто пары виден
ученику в подтвержденной броне даже при заблокированном авто (ОВ-6 «следует
за перекреплением» не противоречит: перекрепление, а не блокировка, меняет
авто в отображении). Создание НОВЫХ броней блокировкой не запрещается.
Пустое состояние car_id в календарях (MIN-3): при удалении авто пары
(car_id NULL — ОВ-3 Спринта 3) календарь ученика, календарь инструктора и
today_lessons показывают КОРРЕКТНОЕ ПУСТОЕ СОСТОЯНИЕ на месте автомобиля
(«—»), а не ошибку — автомобиль отображения опционален, бронь и слот
остаются видимыми.

## Гонки бронирования (NFR-8) — механика

1. POST запроса брони и POST confirm выполняются в транзакции
   (BEGIN IMMEDIATE — запись лочится до конца транзакции).
2. Создание: INSERT при уже занятом слоте (активный запрос/подтвержденная
   бронь другого ученика) нарушает частичный UNIQUE → откат →
   409 {ok:false, error «Слот уже занят»}. Предварительный SELECT (UX-уровень,
   «занято» в выдаче слотов) не является гарантией — только индекс.
3. Confirm: апдейт статуса 'new'→'confirmed' той же брони конкуренции не
   имеет (бронь уже держит слот частичным UNIQUE); конфликтный случай —
   гонка двух INSERT → проигравший получает 409, а не молчаливую порчу.
4. Reject: комментарий обязателен (пустой/отсутствующий → 422, действие
   заблокировано — ОВ-2); освобождает слот (статус 'rejected' выпадает из
   частичного индекса) — повторный запрос возможен (ОВ-5).

## Диагностика бага 5.2 (FR-42)

Симптом: photo_path в БД есть, фото не отображается ни у владельца, ни у
ученика. Наблюдаемое требование фиксирует спека (FR-42); спека НЕ
предписывает способ починки. Задача диагностики (tasks.md 1.1) проверяет
цепочку по звеньям и фиксирует корень в отчете задачи:

- (а) выдача: GET /api/instructor/cars возвращает ли фото-ссылку/поле
  photo_path; GET …/photo отдает ли изображение владельцу (матрица кодов
  MIN-2);
- (б) клиент: какой URL строит фронт плитки (инструктор-дашборд,
  карточка ученика) — совпадает ли с реальным маршрутом выдачи; не
  подставляется ли путь файла (data/uploads/…, статикой не раздается —
  NFR-1) вместо URL эндпоинта;
- (в) кэш/сессия: воспроизводится ли после перезагрузки и повторного
  входа (условие снятия симптома из FR-42).

Известный вклад Спринта 3 (design.md архива): на публичной карточке
ученику фото не отдавалось вовсе — этот объем МЕНЯЕТ правило доступа
(MODIFIED-дельта instructor-cars: фото — владельцу и ученикам пары),
поэтому часть симптома у ученики закрывается самой дельтой доступа, часть
(у владельца) — фиксацией по результатам диагностики.

## API-эндпоинты (методы / роли / валидации)

Формат ответов — механика Спринтов 1–3: 200 {ok:true, …}; ошибки
{ok:false, error:"<по-русски>"}; 401/403/404/409/422 — как в design.md
Спринта 3. SQL параметризованный (NFR-10←NFR-3); токены/персональные
данные в логах запрещены.

## Доступ к файлам (NFR-7, NFR-9) — сводка

- Выдача ВСЕХ новых фото — только через авторизованные эндпоинты; прямые
  URL исключены (data/uploads/ вне статики — наследование NFR-1).
  Матрица: ракурсы — владелец + ученики пары; СТС — только владелец;
  ВУ — как Спринт 3 (админ-токен; в «Мои документы» — владельцу).
- Проверка пары на КАЖДОМ запросе фото/слотов/броней — серверная
  (параметризованный SELECT student_requests), UI-скрытие не считается.
- Файлы: magic bytes JPEG/PNG + ≤5 МБ до записи (существующий uploads.py,
  новые kinds: car_photo → data/uploads/car_photo/<uuid>.<ext>,
  car_sts → data/uploads/car_sts/<uuid>.<ext>); имена генерирует сервер;
  содержимое не исполняется.

## Обработка ошибок (сводка)

## Решения по НФТ

- NFR-7: матрица доступа выше; серверная проверка при каждом запросе.
- NFR-8: частичный UNIQUE + BEGIN IMMEDIATE + 409 (раздел «Гонки»).
- NFR-9: существующий uploads.py (magic bytes, 5 МБ, uuid-имена),
  расширение kinds.
- NFR-10 (наследование NFR-3/NFR-4): параметризованный SQL во всех новых
  запросах (grep-контроль — задача приемки); токены, заголовки,
  персональные данные (ФИО учеников, документы) в логах запрещены.

## Сознательные ограничения (задокументированы)

- Перенос/отмена подтвержденной брони — точка расширения: статусы
  ('new','confirmed','rejected') и календари допускают новую
  операцию/статус без переделки; в этом объеме операций изменения нет.
- lesson_date материализуется на момент брони; повторение слота на
  следующие недели — вне объема (уникальность слота, а не даты — по
  букве NFR-8 и ОВ-4).
- Разблокировка авто — вне объема (в ТЗ только кнопка блокировки).
- Отдельная сущность «пара» не заводится — связь = статус accepted
  student_requests (наследование ADR-004).
- Колонка photo_path объявляется устаревшей без миграции данных;
  файлы-сироты — унаследованный техдолг.
- In-memory сессии/токены, single-worker, статика без серверной защиты
  страниц — наследованные ограничения, не revisiting.

## Соответствие ADR-004

Отступлений от ADR-004 нет: ФИО — только в users (JOIN/склейка); файлы —
data/uploads/ вне статики, выдача авторизованными эндпоинтами; связь
«принят» — статус заявки; рейтинг не затронут. Новое решение объема —
таблица booking поверх availability (слот целиком) с частичным UNIQUE —
модульный домен по директиве Заказчика; ADR/карта архитектуры
обновляются архитектором при ревью пакета (вне этого пакета).
