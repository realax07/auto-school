# Design: add-pdd-learning

## Context

Кабинет ученика — страница каркаса Vue (С15, multi-entry MPA): вход
frontend/vue/cabinet.html + src/pages/cabinet/App.vue (1106 строк; плоский
DOM + wiring в onMounted — перенос легаси 1:1), разметка дублируется
синхронно в обоих носителях (правило «Разметку держать синхронной с
App.vue», test_cabinet_page.py). Сайдбар .snav — 5 пунктов (Главная, Мои
заявки, Выбрать инструктора (goto), Мои брони, Кошелек), переключение
разделов navTo() по data-tab с хеш-синхронизацией (#/my-requests,
#/my-bookings, #/wallet) через history.replaceState. Секция = div#sec-* с
display:none, «Главная» — секция по умолчанию.

Контент-корпус content/pdd/ в main (PR#137/138): pravila/ 26 глав .md
(332 КБ), znaki/ 8 групп .md — 321 знак (44 КБ), bilety/{abm,cd}/ 80
билетов × 20 вопросов (1.8 МБ; верный ответ помечен ✅, пояснение,
markdown-ссылки ../images/bilety/*), shtrafi/shtrafi-gibdd.md (58
tab-separated строк таблицы + блок «Популярные»), images/znaki/ 321 файл
.png + images/bilety/ 1292 файла — суммарно ~48 МБ. Мокапы согласованы
(«отлично, погнали»): design/mocks/pdd-znaki-student.html,
pdd-pravila-student.html (two-column — правка Заказчика),
pdd-bilety-trenazher.html, pdd-shtrafi-student.html — ИСТОЧНИК ДИЗАЙНА
(классы секций: chips/chip, zn-grid/zn/zn-detail/fine; toc/toc-item/
chapter/prav-wrap; exam-bar/exam-meta, q-card/q-img/q-text/answers/ans,
q-nav/qn/score; search/fines).

Ограничение: NFR-26 (Frontend spec) — первый заход КАЖДОЙ из 14 страниц
≤ 200 КБ gzip (page-чанк + static-import graph), vendor ≤ 150 КБ,
чужих page-чанков в замыкании нет; носитель гейта —
frontend/vue/scripts/check-budgets.mjs (npm run check:budgets, PAGES=14).
Правило репозитория: без новых библиотек (комментарий check-budgets:
«сокращать зависимости (без новых библиотек)»).

## Цели и не-цели

Цели: 4 обучающих раздела в сайдбаре ученика по согласованным мокапам;
контент — из корпуса без ручных правок; кабинет не распухает (первый заход
не меняется); целостность контента проверяется машиной на сборке.

Не-цели: «Вопросы по темам» (36 тем) — дословно «пока не надо»;
персистентность прогресса тренажёра (клиент, MVP); мокап-иллюстрации без
данных в корпусе (текст описания знака, блок штрафа детали, 63-я строка
штрафов); правки .md корпуса руками.

## Решение 1: Доставка контента — build-time JSON + статика изображений

### Тексты .md → build-time JSON (не runtime-парсинг)

Варианты:
- **A (принято)**: build-time генератор .md → структурированные JSON,
  Vite код-сплитит их в lazy-чанки разделов.
- B: runtime fetch .md + парсер markdown в браузере.
- C: класть .md в vite-бандл импортами `?raw` без генератора.

Решение — A. Обоснование:
- B требует новую зависимость (marked/markdown-it — запрещено бюджетным
  правилом «без новых библиотек») или самописный парсер — хрупко против
  фактических вариаций корпуса (формат t8 «## | 8.1.1» с pipe, tab-separated
  таблица штрафов, метка ✅ внутри элемента списка, markdown-ссылки
  картинок). Парсить на каждом клиенте каждый заход — бессмысленная работа
  при неизменном корпусе.
- C вталкивает сырые .md в чанки без валидации и маппинга картинок
  (../images/* неразрешимы в рантайме продукта); нет контроля целостности
  до сборки.

Генератор: frontend/vue/scripts/generate-pdd-json.mjs (Node stdlib, без
зависимостей), шаг сборки: package.json `"build": "node
scripts/generate-pdd-json.mjs && vite build"` — Dockerfile
frontend-builder выполняет `npm run build` (генератор попадает в образ
автоматически), bare-metal-порядок `npm ci && npm run build` не меняется
(FR-57). Выход: frontend/vue/src/pages/cabinet/pdd-data/*.json — В GIT НЕ
КОММИТЯТСЯ (.gitignore), корпус — единственный источник истины, рассинхрон
невозможен по построению (генератор перезаписывает всё). Имена файлов —
с префиксом pdd- (роль чанка в check-budgets определяется тривиально):

- pdd-znaki.json — 8 групп (id, название, счётчик), знаки (номер, название,
  группа, image=/pdd-assets/znaki/<номер>small.png);
- pdd-pravila.json — 26 глав (id, заголовок, html-блоки пунктов);
- pdd-shtrafi.json — строки (article, violation, penalty);
- pdd-bilety-index.json — 2 категории × 40 билетов (id, номер,
  количество вопросов, флаг «есть картинки»);
- pdd-bilety-abm-01.json … pdd-bilety-cd-40.json — по билету: 20 вопросов
  (text, image|null → /pdd-assets/bilety/<имя>, options[{text, correct}],
  explanation) — ШАРДИНГ ПО БИЛЕТУ (см. «Бюджеты»: sharding обоснован
  арифметикой чанков).

HTML для правил: генератор делает минимальную белую конвертацию
абзацев/заголовков корпуса в строки html (разбивка по пустой строке,
экранирование спецсимволов, без markdown-парсера) — форматы корпуса
известны и конечны (прецедент селекторов краулера в README корпуса).
Разметка секций рендерит строки через v-html ТОЛЬКО для этих
сгенерированных полей (контент корпуса — доверенный источник репозитория;
пользовательский ввод в разделах отсутствует).

Гейты целостности генератора (провал сборки при нарушении — build fails
loudly):
- bilety: 80 билетов, ровно 20 вопросов в каждом, ровно один ✅ на вопрос,
  2–5 вариантов; каждая ссылка ../images/bilety/* существует на диске
  (факт: 1094/1094 ✓);
- znaki: 8 групп; 321 знак; у каждого ровно один
  images/znaki/<номер>small.png (факт: 321/321 ✓; дедупликация stem по
  точному совпадению — «1.1small» ≠ «1.10small», коллизий нет: stems
  уникальны);
- pravila: 26 файлов, ровно один H1 в каждом (факт: 26/26 ✓);
- shtrafi: заголовок таблицы «Пункт КоАП…» найден, строк ≥ 1, каждая
  строка имеет 3 tab-поля (факт: 58/58 ✓).

### Картинки — статикой мимо бандла (роут /pdd-assets)

Варианты:
- **A (принято)**: GET /pdd-assets/{group}/{file} в backend/app.py —
  FileResponse из content/pdd/images/{group}/.
- B: nginx alias /pdd-assets/ → content/.
- C: импортировать изображения в vite (assetsInclude) — 48 МБ в dist и
  бандл-графе.

Решение — A. Обоснование: прецедент /vue/assets/{path} в том же app.py
(С9 задача 2.3; «отдача тем же сервисом — ADR-001»; ADR-001 отклонил
отдельный фронтенд-вебсервер для статики) — тот же traversal-guard
(«/», «..», скрытые), явная карта media-types (.png/.gif/.jpg/.jpeg —
не зависеть от системных mimetypes; неизвестный суффикс — 404), групп
ровно две (znaki|bilety — остальное 404, угадывание не вводится).
B ломает константу «один FastAPI-сервис отдает API и статику» (ADR-001) и
bare-metal-деплой без nginx (compose-nginx проксирует app — отдельный
alias потребовал бы nginx-конфига в обоих режимах). C делает dist ~50 МБ
и тянет 48 МБ в бандл-инвентарь — прямо противоречит цели.

Маршрут публичный (без auth) — как /vue/assets: материалы — публичные
учебные (правила/знаки/официальные экзаменационные вопросы ГИБДД;
правовая заметка README корпуса — про продакшн-использование, кабинет
авторизован, а <img>-теги без токенов не усложняются).

Dockerfile: `COPY content/ content/` рядом с `COPY frontend/ frontend/`
(роут читает content/pdd/images относительно ROOT — тот же layout, что в
репозитории; bare-metal без изменений). Образ +~48 МБ — принимается
(CDN/обрезка — вне скоупа S17; в образ идут и 198 неиспользуемых файлов
bilety — сознательно: корпус не выборочно трепется).

## Решение 2: Тренажёр «Билеты» — клиентский автомат

Состояние — Vue ref внутри lazy-компонента секции; сервер НЕ участвует
(MVP, решение Заказчика: персистентность НЕ требуется). Данные —
pdd-bilety-index.json (статический импорт компонента) + JSON билета
(динамический import по выбору — отдельный чанк ~6–8 КБ gzip).

Автомат экранов: выбор (категория abm|cd, билет 1–40) → тренировка →
результат. Тренировка:
- шапка exam-bar: «Билет N», категория, ТАЙМЕР 20:00 (обратный отсчет,
  setInterval 1с; 00:00 → авто-«сдать» с подсчётом отвеченного);
- карточка вопроса: номер (qn), текст (q-text), изображение (q-img,
  /pdd-assets/bilety/…, native loading="lazy" — 48 МБ не тянутся заранее),
  варианты (ans); клик по варианту ФИКСИРУЕТ ответ немедленно: подсветка
  выбранного (неверный — красный), верного (зелёный), раскрытие блока
  пояснения («Пояснение» из корпуса); повторный клик по тому же вопросу
  ответ не меняет (фиксация однократная — статус для навигации честный);
- навигация q-nav 1–20 со статусами: отвечен верно (зелёный), неверно
  (красный), не отвечен (нейтральный), текущий (подсветка on);
- «Сдать» досрочно в любой момент;
- результат: счёт верных из отвеченных, список 1–20 со статусами, кнопки
  «Пройти снова» и «Выбрать другой билет».

Случайный/последовательный порядок: последовательный порядок вопросов
билета (как на источнике — билет фиксированный); случайный порядок —
не требуется решением и усложняет сверку с источником. Порядок ВАРИАНТОВ
— как в корпусе.

## Решение 3: Интеграция кабинета — сайдбар, хеши, lazy-секции

- 4 кнопки .snav после «Кошелек» (к порядку существующих, БЕЗ
  перегруппировки): Знаки (ico ◈), Правила (ico ☰), Билеты (ico ◉),
  Штрафы (ico ₽-стиль ⊘/⚠ — из мокапов не берется, у секций мокапов свой
  side-nav; иконки — существующие юникод-глифы стиля кабинета).
- Хеши: #/pdd-signs, #/pdd-rules, #/pdd-tickets, #/pdd-fines — паттерн
  navTo(): is/is/is-цепочка расширяется; wantHash-тернарник; начальные
  if (location.hash === '#/pdd-signs') navTo(...) и т.д. (прецедент
  #/my-requests/#/wallet; reload сохраняет раздел — replaceState).
- Секции: div#sec-pdd-* (display:none) в обоих носителях; содержимое —
  defineAsyncComponent(() => import('./sections/PddSigns.vue')) с
  v-if="visited" (чанк грузится при ПЕРВОМ открытии раздела, остается
  смонтированным). Разметка-скелет (page-head: kicker «Обучение · ПДД» +
  h1 из мокапа) — синхронно в cabinet.html и App.vue; динамические списки
  (чипы/сетка/toc/вопросы/таблица) — только в компонентах (прецедент
  sec-requests: скелет во входе, v-for в App.vue). navTo дергает
  visited/загрузку — flat-стиль wiring сохраняется.
- UX-переполнение сайдбара (9 пунктов): высота .snav 9×~45px + brand —
  на десктопе помещается, на низких окнах — нет. Решение: одна добавленная
  CSS-строка в КОНЦЕ styles.css `.snav{overflow-y:auto}` (+ при
  необходимости max-height) — вербатим-гард test_cabinet_page.py требует
  дословности СУЩЕСТВУЮЩИХ строк мокапа, добавление правил в конец —
  разрешенный паттерн (прецедент С16: «новые правила только добавлены в
  конце <style>»). Сворачивание групп НЕ вводится (два визуальных блока
  «обучение» из мокапов в сайдбар кабинета не переносились — мокапы
  задают контент секций, не реструктуризацию .snav).
- Плитки «Главной» («Обучение ПДД» СКОРО и др.) не трогаются —
  вербатим-гард плиток (test_cabinet_page.py: «разметка плиток
  отличается от мокапа» — падение при правке).

## Бюджеты чанков: доработка check-budgets (носитель гейта NFR-26)

Факт-инвентарь: scripts/check-budgets.mjs считает замыкание входа
регуляркой `(?:from"|import")…` — она ловит и ДИНАМИЧЕСКИЕ импорты
(`import("./pdd-…js")`), т.е. lazy-чанки попали бы в «первый заход»
кабинета и (в) «чужие чанки» бы сработали ложно. Собственный текст
NFR-26 (и комментарий скрипта) — «static-import graph»: скрипт правится
под свою же спеку, без правки спеки Frontend.

Изменения скрипта (задача 17.2):
1. importedChunks разделяет статические (`from"…`, `import"…`) и
   динамические (`import("…")`) импорты;
2. (б)/(в) — замыкание = СТАТИЧЕСКОЕ (семантика NFR-26, поведение для
   14 существующих страниц не меняется — динамических импортов у них
   сегодня нет);
3. роль 'lazy': имя чанка с префиксом pdd- (роль 'page'/'shared'/
   'vendor' без изменений; PAGES = 14 — новых html-входов нет);
4. НОВОЕ (г): каждый lazy-чанк ≤ 150 КБ gzip (выравнено с vendor-лимитом);
5. НОВОЕ (д): ни один lazy-чанк не входит в статическое замыкание ни
   одной страницы (гард «кабинет не распухает» — первый заход всех 14
   страниц не меняется вообще).

Арифметика чанков (по факту корпуса; gzip русского текста ≈ ×3.5–4):
- pdd-znaki.json → ~15 КБ gzip — один чанк;
- pdd-pravila.json → ~90 КБ gzip — один чанк (шардинг по главе не нужен:
  26 входов усложняют toc без выигрыша первого захода — он и так lazy);
- pdd-shtrafi.json → ~6 КБ gzip;
- bilety: whole-corpus JSON 1.8 МБ ≈ 450–500 КБ gzip — В ПРЕДЕЛ (г) НЕ
  влезает; по категориям (abm/cd) ≈ 250 КБ gzip — тоже нет; ПО БИЛЕТУ
  (80 файлов ≈ 20 КБ raw ≈ 6–8 КБ gzip каждый) — да. Отсюда шардинг
  pdd-bilety-<cat>-<nn>.json: (г) делает выбор «по билету» вынужденным,
  а не вкусовым — index-чанк мал, выбор билета тянет один маленький чанк.

Итог по NFR-26: первый заход кабинета = page + shared + vue (без
изменений, ≤ 200 КБ gzip, проверяется тем же гейтом); контент-чанки —
отдельные lazy-чанки разделов с собственным бюджетом (г) и гардом (д).

## Мокапы — источник дизайна и границы переноса

design/mocks/pdd-*.html — согласованы («отлично, погнали»), переносятся
классы/структура/стили секций (chips/zn-grid/zn-detail/fine, toc/chapter/
prav-wrap, exam-bar/q-card/answers/q-nav/score, search/fines) в контекст
кабинета (грид hero/frame). НЕ переносятся: side-nav мокапов (свой
нав-список мокапа — сайдбар кабинета уже существует), side-user, brand —
кабинетские. Иллюстративные данные мокапов (описание знака, fine-текст,
63 строки таблицы, 29 пунктов toc) не переносятся как данные — рендер по
корпусу (см. proposal «Сверка»). Гарды мокапов кабинета (cabinet-student)
не затрагиваются: существующие строки/CSS-фрагменты дословны, новые —

## Риски и открытые вопросы

- Расхождение «63 строки» решения vs 58 строк корпуса — не блокирует
  (раздел по корпусу; пополнение перегенерацией; при потребности
  Заказчика — сверка с источником, примечание уже в decision-файле).
- Описания знаков и карта знак→статья КоАП отсутствуют в корпусе —
  интерфейс допускает, данные появятся перегенерацией (решение
  Заказчика); S17 не сочиняет контент.
- Правовая заметка README корпуса (лицензионные условия источника перед
  публичной частью) — разделы живут в авторизованном кабинете; вынос
  за авторизацию/публичная часть — вне скоупа S17.
- Размер образа +~48 МБ и 198 неиспользуемых изображений bilety —
  принимается MVP (чистка корпуса = правка контента, вне S17).
- v-html для сгенерированных полей правил — допустимо (контент корпуса —
  репозиторный, пользовательского ввода в разделах нет); экранирование
  на этапе генерации, никаких сырых md-строк в рантайме.
