# Design: add-calendar-weeks-availability

Источники решений: requirements-sprint10.md (УТВЕРЖДЕН, FR-87…FR-97,
NFR-29…NFR-32; дословное решение Заказчика — в разделе «Первичный
источник»); decisions/2026-11-04-sprint10-calendar-go.md; существующий
контур: openspec/specs/instructor-availability/spec.md (интервалы по дням
недели), openspec/specs/booking/spec.md (бронь слота целиком, MAJ-1),
backend/instructor_availability.py (PUT полной замены + 409 через
booking.blocking_bookings, BEGIN IMMEDIATE), backend/booking.py
(booking.availability_id, lesson_date = ближайшая дата weekday, частичный
UNIQUE uq_booking_active_slot по availability_id), backend/db.py (CREATE
TABLE IF NOT EXISTS + _COLUMN_MIGRATIONS, init_db через lifespan),
frontend/js/dashboard-instructor.js (calBuildGrid — понедельник текущей
недели, calSelected «weekday-hour», «Сохранить график» = один PUT),
frontend/cabinet.html + js/cabinet.js («График на неделю», слоты
free/taken/mine). Альтернативы — research.md (R1–R5). ADR-010 фиксирует
модель recurring/one_off.

Ключевые решения СА: **D1** тип слота recurring|one_off на записи
availability; **D2** миграция — перестройка таблицы под расширенный UNIQUE,
существующие строки → recurring через DEFAULT без перезаписи данных;
**D3** экземпляр = (availability_id, дата), серии не материализуются;
**D4** занятость/бронь на уровне экземпляра (частичный индекс
availability_id + lesson_date), контракт POST брони не меняется;
**D5** API — расширение существующего PUT/GET (не новый эндпоинт), MAJ-1
→ 409 с датой в перечне; **D6** запрет прошлого — серверная валидация
каждого PUT (422), прошедшие one_off — immutable-история; **D7** ученику
экземпляры недели выдает сервер (GET slots?date=), инструктор разворачивает
серии локально; **D8** история состояний серий не хранится (факты истории —
брони с lesson_date); **D9** рендер недели — 7 реальных дат от понедельника,
подпись диапазона с обеими частями; **D10** попап — оверлей у ячейки,
решение по каждой ячейке индивидуально.

## Модель данных (NFR-30; DDL уточняет dev в границах)

### Таблица availability — расширяется (перестройка, D1/D2)

Новые колонки (перестройка таблицы — SQLite не снимает табличный UNIQUE
через ALTER):

- `slot_type TEXT NOT NULL DEFAULT 'recurring' CHECK (slot_type IN
  ('recurring','one_off'))` — recurring = еженедельная серия (weekday +
  start_time + end_time); one_off = конкретная дата (FR-90)
- `slot_date TEXT NOT NULL DEFAULT ''` — дата экземпляра one_off
  'YYYY-MM-DD'; '' для recurring; CHECK
  `(slot_type = 'recurring' AND slot_date = '') OR (slot_type = 'one_off'
  AND slot_date <> '')`
- UNIQUE `(instructor_id, weekday, start_time, end_time, slot_date)` —
  заменяет старый UNIQUE: recurring-дубли невозможны, как прежде; one_off
  допускает ту же пару «день недели + время» на ДРУГУЮ дату; одна one_off
  на дату+время — ровно одна строка. Для one_off weekday = день недели
  slot_date (сервер проверяет при PUT — 422 при несоответствии)
- индекс idx_availability_instructor — пересоздается после rebuild

Миграция (idempotent, guard по отсутствию колонки slot_type): одна
транзакция BEGIN IMMEDIATE → CREATE TABLE availability_new (полный новый
DDL) → INSERT INTO … SELECT id, instructor_id, weekday, start_time,
end_time, created_at FROM availability (id и created_at СОХРАНЯЮТСЯ —
ссылки броней booking.availability_id остаются валидными; FK-контракта нет,
PRAGMA foreign_keys не включает) → DROP TABLE availability → RENAME →
пересоздать индекс. Существующие строки получают slot_type='recurring',
slot_date='' через DEFAULT — данные НЕ перезаписываются: «существующие
интервалы становятся повторяющимися» (FR-97) выполняется самим
определением колонки. Повторный запуск — no-op (guard), дубли невозможны
(NFR-30). Откат отката не требуется: колонки аддитивны, старый код читает
старые колонки без изменений.

### Таблица booking — только замена индекса (D4)

- Частичный UNIQUE `uq_booking_active_slot` переиндексируется:
  `ON booking(availability_id, lesson_date) WHERE status IN
  ('new','confirmed')`. Существующие данные совместимы (две активные брони
  одного availability_id сегодня невозможны — старый индекс строже).
  Эффект: разные ДАТЫ одной recurring-серии бронируются независимо;
  «Слот уже занят» = занят ЭКЗЕМПЛЯР (дата + время) (FR-95/FR-96);
  один и тот же экземпляр по-прежнему максимум одна активная бронь
  (наследование NFR-8).
- lesson_date: для новых броней — ТОЧНАЯ дата экземпляра (поле date
  запроса или материализация легаси-пути); тип TEXT 'YYYY-MM-DD' — без
  изменений схемы. materialize_lesson_date (MIN-1) сохраняется для
  легаси-пути и как правило «сегодня» сервера.

### Экземпляр и разворот серий (D3, D8)

- Экземпляр слота = (availability_id, дата). Разворот recurring-серии в
  даты — вычисление при выдаче/рендере: экземпляры не материализуются в
  строки (точка расширения — исключение экземпляра серии).
- one_off отображается только на slot_date; recurring — на каждой неделе
  в колонке weekday. Совпадение one_off (дата+время) с экземпляром серии:
  в БД возможны обе строки (уникальность допускает), отображается ОДИН
  слот — тип в UI one_off (более специфичный, закреплен за датой);
  покрытие экземпляра новым графиком (проверки 409/запрета прошлого) —
  по (дата, start_time, end_time): экземпляр покрыт, если его покрывает
  ЛЮБАЯ строка нового графика (one_off с этой датой+временем ИЛИ серия с
  этим weekday+временем) — дублей отображения нет (FR-90), брони обеих
  строк учитываются.
- История состояний серий НЕ хранится (D8): прошлые недели серий
  отображаются по текущему состоянию серии; фактическая история — записи
  booking (lesson_date, статус, decided_at) неизменяемы. Версионирование
  серий — точка расширения.

## Контракт availability (NFR-29; D5)

### GET /api/instructor/availability (расширение, только владелец)

Ответ 200 {ok:true, intervals:[{weekday, start_time, end_time, slot_type,
date}]}, упорядочены по weekday, start_time (как прежде); slot_type ∈
'recurring'|'one_off'; date — 'YYYY-MM-DD' для one_off, null для recurring.
Существующие потребители (старый UI до Спринта 10, тесты s3/s7) читают
weekday/start/end — поля аддитивны. Список полон: все recurring-серии и
все one_off независимо от дат — клиент разворачивает серии сам (D7).

### PUT /api/instructor/availability (расширение, только владелец)

Тело: {intervals:[{weekday, start_time, end_time, slot_type?, date?}]} —
ПОЛНЫЙ новый график (наследование полной замены FR-29/FR-30). Валидации
(422 {ok:false, error}, до транзакции):

- базовые — без изменений: weekday 0..6, HH:MM, start < end, дубликаты
  (с учетом slot_type/date) схлопываются;
- slot_type отсутствует → 'recurring' (старое тело = график из recurring
  слотов — NFR-29: «означает сохранение графика из ПОВТОРЯЮЩИХСЯ слотов»);
  one_off и recurring в одном теле допустимы в любом сочетании;
- slot_type='one_off': date обязательна (ISO YYYY-MM-DD, существующая
  дата) → иначе 422; weekday обязан совпадать с днем недели date → иначе
  422 (сервер не доверяет клиенту); slot_type='recurring' с непустой date
  → 422;
- ЗАПРЕТ ПРОШЛОГО (D6, FR-93, NFR-31 — серверная проверка каждого PUT):
  пусть NOW = локальное время сервера (МСК). Отклонить 422
  «Прошедшие слоты не подлежат изменению», если:
  (а) в payload есть слот (recurring — материал первого экземпляра серии
  ≥ сегодня НЕ проверяется: серия правится на будущее; one_off —
  date+start_time), у которого начало ≤ NOW — т.е. создание/изменение
  прошедшего one_off запрещено (правило границы: начало слота < текущего
  момента → прошедший; инструктору разрешено править НАЧАВШИЙСЯ текущий
  слот серии — дословно «≥ текущей даты/времени», открытый вопрос
  требований);
  (б) в БД существует one_off с началом < NOW, отсутствующий в payload
  или измененный — прошедшие one_off immutable-история; клиент возвращает
  их в payload без изменений (сетка прошедшей недели рендерит их и
  отправляет);
  прошедшие ЭКЗЕМПЛЯРЫ recurring-серий не хранятся и не проверяются
  (история фиксируется бронями — D8); правка серии меняет только текущие/
  будущие экземпляры (FR-91).

Проверка MAJ-1 (в транзакции BEGIN IMMEDIATE, сериализация с
create_booking — наследование M-3 review-001): для каждой активной брони
('new'/'confirmed') вычислить экземпляр (start_time, end_time, дата
= booking.lesson_date) и проверить покрытие новым графиком (см. правило
совпадения выше); экземпляры с началом < NOW не проверяются (прошедшее
не блокирует — замена не меняет записей истории). Нераскрытые экземпляры
→ 409 {ok:false, error, conflicts:[{weekday, start_time, end_time, date,
booking_statuses}]} — перечень затронутых слотов С ДАТОЙ (FR-92, NFR-29:
«в перечень затронутых добавляется дата»); прежний график не изменен,
брони не меняются. Формат легаси-конфликтов сохраняется: для recurring-
экземпляров без брони-привязки к дате поле date = null; потребителей
поля conflicts (UI Спринта 7) расширяем датой — аддитивно.

Запись: DELETE + INSERT (учитывая slot_type/slot_date) в той же
транзакции. Ответ 200 — как GET (полный сохраненный график с типами и
датами).

### Совместимость (NFR-29)

- старое тело {intervals:[{weekday,start_time,end_time}]} продолжает
  приниматься: валидации/коды/формат ответа прежние; семантика — график
  из recurring слотов (one_off-строки, если были, заменяются — с 409-
  защитой при активных бронях на их экземплярах);
- тесты tests/test_s3_backend.py, tests/test_s7_backend.py (PUT/GET)
  остаются зелеными без правок — контроль задачей приемки;
- Кейс «сохранение в момент, когда слот стал прошедшим» (гонка
  правки и времени): PUT с прошедшим one_off отклоняется 422, UI показывает
  ошибку и перезагружает сохраненное состояние (открытый вопрос — дефолт).

## Контракт booking (FR-95, FR-96, NFR-31; D4/D7)

### POST /api/student/bookings (расширение, без ломающих изменений)

Тело: {availability_id, date?} — date опциональна 'YYYY-MM-DD':

- date указана: recurring — date должна попадать на weekday серии (сервер
  проверяет, 422) → lesson_date = date (точный экземпляр); one_off —
  date должна равняться slot_date (иначе 422);
- date отсутствует (легаси-вызов старого UI): materialize_lesson_date
  (ближайшая дата weekday, MIN-1) — поведение прежнее; для one_off
  lesson_date = slot_date (единственная дата);
- ДОСТУП/ГОНКИ — без изменений: нет принятой пары → 403; слот не существует
  или чужой → 404; транзакция BEGIN IMMEDIATE + частичный индекс
  (availability_id, lesson_date) → занятый ЭКЗЕМПЛЯР → 409 «Слот уже занят»
  (NFR-8);
- НОВОЕ — проверка будущего (FR-96, NFR-31): дата+start_time экземпляра
  (lesson_date + start_time) ДОЛЖНА быть строго больше NOW (МСК) → иначе
  422 {ok:false} «Слот уже начался или прошел» — независимо от клиента.
  Легаси-путь материализует ≥ сегодня; кейс «сегодня, но уже начался»
  теперь отклоняется (сужение поведения по FR-96 — задокументировано;
  проверить время-зависимость существующих тестов s5 на приемке);
- решение «начавшийся слот» — по началу слота (не по концу).

### GET /api/student/instructors/{id}/slots?date=YYYY-MM-DD (расширение)

- Без параметра — легаси-ответ без изменений: {ok, slots:[{id, weekday,
  start_time, end_time, state}]} (старый UI и существующие тесты);
- С параметром date (любой день отображаемой недели; сервер приводит к
  понедельнику этой недели): {ok, week:{monday:'YYYY-MM-DD',
  sunday:'YYYY-MM-DD'}, instances:[{availability_id, date, weekday,
  start_time, end_time, state}]} — разворот серий в ЭКЗЕМПЛЯРЫ недели
  (D7): recurring → один instance на дату серии в этой неделе (включая
  прошедшие дни недели — для прошлых недель ученик видит свои статусы);
  one_off → instance на slot_date (только если попадает в неделю);
  state по экземпляру: free / busy (чужая или своя confirmed активная
  бронь ЭТОГО экземпляра) / pending (свой запрос 'new' на ЭТОТ экземпляр)
  — наследование состояний, поднятое с availability_id на (id, date);
  доступ — наследование: не принятая пара → 403, инструктор не существует
  → 404 (проверки прежние).

### GET /api/student/bookings, GET /api/instructor/bookings, confirm/reject/cancel

БЕЗ ИЗМЕНЕНИЙ: lesson_date уже в выдаче — календари отображают брони
РОВНО на своих датах (наследование FR-74); решения немедленно, мимо
«Сохранить».

## Клиентский контракт: реальный календарь (D9; FR-87, FR-88, NFR-32)

- Неделя = 7 последовательных реальных дат, начало — понедельник
  отображаемой недели; состояние UI — якорная дата (любой день недели),
  навигация «←»/«→» сдвигает якорь на ±7 дней; «эта неделя» — якорь =
  текущая дата. Переходы — без перезагрузки страницы.
- Колонки подписываются реальной датой (день месяца) и днем недели;
  попадание в день недели — по самому числу календаря (валидационные
  факты приемки: 30.11.2026 — понедельник; 31.12.2026 — четверг;
  29.02.2028 — вторник); длина месяцев 28/29/30/31 и смена месяца/года
  внутри недели — следствия арифметики дат, фиксированных решеток без
  дат нет.
- Подпись диапазона: «D месяца — D месяца год»; обе части при пересечении
  месяца («30 ноября — 6 декабря 2026») и года («28 декабря 2026 —
  3 января 2027»); подпись всегда согласована с колонками (обновление
  атомарно с сеткой).
- «Сегодня» — колонка реальной текущей даты по МСК (клиент вычисляет
  МСК как UTC+3 — единая точка с сервером nowMoscow/MIN-1; локальная
  таймзона браузера не используется).
- «Сейчас» (граница правок/брони на клиенте) — тоже МСК: ячейка
  редактируема, если date+start_time ≥ NOW (инструктор) / > NOW (ученик);
  клиентская проверка — UX, не защита (сервер проверяет всегда).
- Горизонт навигации ±12 месяцев от текущей недели (дефолт открытого
  вопроса; ПМ может пересмотреть) — кнопки за пределами неактивны.
- NFR-32: инструктор рендерит любую неделю ИЗ УЖЕ ЗАГРУЖЕННЫХ
  определений GET availability (разворот серий локально) — переключение
  недели без сетевого запроса; догрузка броней (GET bookings) —
  асинхронно, не блокирует решетку. Ученик: колонки и подпись недели
  отрисовываются локально сразу, экземпляры/состояния недели — GET
  slots?date= асинхронно (≤ 500 мс лаг решетки; попап ≤ 200 мс —
  локальная отрисовка).

## Клиентский контракт: попап-редактор (D10; FR-89, FR-91)

- Клик по свободной редактируемой ячейке (начало ≥ NOW) открывает popover:
  мини-окно НАД ячейкой, ПОВЕРХ страницы (оверлей, position у ячейки —
  над или под), выбор «Разово» / «Повторяющееся» (радио) + подтверждение;
  клик по отмеченной редактируемой ячейке — тот же попап с ТЕКУЩИМ типом
  (предвыбран) и действиями «сменить тип» (выбор другого + подтвердить) и
  «убрать слот».
- Тип применяется к ячейке ТОЛЬКО по подтверждению в попапе и входит в
  несохраненные правки до «Сохранить график» (наследование контура
  «Сохранить/Отменить» FR-68); попап не сдвигает и не переполняет сетку
  (абсолютное позиционирование поверх), у границ вьюпорта сдвигается
  внутрь без обрезки; закрытие без подтверждения (клик вне, кнопка
  закрытия, Esc) — ячейка без изменений.
- Тип выбирается ИНДИВИДУАЛЬНО для каждой ячейки — режима «весь график
  разовый/повторяющийся» нет; правка recurring-ячейки применяется к
  серии (текущие/будущие экземпляры), one_off — к своей дате (сервер
  исполняет, клиент отображает).
- Прошедшая ячейка (начало < NOW) попап не открывает (стиль просмотра,
  cursor по умолчанию); прошедшая неделя — вся сетка просмотр (клиент;
  сервер дублирует — D6).
- Отрисовка попапа — локальная, без сетевых вызовов (≤ 200 мс, NFR-32).

## Видимость и доступ (NFR-7, наследование) — матрица

|| Поверхность | Кто видит |
||---|---|
|| GET/PUT /api/instructor/availability (типы, даты, правки) | только владелец (чужой/несуществующий → 404-неразличение) |
|| GET slots?date= (экземпляры недели) | только ученик принятой пары (403 иначе, 404 инструктора) |
|| POST /api/student/bookings (+date) | только ученик принятой пары; чужой слот → 404 |
|| Прошедшие недели/ячейки | просмотр у обоих; правки отклоняются сервером (NFR-31) |

Проверки — на сервере при каждом запросе; UI-скрытие проверкой не
считается; SQL параметризованный (NFR-10); даты/времена — из параметров
запросов, weekday вычисляется серверно из даты (не доверять клиенту).

## Обработка ошибок (сводка)

|| Ситуация | Ответ | Требование/решение |
||---|---|---|
|| PUT: one_off без date / несуществующая дата / weekday ≠ дню недели даты / recurring с date | 422 | FR-90, D5 |
|| PUT: payload создает/меняет прошедший one_off (начало ≤ NOW) | 422 «Прошедшие слоты не подлежат изменению» | FR-93, NFR-31, D6 |
|| PUT: payload убирает/меняет прошедший one_off из БД | 422 | FR-93, D6 (immutable-история) |
|| PUT: убирает экземпляр с активной бронью (дата в перечне) | 409 conflicts[{…, date}] | FR-92, MAJ-1, NFR-29 |
|| PUT: старое тело без slot_type/date | 200 — график из recurring слотов | NFR-29 |
|| POST bookings: date ≠ slot_date / date не на weekday серии | 422 | D4 |
|| POST bookings: экземпляр начался/прошел (начало ≤ NOW) | 422 «Слот уже начался или прошел» | FR-96, NFR-31 |
|| POST bookings: экземпляр занят (активная бронь этой даты) | 409 «Слот уже занят» | NFR-8, D4 |
|| POST bookings: нет принятой пары / чужой слот | 403 / 404 | наследование NFR-7 |
|| GET slots без pair / чужой инструктор | 403 / 404 | наследование (без изменений) |

## Решения по НФТ

- NFR-29: расширение PUT/GET аддитивно; легаси-тело = recurring-график;
  коды/форматы прежние; GET достаточен для нового UI (типы+даты); 409
  расширен датой; тесты s3/s7 — без правок (контроль на приемке).
- NFR-30: миграция idempotent по построению (guard по колонке; DEFAULT —
  существующие строки recurring без перезаписи; rebuild сохраняет id и
  created_at; повторный запуск — no-op); ни один интервал и бронь не
  теряются (INSERT SELECT всех строк); контроль — предсозданная БД в
  тестах.
- NFR-31: серверная проверка границы времени при КАЖДОМ PUT availability
  и POST bookings (422 {ok:false}); NOW — локальное время сервера (МСК,
  nowMoscow/MIN-1); доступ — наследование (404-неразличение, 403 пара);
  параметризованный SQL, формат ошибок {ok:false}.
- NFR-32: инструктор — рендер недели из загруженных определений (нулевая
  сеть при листании), догрузка броней асинхронна; ученик — решетка
  локально, экземпляры асинхронно; попап — локальная отрисовка; подпись
  обновляется атомарно с колонками.
- Наследование NFR-7…NFR-10, NFR-11…NFR-28 — без изменений (префиксы API,
  {ok:false}, single-worker, idempotent-миграции на существующем volume).

## Сознательные ограничения (задокументированы)

- История состояний серий не хранится (D8) — прошлые недели серий
  отображаются по текущему состоянию; записи броней — факты истории.
- one_off поверх экземпляра серии хранится обеими строками (уникальность
  допускает), отображается один слот (тип one_off); «исключение экземпляра
  серии» — точка расширения, NOT в объеме.
- Легаси-POST bookings без date бронирует ближайший экземпляр серии;
  кейс «сегодня, но начался» теперь отклоняется (сужение по FR-96) —
  проверить время-зависимость тестов s5.
- Горизонт навигации ±12 месяцев — клиентский дефолт открытого вопроса
  (ПМ может пересмотреть); серверного лимита листания нет.
- Сервер не лимитирует горизонт PUT (создание one_off на даты дальше
  ±12 месяцев валидно) — клиентское ограничение достаточно; серверный
  лимит — точка расширения.
- Уведомления об изменениях графика — backlog; Vue 3 — вне Спринта 10.

## Соответствие ADR

Новые решения объема фиксирует ADR-010 (модель recurring/one_off,
совместимость, альтернативы R1–R5). ADR-004/005 (ПД в users, слоты целиком,
409 MAJ-1) — без отступлений: тип слота не ПД; слот бронируется целиком;
защита броней расширена на экземпляры (усиление того же решения). Карта
архитектуры обновляется архитектором при ревью пакета (задача 10.3).
