# Delta: booking

## MODIFIED Requirements

### Requirement: Запрос брони на слот

Ученик пары MUST уметь выбрать слот из графика инструктора и отправить
запрос брони; слот — интервал графика целиком, без нарезки на
подынтервалы (ОВ-3). Запрос создается со статусом «новая» и виден
инструктору. Повторный запрос на занятый слот (активный запрос или
подтвержденная бронь) не создается. Повторный запрос после отклонения
допустим, без ограничений на количество (наследование FR-47, ОВ-3…ОВ-5).
Бронирование MUST быть возможно ТОЛЬКО для будущих слотов: запрос
брони возможен для слота (экземпляра), время начала которого строго
больше текущего момента (МСК); прошедшие и уже начавшиеся слоты — просмотр
без кнопки брони, и сервер MUST отклонять запрос брони на прошедший/
начавшийся слот независимо от клиента (FR-96, NFR-31). Бронь MUST
фиксироваться на КОНКРЕТНОЙ ДАТЕ экземпляра: для разового слота — его
дата; для повторяющегося — дата недели, в которой ученик бронирует слот
(новое поле даты запроса — аддитивно; запрос без даты в старом формате
продолжает приниматься и бронирует ближайший будущий экземпляр серии,
как прежде — контракт POST не меняется ломающим образом). Остальной
контур брони — без изменений: POST /api/student/bookings по
availability_id, гонка «Слот уже занят», доступ по принятой паре,
решения инструктора немедленно (Спринты 5–7).

Источник: requirements-sprint10.md FR-96, NFR-31; наследование
requirements-booking-docs.md FR-47, ОВ-3, ОВ-4, ОВ-5.

#### Scenario: Запрос создается со статусом «новая» и виден инструктору

- **GIVEN** пара создана и у инструктора есть свободный будущий слот
- **WHEN** ученик выбирает слот и отправляет запрос брони
- **THEN** запрос создан со статусом «новая» и появляется у инструктора в запросах брони

#### Scenario: Занятый слот не бронируется повторно

- **GIVEN** у слота есть активный запрос или подтвержденная бронь одного ученика пары
- **WHEN** другой ученик той же пары пытается забронировать этот слот
- **THEN** действие отклонено, дублирующий запрос не создан

#### Scenario: Слот бронируется целиком

- **GIVEN** у инструктора есть интервал графика 10:00–14:00
- **WHEN** ученик бронирует этот слот
- **THEN** занятием считается весь интервал 10:00–14:00 (нарезка на подынтервалы не выполняется)

#### Scenario: Повторный запрос после отклонения допустим

- **GIVEN** запрос брони ученика на слот отклонен инструктором (с комментарием)
- **WHEN** ученик снова отправляет запрос на этот же слот
- **THEN** новый запрос создается (повторная подача не ограничена)

#### Scenario: Бронь фиксируется на конкретной дате экземпляра

- **GIVEN** повторяющийся слот «Чт 16:00–18:00», ученик бронирует экземпляр на 12 ноября
- **WHEN** запрос брони отправлен с этой датой
- **THEN** бронь создана именно на 12 ноября 16:00–18:00 (дата экземпляра зафиксирована в записи брони); запрос с датой, не попадающей на день недели серии (или не равной дате разового слота), отклоняется сервером

#### Scenario: Запрос брони на прошедший или начавшийся слот отклоняется сервером

- **GIVEN** слот сегодня 10:00–12:00 при текущем времени 14:30 (или дата слота прошла)
- **WHEN** запрос брони на этот слот отправлен, в том числе прямым вызовом API в обход UI
- **THEN** сервер отклоняет запрос ({ok:false}), записи нет; в UI слот отображается без кнопки брони

#### Scenario: Запрос в старом формате (без даты) продолжает приниматься

- **GIVEN** клиент отправляет POST {availability_id} без поля даты на будущий слот
- **WHEN** сервер обрабатывает запрос
- **THEN** запрос принимается без ошибки: бронь создается на ближайшую будущую дату экземпляра серии (прежнее поведение), остальные проверки прежние

### Requirement: Занятый слот недоступен другим ученикам

Занятый слот (активный запрос или подтвержденная бронь) MUST быть
недоступен другим ученикам: не отображается как доступный и не
бронируется повторно; другому ученику пары виден как «занято» без
раскрытия, кем. Занятость определяется на уровне ЭКЗЕМПЛЯРА слота —
конкретных даты и времени (повторяющийся слот развернут в экземпляры
дат: бронь на одной дате серии не делает занятыми другие даты серии).
Экземпляр может быть представлен ДВУМЯ строками графика (разовый слот,
совпавший по дате+времени с экземпляром повторяющегося, — FR-90);
занятость и правило «на один экземпляр максимум одна активная/
подтвержденная бронь» действуют КРОСС-СТРОЧНО — по всем строкам графика
инструктора, покрывающим экземпляр (дата+время): сервер проверяет это
ВНУТРИ транзакции создания брони (BEGIN IMMEDIATE, single-writer
сериализует с правками графика), а внутри одной строки гарантию держит
частичный UNIQUE-индекс (availability_id, lesson_date). Гарантия — на
уровне хранилища в этих двух механизмах единственного пути записи
броней; параллельные запросы не создают двойного подтверждения
(наследование FR-50, NFR-8; защита MAJ-1 правок графика — на уровне
экземпляров, FR-92: 409 с перечнем, содержащим дату).

Источник: requirements-sprint10.md FR-92, FR-95; наследование
requirements-booking-docs.md FR-50, NFR-8, MAJ-1.

#### Scenario: Занятый слот не отображается как доступный

- **GIVEN** экземпляр слота подтвержден ученику А
- **WHEN** ученик Б (другая пара с тем же инструктором) обновляет расписание этой недели
- **THEN** экземпляр недоступен для выбора

#### Scenario: Занятость видна без раскрытия, кем занято

- **GIVEN** экземпляр занят запросом/бронью ученика А
- **WHEN** другой ученик пары смотрит расписание
- **THEN** экземпляр помечен «занято», данные занявшего (кем именно) не раскрываются

#### Scenario: Другие даты повторяющейся серии остаются доступными

- **GIVEN** повторяющийся слот «Чт 16:00–18:00», экземпляр 12 ноября занят бронью ученика А
- **WHEN** ученик Б смотрит будущие недели
- **THEN** экземпляры серии на другие даты (например, 19 ноября) доступны для бронирования; занят только экземпляр 12 ноября

#### Scenario: Параллельные запросы на один слот — максимум одна бронь

- **GIVEN** два запроса брони на один экземпляр слота (дата+время) обрабатываются одновременно
- **WHEN** оба запроса обработаны хранилищем
- **THEN** подтверждена/активна максимум одна бронь, вторая получает явный отказ конфликта («Слот уже занят»), а не молчаливую порчу

#### Scenario: Бронь через вторую строку того же экземпляра отклоняется (MAJ-1)

- **GIVEN** разовый слот «12 ноября 16:00–18:00» совпал по дате+времени с экземпляром повторяющегося слота «Чт 16:00–18:00» (обе строки графика существуют), бронь ученика А создана через разовый слот
- **WHEN** ученик Б отправляет запрос брони на тот же экземпляр (12 ноября 16:00–18:00) через повторяющийся слот — вторую строку того же экземпляра
- **THEN** сервер отклоняет запрос (409 «Слот уже занят»), записи нет: на одном экземпляре максимум одна активная бронь независимо от строки графика

## ADDED Requirements

### Requirement: Календарь ученика: недели, реальные даты и разворот повторений

Календарь ученика MUST иметь ту же навигацию недель и реальный
календарь, что инструктор: «←»/«→» без перезагрузки, подпись диапазона,
реальные даты с верными днями недели, «сегодня» (МСК); при открытии —
неделя текущей даты. Повторяющиеся слоты MUST разворачиваться в
экземпляры дат недель; разовые — на своих датах; свои брони/запросы —
ровно на своих слотах. Прошедшие недели — только просмотр (история
броней) (FR-94, FR-95).

Источник: requirements-sprint10.md FR-94, FR-95.

#### Scenario: При открытии показана неделя с текущей датой и реальные даты колонок

- **GIVEN** ученик открыл раздел «Мои брони»
- **THEN** показана неделя с текущей датой, колонки — реальные даты с корректными днями недели

#### Scenario: Навигация неделями без перезагрузки страницы

- **GIVEN** открыт календарь ученика
- **WHEN** клик «→» или «←»
- **THEN** следующая/предыдущая неделя с корректными датами отображается без перезагрузки страницы; подпись диапазона согласована с колонками

#### Scenario: Граница месяца в подписи и колонках

- **GIVEN** отображаемая неделя пересекает границу месяца
- **THEN** подпись диапазона отражает обе части, колонки содержат реальные даты обеих частей с корректными днями недели

#### Scenario: «Сегодня» на реальной дате

- **GIVEN** открыт календарь ученика на текущей неделе
- **THEN** «сегодня» отмечена на колонке реальной сегодняшней даты (МСК)

#### Scenario: Повторяющийся слот развернут в экземпляры каждой отображаемой недели

- **GIVEN** инструктор имеет повторяющийся слот «Чт 16:00–18:00»
- **WHEN** ученик листает будущие недели
- **THEN** в каждой из них слот виден в колонке четверга 16:00–18:00 как конкретная дата этой недели

#### Scenario: Разовый слот виден только на своей дате

- **GIVEN** разовый слот инструктора на 12 ноября
- **WHEN** ученик листает недели
- **THEN** слот виден только в неделе с 12 ноября и только на этой дате

#### Scenario: Свои брони и запросы показаны ровно на своих слотах

- **GIVEN** броня ученика подтверждена на конкретную дату
- **WHEN** ученик открывает неделю этой даты
- **THEN** броня показана ровно на этом слоте (дата+время), на соседних слотах ее нет

#### Scenario: Прошедшая неделя — только просмотр

- **GIVEN** ученик открыл прошедшую неделю
- **THEN** видны только статусы своих броней/запросов (история с итоговыми статусами), слоты прошлых недель без действий (бронирование недоступно)
