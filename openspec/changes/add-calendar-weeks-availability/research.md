# Research: add-calendar-weeks-availability

Альтернативы ключевых техрешений до design.md. Источники: существующий
контур (backend/instructor_availability.py, backend/booking.py, db.py —
UNIQUE (instructor_id, weekday, start_time, end_time), частичный
uq_booking_active_slot по availability_id), requirements-sprint10.md
(FR-90…FR-97, NFR-29…NFR-32: «механика модели — зона СА»).

## R1. Представление повторяющихся/разовых слотов

- **A (выбрано): та же таблица availability + колонки slot_type/slot_date.**
  Минимальный шов: booking.availability_id, GET/PUT, индексы и все
  потребители сохраняются; существующие строки → recurring через DEFAULT
  (без перезаписи данных — FR-97/NFR-30 тривиально idempotent). Цена:
  перестройка таблицы (старый UNIQUE не выражает one_off на тот же
  день+время, что recurring-серия) — единовременная guarded-миграция.
- B: отдельная таблица экземпляров с материализацией серий на N недель
  вперед. Отклонено: ломает booking.availability_id (ссылки на определения
  серий) — прямое противоречие «без ломающих изменений контрактов броней»;
  материализация требует джоба/пересчета при каждой правке; дубли истины.
- C: JSON-поле с описанием серии внутри availability. Отклонено: теряет
  SQL-проверки (CHECK/UNIQUE), параметризованные выборки по датам/типам
  усложняются, существующие колонки дублируются.
- D: новая таблица availability_v2 + вью совместимости. Отклонено: две
  сущности-источника истины, миграция ссылок броней — тот же ломающий
  эффект, что B, дороже в поддержке.

## R2. API: расширение PUT availability vs новый эндпоинт

- **A (выбрано): обратно-совместимое расширение существующего PUT/GET
  /api/instructor/availability.** NFR-29 прямо описывает расширение
  (старое тело = график из recurring слотов; коды и формат ответа —
  прежние); «Сохранить график» — один запрос полной замены (FR-92,
  наследование FR-68) сохраняет контур «Сохранить/Отменить» и 409-защиту
  без нового клиента.
- B: новый PUT /api/instructor/availability/v2. Отклонено: два эндпоинта
  на один ресурс — расхождение валидаций/защит (MAJ-1, запрет прошлого),
  старый клиент получает другой контракт 409 (не «прежние коды»), дольше
  сходится приемка NFR-29.
- C: PATCH инкрементальных правок (список изменений недели). Отклонено:
  меняет семантику сохранения (полная замена → дельта) — ломающее
  изменение поведения FR-29/FR-30 и наследуемых тестов.

## R3. Занятость и бронирование на уровне экземпляра

- **A (выбрано): занятость = (availability_id, lesson_date) — точная дата
  экземпляра в существующей booking.** Частичный UNIQUE-индекс
  переиндексируется на два поля (данные совместимы), POST bookings —
  опциональное поле date (легаси-вызов без date → ближайшая дата серии,
  как сейчас). Контракты и статусы броней не меняются; «Слот уже занят»
  становится честным по отношению к развороту серий (FR-95: занят экземпляр
  даты, не вся серия); MAJ-1 естественно считается по экземплярам (FR-92).
- B: занятость по availability_id без дат (как сейчас). Отклонено: одна
  бронь на серию делает все будущие экземпляры «занятыми» — ученик видит
  в будущих неделях свободные слоты, которые невозможно забронировать;
  противоречит развороту серий FR-95/FR-96.
- C: отдельная таблица booking_instances. Отклонено: дубль истины брони,
  ломает выдачи «Мои брони»/подтверждения.

## R4. Разворот серий: клиент vs сервер

- **A (выбрано): инструктор разворачивает серии локально (полный список
  определений из GET availability, NFR-32 — переключение недели без
  сетевого запроса); ученику экземпляры недели выдает сервер
  (GET slots?date=…), т.к. ученик не имеет доступа к определениям графика
  (403-наследование) и состояния слотов считает сервер.**
- B: экземпляры обоим выдает сервер. Отклонено для инструктора: лаг
  навигации зависит от сети — риск NFR-32 (500 мс) при деградации; лишние
  запросы на каждый лист.
- C: экземпляры обоим считает клиент. Отклонено для ученика: ученический
  клиент не владеет данными занятости per-date — честные состояния
  (free/busy/pending) может выдать только сервер.

## R5. Граница «прошедшее» и часовой пояс

- **A (выбрано): локальное время сервера (МСК), граница — начало слота;
  сервер — единственный арбитр (NFR-31), клиентская блокировка попапа —
  UX.** Асимметрия границ сохранена дословно по Заказчику (открытый
  вопрос): инструктор правит при «начало ≥ сейчас», ученик бронирует при
  «начало > сейчас».
- B: таймзона клиента. Отклонено: наследование nowMoscow/MIN-1 (правило
  материализации lesson_date) — единая точка истины сервера.
