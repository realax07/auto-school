## Проверка по фактам диффа

### MAJ-1 — ЗАКРЫТ: одна политика кросс-строчных броней зафиксирована

Выбран вариант (б), альтернатива (а) отклонена документально — ОДНА политика
во всех восьми файлах диффа, противоречащих чтений нет:

- design.md «Контракт booking» (POST): кросс-строчная проверка экземпляра В
  ТОЙ ЖЕ транзакции BEGIN IMMEDIATE ДО INSERT — активная бронь
  ('new'/'confirmed') ЛЮБОЙ строки графика инструктора, покрывающая
  (lesson_date, start_time, end_time), → 409 «Слот уже занят»; single-writer
  сериализует с PUT (наследование M-3 review-001); частичный индекс
  (availability_id, lesson_date) остается гарантией ВНУТРИ строки — ровно
  формулировка варианта (б) из ревью-001.
- design.md «Экземпляр и разворот серий» + D4: совпадение one_off с серией —
  две строки ДОПУСТИМЫ (FR-90/FR-91), занятость ЕДИНА по обеим строкам;
  GET slots?date= дедуплицирует instances по (date, start_time, end_time) —
  приоритет one_off, state агрегируется по покрывающим строкам (вторая
  обязательная половина варианта (б)).
- specs/booking «Занятый слот недоступен другим ученикам» (MODIFIED):
  гарантия хранилища ПЕРЕПИСАНА ПО МЕХАНИЗМ, а не декларацией — два
  механизма единственного пути записи (транзакционная кросс-строчная
  проверка + частичный UNIQUE внутри строки); СЦЕНАРИЙ добавлен:
  «Бронь через вторую строку того же экземпляра отклоняется (MAJ-1)»
  (GIVEN обе строки + бронь через одну → WHEN бронь через вторую →
  THEN 409, записи нет) — тот TC, который требовало ревью-001.
- tasks 2.1: кросс-строчная проверка в (б), дедупликация в (в); кейс в
  «Готовности» (обе строки → вторая → 409, записи нет); TC-S10BE-006.
  tasks 3.1: дифф-запись PUT + тесты перепривязки; TC-S10BE-004.
- research R6: вариант A выбран, B (422 на совпадающий one_off — вариант (а)
  ревью-001) и C (чисто индексная защита) отклонены с аргументами
  (FR-91 «сменить тип», разные экземпляры одного дня, контракт записи).
- ADR-010 «Уточнение» (2026-11-05): граница решений 3/4 — кросс-строчная
  защита; решения 1–5 в силе. proposal: «Отслеживание» и «Impact»
  синхронизированы.

НОВОЕ в доработке (выходило за букву ревью-001, проверено): PUT переведен
с wholesale DELETE+INSERT на ДИФФ (совпадающие полным ключом строки не
пересоздаются — id сохраняются) с ПЕРЕПРИВЯЗКОЙ booking.availability_id на
строку-носитель при покрытой замене (поля брони не меняются, на 409 —
ничего). Проверено на необходимость: FK booking→availability нет (факт
db.py из ревью-001), без перепривязки бронь-сирота выпадала бы из INNER
JOIN выдач и из кросс-строчной проверки — гарантия (б) была бы обходимой.
Составляющая согласована по всем слоям (design, tasks 3.1, R6, ADR-010,
proposal) и не меняет архитектуру (та же транзакция PUT) — принимается как
часть закрытия MAJ-1, не как замечание.

Согласованность с гарантией спеки booking — ДА: спека теперь называет оба
механизма и единственный путь записи; design «Обработка ошибок» и
«Сознательные ограничения» (точное совпадение интервалов) ей не
противоречат.

### MAJ-2 — ЗАКРЫТ: одна непротиворечивая семантика легаси-тела

- design.md §PUT (б): правило запрета прошлого ограничено телом НОВОГО
  формата («правило применяется к телу НОВОГО формата»).
- design.md §Совместимость: ЕДИНАЯ семантика — эффективный payload
  легаси-PUT = recurring-интервалы тела + СУЩЕСТВУЮЩИЕ one_off сохраняются
  без изменений (ПРОШЕДШИЕ И БУДУЩИЕ — выбор СА, R7); правило (б)
  выполняется конструктивно (прошедшие one_off не «отсутствуют в payload»).
  Буквальное противоречие ревью-001 («one_off-строки, если были,
  заменяются») ИЗ ТЕКСТА УДАЛЕНО — проверено grep'ом: формулировки
  «заменяются/заменяет» остались только про миграционный UNIQUE (design:107)
  и про замену НОВЫМ форматом (spec instructor-availability:11) — оба
  чтения легальны.
- specs/instructor-availability: сценарий «Запрос в старом формате…» — GIVEN
  дополнен one_off в БД (прошедшие и будущие), THEN — сохранены без
  изменений; «Попытка изменения прошедшего слота» — scoped к новому
  формату. NFR-29 («принимается без ошибки») и FR-93/NFR-31 (immutable
  прошлое) больше не сталкиваются: легаси-клиент не может ни убрать, ни
  изменить прошедший one_off.
- tasks 3.1: тест «легаси-тело при наличии прошедшей И будущей one_off →
  200, обе сохранены»; TC-S10BE-002 дополнен; таблица ошибок design:
  строка «PUT: старое тело… (в т.ч. при наличии one_off в БД) | 200 —
  recurring из тела, one_off сохранены без изменений | NFR-29, MAJ-2».
- research R7: A выбран, B (замена one_off легаси-PUT) отклонен — как
  требовало ревью-001.
