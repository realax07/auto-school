# containerization Specification

## Purpose

Возможность определяет контейнерный контур поставки Auto School: образ приложения (multi-stage, non-root, healthcheck), docker compose-стек (app + nginx + MinIO), volumes для БД и загрузок, прогон тестов внутри образа, CI-сборка. Устраняет хрупкость bare-metal хоста (INC-001) и готовит S3-хранилище файлов (MinIO → S3-адаптер uploads.py).

## Requirements

### Requirement: Образ приложения

Репозиторий MUST содержать Dockerfile, собирающий образ приложения на
базе официального python-slim: зависимости — в виртуальном окружении
(.venv), устанавливаемом на multi-stage builder-этапе и переносимом в
финальный образ; приложение в контейнере запускается от непривилегированного
пользователя; версии базового образа и зависимостей зафиксированы
(трассировка: FR-51, NFR-11, NFR-12).

Источник: requirements-containerization.md FR-51, NFR-11, NFR-12.

#### Scenario: Сборка образа на чистой машине

- **GIVEN** чистая машина с установленным Docker и копия репозитория
- **WHEN** выполняется сборка образа из репозитория
- **THEN** сборка проходит без ручных шагов, запуск образа поднимает uvicorn, а процесс в контейнере работает не от root

#### Scenario: Builder-артефакты не попадают в финальный образ

- **GIVEN** образ собран через multi-stage (builder-этап с pip-кэшами и venv)
- **WHEN** финальный образ инспектируется
- **THEN** в нем нет артефактов builder-этапа (кэши pip, компиляторы), а виртуальное окружение с зависимостями присутствует

#### Scenario: Версии зафиксированы

- **GIVEN** Dockerfile и requirements.txt изменены вне задачи
- **WHEN** выполняется повторная сборка без изменения зафиксированных входов
- **THEN** базовый образ, версии зависимостей и версии образов nginx/MinIO берутся из зафиксированных значений, а не из плавающих тегов

### Requirement: Compose-стек app + nginx + MinIO

Репозиторий MUST содержать docker-compose-стек из трех сервисов: app
(образ из Dockerfile), nginx (reverse proxy, эквивалентный текущему
deploy/nginx-autoschool.conf: статика и /api/* на app, TLS из
монтируемых файлов вне образов) и MinIO (S3-совместимое хранилище —
контур под будущий перенос файлов). Данные БД и загрузок MUST храниться
на именованных томах и переживать пересоздание контейнеров
(трассировка: FR-52, NFR-15).

Источник: requirements-containerization.md FR-52, NFR-15.

#### Scenario: Данные переживают пересоздание контейнеров

- **GIVEN** поднятый стек, в котором создан пользователь и загружен файл
- **WHEN** выполняется `docker compose down` и затем `docker compose up`
- **THEN** записи БД и загруженные файлы доступны без восстановительных действий (named volumes db и uploads)

### Requirement: Секреты вне образа и сегментация сетей

Секреты (админ-креды, ключи MinIO, TLS-ключи) MUST попадать в
контейнеры только через окружение (env_file) и монтируемые файлы —
ни один секрет не зашивается в слои образов и не лежит в контексте
сборки. Стек MUST быть сегментирован на сети: внешнюю (nginx ↔
клиенты) и внутреннюю (app ↔ MinIO); наружу публикуются только порты
nginx (80/443) (трассировка: NFR-14, NFR-16).

Источник: requirements-containerization.md NFR-14, NFR-16.

#### Scenario: Секреты не зашиты в образ

- **GIVEN** образ приложения собран
- **WHEN** образ и контекст сборки инспектируются
- **THEN** ни один секрет (админ-креды, ключи MinIO, TLS-ключи) не присутствует в слоях образа и в контексте сборки — секреты приходят только через env_file и монтирования

#### Scenario: Наружу публикуются только порты nginx

- **GIVEN** стек поднят
- **WHEN** просматриваются публикуемые порты хоста
- **THEN** слушаются только порты nginx (80/443); порты app и MinIO не публикуются и доступны только внутри сетей стека

#### Scenario: MinIO готов принимать данные, файлы пока на volume

- **GIVEN** стек поднят
- **WHEN** проверяется сервис MinIO
- **THEN** MinIO доступен из внутренней сети стека и хранит данные на своем томе, при этом загрузки приложения продолжают работать через локальный volume (S3-адаптер — отдельный объем)

### Requirement: Идемпотентная инициализация БД при старте

Контейнер app MUST выполнять при старте инициализацию БД (создание
таблиц, миграции колонок) идемпотентно — существующей механикой
init_db/idempotent-миграций; повторный старт на томе с существующей БД
не разрушает данные и не падает от повторного применения миграций
(трассировка: FR-53).

Источник: requirements-containerization.md FR-53.

#### Scenario: Старт на томе с БД предыдущей версии

- **GIVEN** named volume с БД, созданной предыдущим состоянием кода
- **WHEN** контейнер app стартует
- **THEN** схема доводится до актуальной, данные целы

#### Scenario: Повторный старт без побочных эффектов

- **GIVEN** тот же том с уже актуализированной схемой
- **WHEN** контейнер перезапускается
- **THEN** старт проходит без ошибок повторного применения миграций, данные не дублируются и не портятся

### Requirement: Healthcheck по /api/health

Живость приложения MUST проверяться HTTP-эндпоинтом /api/health:
healthcheck прописан и в образе (HEALTHCHECK), и в compose-сервисе app;
проверка выполняется средствами, уже находящимися в образе, без установки
дополнительных утилит ради healthcheck (трассировка: FR-54, NFR-13).

Источник: requirements-containerization.md FR-54, NFR-13.

#### Scenario: Здоровый контейнер сообщается healthy

- **GIVEN** работающий контейнер app
- **WHEN** выполняется `docker compose ps` (или docker ps)
- **THEN** сервис app имеет статус healthy

#### Scenario: Зависание приложения переводит сервис в unhealthy

- **GIVEN** приложение в контейнере не отвечает на /api/health (зависание event loop, соединение не отвечает до таймаута проверки)
- **WHEN** healthcheck отрабатывает по расписанию
- **THEN** статус сервиса становится unhealthy

### Requirement: Тесты внутри контейнера на том же образе

Backend-тесты MUST прогоняться ВНУТРИ контейнера на том же образе,
который поставляется (без отдельного «тестового» образа): pytest
выполняется с временной БД вне постоянных томов; механика прогона одна
и та же локально и в CI и является документированной процедурой
(трассировка: FR-55, NFR-17).

Источник: requirements-containerization.md FR-55, NFR-17.

#### Scenario: Прогон тестов внутри поставляемого образа

- **GIVEN** собранный образ приложения
- **WHEN** внутри контейнера из этого образа выполняется pytest с временной БД
- **THEN** тесты проходят, и в постоянных томах не остается артефактов прогона

#### Scenario: Тестируется ровно поставляемый digest

- **GIVEN** образ собран и протестирован в контейнере
- **WHEN** стек поднимается тем же образом
- **THEN** используется тот же digest образа, на котором прогонялись тесты

### Requirement: CI собирает образ и гоняет тесты в контейнере

CI MUST собирать образ приложения на каждый pull request и прогонять
тесты внутри собранного образа; провал сборки или тестов красит проверку
PR (трассировка: FR-56).

Источник: requirements-containerization.md FR-56.

#### Scenario: Падающий тест красит PR

- **GIVEN** pull request с падающим тестом
- **WHEN** CI завершает прогон тестов внутри собранного образа
- **THEN** статус проверки — ошибка

#### Scenario: Ломающий Dockerfile красит PR

- **GIVEN** pull request с Dockerfile, сборка которого падает
- **WHEN** CI выполняет job сборки образа
- **THEN** статус проверки — ошибка

### Requirement: Обратная совместимость bare-metal-деплоя

Существующий bare-metal-деплой (deploy/autoschool.service,
deploy/nginx-autoschool.conf) MUST остаться рабочим без изменения кода
приложения: режим развертывания (контейнер или systemd) определяется
окружением и конфигурацией; репозиторий документирует оба режима
(трассировка: FR-57).

Источник: requirements-containerization.md FR-57.

#### Scenario: systemd-деплой продолжает работать

- **GIVEN** машина с существующим bare-metal systemd-деплоем
- **WHEN** выполняются pull репозитория и рестарт сервиса
- **THEN** сервис работает как раньше без правок кода приложения

#### Scenario: Переключение на контейнерный режим без правок кода

- **GIVEN** принято решение поднять стенд через compose
- **WHEN** режим переключается
- **THEN** изменяются только окружение и конфигурации (env, compose, nginx-конфиг), код backend/ и frontend/ не меняется, оба режима описаны в документации репозитория
