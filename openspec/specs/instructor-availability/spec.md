# instructor-availability Specification

## Purpose

Возможность дает инструктору управлять рабочими интервалами недели (календарь часов работы): сохранение графика, валидация интервалов. График служит источником слотов для бронирования учениками (Спринт 5).

## Requirements

### Requirement: Выбор рабочих интервалов в календаре

Раздел «Календарь» кабинета инструктора MUST позволять выбирать часы
работы на сетке недели/дня: выделенные интервалы помечаются как рабочие.
Интервал MUST иметь корректные границы (начало раньше конца); некорректный
интервал не сохраняется (трассировка: FR-29, NFR-5).

Источник: requirements-instructor-student-loop.md FR-29, NFR-5.

#### Scenario: Выделенный интервал помечается рабочим

- **GIVEN** инструктор с валидной сессией находится в разделе «Календарь»
- **WHEN** он выделяет интервал (например, Пн 10:00–14:00) и сохраняет
- **THEN** интервал помечен как рабочий (сохранен как рабочий час инструктора)

#### Scenario: Некорректный интервал отклоняется

- **GIVEN** инструктор задает интервал с концом раньше начала (например, Пн 14:00–10:00)
- **WHEN** он пытается сохранить график с таким интервалом
- **THEN** интервал не сохраняется, клиент получает ошибку валидации

#### Scenario: Доступ к календарю без инструкторской сессии отклоняется

- **GIVEN** гость без сессии или пользователь с ролью 'student'
- **WHEN** запрашивается график часов работы этого инструктора
- **THEN** доступ запрещен (401 для гостя, 403 для иной роли), график не возвращается

### Requirement: Сохранение и восстановление графика

График MUST сохраняться (availability) и восстанавливаться при входе.
Слоты: recurring (еженедельно) и one_off (конкретная дата); полный
новый график заменяет сохраненный. Изменения — ТОЛЬКО по «Сохранить»
(один PUT); «Отменить» — без PUT. Замена согласована с booking на
уровне ЭКЗЕМПЛЯРОВ (FR-92): убирающий экземпляр с активной бронью —
409 с перечнем; прошедшие не блокируют. Легаси-тело принимается
(recurring-часть; one_off сохраняются). Правка прошедшего MUST
отклоняться (FR-93/NFR-31).

#### Scenario: График восстанавливается после перезахода

- **GIVEN** график сохранен (например, Пн 10:00–14:00 — повторяющийся)
- **WHEN** инструктор выходит, входит заново и открывает календарь
- **THEN** отмечены те же слоты с теми же типами, что были сохранены

#### Scenario: Изменение графика перезаписывает сохраненный

- **GIVEN** график Пн 10:00–14:00 сохранен
- **WHEN** инструктор снимает этот интервал, добавляет разовый Ср 09:00–12:00 на конкретную дату и сохраняет
- **THEN** при следующем входе отмечен только разовый Ср 09:00–12:00 на своей дате

#### Scenario: «Сохранить» отправляет один PUT полной замены

- **GIVEN** инструктор изменил слоты календаря (добавил, удалил, поменял типы)
- **WHEN** он нажимает «Сохранить»
- **THEN** отправляется один PUT /api/instructor/availability с полным новым графиком (повторяющиеся и разовые слоты с датами); после ответа календарь отражает сохраненный график, и при перезаходе он восстанавливается

#### Scenario: «Отменить» возвращает сохраненный график без вызова PUT

- **GIVEN** инструктор изменил слоты календаря и еще не сохранял
- **WHEN** он нажимает «Отменить»
- **THEN** календарь перезагружает последний сохраненный график с сервера; PUT не вызывается, на сервере ничего не изменилось

#### Scenario: PUT с удалением интервала с активной бронью отклоняется (MAJ-1)

- **GIVEN** у экземпляра Чт 16:00–18:00 на 12 ноября (разовый слот или экземпляр повторяющейся серии) есть бронь в статусе «новая» или «подтвержденная»
- **WHEN** инструктор нажимает «Сохранить», и новый график не покрывает этот экземпляр (не содержит дату 12 ноября 16:00–18:00)
- **THEN** PUT отклоняется с 409 и перечнем затронутых слотов с датой (12 ноября, 16:00–18:00, статусы броней); прежний график остается без изменений, брони не меняются, календарь показывает ошибку и сохраненное состояние

#### Scenario: Интервалы с только отклоненными бронями замене не мешают

- **GIVEN** у убираемого экземпляра есть только бронь(и) в статусе «отклонена»
- **WHEN** инструктор сохраняет график без этого экземпляра
- **THEN** график сохраняется без отказа

#### Scenario: Прошедшие экземпляры не блокируют замену и не изменяются

- **GIVEN** активная бронь относится к экземпляру, дата и время начала которого уже прошли, а новый график правит только будущие слоты
- **WHEN** инструктор сохраняет график
- **THEN** сохранение проходит; запись брони (дата, статус) остается без изменений как история

#### Scenario: Запрос в старом формате продолжает приниматься (MAJ-2)

- **GIVEN** клиент отправляет PUT с телом {intervals:[{weekday,start_time,end_time}]} без полей типа и даты; в БД сохранены разовые слоты — прошедшие и будущие
- **WHEN** сервер обрабатывает запрос
- **THEN** запрос принимается без ошибки: график сохраняется из повторяющихся слотов тела, разовые слоты (прошедшие и будущие) остаются без изменений, код успеха и формат ответа прежние (существующие автотесты контракта проходят без правок); прошедшие разовые слоты не удалены и не изменены

#### Scenario: Попытка изменения прошедшего слота отклоняется сервером

- **GIVEN** запрос сохранения В НОВОМ ФОРМАТЕ (с полями типа/даты), меняющий прошедший one_off (убирающий его или создающий слот с прошедшей датой/временем), отправлен в обход UI
- **WHEN** сервер обрабатывает PUT
- **THEN** сохранение отклоняется с ошибкой {ok:false}, график остается без изменений

### Requirement: Запросы и брони учеников на слотах календаря

Календарь MUST показывать запросы (new) и брони (confirmed) РОВНО на
выбранных учеником слотах (дата+время запроса = слоту availability),
без агрегированных списков и попаданий на соседние слоты.
«Сохранить/Отменить» графика — наследование FR-68 (409 MAJ-1 — без
правок бэкенда). Раздел «Бронирования» удаляется без остатков; старые
ссылки — редирект в календарь (BUG-047). Контракты booking/
availability не меняются (NFR-23).

Источник: requirements-sprint8.md FR-74, NFR-23; ОВ-6, MAJ-1.

#### Scenario: Запрос виден именно на выбранном слоте

- **GIVEN** ученик отправил запрос на слот 14:00–15:00 даты D (слот задан графиком инструктора)
- **WHEN** инструктор открывает календарь на дату D
- **THEN** запрос показан именно на слоте 14:00–15:00 (ячейка слота) с кнопками подтвердить/отклонить; на соседних слотах запроса нет; отдельного списка запросов «рядом с календарем» нет

#### Scenario: Решения по брони — немедленно, мимо кнопок графика

- **GIVEN** в календаре есть запрос ученика на слоте и несохраненные правки графика
- **WHEN** инструктор подтверждает (или отклоняет) запрос
- **THEN** решение применяется немедленно (POST confirm/reject), вызов PUT графика не требуется; кнопки «Сохранить/Отменить» относятся только к графику

#### Scenario: «Сохранить/Отменить» графика — наследование без изменений

- **GIVEN** инструктор изменил отметки слотов и нажал «Сохранить»
- **WHEN** отправляется изменение
- **THEN** отправляется ОДИН PUT полной замены; «Отменить» возвращает сохраненный график перезагрузкой GET без PUT; PUT, удаляющий интервал с активной бронью, получает 409 с перечнем затронутых — показывается с сохраненным графиком

#### Scenario: Раздел «Бронирования» удален без остатков

- **GIVEN** инструктор открыл кабинет
- **WHEN** отображена навигация
- **THEN** пункта меню «Бронирования» нет; секция раздела и его JS-контур отсутствуют; GIVEN старая ссылка #/bookings открыта THEN выполняется редирект в календарь

#### Scenario: API-контракты броней и графика не меняются

- **GIVEN** существующие брони и график инструктора
- **WHEN** раздел «Бронирования» удален и календарь переработан
- **THEN** контракты GET /api/instructor/bookings, POST confirm/reject/cancel, PUT/GET /api/instructor/availability не изменены (NFR-23); существующие брони и запросы доступны в календаре

### Requirement: Типы слотов: повторяющиеся и разовые

Каждая ячейка MUST иметь индивидуальный тип: «Повторяющееся» —
еженедельное (тот же день недели и время), видна во ВСЕХ неделях;
«Разовое» — конкретная дата + время, только на своей дате. Допустимы
оба типа в одной неделе; совпадение разового с экземпляром серии —
один слот. Правка серии касается текущих и будущих экземпляров,
прошедшие не меняются; разовый — только его даты. Смена типа — через
попап, до «Сохранить» (FR-90, FR-91).

Источник: requirements-sprint10.md FR-90, FR-91.

#### Scenario: Повторяющийся слот виден в каждой отображаемой неделе

- **GIVEN** есть повторяющийся слот «Чт 16:00–18:00»
- **WHEN** инструктор листает недели (прошлые и будущие)
- **THEN** слот виден в каждой отображаемой неделе в колонке четверга 16:00–18:00

#### Scenario: Разовый слот виден только на своей дате

- **GIVEN** есть разовый слот на 12 ноября
- **WHEN** инструктор листает недели
- **THEN** слот виден только в неделе с 12 ноября и только на этой дате

#### Scenario: В одной неделе сочетаются оба типа

- **GIVEN** в одной неделе есть и повторяющиеся, и разовые ячейки
- **WHEN** неделя отображается
- **THEN** все слоты обоих типов отображены одновременно, независимо друг от друга

#### Scenario: Совпадение разового с экземпляром повторяющегося отображается одним слотом

- **GIVEN** разовый слот по дате+времени совпал с экземпляром повторяющегося слота той же недели
- **WHEN** неделя отображается
- **THEN** в сетке один слот, дублей нет

#### Scenario: Клик по отмеченной ячейке показывает текущий тип и действия

- **GIVEN** отмеченная повторяющаяся ячейка
- **WHEN** инструктор кликает по ней
- **THEN** попап показывает «Повторяющееся» как текущий тип и действия «сменить тип» и «убрать слот»

#### Scenario: Правка серии применяется к текущим и будущим экземплярам

- **GIVEN** время повторяющейся серии изменено и сохранено, прошедшие экземпляры серии существовали
- **WHEN** инструктор открывает будущую и прошедшую недели
- **THEN** экземпляры будущих недель отображают новое время; экземпляры прошедших недель не редактируются (просмотр), записи броней прошлого без изменений

#### Scenario: Убранный разовый слот исчезает только со своей даты

- **GIVEN** разовая ячейка убрана и сохранение выполнено
- **WHEN** инструктор листает недели
- **THEN** слот исчез только со своей даты, повторяющиеся слоты других дат не изменились

### Requirement: Навигация неделями и реальный календарь инструктора

Календарь инструктора MUST иметь навигацию «←»/«→» и подпись диапазона
недели (месяц, год; обе части при пересечении). Сетка привязана к неделе
реальных дат; при открытии — неделя текущей даты (МСК); точка возврата
достижима; переходы без перезагрузки. Сетка — из реального календаря: 7
дат, верные дни недели на границах месяцев/годов и в високосные годы;
решетки без дат не допускаются; «сегодня» — на реальной дате
(FR-87, FR-88).

Источник: requirements-sprint10.md FR-87, FR-88.

#### Scenario: Подпись диапазона отражает обе части на границе месяца и года

- **GIVEN** открыта неделя 30 ноября — 6 декабря 2026
- **THEN** подпись показывает «30 ноября — 6 декабря 2026», колонки — реальные даты с 30 по 6; GIVEN неделя 28 декабря 2026 — 3 января 2027 THEN подпись и колонки корректно пересекают границу года

#### Scenario: Переход на неделю вперед и назад без перезагрузки страницы

- **GIVEN** открыт календарь инструктора
- **WHEN** клик «→» или «←»
- **THEN** отображается следующая/предыдущая неделя без перезагрузки страницы, подпись и колонки обновлены согласованно

#### Scenario: При открытии показана неделя с текущей датой, точка возврата достижима

- **GIVEN** инструктор открыл раздел «Календарь»
- **THEN** показана неделя, содержащая текущую дату; GIVEN инструктор ушел на произвольную неделю THEN от любой отображаемой недели неделя с текущей датой достижима (кнопка «эта неделя» или эквивалент)

#### Scenario: Колонки — реальные даты с корректным днем недели

- **GIVEN** отображается неделя, содержащая 30 ноября 2026
- **THEN** колонка с датой 30 подписана «Пн» и датой 30; GIVEN неделя февраля високосного 2028 года THEN в сетке существует колонка 29 февраля в позиции вторника

#### Scenario: «Сегодня» отмечена на реальной текущей дате

- **GIVEN** открыт календарь на текущей неделе
- **WHEN** сетка отображена
- **THEN** «сегодня» отмечена на колонке реальной сегодняшней даты (МСК)

### Requirement: Попап-редактор над ячейкой

Клик по свободной редактируемой ячейке MUST открывать мини-окно (popover)
НАД ячейкой, поверх страницы: выбор «Разово»/«Повторяющееся» и
подтверждение. Тип — индивидуально для каждой ячейки, применяется после
подтверждения (несохраненная правка до «Сохранить»). Popover — у ячейки,
не смещает и не переполняет сетку; у границ вьюпорта сдвигается внутрь
без обрезки. Закрытие без подтверждения не меняет ячейку (FR-89).

Источник: requirements-sprint10.md FR-89 (сценарий Заказчика).

#### Scenario: Клик по свободной ячейке открывает попап с выбором типа

- **GIVEN** редактируемая свободная ячейка «Чт 16:00–18:00»
- **WHEN** инструктор кликает по ней
- **THEN** попап открыт рядом с этой ячейкой поверх страницы с выбором «Разово»/«Повторяющееся» и подтверждением

#### Scenario: Подтверждение отмечает ячейку выбранным типом как несохраненную правку

- **GIVEN** попап открыт, выбрано «Повторяющееся»
- **WHEN** инструктор подтверждает
- **THEN** ячейка отмечена как повторяющаяся до «Сохранить» (несохраненная правка, индикатор изменений виден)

#### Scenario: Закрытие без подтверждения не меняет ячейку и не сдвигает сетку

- **GIVEN** попап открыт по свободной ячейке
- **WHEN** попап закрыт без подтверждения (клик вне окна или кнопка закрытия)
- **THEN** ячейка осталась неотмеченной, сетка не сдвинулась и не переполнилась

#### Scenario: Попап не обрезается у границ вьюпорта

- **GIVEN** ячейка у верхней границы или у правого края вьюпорта
- **WHEN** попап открывается
- **THEN** окно сдвинуто внутрь вьюпорта и полностью видимо, содержимое не обрезано

#### Scenario: Тип выбирается индивидуально для каждой ячейки

- **GIVEN** одна ячейка отмечена как разовая, соседняя — как повторяющаяся
- **WHEN** инструктор сохраняет график
- **THEN** обе отметки сохранены каждая со своим типом; режима применения типа ко всему графику не существует

### Requirement: Запрет правки прошлого

Правки графика (отметить, снять, сменить тип, убрать) MUST быть возможны
ТОЛЬКО для слотов с началом ≥ текущего момента (МСК): клик по прошедшей
ячейке не открывает попап и не меняет ее. Прошедшие недели и прошедшие
ячейки текущей недели — только просмотр. Граница — по началу слота.
Проверка — на клиенте и сервере: сохранение, меняющее прошедший
экземпляр, в обход UI — отклоняется сервером (FR-93, NFR-31).

Источник: requirements-sprint10.md FR-93, NFR-31 (АД-директива).

#### Scenario: Прошедшие ячейки текущей недели не открывают попап

- **GIVEN** сегодня четверг 14:30 (МСК)
- **WHEN** инструктор кликает по ячейкам четверга с началом до 14:30 и по всем ячейкам понедельника–среды этой недели
- **THEN** попап не открывается, состояние ячеек не изменяется; ячейка четверга 16:00–18:00 редактируема (16:00 ≥ 14:30)

#### Scenario: Прошедшая неделя целиком — только просмотр

- **GIVEN** отображена прошедшая неделя
- **THEN** вся сетка — просмотр: ни одной редактируемой ячейки, график и брони с их статусами видны без действий

#### Scenario: Сервер отклоняет сохранение, меняющее прошедший экземпляр, в обход UI

- **GIVEN** запрос сохранения, меняющий прошедший экземпляр графика, отправлен прямым вызовом API
- **WHEN** сервер обрабатывает запрос
- **THEN** сохранение отклоняется ({ok:false}), график остается без изменений

### Requirement: Существующий график становится повторяющимся (миграция)

Существующие интервалы «день недели + время» MUST продолжать действовать
как ПОВТОРЯЮЩИЕСЯ слоты: видны у инструктора с типом «Повторяющееся» и
доступны ученикам в будущих неделях БЕЗ повторного сохранения;
существующие брони остаются на своих слотах и видны на конкретных датах;

#### Scenario: Существующий интервал после релиза виден как повторяющийся без действий

- **GIVEN** до релиза сохранен график «Пн 10:00–14:00»
- **WHEN** инструктор после релиза открывает календарь (любую неделю)
- **THEN** интервал виден как повторяющийся во всех отображаемых неделях без действий инструктора

#### Scenario: Существующие брони остаются на своих слотах и видны на конкретных датах

- **GIVEN** ученик с подтвержденной бронью на интервал этой серии
- **WHEN** инструктор или ученик открывают будущую неделю
- **THEN** броня и слот видны на конкретной дате; записи броней не аннулированы и не потеряны

#### Scenario: Повторный запуск миграции не создает дублей

- **GIVEN** миграция выполнена первый раз (все интервалы recurring, все брони на месте)
- **WHEN** миграция запускается повторно
- **THEN** дубли интервалов не создаются, состояние графика и броней не меняется
