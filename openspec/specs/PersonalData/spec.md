# PersonalData Specification

## Purpose

Персональные данные: страница /policy из отдельного заменяемого артефакта (152-ФЗ шаблон), согласие при регистрации (чекбокс + фиксация даты/версии политики).

## Requirements

### Requirement: Публичная страница политики персональных данных (/policy)

Сервис MUST иметь публичную страницу /policy (без входа, с любого
устройства), отображающую текст политики персональных данных и его
версию с датой. Текст MUST поступать из отдельного заменяемого
артефакта — файла вне кода страниц: в исходниках HTML/JS текста
политики нет; версия и дата задаются метаданными артефакта. Ссылка
на /policy MUST быть видна и открываться из обоих мест согласия:
анкета инструктора и форма регистрации ученика.

Источник: requirements-sprint9.md FR-76; NFR-25; ОВ-1, ОВ-2.

#### Scenario: Страница открывается без входа и показывает текст и версию

- **GIVEN** гость (без сессии, с любого устройства) открывает /policy
- **WHEN** страница загружена
- **THEN** показаны полный текст политики и версия с датой из метаданных артефакта; вход и идентификация не требуются

#### Scenario: Политика охватывает данные существующих форм

- **GIVEN** открыт текст политики на /policy
- **WHEN** он сверяется с формами сервиса
- **THEN** политика описывает данные, собираемые существующими формами: ФИО, телефон, email, адрес, реквизиты ВУ (номер/категория/дата выдачи), фото ВУ, госномер, фото СТС, фото авто

#### Scenario: Текст политики отсутствует в исходниках страниц

- **GIVEN** сервис развернут с актуальным артефактом
- **WHEN** выполняется поиск по исходникам страниц (HTML/JS, включая собранные бандлы)
- **THEN** ни одной строки текста политики в исходниках не найдено — текст поступает только из артефакта через API

#### Scenario: Подмена артефакта меняет текст и версию без правки кода

- **GIVEN** сервис работает с артефактом версии 1.0
- **WHEN** владелец сервиса заменяет файл артефакта новым текстом с версией 2.0 (без правки кода и пересборки) и перезапускает сервис
- **THEN** /policy показывает новый текст и версию 2.0; операция выполнена без участия разработчика

#### Scenario: Ссылка на политику видна из обоих мест согласия

- **GIVEN** открыта анкета инструктора или форма регистрации ученика
- **WHEN** пользователь просматривает блок согласия
- **THEN** ссылка на /policy видна, открывается и ведет на страницу политики

#### Scenario: Артефакт поврежден — честная ошибка страницы

- **GIVEN** артефакт отсутствует или поврежден (нарушен формат метаданных)
- **WHEN** гость открывает /policy
- **THEN** страница показывает честное сообщение о недоступности политики (не пустую страницу и не имитацию текста)

### Requirement: Обязательное согласие при регистрации инструктора

Анкета инструктора (/instructors/apply) MUST содержать обязательный
чекбокс согласия с политикой персональных данных со ссылкой на /policy:
отправка при неустановленном чекбоксе невозможна на клиенте (кнопка
сабмита блокирована до установки) и отклоняется на сервере — POST
/api/instructors/apply без согласия отвечает 422 {ok:false}, заявка не
создается.

Источник: requirements-sprint9.md FR-77; ОВ-2 (серверная проверка —
наследование MIN-2 Спринта 3).

#### Scenario: Чекбокс не установлен — отправка блокирована на клиенте

- **GIVEN** анкета инструктора заполнена, чекбокс согласия не установлен
- **WHEN** пользователь пытается отправить анкету
- **THEN** кнопка отправки недоступна, запрос не отправляется

#### Scenario: Прямой POST без согласия отклоняется сервером

- **GIVEN** валидные данные анкеты без флага согласия (consent не true)
- **WHEN** POST /api/instructors/apply отправлен напрямую
- **THEN** ответ 422 {ok:false, error:"Согласие: поле обязательно"}; заявка не создана

#### Scenario: Согласие установлено — заявка создана

- **GIVEN** чекбокс установлен, анкета заполнена валидно
- **WHEN** анкета отправлена
- **THEN** заявка создана (status waiting) с фиксацией согласия — см. «Фиксация согласия в данных заявки и регистрации»

### Requirement: Обязательное согласие при регистрации ученика

Форма регистрации ученика (модалка «Регистрация» на лендинге,
POST /api/register) MUST содержать обязательный чекбокс согласия с
политикой со ссылкой на /policy; правила те же, что для анкеты
инструктора: сабмит без чекбокса блокирован на клиенте и отклоняется
на сервере — POST /api/register без согласия отвечает 422 {ok:false},
пользователь не создается.

Источник: requirements-sprint9.md FR-78; ОВ-2.

#### Scenario: Чекбокс не установлен — регистрация блокирована на клиенте

- **GIVEN** форма регистрации ученика заполнена, чекбокс согласия не установлен
- **WHEN** пользователь пытается отправить форму
- **THEN** кнопка регистрации недоступна, запрос не отправляется

#### Scenario: Прямой POST /api/register без согласия отклоняется сервером

- **GIVEN** валидные данные регистрации без флага согласия (consent не true)
- **WHEN** POST /api/register отправлен напрямую
- **THEN** ответ 422 {ok:false, error:"Согласие: поле обязательно"}; пользователь не создан

#### Scenario: Согласие установлено — пользователь создан

- **GIVEN** чекбокс установлен, форма заполнена валидно
- **WHEN** форма отправлена
- **THEN** пользователь создан (роль student) с фиксацией согласия — см. «Фиксация согласия в данных заявки и регистрации»; ответ содержит сессию как прежде

### Requirement: Фиксация согласия в данных заявки и регистрации

При успешной отправке анкеты инструктора сервис MUST сохранять в
заявке дату согласия (UTC сервера) и версию политики; при успешной
регистрации ученика — те же поля в записи пользователя. Версия
берется сервером из метаданных артефакта на момент сабмита; ранее
созданные записи сохраняют свою версию на момент сабмита и не
переписываются.

Источник: requirements-sprint9.md FR-79; NFR-27; NFR-24-механика
(idempotent-миграция новых колонок).

#### Scenario: Заявка инструктора содержит дату и версию политики

- **GIVEN** валидная анкета с установленным согласием отправлена при артефакте версии 1.0
- **WHEN** заявка создана
- **THEN** в данных заявки сохранены дата согласия (UTC сервера, момент сабмита) и версия «1.0»

#### Scenario: Запись ученика содержит дату и версию политики

- **GIVEN** валидная регистрация ученика с установленным согласием отправлена при артефакте версии 1.0
- **WHEN** пользователь создан
- **THEN** в записи пользователя сохранены дата согласия (UTC сервера, момент сабмита) и версия «1.0»

#### Scenario: Новая версия политики — новые записи фиксируют ее, прежние сохраняют свою

- **GIVEN** после релиза текст политики заменен артефактом версии 2.0; существуют заявка и пользователь, созданные при версии 1.0
- **WHEN** создаются новая заявка и новый пользователь
- **THEN** новые записи фиксируют версию «2.0»; прежние записи сохраняют «1.0» (сохраненные значения не переписываются)

#### Scenario: Записи до введения фиксации не переписываются

- **GIVEN** БД с заявками/пользователями, созданными до введения политики (колонки фиксации NULL)
- **WHEN** выполняется миграция (в том числе повторно — idempotent)
- **THEN** легаси-записи остаются с NULL фиксации (без seed/backfill); новые записи всегда имеют обе колонки непустыми

### Requirement: Заменяемость артефакта политики

Текст политики MUST храниться как единственный заменяемый артефакт —
файл с метаданными (версия, дата) в шапке: подмена выполняется заменой
одного файла без правки исходников HTML/JS и без пересборки
фронтенд-бандлов, в пределах 15 минут без участия разработчика.
Поврежденный или отсутствующий артефакт — честная ошибка API;
создание заявок/пользователей в этот момент не выполняется.

Источник: requirements-sprint9.md NFR-25, FR-79; ОВ-1.

#### Scenario: Подмена одного файла — без пересборки и правки кода

- **GIVEN** развернутый сервис с артефактом версии 1.0
- **WHEN** файл артефакта заменен новым (версия 2.0) и сервис перезапущен
- **THEN** /policy и GET /api/policy показывают новый текст и версию 2.0; ни один файл исходников HTML/JS не менялся, пересборка фронтенд-бандлов не выполнялась; операция уложилась в 15 минут без разработчика

#### Scenario: Версия для фиксации берется из артефакта на момент сабмита

- **GIVEN** артефакт версии 2.0 развернут
- **WHEN** отправляются заявка инструктора и регистрация ученика с согласием
- **THEN** обе новые записи фиксируют версию «2.0» — значение прочитано сервером из метаданных артефакта, а не из запроса клиента

#### Scenario: Поврежденный артефакт — записи не создаются

- **GIVEN** артефакт отсутствует или поврежден (нет/битая шапка метаданных, пустой текст)
- **WHEN** POST /api/instructors/apply или POST /api/register с согласием отправлены
- **THEN** ответ 500 {ok:false}; заявка/пользователь НЕ созданы — фиксация версии невозможна, и сервис не создает запись без согласия на конкретную версию
