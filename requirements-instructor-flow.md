# Требования: Поток инструктора — лендинг, анкета, модерация (Спринт 2, часть 1)

> Автор: PM-агент (main, Egor Kotov)
> Статус: УТВЕРЖДЕН
> Источник: ТЗ Заказчика (чат 2026-10-12, дословные цитаты в decisions/)

## Описание

Поток подключения инструктора: лендинг (прямая ссылка) → анкета заявки →
ожидание модерации → кабинет инструктора. Модерация — в админке.
Кабинет инструктора в этом объеме НЕ реализуется (макет сохранен,
реализация — следующий объем).

## Аудитория

Инструкторы (заявка, ожидание), администратор (модерация заявок).

## Функциональные требования

- FR-10: Лендинг инструкторов (design/mocks/landing-instructors.html) MUST
  быть доступен по прямой ссылке /instructors; кнопки CTA ведут на анкету
  /instructors/apply (макет registration-instructor.html).
- FR-11: Анкета MUST собирать: ФИО, телефон, email, адрес, формат работы
  (свой авто / авто Сбера), госномер (если свой), номер и дату ВУ,
  категорию, стаж, пароль + подтверждение пароля. Обязательные поля —
  по макету (со звёздочкой) + пароль.
- FR-11.1: Пароль из анкеты MUST храниться только как bcrypt-хэш (тот же
  механизм, что register.py, cost ≥ 12); открытый пароль не хранится и
  не логируется. Хэш сохраняется в заявке и при одобрении переносится в
  users (повторное хэширование не требуется — хэш уже стойкий).
- FR-12: Отправка анкеты MUST создавать заявку инструктора со статусом
  waiting и показывать экран ожидания /instructors/pending («заявка на
  рассмотрении»).
- FR-13: Вход инструктора — по логину (email) и паролю через
  /api/auth/login (тот же механизм сессий, что у учеников; Spirint 1).
  При входе: пользователь найден (approved) → личный кабинет (в этом
  объеме — заглушка «кабинет скоро»); заявка waiting → экран ожидания;
  заявка deny → экран отказа с причиной (комментарий из админки);
  заявки нет → единое сообщение об отказе входа (как у учеников).
- FR-14: В админке MUST появиться раздел «Заявки инструкторов»: таблица
  всех заявок с данными анкеты (включая bcrypt-хэш пароля); клик по
  строке → действия «Одобрить» / «Отклонить».
- FR-15: «Отклонить» MUST требовать обязательный комментарий (причина);
  без комментария действие недоступно. Статус заявки → deny, причина
  сохраняется и показывается инструктору при следующем входе (FR-13).
- FR-16: «Одобрить» MUST создавать пользователя в users из данных заявки
  (email + уже готовый bcrypt-хэш из заявки); статус заявки → approved.
  Повторное одобрение недоступно (кнопка скрыта). Email в users должен
  оставаться UNIQUE — заявка с существующим email отклоняется на этапе
  отправки анкеты единым сообщением.
- FR-17: Экран ожидания и экран отказа MUST соответствовать макетам
  Заказчика по тону (тексты согласуются при реализации; проверка —
  design check).

## Нефункциональные требования

- NFR-2: SQL параметризованный (переносится из Спринта 1).
- NFR-3: Токены/секреты не в логах и репозитории (переносится).
- NFR-4: Таблица instructor_applications хранит полные данные анкеты +
  статус (waiting/approved/deny) + review_comment + timestamp.

## Приоритеты (MoSCoW)

- Must: FR-10…FR-17, NFR-2…NFR-4.

## Ограничения

- Кабинет инструктора (dashboard-instructor.html) — вне этого объема
  (макет сохранен); после одобрения инструктор входит по логину/паролю и
  видит заглушку «кабинет скоро».
- Файл загрузки ВУ в анкете — не сохраняем в этом объеме (поле макета,
  помечено «макет без реальной загрузки»); факт заявки фиксируется.
- Авторизация инструкторов — общий механизм /api/auth/login (Спринт 1);
  разделение «ученик/инструктор» — по наличию записи users + флаг роли
  в данных заявки/пользователя (детали — в design.md).
- Экраны ожидания/отказа доступны только после ввода логина/пароля
  (claim по email без пароля отклонен Заказчиком).
