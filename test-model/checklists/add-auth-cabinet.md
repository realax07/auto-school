| CHK-1 | Вход ученика + FR-1 | Успешный вход: POST /api/auth/login с email E и паролем P зарегистрированного ученика (пароль в виде bcrypt-хэша в users) → 200 {ok:true, token}; сессионный токен выдан | поз | Must |
| CHK-2 | Вход ученика + FR-1 | Токен после входа принимается защищенным ресурсом: GET /api/auth/me с заголовком X-Session-Token → 200 с данными записи {id, surname, name, patronymic, email} | поз | Must |
| CHK-3 | Хранение учетных данных + FR-3 | Проверка пароля идет против bcrypt-хэша: после входа с корректным паролем вход разрешен, в users для email — bcrypt-хэш (префикс $2b$/$2a$), bcrypt.checkpw(P, hash) = true | поз | Must |
| CHK-4 | Выход ученика + FR-8 | Успешный выход: POST /api/auth/logout с действующим токеном → токен аннулирован; фронт: очистка sessionStorage и редирект на главную | поз | Must |

## Auth: анти-брутфорс (негативные)

| CHK-13 | Ограничение попыток входа (анти-брутфорс) + FR-2 | Негатив (порог): с одного IP подряд выполнено больше допустимого порога неудачных попыток → очередная попытка с этого IP отклоняется БЕЗ проверки учетных данных (в т.ч. с корректными кредами существующего ученика) тем же 401 с единым сообщением; токен не выдан | нег | Must |
| CHK-14 | Ограничение попыток входа (анти-брутфорс) + FR-2 | Негатив (нарастание): после повторного превышения порога новая блокировка длится не меньше (дольше) предыдущей — длительность нарастает с каждым срабатыванием блокировки (замер: сдвиг времени без sleep, см. D2 о значении порога/длительностей) | нег | Must |
| CHK-15 | Ограничение попыток входа (анти-брутфорс) + FR-2 | Негатив (сброс): несколько неудачных попыток с IP (меньше порога) → успешный вход обнуляет счетчик; последующие изолированные неудачные попытки (меньше порога) не приводят к блокировке | нег | Must |
| CHK-16 | Ограничение попыток входа (анти-брутфорс) + FR-2 | Негатив (не раскрытие): при активной блокировке попытка входа с корректными учетными данными существующего ученика → ответ идентичен отказу при неверных кредах (тот же код, тот же текст), блокировка нигде не названа, токен не выдан | нег | Must |
| CHK-17 | Ограничение попыток входа (анти-брутфорс) + FR-2 | Граница (изоляция по IP): блокировка одного IP не влияет на другие IP — с другого IP вход (успешный и отказной) работает штатно в течение блокировки первого | гран | Must |

## Дефекты спеки (эскалация проектному менеджеру)

- **D1 (нетестируемо в лоб).** «Ограниченный срок действия (TTL)»: значение TTL
  в спеке не определено (12 ч — только в design.md/tasks.md 1.1; реестр в
  памяти, время не инъецируется). Проверка CHK-9 требует тестового механизма
  сдвига времени/реестра (аналог D6 чеклиста Спринта 0). Рекомендация:
  зафиксировать TTL в дельте.
- **D2 (недоопределено).** Порог анти-брутфорса в спеке — диапазон «3–10,
  точное значение фиксирует разработчик»; длительности блокировки (≥30 с …
  ≤15 мин, нарастание) — только в design.md. CHK-13/CHK-14 проверяются
  параметрически относительно фактического значения (фактически 5, review-001-1.1);
  без фиксации в спеке регресс порога тестом не ловится.
- **D3 (недоопределено).** «Возвращает пользователя на страницу входа»
  (auth, истекший токен; cabinet, доступ без токена): отдельной страницы входа
  нет — реализация редиректит на лендинг `/` с модалкой m-login (design
  поток 2, review-001-2.1). Критерий «страница входа» в CHK-9/CHK-19/CHK-20
  трактован как «лендинг с модалкой входа»; подтвердить у ПМ как контракт.
- **D4 (пробел спеки, review-001-2.1 #1).** Поведение кабинета при сетевой
  ошибке /me не оговорено: реализация fail-open (страница остается с мокапным
  примером «Иван Иванов», сессия не проверена). Спека покрывает только 401/нет
  токена. В чеклист не включен (нет источника); решение ПМ: fail-closed или
  принять as-is.
- **D5 (пробел спеки, review-001-2.2 #2).** Текст «Ошибка сети» в модалке входа
  при недоступности API отличается от единого сообщения FR-2; FR-2 покрывает
  только серверный отказ (401). Вне чеклиста; зафиксировано как осознанное
  исключение.
- **D6 (ограничение проверяемости, review-001-1.1).** Анти-брутфорс учитывает
  IP из request.client.host: за обратным прокси/балансировщиком все клиенты
  сольются в один IP (X-Forwarded-For не обрабатывается) — спека определение
  IP не дает. Для текущего деплоя без прокси проверяемо; при появлении прокси
  — пересмотр.
- **D7 (недоопределено).** Регистрозависимость email при входе
  (`User@x.com` vs `user@x.com`) не определена (аналог D7 Спринта 0); класс
  исключен из чеклиста до уточнения.
- **D8 (пробел спеки, review-001-2.1).** Частичное ФИО (пустое отчество в БД):
  код обрабатывает (filter(Boolean)), сценария в спеке нет — класс исключен
  до уточнения.
- **D9 (вне спеки, review-001-2.2 #1).** Двойной сабмит модалки входа шлет два
  POST login (второй дубль плюсуется в анти-брутфорс); Enter не сабмитит форму.
  Спека не регламентирует — UX-замечание, в чеклист не включено.
- **D10 (порядок проверок, review-001-1.1 #3).** При активной блокировке IP
  запрос с пустым телом дает 401 (единый отказ), а не 422: проверка блокировки
  выполняется до валидации полей. Из сценария «Блокировка после превышения
  порога» («без проверки учетных данных») это следует; порядок «блокировка →
  валидация» в спеке явно не зафиксирован — CHK-13 ожидает 401.
