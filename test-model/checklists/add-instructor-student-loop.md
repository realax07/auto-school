## Дефекты спеки (эскалация проектному менеджеру)

- **D1 (расхождение формулировки задачи с design.md).** Формулировка задачи 12
  упоминает лимиты фото «413/415»; design.md change'а фиксирует единый контракт
  валидации: файл не JPEG/PNG (magic bytes) или > 5 МБ → 422 {ok:false}
  (таблица ошибок design.md; как для ВУ, так и для фото авто). Кейсы
  TC-VUD-002/TC-CAR-006 проверяют по design.md (422). Эскалировано ПМ:
  подтвердить 422 как контракт либо изменить design.md.
- **D2 (пробел спеки, унаследован форматом).** «Отправка без файла ВУ»
  определена через «правила обязательности полей утвержденного макета»
  (задача 3.3, макет) — спека не фиксирует исход. CHK-4/TC-VUD-002 проверяют
  обе ветки по факту утверждения макета; до утверждения кейс исполняется
  по фактическому поведению с фиксацией расхождения.
- **D3 (недоопределено спекой, закрыто design.md).** Спеки дают «отказ
  доступа» без кодов; design.md фиксирует матрицу 401/403/404 (404 — чужой/
  несуществующий без раскрытия существования). Кейсы проверяют по design.md
  (CHK-8, CHK-10, CHK-18, CHK-23, CHK-49, CHK-54, CHK-62).
- **D4 (вне спеки, контроль).** Уведомления о заявках/решениях и модерация
  отзывов админом — вне объема (ОВ-6, ограничения ТЗ); классов проверок нет.
  Системный комментарий при закрытии заявок после accept проверяется только
  на «видим ученику» (CHK-58/CHK-59), точный текст — контракт реализации.
- **D5 (недоопределено design.md, эскалация ПМ).** Для
  POST /api/instructor/requests/{id}/accept design.md фиксирует «заявка —
  этому инструктору и в 'new' (иначе 404/409)» без разбиения условий по кодам.
  Кейс TC-REQ-007 разводит проверки по общей матрице кодов design.md:
  чужая заявка → 404 («чужой объект (авто, заявка) по id», 404-неразличение),
  accept заявки не в 'new' → 409 (конфликт состояния). До подтверждения ПМ
  фактический код ответа фиксировать при исполнении кейса; при расхождении
  с матрицей — эскалация и правка design.md.
