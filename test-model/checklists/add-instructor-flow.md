## Дефекты спеки (эскалация проектному менеджеру)

- **D1 (параметрическое, наследие Спринта 1).** Порог и длительности анти-брутфорса
  в спеке потока не зафиксированы (наследуется диапазон «3–10, нарастание» из
  design.md Спринта 1). CHK-45…CHK-47 проверяются параметрически относительно
  фактического значения; без фиксации регресс порога тестом не ловится.
- **D2 (пробел спеки, MIN-4 arch-review).** Роль при доступе к статусным
  экранам/заглушке не проверяется серверно: /api/auth/me не возвращает role, доступ
  к /instructor/cabinet-stub требует лишь действующей сессии (одобренный ученик,
  открыв заглушку напрямую, увидит ее). Спеке это противоречит формально только
  частично («доступ — только с действующей сессией»); гранулярность по роли не
  зафиксирована — решение ПМ: принять as-is или зафиксировать серверную проверку роли.
- **D3 (пробел спеки, review-001-4.4 #1).** Поведение /instructor/cabinet-stub при
  сетевой ошибке /me не оговорено: реализация fail-open (страница остается с ФИО
  «—», сессия не проверена). Спека покрывает только 401/нет токена. В чеклист не
  включен (нет источника); решение ПМ: fail-closed или принять as-is (аналог D4
  Спринта 1).
- **D4 (противоречие design ↔ реализация, review-001-4.3 #1).** Причина отказа
  читается из sessionStorage, но не удаляется после показа — повторное открытие
  /instructors/rejected в той же вкладке показывает причину БЕЗ повторного входа,
  тогда как design заявляет «повторное открытие требует повторного входа». CHK-41
  проверяет только прямое открытие без выполненного входа; класс «повторный показ
  причины в живой вкладке» исключен до решения ПМ (задокументированный компромисс
  sessionStorage).
- **D5 (недоопределено, наследие Спринтов 0–1).** Регистрозависимость email
  (`User@x.com` vs `user@x.com`) при apply/login не определена; класс исключен из
  чеклиста до уточнения.
- **D6 (ограничение проверяемости).** FR-17 «соответствие по тону» — качественный
  критерий, тексты согласуются при реализации: автоматизируемая проверка
  невозможна, CHK-48 выполняется как design check 6.1 (включая контроль служебного
  hint мокапа под чекбоксом согласия — review-001-4.2 #2).
- **D7 (вне контракта, review-001-3.1 #1).** Вырожденный случай «approve без записи
  users» (статус вне контракта §15.5): вход по такой заявке тратит bcrypt-проверку
  и учитывается анти-брутфорсом как failure (fail-closed, безопасно). Спека
  вырожденный случай не оговаривает — вне чеклиста, зафиксировано как известное
  поведение.
- **D8 (механика теста, review-001-1.1 #1).** Честное воспроизведение пути
  sqlite3.IntegrityError в apply требует обертки/monkeypatch (естественный тест
  отсекается SELECT-проверкой). CHK-18 фиксирует требование к покрытию; механика —
  на этапе авторства TC.
