## 1. Проверка закрытия major-замечаний review-001

### MAJ-1 (контракт 422 ломался штатной Pydantic-валидацией) — ЗАКРЫТО

| Место | Что требовалось | Что сделано | Статус |
|---|---|---|---|
| sdd.md §3.1 | Зафиксировать: поля с дефолтами, обязательность в хендлере в фиксированном порядке, отсутствующий ключ → контрактный 422 | Добавлен абзац «Валидация — хендлерная, НЕ Pydantic-required (MAJ-1, решение ПМ)»: `str = ""`, проверка в обработчике, отсутствующий ключ = пустое поле → `422 {"ok":false,"error":"<поле-ру>: поле обязательно"}`, явно запрещен дефолтный `{detail:[...]}` | Закрыто |
| tasks.md 2.1 | То же + тест «тело без ключа email → 422 в контрактном формате» | Задача дополнена (дефолты, запрет Pydantic-required); в «Готовность» добавлен тест «тело без ключа `email` → 422 {ok:false, error:"email: …"} (не Pydantic detail)» | Закрыто |
| specs/registration/spec.md, сценарий «Незаполненное обязательное поле» | WHEN/THEN покрывают отсутствующий ключ | WHEN дополнен «(или соответствующий ключ отсутствует в JSON-запросе)»; THEN — контрактный 422 с указанием, что валидация в обработчике, не на уровне схемы | Закрыто |

Сверка с решением ПМ (спека 2026-10-08, раздел «Обработка ошибок
регистрации»): совпадает — те же дефолты, тот же фиксированный порядок
(surname, name, patronymic, email, phone, password, password_confirm →
формат email → телефон → пароль → confirm → дубликат), тот же контракт 422,
тот же тест на отсутствующий ключ. Расхождений пакет ↔ мандат нет.

Техническая корректность подхода: да. Pydantic-модель без required-полей не
перехватывает отсутствующие ключи до хендлера, контракт FR-2 (сообщить
причину) и фронт-wiring восстановлены. Замечание снято полностью.
