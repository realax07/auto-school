# TC-REQ-003 — Параллельные заявки разным инструкторам; повтор после отказа

- ID кейса: TC-REQ-003
- ID чеклиста: CHK-47, CHK-48
- Источник: CHK-47/48 → Requirement «Подача заявки инструктору» (student-requests) → FR-36, ОВ-1, ОВ-2; Scenarios «Параллельные заявки разным инструкторам допустимы», «Повторная заявка после отказа допустима»
- Тип: граничный
- Приоритет: Must
- Статус: ручной (не исполнялся; автоматизация — после утверждения кейсов, контракт 6; плановые TC-ID в docstring автотестов действуют до утверждения, rule 6)

## GIVEN / WHEN / THEN
- GIVEN ученик имеет активную заявку инструктору А (A); заявка инструктору А отклонена с комментарием (B)
- WHEN A: POST requests {instructor_id:Б}; B: POST requests {instructor_id:A} снова
- THEN A: заявка Б создается (обе активны одновременно, ОВ-1); B: новая заявка А создается (повторная подача не ограничена, ОВ-2 — без троттлинга)

## Предусловия
- Сервис собран через create_app() (uvicorn, single-worker); допускается TestClient без сети (паттерн tests/conftest.py). Чистая БД (AUTOSCHOOL_DB_PATH в tmp), init_db при старте. Контроль живости: GET /api/health → 200 {"ok": true}.
- Сессии/данные фикстур: одобренные инструкторы А и Б (approved-заявка, Спринт 2; users.role='instructor'), ученик с валидной сессией (role='student'), X-Admin-Token администратора (Спринт 0). Сессии получены через /api/auth/login.
- Все запросы к API передают токены в заголовках X-Session-Token / X-Admin-Token (механика Спринтов 0–2).

## Шаги
1. POST requests {A} → 'new'.
2. POST requests {Б} → код.
3. GET /api/instructor/requests инструктором Б — видна ли заявка.
4. А отказывает (deny с комментарием, TC-REQ-006); POST requests {A} снова → код.
5. GET /api/instructor/requests инструктором А.

## Ожидаемый результат
2. 200 {ok:true} — обе заявки активны.
3. Заявка видна Б.
4. 200 {ok:true} — новая заявка создана сразу, без ограничений.
5. У А видна новая 'new' заявка (прежняя 'denied' — отдельной записью).
