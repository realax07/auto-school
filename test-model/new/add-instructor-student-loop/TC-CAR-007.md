# TC-CAR-007 — Редактирование автомобиля; чужой автомобиль не изменяется

- ID кейса: TC-CAR-007
- ID чеклиста: CHK-20, CHK-23
- Источник: CHK-20/23 → Requirement «Редактирование и удаление автомобиля» (instructor-cars) → FR-28; Scenarios «Редактирование автомобиля сохраняется», «Чужой автомобиль не редактируется и не удаляется»
- Тип: позитивный + негативный
- Приоритет: Must
- Статус: ручной (не исполнялся; автоматизация — после утверждения кейсов, контракт 6; плановые TC-ID в docstring автотестов действуют до утверждения, rule 6)

## GIVEN / WHEN / THEN
- GIVEN автомобиль {car_id} принадлежит инструктору А; у инструктора Б своя валидная сессия
- WHEN А выполняет PATCH /api/instructor/cars/{car_id} {plate:"В456ВС77"} (A); Б выполняет PATCH и DELETE того же {car_id} (B)
- THEN A: изменения сохранены и отображаются; B: каждый запрос → 404 {ok:false}, автомобиль не изменен и не удален

## Предусловия
- Сервис собран через create_app() (uvicorn, single-worker); допускается TestClient без сети (паттерн tests/conftest.py). Чистая БД (AUTOSCHOOL_DB_PATH в tmp), init_db при старте. Контроль живости: GET /api/health → 200 {"ok": true}.
- Сессии/данные фикстур: одобренные инструкторы А и Б (approved-заявка, Спринт 2; users.role='instructor'), ученик с валидной сессией (role='student'), X-Admin-Token администратора (Спринт 0). Сессии получены через /api/auth/login.
- Все запросы к API передают токены в заголовках X-Session-Token / X-Admin-Token (механика Спринтов 0–2).

## Шаги
1. PATCH .../cars/{car_id} токеном А → код.
2. GET cars токеном А — госномер?
3. PATCH .../cars/{car_id} токеном Б → код.
4. DELETE .../cars/{car_id} токеном Б → код.
5. GET cars токеном А — автомобиль и его поля?

## Ожидаемый результат
1. 200 {ok:true}.
2. plate = В456ВС77.
3. 404 {ok:false}.
4. 404 {ok:false}.
5. Автомобиль на месте, данные после шага 1 не изменились.
