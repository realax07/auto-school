# TC-NFR-002 — SQL параметризован; SQL-инъекция не исполняется

- ID кейса: TC-NFR-002
- ID чеклиста: CHK-37
- Источник: CHK-37 → requirements.md NFR-2 (сквозное; db-слой, registration); контроль по design/sdd: только «?»-плейсхолдеры, конкатенация запрещена
- Тип: НФТ
- Приоритет: Must

## Предусловия
- Сервис запущен (uvicorn, single-worker); базовый URL: http://127.0.0.1:8000.
- БД data/app.db инициализирована (init_db при старте), таблица users пуста (чистое тестовое окружение).
- Окружение .env задано: ADMIN_USER, ADMIN_PASSWORD_HASH (bcrypt), SECRET.
- Контроль живости: GET /api/health -> 200 {"ok": true}.

## Шаги
1. Инспекция db-слоя (backend/db.py, register.py, admin.py): каждый SQL-запрос использует только «?»-плейсхолдеры; отсутствуют f-строки, «%»-форматирование и конкатенация строк при построении SQL. Зафиксировать каждый найденный SQL.
2. Динамическая проба: POST /api/register со surname = "' OR 1=1 --" (остальные поля валидны, email "inj@example.com").
3. SELECT COUNT(*) FROM users;
4. GET /api/admin/users (с токеном) — посмотреть fio записи.
5. Контроль целостности: зарегистрировать второго пользователя, проверить COUNT(*) = 2 и работу проверки дубликата email.

## Ожидаемый результат
1. Все SQL — параметризованные («?»); нарушений (конкатенация/f-string в SQL) нет.
2–3. Регистрация: 200; COUNT(*) = 1 (инъекция не вернула «все записи» — значение сохранено как литеральные данные).
4. fio записи = "' OR 1=1 -- Анна Оттовна" — литерально, записи не искажены.
5. Второй пользователь регистрируется (COUNT = 2); проверка уникальности email работает — логика выборок не повреждена.

## Тестовые данные
- Проба: surname `'<OR-инъекция>` = `' OR 1=1 --`; name `Анна`; patronymic `Оттовна`; email `inj@example.com`; phone `+7 999 555-66-77`; пароли `Parol9999`.
