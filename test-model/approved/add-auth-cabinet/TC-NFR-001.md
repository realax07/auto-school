# TC-NFR-001 — Замер времени POST /api/auth/login ≤ 500 мс

- ID кейса: TC-NFR-001
- ID чеклиста: CHK-31
- Источник: CHK-31 → requirements.md NFR-1 (сквозное); sdd §12 (bcrypt cost 12 ~250 мс + SELECT по UNIQUE email в бюджете; ориентир ревью ~350 мс); сигнал риска review-001-1.1 «замера нет в тестах»
- Тип: НФТ
- Приоритет: Must
- Статус: manual/toBeAutomated (замер на поднятой инстанции; автотест-замер в tests отсутствует — сигнал риска чеклиста; см. scripts/check_auth_timing.py для статических инвариантов)

## GIVEN / WHEN / THEN
- GIVEN сервис запущен; зарегистрирован ученик с типичными данными (bcrypt cost 12)
- WHEN выполняется 5 прогонов POST /api/auth/login с корректными типичными данными, замер по часам вокруг HTTP-запроса (time.perf_counter)
- THEN время ответа КАЖДОГО прогона ≤ 500 мс (бюджет NFR-1)

## Предусловия
- Сервис запущен (uvicorn, single-worker); базовый URL http://127.0.0.1:8000; чистая БД; /api/health → 200.
- Замер по сети к поднятой инстанции (не TestClient), чтобы включить полный стек HTTP.

## Шаги
1. POST /api/register с типичным пользователем (email perf@example.com) → 200.
2. Выполнить 5 прогонов POST /api/auth/login {"email": "perf@example.com", "password": "Qwerty123"}; вокруг каждого запроса — time.perf_counter.
3. Зафиксировать статус и время каждого прогона в мс; вычислить max и медиану.

## Ожидаемый результат
2. Каждый прогон: 200 {"ok": true, "token": "..."}.
3. Время КАЖДОГО прогона ≤ 500 мс; max и медиана фиксируются в отчете (ориентир ~350 мс, не порог).

## Тестовые данные
Типичный пользователь: perf@example.com / Qwerty123 (регистрация полным базовым набором 7 полей).
