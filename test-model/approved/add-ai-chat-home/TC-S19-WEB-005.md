# TC-S19-WEB-005 — Ошибки провайдера и валидации в UI: человеческий текст у поля, оба шейпа ответа, без кодов/стеков; обмен не попадает в историю

- Автоматизация: носителя НЕТ (19.3.4 открыт) — пишет qa_automation в этой волне: e2e `tests/web/test_ui_playwright.py`. Механика: шейп 1 (контрактный {ok:false, error}) — провайдер изолируется швом set_provider (QA-fake бросает ProviderError → сервер 503 {ok:false,error:«…»}, как юнит TC-S19-008); шейп 2 (машинный) — page.route перехватывает POST /api/ai/chat и возвращает 422 {detail:[…]} (FastAPI-дефолт) / обрыв сети (status 0) — фронт сводит ОБА шейпа к человеческому тексту (aiHumanError). Якоря: #ai-error (текст у поля #ai-input), пузырь user убран, черновик возвращен в поле. Серверная сторона ошибок уже green: tests/unit/test_s19_ai_chat.py TC-S19-007 (422 контрактный, {ok:false,error:"Сообщение…"}, провайдер не вызывается) и TC-S19-008 (503, без «ProviderError»/«Traceback»/«hermes»/«subprocess»/«503», ai_messages пуст).
- Приоритет: Must (FR-19.3 «Ожидание и ошибка»; NFR ≤30 с, секреты не в логах)
- Статус: не автоматизирован — кейс партии change add-ai-chat-home (новый, 19.4); серверная нога автоматизирована (TC-S19-UNIT-001)
- Трассировка:
  - Requirement: Композер отправляет сообщение и показывает ответ ассистента (openspec/changes/add-ai-chat-home/specs/ai-chat/spec.md)
  - Scenario: Ожидание и ошибка (FR-19.3 — «человеческий текст у поля, без кодов и стеков»)
  - Requirement: Доступ к чату — только валидная сессия ученика (openspec/changes/add-ai-chat-home/specs/ai-chat/spec.md) — нога: сбой не пишет историю и не раскрывает механику (NFR)
  - Носитель: e2e с set_provider-фейком + page.route (план прогонов №3); юнит TC-S19-007/008 (уже green)

## GIVEN / WHEN / THEN
- GIVEN ученик вошел в кабинет, «Главная» открыта; сценарий А — провайдер-фейк бросает ProviderError (сервер отвечает 503 {ok:false, error:«<человеческий текст>»}); сценарий Б — POST /api/ai/chat перехвачен и возвращает 422 {detail:[…]} (машинный шейп); сценарий В — сеть недоступна (status 0); сценарий Г — пустое/пробельное сообщение
- WHEN отправлено непустое сообщение (А, Б, В); введено только «   » и нажата отправка (Г)
- THEN (А, Б, В) человеческий текст ошибки виден у поля (#ai-error) — БЕЗ кодов ответа («503», «422»), стека, слов «ProviderError», «hermes», «subprocess», «Traceback»; пузырь user УБРАН из чата, введенный текст возвращен в поле для повторной отправки; приветствие при пустой истории возвращено (обмен не состоялся — сервер историю не сохранял, контроль юнитом TC-S19-008: ai_messages пуст); ожидание во время запроса показано индикатором, не молча; (Г) отправки нет — пузыря нет, запроса нет (юнит TC-S19-007: провайдер не вызывался, 422 {ok:false, error:"Сообщение…"})

## Примечание
- Шейпы (design/фронт, 19.3.2, MIN-3 review-19.2): контрактный {ok:false, error} (конвенция Sprint-0 — 422 валидации и 503 провайдера из routes.py) И машинный FastAPI {detail:[…]} (глобального обработчика валидации в app.py нет). Фронт: контрактному доверяет текст, машинному/сети — общий текст «Не получилось отправить сообщение. Попробуйте еще раз чуть позже.» (App.vue aiHumanError).
- История — только состоявшие обмены: ни 422, ни 503 не оставляют записей (юниты TC-S19-007/008); 401-нога (токен истек во время отправки) — пузырь убран, редирект на вход (handleAuthFail) — вне этого кейса (NFR-доступ, кейсы UNIT/API).
- Таймаут провайдера ≤30 с — серверный (PROVIDER_TIMEOUT_SECONDS/--run-budget, юнит TC-S19-009/010); в UI это тот же шейп 503 — отдельного «UI-таймера» требовать не по спеке.
