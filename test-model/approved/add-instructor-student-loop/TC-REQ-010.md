# TC-REQ-010 — Принятие закрывает остальные активные заявки ученика

- ID кейса: TC-REQ-010
- ID чеклиста: CHK-58
- Источник: CHK-58 → Requirement «Принятие заявки с привязкой к автомобилю» (student-requests) → FR-39, ОВ-1 (MAJ-1 arch-review: 'new' И 'accepted'); Scenario «Принятие закрывает остальные активные заявки ученика»
- Тип: граничный
- Приоритет: Must
- Статус: ручной (не исполнялся; автоматизация — после утверждения кейсов, контракт 6; плановые TC-ID в docstring автотестов действуют до утверждения, rule 6)

## GIVEN / WHEN / THEN
- GIVEN ученик имеет активные заявки инструкторам А и Б (обе 'new')
- WHEN инструктор А принимает свою заявку (accept {car_id})
- THEN заявка А → 'accepted' с car_id; активная заявка Б → 'denied' с системным комментарием, видимым ученику в «Моих заявках»

## Предусловия
- Сервис собран через create_app() (uvicorn, single-worker); допускается TestClient без сети (паттерн tests/conftest.py). Чистая БД (AUTOSCHOOL_DB_PATH в tmp), init_db при старте. Контроль живости: GET /api/health → 200 {"ok": true}.
- Сессии/данные фикстур: одобренные инструкторы А и Б (approved-заявка, Спринт 2; users.role='instructor'), ученик с валидной сессией (role='student'), X-Admin-Token администратора (Спринт 0). Сессии получены через /api/auth/login.
- Все запросы к API передают токены в заголовках X-Session-Token / X-Admin-Token (механика Спринтов 0–2).

## Шаги
1. Ученик подал заявки А и Б; у обоих есть автомобили.
2. А выполняет accept {car_id} → код.
3. GET /api/student/requests учеником — статусы и комментарии.
4. GET /api/instructor/requests инструктором Б.
5. Разрыв уже принятой ('accepted') связи при accept — отдельный кейс TC-REQ-011 (CHK-59); здесь не дублируется.

## Ожидаемый результат
2. 200 {ok:true}.
3. Заявка А «принята»; заявка Б «отказана» с системным комментарием (текст виден ученику).
4. У Б заявка 'denied'; ученик не в «Моих учениках» Б.
