## GIVEN / WHEN / THEN
- GIVEN ученик открыл раздел «Билеты» (#/pdd-tickets); данные — pdd-bilety-index.json (2 категории × 40 билетов, гейт корпуса 80×20) и JSON выбранного билета (отдельный lazy-чанк на билет); порядок вопросов/вариантов — как в корпусе
- WHEN ученик выбирает категорию A/B/M и билет 1, отвечает на вопросы (верно/неверно), перемещается по сетке 1–20, нажимает «Сдать» досрочно либо доводит таймер до 00:00, перезагружает страницу или уходит в другой раздел и возвращается
- THEN старт попытки показывает вопрос 1 из корпуса, таймер 20:00 тикает вниз; у вопросов с изображением картинка грузится с /pdd-assets/bilety/ (native lazy); клик по варианту фиксируется ОДНОКРАТНО: неверный выбор — красным, верный — зелёным с тегом «Верный», раскрыто пояснение корпуса, повторные клики ответ не меняют; q-nav показывает статусы всех 20 (верно — done-g, неверно — done-r, не отвечен — нейтральный, текущий — cur); «Сдать» и достижение 00:00 (timeUp — авто-финиш, unit-логика) приводят к одному и тому же экрану результата: счёт верных из 20, детальные статусы 1–20, кнопки «Пройти снова»/«Выбрать другой билет»; после перезагрузки/ухода попытка начинается заново с выбора билета — никаких серверных записей прогресса не создается (новых API/таблиц нет, proposal «НЕ входит»)

## Примечание
- Ручной остаток: 20-минутный прогон до естественного 00:00 на приемке НЕ выполняется (в e2e таймер проверен тиком −1, авто-финиш — unit-логикой timeUp + wiring-гардой вызова в компоненте); проба «reload посреди попытки → экран выбора, серверных записей нет» — ручная (нет новых API — конструктивная гарантия отсутствия записей).
- Верный/неверный варианты в e2e взяты из фактического корпуса (abm-01: q1 → вариант 2, q2 → вариант 1) — сверка «тренажер по корпусу», не по выдуманным данным.
