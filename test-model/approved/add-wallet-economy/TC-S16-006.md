# TC-S16-006 — Выплаты по СБП (мок): заявка инструктора → подтверждение оператора, guard баланса (недостача — без списания), одна активная заявка

- Автоматизация: `tests/api/test_s16_backend.py::test_s16_instructor_payout_request_guards` (плановый ID TC-S16-019 — заявка при amount ≤ доступно: запись payouts «заявка», баланс не изменился, видна в списке своих; сумма больше баланса — отклонение без записи; вторая активная — конфликт, частичный UNIQUE; банк/телефон обязательны), `::test_s16_admin_payout_confirm_and_insufficiency` (TC-S16-021 — подтверждение: ровно одна payout-транзакция, баланс уменьшился, статус «выплачено» со временем; повторное/параллельное подтверждение — без дубля; недостача — отклонение с объяснением, заявка осталась активной, списания нет), `tests/api/test_qa_s16_money.py::test_tc_s16_m_003_wallet_mocks_have_no_http_clients` (TC-S16-M-003, NFR-36 — в backend/wallet/** нет httpx/requests/urlopen: СБП захардкожен как мок, внешних вызовов нет), e2e `tests/web/test_ui_playwright.py::test_tc_ui_062_admin_transactions_section_and_company_balance` (TC-UI-062 — очередь выплат: честное пустое состояние #tx-payouts-empty)
- Приоритет: Must
- Статус: автоматизированный прогон на приемке/регрессе (approved-кейс партии change add-wallet-economy, Спринт 16); автоматизация существует (Н5)
- Трассировка:
  - Requirement: Заявка вывода средств по СБП (мок) (openspec/changes/add-wallet-economy/specs/payouts/spec.md)
  - Scenario: Заявка вывода создается
  - Scenario: Сумма больше баланса отклоняется
  - Scenario: Вторая активная заявка отклоняется
  - Scenario: Мок без внешних интеграций
  - Requirement: Подтверждение выплаты оператором
  - Scenario: Подтверждение списывает баланс один раз
  - Scenario: Недостача к моменту подтверждения
  - Scenario: Подтвердить чужую/уже выплаченную нельзя
  - Requirement: Подтверждение выплат и решения по спорам в разделе — выплатная очередь (openspec/changes/add-wallet-economy/specs/admin-transactions/spec.md)
  - Scenario: Оператор подтверждает выплату из раздела

## GIVEN / WHEN / THEN
- GIVEN инструктор с net-балансом больше нуля (release-транзакции в журнале); для недостачи — активная заявка, суммарные списания (вторая выплата) уменьшили баланс ниже суммы заявки
- WHEN инструктор подает заявку (POST /api/instructor/payouts: сумма ≤ баланс, банк СБП, телефон) и вторую при неподтвержденной первой (в том числе параллельными запросами); оператор подтверждает (POST /api/admin/payouts/{id}/confirm) — однократно, повторно, параллельно; подтверждает при недостаче
- THEN заявка создается в отдельной таблице payouts со статусом «заявка», баланс НЕ меняется (списание — только при подтверждении), заявка видна владельцу в списке своих выплат; сумма больше баланса — отклонение валидацией без записи; вторая активная — конфликт (гвард + частичный UNIQUE, в БД не более одной); подтверждение: ровно одна payout-транзакция, баланс уменьшился на сумму, статус «выплачено» со временем; повтор/гонка — дубль-транзакции нет; недостача — отклонение с честным объяснением, деньги не списаны, заявка осталась активной; чужую/выплаченную подтвердить нельзя; мок без сети (grep-гард NFR-36)

## Примечание
- Ручные остатки: форма заявки в разделе «Доходы и выплаты» инструктора (банк «Сбер/другие банки РФ», телефон) и диалог подтверждения в админке (confirm() — прецедент admin-диалогов) — ручные пробы приемки; API-контракты покрыты TC-S16-019/021, честное пустое состояние очереди — TC-UI-062.
- Банк/телефон видны только владельцу и оператору, в логи не попадают — контроль чтением исходников (выдача payouts ограничена владельцем/оператором; NFR-36-гард исходников в партии).
