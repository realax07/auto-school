## Контекст

Спринт 3, Партия A замыкает цикл «инструктор ↔ ученик»: профиль инструктора
(автомобили с фото, часы работы) → выбор учеником (карточки с фильтрами) →
заявка → решение (принять с привязкой к авто / отказать с обязательным
комментарием) → отзыв. Появляются первые пользовательские файлы (ВУ в
анкете, фото автомобилей), первая связь «многие-ко-многим через статус»
(ученик ↔ инструктор) и первый вычисляемый публичный показатель (рейтинг).
Нужно зафиксировать: где живут ФИО участников контура, где хранятся файлы
и как считается рейтинг.

## Решение

1. **ФИО-поля — гранулярные (surname/name/patronymic) в users; новые
   таблицы ФИО не дублируют.** Инструкторское ФИО попадает в users при
   approve из заявки (механика ADR-003, sdd.md §16), ученическое — при
   регистрации (ADR-002). Все новые сущности (instructor_cars, availability,
   reviews, student_requests) ссылаются на users по id; карточка
   инструктора, «Запросы учеников», «Мои ученики», «Привязанные ученики»
   собирают ФИО JOIN-ом к users — одной строки формата «ФИО единым полем»
   не заводится нигде. Причина: дублирование имени в 4+ таблицах создало бы
   ту же проблему рассинхронизации, что отклонена в ADR-002/003 для
   учетных данных; переименование/правка ФИО остается одноразовой правкой
   users. Выдача ФИО в ответах API — склейкой на сервере (механика
   /api/auth/me, Спринт 1).
2. **Файлы — каталог data/uploads/{license,cars}/ вне frontend/, выдача
   только через авторизованные эндпоинты.** Имена генерирует сервер
   (<uuid>.<ext>), оригинальные имена в путях не участвуют; валидация по
   magic bytes (JPEG/PNG) и лимиту 5 МБ (ОВ-5) ДО записи на диск,
   Content-Type клиента не доверенный (NFR-6). Каталог статикой не
   раздается — прямой URL невозможен конструктивно; изображение ВУ выдается
   только по X-Admin-Token (NFR-1), фото автомобиля — только владельцу по
   сессии, публичная карточка показывает характеристики авто без фото и
   госномера. Альтернативы (раздача статикой из frontend/, BLOB в SQLite)
   отклонены — research.md §1.
3. **Рейтинг — агрегат AVG/COUNT по reviews на лету, без денормализации.**
   Никакой колонки rating_avg в users нет: карточка и фильтр min_rating
   вычисляют среднюю и количество по отзывам при каждом чтении (индекс по
   instructor_id; отзывы у инструктора — единицы, объемы спринта малы).
   При пустом наборе — {has_reviews:false} («нет отзывов», не 0.0, FR-35).
   Причина: денормализация требовала бы поддерживать инвариант
   «средняя = AVG(отзывы)» в трех местах (создание/правка/удаление отзыва)
   — источник рассинхронов при нулевой выгоде на текущих объемах.
   Альтернатива отклонена — research.md §4.
4. **Связь «ученик принят» — статус заявки, не отдельная сущность.**
   student_requests.status='accepted' — единственный источник связи
   «ученик ↔ инструктор» (и car_id — привязка к авто); отдельная таблица
   students_instructors не заводится (research.md §2). Отзывы, «Мои
   ученики», виджет «Привязанные ученики» читают эту связь.

## Альтернативы (и почему отклонены)

- **ФИО одной строкой full_name в новых таблицах** (денормализация для
  «дешевых» списков) — отклонено: рассинхрон при правке ФИО, два формата
  одного атрибута в схеме; JOIN по PK в SQLite на этих объемах бесплатен.
- **Раздача uploads статикой / BLOB в БД** — отклонено: прямое нарушение
  NFR-1 (первый) и раздувание БД без преимуществ (второй) — research.md §1.
- **Денормализация рейтинга в users.rating_avg** — отклонено: research.md §4.
- **Булева сетка 7×48 вместо интервалов availability** — отклонено: против
  NFR-5 («availability — интервалы»), миграция при смене шага сетки —
  research.md §3.

## Последствия

- Положительные: единственный источник каждого факта (ФИО — users, связь —
  статус заявки, рейтинг — отзывы); файлы недоступны в обход авторизации
  по построению; ни одной фоновой задачи согласования (нет кронов/пересчетов).
- Отрицательные / техдолг (принят осознанно): списки карточек требуют
  JOIN + агрегат на каждое чтение (при росте отзывов — кэш, вне объема);
  файлы-сироты в data/uploads/ после DELETE авто/обработки заявок
  (cleanup — MIN-3 arch-review, зафиксировать в design.md); выдача ФИО
  склейкой повторяется в нескольких эндпоинтах (дробление вынесется
  helper-ом при первом рефакторе).
- Контроль допущений: валидация magic bytes обязательна до записи (тесты
  задачи 1.1 — PDF и 6 МБ → 422); «нет отзывов» — не 0.0 (тест 4.1);
  уникальность отзыва — UNIQUE(instructor_id, student_id) в DDL, не только
  кодом (тест 5.1).
