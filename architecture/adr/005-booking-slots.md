# ADR-005: Бронирование слотов поверх availability — частичный UNIQUE против гонок, ракурсы фото как kinds uploads, комплектность валидирует человек в админке

- Статус: Принято
- Дата: 2026-10-22
- Решение: Заказчик — дословно «1 все обязательны. Валидирует человек в
  админке. 2. Да. 3. Целиком. 4. Без лимита. 5. Да. 6. Да» (ОВ-1…ОВ-6,
  requirements-booking-docs.md, раздел «Решения Заказчика», 2026-10-22);
  техрешения — research.md/design.md пакета add-booking-docs
- Change: add-booking-docs (openspec/changes/add-booking-docs/)
- Ревью: openspec/changes/add-booking-docs/arch-review.md (verdict:
  needs-rework — MAJ-1 согласование PUT availability с бронями, MIN-1…4;
  три ключевых решения настоящего ADR от замечаний не зависят — прецедент
  ADR-004)

## Контекст

Спринт 5 достраивает контур инструктор↔ученик до реального расписания:
после Спринта 3 есть график (availability — недельные интервалы) и принятые
ученики (student_requests.status='accepted'), но бронировать занятия нечем
(виджет «Занятия на сегодня» — честная заглушка FR-41). Параллельно
закрывается контур документов: автомобиль переходит на набор из 5 фото
ракурсов + обязательное фото СТС при создании (и фиксируется баг 5.2 с
неотображающимися фото), у инструктора появляется «Мои документы» (ВУ +
СТС). Нужно зафиксировать: как гарантировать «один слот = одна бронь» при
параллельных запросах, где живут фото ракурсов/СТС и кто проверяет
комплектность фотонабора.

## Решение

1. **Бронь — строка таблицы booking поверх availability_id; слот = интервал
   графика ЦЕЛИКОМ (ОВ-3); единственность — частичный уникальный индекс
   `CREATE UNIQUE INDEX uq_booking_active_slot ON booking(availability_id)
   WHERE status IN ('new','confirmed')` + транзакции BEGIN IMMEDIATE.**
   На слоте существует максимум одна активная/подтвержденная бронь —
   гарантия на уровне хранилища (буква NFR-8), а не проверкой SELECT перед
   INSERT (проигрывает гонкам) и не полным UNIQUE(availability_id) (блокировал
   бы повторный запрос после отклонения — ОВ-5): статус 'rejected' выпадает
   из частичного индекса, слот освобождается. Проигравший в гонке INSERT
   получает 409 без записи — «отказ конфликта, а не молчаливая порча».
   Confirm конкуренции не имеет: бронь уже держит слот индексом, перевод
   'new'→'confirmed' атомарен. Дата занятия материализуется в lesson_date
   (ближайшая будущая дата weekday на момент брони) — availability без дат,
   а календари FR-49 показывают дату; повторение слота по неделям — точка
   расширения (кандидат — новый статус/операция, статусная модель
   ('new','confirmed','rejected') открыта для «перенос/отмена» без
   переделки). Отдельная сущность «пара» не заводится — связь «принят» =
   student_requests.status='accepted' (наследование ADR-004, решение 4);
   instructor_id денормализован в booking для прямых выборок календарей со
   сверкой при создании (пара в этом объеме иммутабельна). Альтернативы
   отклонены — research.md §2, §3.
2. **Фото ракурсов и СТС — kinds существующего uploads.py (car_photo,
   car_sts) + фиксированный набор колонок в instructor_cars
   (photo_front/rear/interior/left/right, photo_sts); mechanic helper
   (magic bytes JPEG/PNG, ≤5 МБ до записи, <uuid>.<ext>, data/uploads/
   вне статики, выдача авторизованными эндпоинтами) не дублируется и не
   меняется — наследование ADR-004, решение 2.** Ракурсы хранятся
   независимыми колонками (замена одного не трогает остальные), СТС —
   отдельным kind с отдельным эндпоинтом выдачи только владельцу (СТС
   ученикам не выдается, NFR-7): разделение kinds дает разные каталоги
   data/uploads/car_photo/ и car_sts/ и разные правила доступа без флагов
   «публиковать/не публиковать» на одном kind. Kind-таблица «авто → фото»
   отклонена: состав фиксирован и конечен, пофайловых метаданных не нужно
   (research.md §1); фронт-каталог студента пары читает те же колонки —
   правило доступа «владелец + ученики пары» (MODIFIED-дельта
   instructor-cars, снятие бага 5.2).
3. **Комплектность фотонабора валидирует человек в админке (ОВ-1, дословно);
   сервер хранит факт и флаг blocked.** Сервер НЕ блокирует сохранение
   автомобиля с неполным комплектом — это прямое решение Заказчика
   («Валидирует человек в админке»): админ-эндпоинт GET
   /api/admin/cars/completeness показывает по каждому авто наличие 5
   ракурсов + СТС, POST /api/admin/cars/{id}/block ставит blocked=1
   (идемпотентно), заблокированное авто скрыто от учеников. Колонка blocked
   в instructor_cars — единственное серверное состояние; разблокировка —
   вне объема (зафиксировано как сознательное ограничение design.md).
   Альтернатива «серверная блокировка сохранения» отклонена — противоречит
   буквальной цитате решения (research.md §6).
4. **Модульность по директиве Заказчика: бронирование — отдельный модуль
   backend/booking.py, «Мои документы» — отдельный backend/instructor_documents.py;
   существующие модули не раздуваются.** Расширения существующих — только
   в своих доменах: instructor_cars.py (ракурсы/СТС/админ-комплектность),
   uploads.py (перечень kinds), instructor_summary.py (today_lessons из
   реальных броней — заглушка FR-41 закрывается серверной агрегацией,
   паттерн 5 карты: логика не на клиенте), db.py (idempotent-миграции),
   app.py (include роутеров, маршруты статики). Правило префиксов API —
   без исключений.

## Альтернативы (и почему отклонены)

- **SELECT-проверка занятости перед INSERT** — отклонено: race condition,
  двойное подтверждение достижимо, NFR-8 требует гарантию хранилища —
  research.md §2.
- **Полный UNIQUE(availability_id)** — отклонено: вечная блокировка слота
  после отклонения брони, нарушение ОВ-5 — research.md §2.
- **Вычисление даты занятия при чтении** — отклонено: недетерминизм между
  чтениями, неоднозначность «today_lessons» — research.md §3.
- **Kind-таблица фото / расширение instructor_cars.py документами** —
  отклонено: research.md §1, §4 (JOIN без выигрыша; раздувание модуля
  против директивы).
- **Серверная валидация комплектности при сохранении авто** — отклонено:
  решение ОВ-1 — человек в админке — research.md §6.
- **Сборка «Занятия на сегодня» на клиенте из /api/instructor/bookings** —
  отклонено: бизнес-логика на фронте против паттерна 5 карты — research.md §5.

## Последствия

- Положительные: инвариант «один слот = одна активная/подтвержденная
  бронь» доказуем схемой (частичный индекс), а не дисциплиной кода;
  отклонение освобождает слот без отдельного учета; новые домены — новые
  модули, существующие контракты (кроме перечисленных расширений) не
  меняются; файловая механика одна на все фото.
- Отрицательные / техдолг (принят осознанно): слот с подтвержденной бронью
  закрыт навсегда в этом объеме (повторение по неделям/завершение занятия —
  точки расширения; уникальность слота, а не даты — по букве NFR-8/ОВ-4);
  lesson_date материализован и не следует за изменением графика —
  взаимодействие PUT availability (полная замена) с активными бронями
  доопределяется по MAJ-1 arch-review; колонка photo_path и одиночный
  /photo-маршрут Спринта 3 устаревают без миграции данных (файлы-сироты —
  унаследованный техдолг ADR-004); блокировка авто необратима в объеме
  (разблокировка — точка расширения); гонки «бронь vs замена графика» и
  семантика дат (MIN-1) — тесты задач 4.1/4.2.
- Контроль допущений: частичный UNIQUE присутствует в схеме (проверка
  приемки 6.1); два параллельных POST на один слот — максимум одна бронь,
  вторая 409 (тест гонок 4.1); повторный запрос после отклонения создается
  (тест 4.1); reject без комментария заблокирован 422 (тест 4.1);
  авто без СТС не создается 422, PDF/6 МБ → 422 (тесты 2.1); доступ к
  ракурсам/СТС/документам по матрице NFR-7 (тесты 2.1, 3.1, 6.1).
