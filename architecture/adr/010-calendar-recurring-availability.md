## Контекст

График инструктора — множество интервалов «день недели + время» (таблица
availability, UNIQUE (instructor_id, weekday, start_time, end_time), PUT
полной замены), что фактически означает еженедельную повторяемость без
явного типа и без дат; бронь (booking.availability_id + lesson_date =
ближайшая дата weekday) и защита MAJ-1 (409 при удалении интервала с
активной бронью) работают на уровне интервала-определения; частичный
UNIQUE uq_booking_active_slot держит максимум одну активную бронь на
availability_id. Сетки календарей строятся только для текущей недели без
реальных дат. Решение Заказчика вводит тип каждой ячейки —
«повторяющееся» (еженедельное) или «разовое» (конкретная дата + время),
навигацию реальными неделями у инструктора и ученика, запрет правок
прошедшего и бронирование только будущих слотов. Нужно зафиксировать:
как хранятся серии и разовые слоты, на чем определяется экземпляр слота
(объект брони/занятости/защиты), как расширяется контракт availability
без ломающих изменений (NFR-29) и как существующие строки и брони
переживают переход без потерь (FR-97, NFR-30).

## Решение

1. **Тип слота — атрибут существующей записи availability, не новая
   сущность.** Колонки slot_type ('recurring' | 'one_off', DEFAULT
   'recurring') и slot_date ('' для recurring, 'YYYY-MM-DD' для one_off,
   CHECK-пара), уникальность расширяется до (instructor_id, weekday,
   start_time, end_time, slot_date) — recurring-дубли невозможны как
   прежде, one_off допускает тот же день недели + время на другую дату.
   Альтернативы отклонены: таблица материализованных экземпляров — ломает
   booking.availability_id (прямое противоречие «контракты броней не
   меняются ломающим образом») и требует пересчета на каждую правку;
   JSON-поле серии — теряет SQL-ограничения и параметризованные выборки;
   availability_v2 + вью — две истины и дороже в поддержке. Отступлений
   от ADR-005 нет: слот по-прежнему бронируется целиком, нарезка не
   вводится.
2. **Миграция — guarded rebuild таблицы availability, существующие строки
   → recurring через DEFAULT без перезаписи данных.** SQLite не снимает
   табличный UNIQUE через ALTER: одна транзакция BEGIN IMMEDIATE
   (CREATE availability_new → INSERT … SELECT id, instructor_id, weekday,
   start_time, end_time, created_at → DROP → RENAME → индексы), guard по
   отсутствию колонки — повторный запуск no-op (NFR-30). id и created_at
   сохраняются: ссылки booking.availability_id остаются валидными
   (FK-контракта нет, PRAGMA foreign_keys не включается). «Все
   существующие интервалы становятся повторяющимися» (FR-97) выполняется
   самим DEFAULT-определением колонки — ни одна строка и ни одна бронь не
   теряются и не меняют владельца/статуса. Приемочный факт: тесты на
   предсозданной БД со старыми данными.
3. **Экземпляр слота = (availability_id, дата); серии не
   материализуются.** Повторение разворачивается в даты при выдаче/рендере
   (инструктор — локально из полного списка определений, NFR-32; ученику
   экземпляры недели с состояниями выдает сервер — GET slots?date=, т.к.
   ученик не имеет доступа к определениям графика и занятость честна
   только сервером). Правка recurring применяется к серии (текущие/будущие
   экземпляры); прошедшие экземпляры серий не хранятся — история
   фиксируется записями брони (lesson_date), версии состояний серий не
   ведутся (сознательное ограничение, точка расширения). Совпадение
   one_off с экземпляром серии: возможны обе строки, отображается один
   слот (тип one_off), покрытие проверок — по (дата, время): любая
   покрывающая строка нового графика.
4. **Бронь/занятость/MAJ-1 — на уровне экземпляра, контракт POST не
   меняется ломающим образом.** lesson_date брони становится точной датой
   экземпляра (POST bookings получает опциональное поле date; легаси-вызов
   без даты — ближайший экземпляр серии, как прежде). Частичный UNIQUE
   uq_booking_active_slot переиндексируется на (availability_id,
   lesson_date) WHERE status IN ('new','confirmed') — разные даты серии
   бронируются независимо, «Слот уже занят» честен по отношению к
   развороту серий (FR-95/96); защита MAJ-1 (409) поднимается с интервала
   на экземпляры с перечнем, содержащим дату (FR-92, NFR-29). Это
   усиление решения ADR-005/MAJ-1 Спринта 5, не пересмотр: слот целиком,
   решения инструктора немедленно, статусная модель броней — без
   изменений.
5. **Контракт availability расширяется обратно-совместимо (не новый
   эндпоинт).** PUT /api/instructor/availability принимает полные
   slot_type/date (отсутствуют → recurring: старое тело = график из
   повторяющихся слотов, коды и формат ответа прежние — NFR-29; тесты
   s3/s7 остаются зелеными без правок); GET дополняет интервалы типом и
   датой (аддитивно, существующие потребители не затронуты). Запрет
   прошлого — серверная валидация каждого PUT (422: создание/изменение
   прошедшего one_off; прошедшие one_off — immutable-история, возвращаются
   клиентом без изменений; прошедшие экземпляры серий не проверяются) с
   границей «начало слота ≥ сейчас» (МСК, nowMoscow/MIN-1); бронирование
   — «начало > сейчас», серверная проверка каждого POST (NFR-31).
   Альтернатива «новый v2-эндпоинт» отклонена: два контракта 409/валидаций
   на один ресурс и старый клиент с другой семантикой — против NFR-29.

## Уточнение (2026-11-05, арх-ревью Спринта 10, MAJ-1 — граница решений 3/4)

Решения 1–5 в силе. MAJ-1: UNIQUE (…, slot_date) допускает одновременно
one_off (дата D, 16:00) и recurring Чт 16:00, а частичный индекс брони
уникален только внутри одной строки — без дополнения «один экземпляр —
одна активная бронь» обходилась двумя бронями через две строки
(решение 3 × решение 4). Политика (research.md R6, design.md):
совпадение one_off с экземпляром серии ДОПУСТИМО (FR-90 регламентирует
его отображение; FR-91 «сменить тип» на ячейке серии его создает), и
уникальность брони действует КРОСС-СТРОЧНО: create_booking проверяет
активные брони по ВСЕМ строкам графика инструктора, покрывающим
(lesson_date, start_time, end_time), ВНУТРИ той же транзакции BEGIN
IMMEDIATE (single-writer сериализует с PUT — наследование M-3
review-001); частичный UNIQUE (availability_id, lesson_date) остается
гарантией внутри строки; GET slots?date= дедуплицирует совпавшие
экземпляры (приоритет one_off, state по всем покрывающим строкам).
Составляющая гарантии: PUT пишет диффом (id непересоздаваемых строк
сохраняются — ссылки броней валидны); строка с активными бронями на
непрошедших экземплярах удаляется только при покрытии этих экземпляров
другой строкой нового графика, при этом booking.availability_id
перепривязывается на строку-носитель того же экземпляра (поля брони не
меняются) — без этого бронь-сирота (FK-контракта нет) выпадала бы из
JOIN выдач и из кросс-строчной проверки. Отклоненная альтернатива — 422
на PUT, создающий совпадающий one_off: против потока FR-91 и делает
правило FR-90 «один слот» мертвым (подробно — research.md R6).

## Последствия

- Старый UNIQUE (instructor_id, weekday, start_time, end_time) перестает
  существовать как табличное ограничение (заменен на 5-колоночный) —
  все прямые предположения о схеме availability в коде/тестах проверяются
  задачей приемки; rebuild затрагивает существующий volume при первом
  init_db после релиза (однократно, в транзакции).
- Одна бронь на серию больше не блокирует всю серию: инструктор видит
  «занято» только на конкретных датах экземпляров; существующие брони
  (одна на availability_id) остаются валидными — данные совместимы со
  старым более строгим индексом.
- Легаси-POST bookings без даты материализует ближайший экземпляр серии
  и теперь отклоняет «сегодня, но уже начался» (сужение поведения по
  FR-96/NFR-31) — задокументировано, время-зависимость тестов s5
  проверяется на приемке.
- История состояний серий не хранится: после смены времени серии прошлые
  недели отображают текущее состояние; фактическая история броней —
  записи booking. Версионирование серий и исключение отдельного экземпляра
  — точки расширения (не Must Спринта 10).
- Горизонт навигации неделями (±12 месяцев) — клиентское ограничение
  (дефолт открытого вопроса требований; ПМ может пересмотреть), серверного
  лимита нет.
- Карта данных и RUNBOOK дополняются архитектором при ревью (задача 10.3);
  миграция выполняется init_db через lifespan на существующем volume
  (наследование add-containerization), отдельный migrate-скрипт не
  вводится — упоминание порядка отката не требуется (rebuild аддитивен по
  читаемым колонкам).
