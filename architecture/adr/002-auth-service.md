# ADR-002: Авторизация учеников — отдельный модуль-сервис, единая таблица users, in-memory сессии

- Статус: Принято
- Дата: 2026-10-09
- Решение: Заказчик (чат-лог Telegram 2026-10-08/09; решения по допущениям СА — коммит 2294a4a, «email-only логин, users-таблица как security-best-practice»; ограничение ТЗ requirements.md Спринта 1)
- Change: add-auth-cabinet (openspec/changes/add-auth-cabinet/, arch-review.md)
- Ревью: openspec/changes/add-auth-cabinet/arch-review.md

## Контекст

Спринт 1 добавляет вход ученика и личный кабинет. В Спринте 0 авторизация
существовала только для одного администратора (in-memory admin-токен, ADR-001).
Заказчик сформулировал ограничения: «Авторизация отдельным сервисом, есть два
типа учеток, ученики, водители. Сейчас делаем учеников», «Пароли хешируются,
в открытом виде не храним. Таблица отдельная». Пакет интерпретировал «отдельную
таблицу users» как уже существующую таблицу регистрации Спринта 0; оба
допущения (email-only логин, users как таблица учетных данных) подтверждены
Заказчиком отдельно. Нужно зафиксировать, как авторизация ложится на карту:
границы модуля, хранилище учетных данных, механизм сессий.

## Решение

1. **Авторизация — отдельный модуль-сервис backend/auth.py**, не вплетена в
   register.py (решение Заказчика + ограничение ТЗ). Роуты: POST
   /api/auth/login, POST /api/auth/logout, GET /api/auth/me; зависимость
   require_session. register.py, admin.py, db.py, config.py не изменяются;
   сборка — только подключение роутера и маршрут /cabinet в app.py.
   Физически модуль живет в том же FastAPI-процессе (single-worker,
   ADR-001): на этапе Спринта 1 «отдельный сервис» означает отдельный
   модуль с собственной границей (роуты /api/auth/*, свой реестр сессий),
   а не отдельный процесс — выделение в процесс возможно в Релизе 1 за
   Gateway (паттерн 2) без изменения API-контрактов (паттерн 7).
2. **Учетные данные — одна таблица users** (создана регистрацией Спринта 0,
   схема без изменений): логин = email (UNIQUE — индексируем, миллисекундный
   SELECT), проверка пароля = bcrypt.checkpw против password_hash
   (bcrypt cost 12, как ADR-001). Подтверждено Заказчиком как
   security-best-practice: нет дублей email/хэша, нет второй линии
   рассинхронизации. Роль хранится неявно (в users пока только ученики);
   колонка role не заводится до появления второго типа учеток — водители
   вне спринта («Пока не трогай водил»), преждевременная колонка без
   потребителя нарушала бы принцип VI (простота прежде полноты).
3. **Сессии in-memory: {token: (expires, user_id)}, TTL 12 ч** — тот же
   механизм, что у admin-токена Спринта 0 (ADR-001 п.4): токен
   secrets.token_urlsafe(32), заголовок X-Session-Token (симметрия с
   X-Admin-Token), выдача только успешным входом, ленивая чистка истекших.
   Следствия — те же задокументированные: single-worker обязателен, рестарт
   = пере-вход учеников. Привязка user_id в записи сессии — для /me без
   дополнительного SELECT (фиксация arch-review MAJ-2).
4. **Вход только по email** (телефон — атрибут учетной записи для связи, не
   идентификатор). Решение подтверждено Заказчиком; placeholder мокапа
   «email или телефон» сохраняется дословно (FR-9), телефон как логин не
   принимается. Расхождение текста placeholder и поведения — осознанное,
   зафиксировано в proposal пакета.
5. **Единое сообщение об отказе входа** (FR-2): одна константная строка для
   неверного email, неверного пароля и отсутствующей записи; для
   выравнивания времени ответа при отсутствующей записи выполняется
   фиктивная bcrypt-проверка (иначе время раскрывает существование записи).

## Альтернативы (и почему отклонены)

- **Эндпоинты входа внутри register.py** — отклонено: нарушение ограничения
  ТЗ и решение Заказчика; слияние доменов регистрации и входа.
- **Отдельная таблица credentials (дубль email + хэш)** — отклонено
  (подтверждено Заказчиком): дублирование данных, синхронизация двух линий,
  изменение Спринта 0 без выигрыша безопасности.
- **Колонка role в users** — отложено до спринта водителей: преждевременная
  колонка без потребителя (водители вне спринта).
- **JWT** — отложено: новая зависимость, управление секретом/ротацией;
  отзыв (FR-8 — аннулирование при выходе) требует доп. хранилища, т.е.
  stateful-составляющую in-memory сессии не устраняет, а усложняет.
  Возврат к вопросу — при нескольких процессах/инстансах (Релиз 1).
- **Сессионные cookie** — отклонено: CSRF-поверхность при fetch и второй
  механизм параллельно заголовочному паттерну Спринта 0.
- **Сессии в БД/Redis** — отклонено: переживание рестарта не является
  требованием спринта; Redis — новый движущийся элемент вопреки принципу VI;
  строки в SQLite сделали бы БД участником логики сессий (паттерн 5 —
  в БД только хранение данных домена).

## Последствия

- Положительные: единый сессионный паттерн с админ-контуром (одна модель
  отказа, один механизм проверки, переиспользование зависимостей FastAPI);
  нулевые новые зависимости; регистрация Спринта 0 не затронута; переход
  «модуль → процесс» в Релизе 1 не меняет API-контрактов.
- Отрицательные / техдолг (принят осознанно): потеря сессий при рестарте
  (пере-вход всех учеников); single-worker обязателен — расширяется на
  ученические сессии (MIN-5 arch-review: фиксация `--workers 1` на этапе
  реализации); **отсутствие rate-limit/анти-брутфорса на публичном
  /api/auth/login** — осознанный принятый риск на период Спринта 1
  (MAJ-3 arch-review), вернуться при первом признаке перебора или в Релизе 1
  за Gateway; /cabinet — статика, защита данных через API, разметка
  доставляется всем (MIN-2 arch-review).
- Контроль допущений: время bcrypt+SELECT ≤ 500 мс на целевой машине —
  тестом замера (tasks 4.1, скрипт check_auth_timing.py уже в scripts/),
  не принято на слово (CONSTITUTION VII).
