# ADR-003: Поток инструктора — bcrypt-хэш пароля в заявке, перенос при approve, общий вход, роль-флаг

- Статус: Принято
- Дата: 2026-10-12
- Решение: Заказчик (чат-лог Telegram 2026-10-12; decisions/2026-10-12-instructor-flow-create-change.md — «В заявке на аппрев все данные, включая хэш пароля», decisions/2026-10-12-instructor-auth-by-login.md — «Идентифицируем по логину паролю»; FR-11.1, FR-13, FR-16 requirements-instructor-flow.md)
- Change: add-instructor-flow (openspec/changes/add-instructor-flow/, arch-review.md)
- Ревью: openspec/changes/add-instructor-flow/arch-review.md (verdict: changes-required — MAJ-1 UNIQUE email заявок; решение ADR не меняет)

## Контекст

Спринт 2, часть 1 вводит поток инструктора: лендинг → анкета заявки →
модерация в админке → экраны ожидания/отказа → (после одобрения) вход и
заглушка кабинета. Пароль инструктор собирает в анкете — до того, как
существует запись в users (она создается только одобрением админа). Нужно
зафиксировать: где живет пароль до одобрения, что происходит при одобрении,
как инструктор входит и как система различает ученика и инструктора.
Ограничение ТЗ: кабинет инструктора — вне объема (заглушка), разделение
«ученик/инструктор» — «по наличию записи users + флаг роли».

## Решение

1. **Пароль заявки — bcrypt-хэш в самой заявке (instructor_applications.password_hash,
   cost 12, механизм register.py).** При отправке анкеты хэшируется и
   сохраняется в заявке; открытый пароль не хранится нигде и не логируется
   (FR-11.1, NFR-3). Решение Заказчика дословно: «в заявке на аппрев все
   данные, включая хэш пароля».
2. **Одобрение (approve) переносит хэш в users без повторного хэширования**
   (FR-16): INSERT INTO users получает password_hash ИЗ ЗАЯВКИ как есть
   (хэш уже стойкий; открытого пароля к моменту approve больше нигде нет —
   повторное хэширование невозможно). users.email остается UNIQUE — вторая
   линия защиты; гонка дубля email обрабатывается IntegrityError → 409
   (симметрично register.py). Созданному пользователю ставится
   role='instructor'; повторный approve отсечен статусом заявки.
3. **Вход инструктора — общий /api/auth/login** (FR-13), без отдельного
   эндпоинта: тот же bcrypt.checkpw, те же in-memory сессии {token:
   (expires, user_id)} TTL 12 ч (ADR-002), то же единое сообщение об отказе
   и тот же анти-брутфорс. Ответ login дополняется роутингом: у пользователя
   есть запись — сессия + route по role; записи нет, но пароль совпал с
   хэшем заявки waiting/deny — route=pending/rejected (deny — с причиной),
   БЕЗ выдачи сессии (защищать нечего); иначе — единый 401. Контракт
   additive: ученический фронт Спринта 1 не ломается.
4. **Роли — флаг role в users: 'student' (дефолт) / 'instructor'**
   (ставится при approve). Миграция additive (ALTER ADD COLUMN с дефолтом) —
   ученики Спринтов 0–1 накрываются дефолтом, схема registration/auth
   не ломается. ADR-002 откладывал колонку role «до появления второго типа
   учеток» — момент настал; ветка «водители» по-прежнему вне спринта.

## Альтернативы (и почему отклонены)

- **Открытый пароль в заявке до approve** — отклонено: персистентное хранение
  открытого пароля неопределенное время нарушает NFR-3 и дух FR-11.1; прямое
  противоречие решению Заказчика.
- **Повторный ввод пароля инструктором при одобрении** — отклонено: новый UX
  вне ТЗ; инструктор может быть недоступен; FR-11.1 явно описывает перенос
  готового хэша.
- **Отдельная таблица instructors с дублем email/хэша** — отклонено:
  дублирование учетных данных и синхронизация (те же аргументы, что в
  ADR-002 против второй credentials-таблицы); вход требовал бы SELECT по двум
  таблицам; противоречит FR-16 («создавать пользователя в users»).
- **Отдельный /api/instructors/login** — отклонено: второй эндпоинт входа
  дублирует механизм сессий и анти-брутфорса, дробит единую модель отказа;
  решение Заказчика — идентификация по логину/паролю через общий механизм.
- **Роль по наличию/статусу записи в instructor_applications** (без колонки
  в users) — отклонено: роль становится динамическим выводом, «плавающим»
  при изменении заявок; явный флаг проще и устойчивее (research.md §2).

## Последствия

- Положительные: нет момента времени, когда открытый пароль персистентен;
  approve — один INSERT без криптографии; единый механизм входа/сессий/анти-брутфорса
  для обоих типов учеток; миграция users — одна additive-колонка; регресс
  Спринтов 0–1 отсутствует (контролируется тестами задач 1.2/3.1/6.1).
- Отрицательные / техдолг (принят осознанно): bcrypt-хэш хранится в двух
  местах (заявка + users); хэш обработанных (approved/deny) заявок не
  обнуляется — уснувший credential-материал при компрометации БД (вернуться
  к обнулению при первом изменении требований FR-14); password_hash заявок
  выдается админ-API (FR-14 — решение Заказчика; возражение архитектора
  MIN-5 arch-review передано ПМ: не рендерить как обычное поле, не логировать);
  роутинг по role — на фронте, серверной проверки роли на /instructor/cabinet-stub
  нет (MIN-4; обязательна при реальном кабинете); статусные экраны — статика,
  причина отказа через sessionStorage (повторное открытие = повторный вход).
- Контроль допущений: UNIQUE instructor_applications.email — обязательное
  условие решения (MAJ-1 arch-review; без него вход при дубликате заявок
  недетерминирован); транзакционность approve (INSERT users + UPDATE статуса
  одной транзакцией — MIN-3 arch-review); тесты схемы и гонок — задачи 1.2/2.1.
