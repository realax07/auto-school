## Контекст

Документы живут без статусной модели: замена ВУ невозможна («Мои
документы» — только просмотр/скачивание, досыл исключен Спринтом 5), а
СТС-дозагрузка (POST …/photo/sts, Спринт 7) перезаписывает файл мимо всякой
верификации. Замечания эксплуатации (Заказчик, 2026-10-31, 7 пунктов)
требуют: замена документа вступает в силу ТОЛЬКО после проверки админом,
до решения действует предыдущая версия; отклонение — с обязательной
причиной; модель единая для ВУ и СТС (СТС — по одному на каждую машину);
ожидающая версия одна, повторная загрузка ее замещает. Существующие
документы хранятся плоско: license_photo_path (instructor_applications) и
photo_sts (instructor_cars) — у них нет ни статусов, ни истории. Нужно
зафиксировать: механизм хранения версий, судьбу существующих данных при
миграции, кто и как верифицирует первичные документы, и как статусы
документов соотносятся со статусной моделью авто Спринта 7
(draft/validating/validated, ADR-005 + add-car-validation-booking).

## Решение

1. **Хранение — таблица `document_versions` (target_type license/car_sts,
   target_id, version, file_path, status pending/verified/rejected,
   reject_reason, uploaded_at, decided_at); канонические колонки
   license_photo_path / photo_sts ОСТАЮТСЯ указателями файла действующей
   версии.** Инварианты — на уровне схемы, а не дисциплины кода (паттерн
   ADR-005: частичный UNIQUE «один слот = одна бронь»):
   - `UNIQUE (target_type, target_id, version)` — номер версии
     детерминирован;
   - частичный `UNIQUE (target_type, target_id) WHERE status='pending'` —
     одна ожидающая версия на документ (ОВ-7), вторая INSERT/UPDATE
     невозможна физически;
   - `CHECK (status <> 'rejected' OR (reject_reason IS NOT NULL AND
     reject_reason <> ''))` — reject без причины невозможен на уровне
     схемы (ОВ-1), 422 API — страховка поверх.
   Действующая версия — последняя verified; предыдущие verified — архив.
   При verify каноническая колонка переключается на файл новой версии
   (одна транзакция); при reject — не меняется. Все существующие
   потребители плоских колонок (sts-выдача, GET …/photo/sts, admin
   completeness, карточка анкеты) продолжают работать без переделки —
   совместимость NFR-23 конструктивна. Механизм хранения делегирован
   решению СА границами NFR-24 — выбрана таблица версий, а не статусные
   колонки в двух существующих таблицах (см. «Альтернативы»).
2. **Миграция существующих документов — seed verified v1, idempotent
   (NFR-24).** Для каждой анкеты с непустым license_photo_path — строка
   (license, application_id, v1, тот же файл, verified); для каждого авто
   с непустым photo_sts — (car_sts, car_id, v1, тот же файл, verified).
   Seed только при отсутствии строк документа (SELECT по
   target_type+target_id); повторный запуск ничего не меняет; выполняется
   init_db через lifespan на существующем volume (наследование
   add-containerization). Эффект: после релиза ни один документ не
   «зависает» на верификации, выдача файлов не меняется (действующая
   версия = тот же файл) — симметрично NFR-20/ОВ-1 Спринта 7. Пустые
   состояния (анкета без ВУ, авто без СТС) строк не создают.
3. **Асимметрия первичной загрузки — сознательная: СТС у авто без
   действующего СТС → photo_sts + verified v1 сразу; ВУ у анкеты без ВУ →
   pending-версия.** Обоснование: первичное СТС проходит человеческий гейт
   Спринта 7 (комплектность фотонабора валидирует человек в админке,
   валидатор авто при validate — ОВ-4/MAJ-1 Спринта 7); вторая
   human-верификация того же файла не добавляет контроля, но удваивает
   очередь — двойная верификация одного файла не вводится. ВУ вне гейта
   авто: другого человеческого контура для него нет, поэтому первичное ВУ
   идет через pending (наследование «верификация — только человек»,
   ОВ-1 Спринта 5); verify переключает license_photo_path. Замена при
   действующей версии — всегда pending для обоих типов («документ не
   мигает»). Асимметрия задокументирована как сознательное ограничение.
4. **Независимость машин состояний «документ» и «авто» (ОВ-6).** Статусы
   документа не влияют на статус авто: замена СТС у validated — validated
   остается validated, повторная валидация авто — отдельное действие
   submit. Уточнение Спринта 7: правило «validated → validating» (MAJ-1)
   остается ТОЛЬКО за заменой 5 ракурсов (валидатор обязан видеть
   актуальные фото); sts-ветка сброса не производит и ракурсы/has_sts/
   счетчики комплектности не трогает. Обратная связь тоже отсутствует:
   pending/rejected документов не блокируют инструктора, не скрывают из
   каталога, не меняют брони (ОВ-3 «не влияет пока что» — точка
   расширения). Влияние статусов на новые действия инструктора — точка
   расширения после эксплуатационного опыта.

Верификация замен — только админ (X-Admin-Token): GET
/api/admin/documents?status=pending (ВУ — с ФИО, СТС — с авто/госномером),
предпросмотр файла версии (ОВ-4 — изображение открывается, контроль на
приемке), verify/reject (не-pending → 409; reject без причины → 422).
Повторная загрузка замещает ожидающую (файл+uploaded_at той же строки,
version не растет до верификации) — не ошибка (ОВ-7); «отозвать pending»
отдельной кнопкой — точка расширения.

## Альтернативы (и почему отклонены)

- **Статусные колонки в instructor_applications/instructor_cars
  (license_status, sts_status, sts_pending_path)** — отклонено: дублирует
  машину состояний в двух таблицах с разной природой владельца (личный
  документ vs документ авто), не дает истории версий (архив требуется
  «предыдущая verified — архив»), третья сущность «СТС-замена» все равно
  потребовала бы отдельной таблицы — получили бы гибрид хуже таблицы
  версий; единая модель ОВ-2 («иначе два механизма для одинаковых по сути
  документов») выполняется одной таблицей.
- **Полный перенос указателя действующей версии в document_versions с
  удалением канонических колонок** — отклонено: ломает всех существующих
  потребителей плоских колонок (sts-выдача, completeness, карточка анкеты)
  и контракт Спринтов 5–7 (NFR-23) — вне объема; перенос — точка
  расширения.
- **Серверная (автоматическая) верификация документов** — отклонено:
  прямое решение Заказчика (наследование ОВ-1 Спринта 5) — верификация
  только человеком в админке.
- **Double-верификация первичного СТС (pending и для первичной
  дозагрузки)** — отклонено: файл уже проходит человеческий гейт
  комплектности/валидации авто Спринта 7; повторная очередь того же файла
  — расход админского времени без прироста контроля (обоснование —
  решение 3).
- **Отзыв pending отдельной операцией** — отклонено в объеме: ОВ-7 —
  замещение повторной загрузкой; отзыв — точка расширения.

## Последствия

- Положительные: инварианты «одна ожидающая на документ» и «reject без
  причины невозможен» доказуемы схемой (частичный UNIQUE + CHECK), а не
  дисциплиной кода; история версий появляется с первого релиза статусной
  модели (архив verified); миграция безопасна на существующем volume и
  повторяема; совместимость — без правок существующих потребителей;
  машины состояний документа и авто независимы и рассуждаются отдельно.
- Отрицательные / техдолг (принят осознанно): файлы-сироты версий —
  замещение ожидающей версии и rejected-версии оставляют файлы в
  data/uploads/ без cleanup (расширение унаследованного техдолга MIN-3
  ревью 3A, ADR-004); асимметрия первичной загрузки — особый случай,
  который надо знать при эксплуатации (первичное СТС не видно в
  админской очереди «Документы»); история версий без просмотра архива —
  точка расширения (админ работает только с ожидающими); влияние
  статусов на активность инструктора — отложено (ОВ-3 «пока что»);
  атомарность «замещающая загрузка × verify/reject» — на условном
  UPDATE/BEGIN IMMEDIATE, контроль тестами (MIN-1 arch-review).
- Контроль допущений: seed-миграция на предсозданной БД — у каждого
  существующего документа ровно одна verified v1 с тем же файлом, второй
  запуск ничего не меняет (тест 1.1); вторая pending на документ
  невозможна, CHECK отклоняет rejected без причины (тест 1.1); замена
  ВУ/СТС — pending создана, каноническая колонка и файл-эндпоинт НЕ
  изменились (тесты 2.1/3.1); замена СТС у validated — статус остался
  validated, ракурсы регрессно → validating (тест 3.1); reject: 422 без
  причины, с причиной — rejected, действующая прежняя (тест 4.1);
  предпросмотр админки открывается (ОВ-4, приемка 11.1).
